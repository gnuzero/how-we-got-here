TCP/IP (பதிவு 41) பன்முக, நம்பகமற்ற, உலகளாவிய வலையமைப்புக்குச் சரியான முதுகெலும்பு. ஒரு datacenter-க்குள் — ஒரு உரிமையாளர், குறுகிய தூரங்கள், பொறியியல் செய்யப்பட்ட fabric — அதே kernel-மத்தியஸ்த பாதை ஒவ்வொரு மைக்ரோவினாடியையும் ஒவ்வொரு byte bandwidth-ஐயும் செலவிடும் workloads-க்கு overhead போல் தோன்றத் தொடங்குகிறது.

> **தமிழ் இடைவெளிக் குறிப்பு:** RDMA, datacenter வலையமைப்பு / fat-tree பற்றித் தமிழ் எழுத்து விளக்கம் கிடைக்கவில்லை; காணொளிச் சான்று YouTube தேடல் முடிவுகள் மட்டும் — காணொளிகள் பார்க்கப்படவில்லை. இங்குள்ள தரவு அளவுகள், வேகங்கள், switch port எண்ணிக்கைகள் கணக்குக்காகத் தேர்ந்தெடுத்த "எடுத்துக்காட்டு மதிப்புகள்"; fat-tree சூத்திரம் கீழே படிப்படியாக வருவிக்கப்படுகிறது. VM பயிற்சியின் நேரங்கள் உண்மையில் ஓட்டி அளந்தவை.

## முதலில் சொற்கள்

- **Kernel-mediated path (kernel வழிப் பாதை):** ஒவ்வொரு அனுப்புதலும் பெறுதலும் system call, kernel buffer, TCP/IP stack வழியாகச் செல்வது.
- **System call (அமைப்பு அழைப்பு):** ஒரு நிரல் kernel-இடம் வேலை கேட்கும் வாசல்; ஒவ்வொரு கடப்புக்கும் நிலைத்த செலவு உண்டு.
- **நகல் (copy):** ஒரே data-வை நினைவகத்தின் ஒரு இடத்திலிருந்து இன்னொரு இடத்துக்கு நகர்த்துவது — நேரமும் நினைவக அலைவரிசையும் செலவாகும்.
- **NIC (network interface card, வலை இடைமுக அட்டை):** கணினியை வலையமைப்புடன் இணைக்கும் வன்பொருள்.
- **RDMA (தொலை நேரடி நினைவக அணுகல்):** பெறுபவரின் CPU, kernel இடையில் வராமல் adapter நேரடியாக நினைவகத்திலிருந்து நினைவகத்துக்கு data நகர்த்துவது.
- **Kernel bypass (kernel தவிர்ப்பு):** data பாதையிலிருந்து kernel-ஐ விலக்குவது.
- **Fat-tree:** மேல் அடுக்குகளுக்குச் செல்லச் செல்லக் கொள்ளளவு குறையாமல் இருக்கும்படி switch-களை அடுக்கும் வடிவம்.
- **Oversubscription (மிகைச் சந்தா விகிதம்):** கீழ்நோக்கிய மொத்த அலைவரிசை ÷ மேல்நோக்கிய மொத்த அலைவரிசை; 1:1 என்றால் தடையில்லை.

## Overhead எங்கிருந்து வருகிறது

பாரம்பரிய TCP/IP send application தரவை kernel buffer-க்கு நகலெடுக்கிறது, stack-ஐ ஓட்டுகிறது, மற்றும் NIC transmit செய்ய அனுமதிக்கிறது — receive-இல் கண்ணாடி. ஒவ்வொரு படியும் CPU சுழற்சிகளைச் செலவழிக்கிறது, மற்றும் latency-க்கு மோசமாக, நினைவக இடங்களுக்கு இடையே உண்மையான *நகல்கள்*. சாதாரண web போக்குவரத்துக்கு நல்லது. வினாடிக்குப் பல முறை gradients பரிமாறும் HPC அல்லது distributed ML training-க்கு விலை உயர்ந்தது.

## நகல்களின் விலை, ஒரு கணக்கில்

எடுத்துக்காட்டு மதிப்புகள்: ஒரு பயிற்சி இயந்திரம் ஒவ்வொரு படியிலும் 100 MB gradient அனுப்புகிறது, 100 MB பெறுகிறது; வினாடிக்கு 10 படிகள். ஒரு CPU core நினைவக நகலை 10 GB/s-இல் செய்கிறது.

| பாதை | ஒரு படியில் CPU நகல்கள் | நகல் நேரம் / படி | வினாடிக்கு |
|---|---|---|---|
| பாரம்பரிய TCP/IP | அனுப்புதல்: பயன்பாடு → kernel (100 MB); பெறுதல்: kernel → பயன்பாடு (100 MB) | 200 MB ÷ 10 GB/s = 20 ms | 10 × 20 = 200 ms — ஒரு core-இன் 20% |
| RDMA | 0 (adapter நினைவகத்திலிருந்து நினைவகத்துக்கு நேரடியாக) | 0 ms | 0 ms |

இது stack-இன் protocol செயலாக்கத்தையும் interrupt-களையும் சேர்க்காத, நகல்களுக்கு மட்டுமான கணக்கு. Gradient-கள் வினாடிக்குப் பலமுறை பரிமாறப்படும்போது ஆங்கிலப் பதிவு சொல்லும் "செலவு" இதுதான்.

## RDMA: Data Path-இலிருந்து Kernel மற்றும் CPU வெளியே

RDMA (Remote Direct Memory Access) ஒரு இயந்திரம் மற்றொன்றின் நினைவகத்தை receiver-இன் CPU அல்லது kernel பரிமாற்றத்தை babysit செய்யாமல் படிக்க அல்லது எழுத அனுமதிக்கிறது. RDMA-திறன் adapter bytes-ஐ வலையமைப்பு குறுக்கே memory-to-memory நகர்த்துகிறது. பதிவு 37-இன் GPUDirect RDMA-இன் அதே கருத்து — குறைந்த நகல்கள், compute-க்கு விடுவிக்கப்பட்ட CPU — ஒரு node-இல் GPU-களுக்கு இடையே மட்டும் அல்ல, முழு இயந்திரங்களுக்கு இடையே பயன்படுத்தப்பட்டது.

## Fat-Tree: ஆயிரக்கணக்கை சமமாக வயரிங் செய்தல்

ஆயிரக்கணக்கான இயந்திரங்களில், topology bandwidth உண்மையா அல்லது விளம்பரப்படுத்தப்பட்டதா என்பதைத் தீர்மானிக்கிறது. ஒரு fat-tree switches-ஐ அமைக்கிறது, சுமைக்குக் கீழே மட்டும் தோன்றும் bottleneck இணைப்புகளை மறைக்காமல், படிநிலையில் மேலே கொள்ளளவு முன்னறிவிக்கக்கூடியபடி அளவிடும். பெரிய training clusters (Phase 10) அந்த வேண்டுமென்ற சிந்தனையுடன் வயர் செய்யப்படுகின்றன — ad-hoc வசதி அல்ல.

## Fat-tree எத்தனை இயந்திரங்களை இணைக்கும்?

ஒவ்வொன்றும் k port கொண்ட ஒரே மாதிரியான switch-களால் கட்டப்படும் மூன்றடுக்கு fat-tree-இன் பொதுவான வடிவம்:

- k "pod"-கள்; ஒவ்வொரு pod-இலும் k/2 விளிம்பு (edge) switch-கள், k/2 திரட்டு (aggregation) switch-கள்.
- ஒவ்வொரு edge switch-உம் தன் k port-களில் பாதியை (k/2) கணினிகளுக்கும், பாதியை மேலுள்ள aggregation switch-களுக்கும் தருகிறது.
- எனவே கணினிகள் = k pod × (k/2 edge) × (k/2 கணினி) = **k³/4**; மேலடுக்கு core switch-கள் = (k/2)².

| k (switch port-கள்) | கணினிகள் k³/4 | core switch-கள் (k/2)² |
|---|---|---|
| 4 | 64 ÷ 4 = 16 | 4 |
| 24 | 13,824 ÷ 4 = 3,456 | 144 |
| 48 | 110,592 ÷ 4 = 27,648 | 576 |

ஒவ்வொரு switch-இலும் கீழ்நோக்கிய port-கள் = மேல்நோக்கிய port-கள் என்பதால், விகிதம் 1:1 — "விளம்பரப்படுத்திய" அலைவரிசை உண்மையானது. மாறாக, ஒரு edge switch-இல் 40 port-கள் × 25 Gb/s கணினிகளுக்கும் 8 port-கள் × 100 Gb/s மேலேயும் இருந்தால் (எடுத்துக்காட்டு மதிப்புகள்): 1,000 Gb/s ÷ 800 Gb/s = **1.25:1** மிகைச் சந்தா — எல்லாக் கணினிகளும் ஒரே நேரத்தில் வெளியே அனுப்பினால் ஒவ்வொன்றும் 25 ÷ 1.25 = 20 Gb/s மட்டுமே பெறும். சுமையின் கீழ் மட்டுமே தெரியும் bottleneck இதுதான்.

## இந்தத் தொடரின் Fabric பணியின் அதே தத்துவம்

தேவையற்ற நகல்களை அகற்றுங்கள்; தேவையில்லாத இடத்தில் kernel-ஐ bypass செய்யுங்கள்; topology அனுமதிக்கும் அளவுக்கு நேரடியாக வன்பொருள் தரவை நகர்த்தட்டும். பதிவு 37 அதை GPU nodes-க்குள்ளும் குறுக்கேயும் பயன்படுத்தியது; இந்தப் பதிவு அதை இயந்திரத்திலிருந்து-இயந்திர வலையமைப்புக்குப் பயன்படுத்துகிறது. ஒன்றாக அவை Phase 7-இன் விநியோகிக்கப்பட்ட அமைப்புகளுக்கு ஒப்படைக்கின்றன — pre-web இணையத்தின் சொந்த ஆரம்ப find-and-talk அமைப்புகளுடன் தொடங்கி.

**இப்போது முயல்க: kernel-ஐக் கடப்பதன் விலையை அளவிடுங்கள்.** கீழே உள்ள VM-இல் அதே 64 MB-ஐ வெவ்வேறு துண்டு அளவுகளில் நகர்த்துங்கள் (எல்லாம் ஓட்டிச் சரிபார்த்தவை; உங்கள் நேரங்கள் வேறுபடும்):
1. `time dd if=/dev/zero of=/dev/null bs=1M count=64`
2. `time dd if=/dev/zero of=/dev/null bs=4k count=16384`
3. `time dd if=/dev/zero of=/dev/null bs=512 count=131072`
4. `time dd if=/dev/zero of=/dev/null bs=64 count=1048576`

ஒவ்வொரு துண்டுக்கும் ஒரு `read` + ஒரு `write` = 2 system call-கள். எங்கள் ஓட்டம்:

| துண்டு அளவு | system call-கள் | `real` நேரம் | வேகம் |
|---|---|---|---|
| 1 MB | 64 × 2 = 128 | 0.05 s | 64 ÷ 0.05 = 1,280 MB/s |
| 4 KB | 16,384 × 2 = 32,768 | 0.18 s | ≈ 356 MB/s |
| 512 B | 131,072 × 2 = 262,144 | 0.72 s | ≈ 89 MB/s |
| 64 B | 1,048,576 × 2 = 2,097,152 | 5.45 s | ≈ 11.7 MB/s |

அதே data, 100 மடங்குக்கும் மேல் நேர வேறுபாடு. 64 B வரிசையில் 5.45 s ÷ 2,097,152 ≈ 2.6 µs ஒவ்வொரு kernel கடப்புக்கும்; அப்போது `sys` நேரம் 4.61 s — பெரும்பாலும் kernel-இல். சிறு, அடிக்கடி வரும் செய்திகளுக்கு kernel பாதையின் நிலைத்த செலவே ஆதிக்கம் செலுத்துகிறது; RDMA போன்ற kernel தவிர்ப்பு அந்தச் செலவையே நீக்க முயல்கிறது.
