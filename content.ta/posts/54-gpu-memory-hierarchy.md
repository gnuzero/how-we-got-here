பதிவு 35 memory wall-ஐப் பெயரிட்டது: DRAM latency compute-ஐப் பின்தங்கினது, எனவே latency பிடிவாதமாக இருந்த இடத்தில் தொழில் *bandwidth*-ஐத் துரத்தியது. அந்தப் பதில் GPU நினைவகத்தை விட எங்கும் விளைவுமிக்கதல்ல — பதிவுகள் 52–53-இன் parallel throughput வழக்கமான DDR (பதிவு 34) உணவளிக்க முடியாத பசியை உருவாக்குகிறது.

> **தமிழ் இடைவெளிக் குறிப்பு:** HBM (High Bandwidth Memory) பற்றித் தமிழில் எழுத்து விளக்கமோ காணொளியோ இல்லை. இங்கே bandwidth-ஐ "அகலம் × வேகம்" என்று கணக்கிட்டு, NVIDIA Tesla V100-இன் உண்மையான நினைவக எண்களுடன் (Volta whitepaper-இலிருந்து சரிபார்த்தவை) GPU-வின் நினைவகப் படிநிலையைக் காட்டுகிறோம். மற்ற எண்கள் "எடுத்துக்காட்டு மதிப்பு".

## முதலில் சொற்கள்

- **Bandwidth (அலைக்கற்றை / தரவு வீதம்):** ஒரு விநாடியில் நகர்த்தக்கூடிய byte-கள் (GB/s).
- **Bus width (பாட்டை அகலம்):** ஒரே நேரத்தில் இணையாகச் செல்லும் தரவுக் கம்பிகளின் (பிட்களின்) எண்ணிக்கை.
- **Per-pin data rate (ஒரு pin-இன் வீதம்):** ஒரு கம்பி ஒரு விநாடியில் அனுப்பும் பிட்கள் (Gb/s).
- **DRAM die:** DRAM சேமிப்பு cell-கள் (பதிவு 10) நிறைந்த ஒரு silicon சில்லு.
- **Stack (அடுக்கு):** பல DRAM die-களை ஒன்றின் மேல் ஒன்றாக அடுக்கிய அமைப்பு.
- **TSV (Through-Silicon Via, சிலிகான் ஊடுருவும் இணைப்பு):** ஒரு die-ஐச் செங்குத்தாகத் துளைத்துச் செல்லும் சிறிய உலோக இணைப்பு; அடுக்கில் உள்ள die-களை மேலிருந்து கீழாக இணைக்கிறது.
- **Interposer (இடைத்தளம்):** பதிவு 51-இல் பார்த்த, die-களை அருகருகே வைத்து அடர்த்தியான கம்பிகளால் இணைக்கும் தளம்.
- **Arithmetic intensity (கணக்கு அடர்த்தி):** நினைவகத்திலிருந்து நகர்த்தும் ஒவ்வொரு byte-க்கும் செய்யப்படும் FLOP-கள் (பதிவு 35).

## GPU-கள் ஏன் CPU-பாணி நினைவகத்தில் பட்டினி கிடக்கின்றன

ஒரு CPU மிதமான எண்ணிக்கையிலான அறிவுறுத்தல் ஓடைகளை ஓட்டும்; caches (பதிவு 15) அடிக்கடி working set-ஐ உறிஞ்சும். ஒரு GPU பல SM-கள் குறுக்கே ஆயிரக்கணக்கான threads ஒரே நேரத்தில் நினைவகம் வேண்டும். On-chip caching உதவும், ஆனால் மொத்த bandwidth தேவை ஒத்த ஆற்றலில் ஒரு CPU நினைவக அமைப்பை விட நாடகரீதியாக உயர்ந்தது — வேறுபட்ட இயற்பியல் பதிலைக் கட்டாயப்படுத்திய கட்டுப்பாடு.

## HBM: Die அருகில் அடுக்குங்கள்

High Bandwidth Memory DRAM dies-ஐச் செங்குத்தாக அடுக்கி, தனியான DIMM-க்கு நீண்ட PCB traces-க்குப் பதிலாக through-silicon vias (TSV-கள்) வழியாக இணைக்கிறது. மிக அகலமான இடைமுகத்துடன் இணைந்து, அது சமமான DDR-ஐ விட வெகு அதிக bandwidth வழங்கும் — பதிவு 51-இன் advanced packaging-இல் செலுத்தப்பட்டது. HBM மற்றும் GPU compute die பொதுவாக ஒரு silicon interposer பகிரும்: chiplets-க்குப் பயன்படுத்தப்பட்ட அதே packaging குடும்பம், இங்கே செயல்பாட்டு dies-ஐப் பிரிக்காமல் நினைவகத்தை compute *அருகில்* வைக்கப் பயன்படுத்தப்பட்டது.

## GPU-க்குள்ளேயே Hierarchy

HBM-vs-DDR-க்கு அப்பால், GPU-க்குத் தன் சொந்த பிரமிடு உண்டு, பதிவு 10-இன் register–cache–main-memory வடிவத்தை GPU-குறிப்பிட்ட அடுக்குகளுடன் எதிரொலிக்கும். ஒவ்வொரு SM-இன் register file வேகமான உள்ளூர் சேமிப்பு. Shared memory — SM-இல் நிரலாளர்-நிர்வகிக்கும் scratchpad — ஒரு block-இல் threads தரவை மேலும் தொலைவுக்குச் சுற்றிச் செல்லாமல் பகிர அனுமதிக்கும். ஒரு L2 cache முழு GPU-வையும் உள்ளடக்கும். HBM "main memory" அடுக்கு: CPU DRAM-ஐ விட மிக உயர் bandwidth, on-chip எதையும் விட இன்னும் உயர் latency — அதே latency-vs-capacity tradeoff, GPU அளவில்.

## அடுத்து வருவதை உணவளித்தல்

இந்தக் கட்டமைப்பு மிகப் பெரிய compute பசியை உணவளிக்கவே உள்ளது. Peak FLOPS, operands வரவும் முடிவுகள் வெளியேறவும் முடியாவிட்டால் ஒன்றுமில்லை. அடுத்த பதிவின் tensor cores HBM-இன் bandwidth வழங்கக் கட்டப்பட்ட compute கட்டமைப்பு — bandwidth framing-ஐ முன்னோக்கிச் சுமந்து செல்லுங்கள்: ஒரு tensor core-இன் peak, அதைத் தாங்கக்கூடிய நினைவக அமைப்புக்கு எதிராக மட்டுமே அர்த்தம் கொள்ளும்.

## Bandwidth = அகலம் × வேகம்

எந்த நினைவக இடைமுகத்துக்கும்:

**Bandwidth (byte/விநாடி) = bus அகலம் (பிட்) × ஒரு pin-இன் வீதம் (பிட்/விநாடி) ÷ 8**

**DDR4-3200, ஒரு channel (பதிவு 35-இல் பார்த்தது):** 64 பிட் அகலம் × 3.2 Gb/s ÷ 8 = **25.6 GB/s**.

**V100-இன் HBM2 (whitepaper):** நான்கு HBM2 stack-கள், ஒவ்வொன்றிலும் நான்கு DRAM die-கள், மொத்தம் 16 GB; இடைமுகம் 4096 பிட் அகலம் (ஒவ்வொரு stack-உம் இரண்டு 512-bit கட்டுப்படுத்திகளால் இயக்கப்படுகிறது → ஒரு stack-க்கு 1024 பிட்); உச்ச bandwidth 900 GB/s. இதிலிருந்து ஒரு pin-இன் வீதத்தைப் பின்னோக்கிக் கணக்கிடலாம்:
1. 900 GB/s × 8 = 7,200 Gb/s
2. 7,200 ÷ 4,096 ≈ **1.76 Gb/s ஒரு pin-க்கு**

அதாவது HBM2-இன் ஒவ்வொரு கம்பியும் DDR4-3200-இன் கம்பியை விட **மெதுவானது** (1.76 எதிர் 3.2 Gb/s). வேகம் வருவது **அகலத்திலிருந்து**: 64 பிட்டுக்குப் பதிலாக 4,096 பிட்.

**அதே 900 GB/s-ஐ DDR4 கொண்டு அடைய முயன்றால்?**
1. 900 ÷ 25.6 ≈ 35 channel-கள்
2. 35 × 64 ≈ **2,250 தரவுக் கம்பிகள்** motherboard-இல் — முகவரி, கட்டுப்பாட்டுக் கம்பிகளைச் சேர்க்காமலே, மற்றும் 35 DIMM slot-கள்.

Motherboard-இல் இது சாத்தியமில்லை. HBM-இல் 4,096 கம்பிகளும் GPU die-க்கு மில்லிமீட்டர் தூரத்தில், interposer-இல் நுண்ணிய bump-கள் வழியாகச் செல்கின்றன — பதிவு 51-இன் pitch கணக்கை நினைவுகூருங்கள்: pitch குறைந்தால் ஒரு mm²-இல் பல மடங்கு அதிக இணைப்புகள். Stack-க்குள் die-களுக்கு இடையே TSV-கள் அதே வேலையைச் செங்குத்தாகச் செய்கின்றன.

**ஆற்றல் பக்கம் (எடுத்துக்காட்டு மதிப்புகள்):** 900 GB/s = 7.2 × 10¹² பிட்/விநாடி.
- குறுகிய interposer கம்பிகள், 4 pJ/பிட் என்று கொண்டால்: 7.2 × 10¹² × 4 × 10⁻¹² = **28.8 W**
- நீண்ட board கம்பிகள், 15 pJ/பிட் என்று கொண்டால்: 7.2 × 10¹² × 15 × 10⁻¹² = **108 W**

நீண்ட கம்பிகள் அதிக capacitance (பதிவு 36-இன் CV²f); அதிக வேகமான pin-களுக்கு அதிக சிக்கலான சமிக்ஞைச் சுற்றுகள் தேவை. "அகலமாகவும் மெதுவாகவும், குறுகிய தூரத்தில்" என்பது bandwidth-க்கும் watt-க்கும் ஒரே நேரத்தில் உதவுகிறது. விலை: advanced packaging (பதிவு 51) மற்றும் நிலையான திறன் — HBM-ஐ DIMM போல பின்னர் சேர்க்க முடியாது.

## V100-க்குள் உள்ள படிநிலை

பதிவு 10-இன் register → cache → முதன்மை நினைவகம் என்ற பிரமிடு, GPU வடிவில் (அளவுகள் Volta whitepaper-இலிருந்து):

| நிலை | எங்கே | அளவு (V100) | யார் கட்டுப்படுத்துகிறார் |
|---|---|---|---|
| Register file | ஒவ்வொரு SM | 256 KB / SM (80 SM-களில் 20 MB) | compiler |
| L1 cache + shared memory (இணைந்தது) | ஒவ்வொரு SM | 128 KB / SM; அதில் shared memory 96 KB வரை | shared: நிரலாளர்; L1: வன்பொருள் |
| L2 cache | முழு GPU-க்கும் பொது | 6,144 KB (6 MB) | வன்பொருள் |
| HBM2 | package-இல், GPU அருகில் | 16 GB, 900 GB/s | — |

கவனிக்க வேண்டியது: register-கள் (20 MB) L2-ஐ (6 MB) விடப் பெரியவை — CPU-வில் தலைகீழ். பதிவு 53-இல் பார்த்ததுபோல, ஆயிரக்கணக்கான குடியிருக்கும் thread-களின் நிலையை chip-இலேயே வைத்திருக்க வேண்டியதே காரணம்.

## Shared memory tiling: HBM போக்குவரத்தைக் குறைக்கும் கணக்கு

V100-இன் "ridge point" (பதிவு 52-இன் பயிற்சி 3): 15.7 TFLOPS ÷ 900 GB/s ≈ **17.4 FLOP/byte**. இதற்குக் கீழே கணக்கு அடர்த்தி உள்ள kernel நினைவகத்துக்காகக் காத்திருக்கும்; மேலே உள்ளது கணக்கு வேகத்தால் வரம்பிடப்படும்.

N × N FP32 matrix பெருக்கல் C = A × B:
- கணக்கு: 2N³ FLOP (ஒவ்வொரு N² வெளியீட்டுக்கும் N FMA-கள்)
- **இலட்சியமாக** ஒவ்வொரு எண்ணையும் HBM-இலிருந்து ஒரே முறை: A, B படிப்பு, C எழுத்து = 3 × 4N² = 12N² byte
- கணக்கு அடர்த்தி = 2N³ ÷ 12N² = **N/6** → N ≥ 105 என்றால் 17.4-ஐத் தாண்டும்

ஆனால் "ஒரே முறை" என்பது A, B முழுவதும் chip-இல் இருந்தால் மட்டுமே சாத்தியம்; அவை பொருந்தாது. நடைமுறைத் தீர்வு **tiling**: C-இன் T × T துண்டைக் கணக்கிட, A-இன் ஒரு T × T துண்டையும் B-இன் ஒரு T × T துண்டையும் shared memory-க்கு ஏற்றி, block-இன் எல்லா thread-களும் அவற்றை மீண்டும் மீண்டும் பயன்படுத்துகின்றன.
- ஒவ்வொரு படியிலும் HBM-இலிருந்து: 2 × T² எண்கள் × 4 byte = 8T² byte
- அந்தத் துண்டுகளால் செய்யும் கணக்கு: T³ FMA = 2T³ FLOP
- HBM-இலிருந்து கணக்கு அடர்த்தி = 2T³ ÷ 8T² = **T/4**

| Tile T | T/4 (FLOP/byte) | 17.4-உடன் ஒப்பிட | தேவையான shared memory (2 × T² × 4 byte) |
|---|---|---|---|
| 32 | 8 | நினைவகத்தால் வரம்பு | 8 KB |
| 64 | 16 | கிட்டத்தட்ட சமநிலை | 32 KB |
| 128 | 32 | கணக்கால் வரம்பு | 128 KB — 96 KB வரம்பைத் தாண்டுகிறது! |

பெரிய tile = சிறந்த மறுபயன்பாடு, ஆனால் shared memory எல்லை உண்டு — மற்றும் பெரிய tile ஒரு SM-இல் குடியிருக்கும் block-களைக் குறைக்கிறது (பதிவு 53-இன் occupancy). உண்மையான kernel-கள் register-களையும் இன்னொரு tiling அடுக்காகப் பயன்படுத்தி இந்த இடைவெளியை மூடுகின்றன. இது "HBM அதிக bandwidth தருகிறது" என்பதன் மறுபக்கம்: அது கூடப் போதாது; மறுபயன்பாடு இல்லாமல் tensor core-களும் (பதிவு 55) பட்டினி கிடக்கும்.

## காகிதப் பயிற்சிகள் (விடைகளுடன்)

1. ஒரு HBM stack 1024 பிட் அகலம், ஒரு pin-க்கு 3.2 Gb/s (எடுத்துக்காட்டு மதிப்பு). ஒரு stack-இன் bandwidth? ஆறு stack-களுக்கு?
   *விடை:* 1024 × 3.2 ÷ 8 = 409.6 GB/s; × 6 ≈ 2,458 GB/s ≈ 2.46 TB/s.
2. ஒரு GPU 50 TFLOPS, 2 TB/s. Ridge point? N × N matmul (இலட்சிய N/6) எந்த N-இலிருந்து கணக்கால் வரம்பிடப்படும்?
   *விடை:* 50 × 10¹² ÷ 2 × 10¹² = 25 FLOP/byte; N/6 ≥ 25 → N ≥ 150.
3. Tile T = 48 என்றால் HBM கணக்கு அடர்த்தியும் shared memory தேவையும்?
   *விடை:* 48 ÷ 4 = 12 FLOP/byte; 2 × 48² × 4 = 18,432 byte = 18 KB.
