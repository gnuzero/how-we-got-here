Out-of-order issue, ஆழமான pipeline-கள், அகலமான superscalar அகலம் — இந்தக் கட்டத்தில் இதுவரை உள்ள அனைத்தும் *ஒரு* அறிவுறுத்தல் ஓடையிலிருந்து அதிக Instruction-Level Parallelism (ILP) பிரித்தெடுக்கிறது. 2000-களின் நடுவில் அந்த அணுகுமுறை உத்தியை மாற்றும் அளவுக்குக் கடினமாக ஒரு கூரையை மோதியது.

"Superscalar" என்ற சொல்லுக்குத் தமிழ் விக்கிப்பீடியாவில் கட்டுரையும் இல்லை, தமிழ் YouTube விளக்கமும் இந்தத் தணிக்கையில் கிடைக்கவில்லை; multicore-க்குச் சில பாடத்திட்டக் காணொளிகள் மட்டுமே. எனவே கூரையை மோதுவதற்கு முன், அந்த அகலம் என்றால் என்ன, அது ஏன் தீர்ந்துபோகிறது என்பதை எண்களோடு பார்ப்போம்.

> **தமிழ் இடைவெளிக் குறிப்பு:** Superscalar-க்குத் தமிழ் விக்கிப்பீடியாவில் தனிக் கட்டுரை இல்லை (2026-11-05); multicore-க்கும் தனி எழுத்துக் கட்டுரை இல்லை. பாடத்திட்டக் காணொளித் தலைப்புகள் சில தேடலில் தோன்றுகின்றன. காணொளி மதிப்பீடு YouTube தேடல் தலைப்புகளை மட்டுமே அடிப்படையாகக் கொண்டது — காணொளிகள் பார்க்கப்படவில்லை. இந்தப் பக்கத்தின் கணக்கு எடுத்துக்காட்டுகள் எங்களுடையவை; "எடுத்துக்காட்டு மதிப்பு" எனக் குறிக்கப்பட்ட எண்கள் உண்மையான சிப் அளவீடுகள் அல்ல.

## முதலில் சொற்கள்

- **Issue அகலம்** (issue width) — ஒரு சுழற்சியில் அதிகபட்சம் எத்தனை அறிவுறுத்தல்களைத் தொடங்கலாம்.
- **IPC** — ஒரு சுழற்சிக்கு முடியும் அறிவுறுத்தல்கள் (CPI-இன் தலைகீழ்).
- **ILP** (instruction-level parallelism) — ஒரு நிரலுக்குள்ளேயே ஒரே நேரத்தில் ஓடக்கூடிய சுதந்திரமான அறிவுறுத்தல்கள்.
- **Core** (செயலி அலகு) — தனக்கென pipeline, பதிவேடுகள் கொண்ட முழுச் செயலி அலகு; ஒரு சிப்பில் பல இருக்கலாம்.
<!-- UNVERIFIED: "செயலி அலகு" for CPU core — no dedicated ta.wikipedia / TVA glossary hit; descriptive desk term. நுண்செயலி = microprocessor. -->
- **Amdahl விதி** — நிரலின் தொடர் (இணையாக்க முடியாத) பகுதியே மொத்த வேகத்துக்குக் கூரை வைக்கிறது.

## Superscalar என்றால் என்ன?

பதிவு 13-இன் pipeline இலட்சியமாக ஒரு சுழற்சிக்கு **ஒரு** அறிவுறுத்தலை முடிக்கிறது (CPI = 1). **Superscalar** செயலி ஒரு சுழற்சிக்கு **பல** அறிவுறுத்தல்களை fetch, decode, issue செய்கிறது — ஒவ்வொரு நிலையையும் அகலமாக்கி, பல ALU-களை இணையாக வைத்து. ஒரு சுழற்சிக்கு அதிகபட்சம் எத்தனை அறிவுறுத்தல்கள் என்பது **issue அகலம்** (issue width): "4-wide" என்றால் 4.

இங்கே CPI-க்குப் பதிலாக அதன் தலைகீழ் பயனுள்ளது: **IPC** (instructions per cycle, ஒரு சுழற்சிக்கான அறிவுறுத்தல்கள்) = 1 / CPI. 4-wide செயலியின் உச்ச IPC = 4. 3 GHz-இல் அது கோட்பாட்டளவில் ஒரு விநாடிக்கு 12 பில்லியன் அறிவுறுத்தல்கள். உண்மையான நிரல்களில் அடையும் IPC அதைவிட மிகக் குறைவு — ஏன் என்பதே இந்தப் பகுதியின் கதை.

## அகலம் பயன்படுவது சுதந்திரமான வேலை இருக்கும்போது மட்டும்

இரண்டு குறியீட்டுத் துண்டுகளை 4-wide இயந்திரத்தில் ஓட்டுவோம் (ஒவ்வொரு கூட்டலும் 1 சுழற்சி):

```
// துண்டு 1: சங்கிலி            // துண்டு 2: சுதந்திரம்
a = x + y;                     a = x + y;
b = a + z;                     b = z + w;
c = b + w;                     c = p + q;
d = c + v;                     d = r + s;
```

துண்டு 1-இல் ஒவ்வொரு வரியும் முந்தையதன் முடிவுக்குக் காத்திருக்கிறது (பதிவு 16-இன் RAW சார்பு) — 4 சுழற்சிகள், IPC = 1; மற்ற மூன்று ALU-களும் சும்மா. துண்டு 2-இல் நான்கும் சுதந்திரம் — **1 சுழற்சி**, IPC = 4. வன்பொருள் ஒன்றே; வேறுபாடு நிரலின் **சார்பு வரைபடத்தில்** (dependency graph).

**Worked example — எட்டு எண்களின் கூட்டுத்தொகை.** `s = s + a[i]` என்ற loop 7 சார்ந்த கூட்டல்கள் → 7 சுழற்சிகள், அகலம் எதுவானாலும். மரக் குறைப்பு (tree reduction): முதல் சுற்றில் (a0+a1), (a2+a3), (a4+a5), (a6+a7) — 4 சுதந்திரக் கூட்டல்கள், 1 சுழற்சி; இரண்டாம் சுற்றில் 2; மூன்றாம் சுற்றில் 1. மொத்தம் **3 சுழற்சிகள்** (அதே 7 கூட்டல்கள்). Compiler-களும் programmer-களும் அகலமான இயந்திரங்களுக்கு வேலையை இப்படி மறுசீரமைக்கின்றன. (மிதப்புப் புள்ளி எண்களில் கூட்டல் வரிசையை மாற்றுவது rounding-ஐச் சற்று மாற்றலாம் — அதனால் compiler-கள் அனுமதி இல்லாமல் இதைத் தானாகச் செய்வதில்லை.)

## அகலம் ஏன் விலை உயர்கிறது

1. **கிளைகள்** — ஒவ்வொரு சில அறிவுறுத்தல்களுக்கும் ஒரு கிளை வருவதால், ஒரு சுழற்சியில் 4 அல்லது 8 அறிவுறுத்தல்களை fetch செய்ய, ஒரே சுழற்சியில் பல கிளைகளைக் கடந்து ஊகிக்க வேண்டும் (பதிவு 14). ஒவ்வொரு தவறான ஊகமும் இப்போது 4 மடங்கு அதிக வேலையை வீணாக்குகிறது.
2. **சார்புச் சரிபார்ப்பு** — ஒரே சுழற்சியில் decode ஆகும் N அறிவுறுத்தல்களில், ஒவ்வொன்றின் மூலப் பதிவேடுகளும் அதற்கு முந்தைய ஒவ்வொன்றின் இலக்குடன் ஒப்பிடப்பட வேண்டும் (renaming-க்காக). ஒப்பீடுகளின் எண்ணிக்கை தோராயமாக N²-உடன் வளர்கிறது: அகலத்தை இரட்டித்தால் அந்த வன்பொருள் சுமார் நான்கு மடங்கு.
3. **நினைவக latency** — ஒரு cache miss (பதிவு 15) நூற்றுக்கணக்கான சுழற்சிகள் எடுத்தால், அகலமான இயந்திரமும் காத்திருக்கிறது; அதை மறைக்கப் பெரிய ROB (பதிவு 16) தேவை, அதுவும் பரப்பும் மின்சாரமும்.

## ஒரே நேரத்தில் இரண்டு சுவர்கள்

உண்மையான நிரல்கள் வரம்பற்ற சுதந்திரமான வேலையை வழங்குவதில்லை. கிளைகள், உண்மையான data dependencies, மற்றும் நினைவக latency ஒரே ஓடையிலிருந்து எத்தனை அறிவுறுத்தல்கள் இணையாக ஓட முடியும் என்பதை வரம்பிடுகின்றன. பெரிய ROB-கள், அதிக reservation stations, அகலமான issue: வளரும் பரப்பு மற்றும் மின்சாரத்திற்குக் குறைந்துவரும் வருவாய். அது ஒரு கட்டமைப்புச் சுவர்.

அதே நேரத்தில், dynamic மின்சாரம் தோராயமாக capacitance, அதிர்வெண், மற்றும் மின்னழுத்தத்தின் வர்க்கத்துடன் அளவிடுகிறது (P ≈ CV²f). ILP-இன் குறைந்துவரும் ஆதாயங்களுக்கு ஈடுசெய்ய clocks-ஐ உயர்த்துவது வெப்பத்தை மோதியது — பதிவு 36 விரிவாக உள்ளடக்கும் clock-speed சுவர். இரண்டு சுதந்திரமான கூரைகள், 2000-களின் நடுவில், எதுவுக்கும் சுத்தமான தனித் தீர்வு இல்லை.

## வேகத்திற்குப் பதிலாக அகலம்

திருப்பம்: ஒரு core ஒரு சுழற்சிக்கு அதிகம் செய்யச் செய்வதை நிறுத்துங்கள்; அதே die-இல் பல, சற்று எளிமையான cores வையுங்கள், ஒவ்வொன்றும் தன் சொந்த ஓடையுடன். Chip throughput ஏறத் தொடரலாம், per-core சிக்கலும் clocks-ம் நிலைபெறும்போது — அந்த cores-க்குக் கொடுக்க இணையான வேலை இருந்தால்.

**மின்சாரக் கணக்கு** (எளிமைப்படுத்திய மாதிரி — மின்னழுத்தம் அதிர்வெண்ணுடன் சேர்ந்து குறைக்கப்படலாம் என்று அனுமானித்து): ஒரு core, மின்னழுத்தம் V, அதிர்வெண் f: P = CV²f. இரண்டு core-கள், ஒவ்வொன்றும் 0.8V, 0.8f:

- ஒவ்வொன்றின் மின்சாரம் = C × (0.8V)² × 0.8f = 0.512 × CV²f
- இரண்டின் மொத்தம் = 1.024 × P — ஏறக்குறைய அதே மின்சாரம்
- வேலை முழுமையாக இணையாகும் என்றால் throughput = 2 × 0.8 = **1.6 மடங்கு**

அதே வெப்ப வரவுசெலவில் 60% அதிக வேலை — ஒரு core-ஐ வேகமாக்க முயல்வதை விட இது மலிவு. அதுதான் multicore திருப்பத்தின் பொருளாதாரம்.

**ஆனால் Amdahl விதி.** ஒரு நிரலின் p பங்கு மட்டுமே இணையாக ஓட முடியும் என்றால், n core-களில் அதிகபட்ச வேகம்:

> வேகம் = 1 / ((1 − p) + p / n)

p = 0.9, n = 8: 1 / (0.1 + 0.1125) ≈ **4.7 மடங்கு** — 8 அல்ல. n → ∞ ஆனாலும் 1 / 0.1 = **10 மடங்கு**தான் உச்சம். தொடர்நிலையில் மிஞ்சும் 10% எல்லாவற்றையும் கட்டுப்படுத்துகிறது.

"வேகமானது" பொருள் மாறியது. ஒரு single-threaded நிரல் நான்கு cores-க்கு எதிராக எட்டு cores-இல் தானாக வெல்வதில்லை; அது இன்னும் ஒரு core-இல் தோராயமாக அதே clock-இல் ஓடுகிறது. Multicore ஆதாயம் பல threads-க்கு எழுதப்பட்ட (அல்லது தொகுக்கப்பட்ட) workloads-க்கு மட்டுமே தோன்றுகிறது. ILP காலம் பெரும்பாலும் ஒவ்வொரு தலைமுறையும் single-thread வேக உயர்வுகளை "இலவசமாக" கொடுத்தது; இந்தக் காலம் parallel-அறிந்த மென்பொருளைக் கோருகிறது. பல core-கள் ஒரே தரவைப் பகிரும்போது cache coherence (பதிவு 15) கூடுதல் செலவாகச் சேர்கிறது.

**கையால் முயல்க.** (இந்தப் பதிவுக்கு lab இல்லை.)

1. `s = ((a + b) + c) + d` மற்றும் `s = (a + b) + (c + d)` — 2-wide இயந்திரத்தில் ஒவ்வொன்றுக்கும் எத்தனை சுழற்சிகள்? (விடை: 3 மற்றும் 2.)
2. 16 எண்களின் கூட்டுத்தொகை: சங்கிலியாக எத்தனை சுழற்சிகள், 8-wide இயந்திரத்தில் மரமாக எத்தனை? (விடை: 15; 4 சுற்றுகள் = 4 சுழற்சிகள்.)
3. p = 0.95 என்றால் 16 core-களில் Amdahl வேகம் என்ன? (விடை: 1 / (0.05 + 0.059375) ≈ 9.1.)
4. உங்கள் சொந்த Linux கணினியில் `nproc` ஓட்டி எத்தனை core-கள் (hardware threads) உள்ளன என்று பாருங்கள்.

## திருப்பம் எங்கு சுட்டுகிறது

அதே விசை — ஒரு சிக்கலான ஒன்றுக்குப் பதிலாக பல எளிமையான அலகுகள் — GPU-களுக்குப் (Phase 9) பின்னால் உள்ள தத்துவம் மேலும் எடுக்கப்பட்டது. Parallel வேலையைச் சரியாக ஒருங்கிணைப்பது ஏன் real-time அமைப்புகளில் (Phase 4) மற்றும் விநியோகிக்கப்பட்ட அமைப்புகளில் (Phase 7) முதன்மைப் பிரச்சனையாகிறது என்பதற்குக் காரணமும் இது: அடுத்த சிப் ஒரு thread-ஐ வேகமாக்கும் வரை காத்திருப்பது இனி முக்கிய வளர்ச்சிப் பாதை அல்ல.
