ஒற்றை GPU-க்கு வரையறுக்கப்பட்ட compute மற்றும் வரையறுக்கப்பட்ட HBM (பதிவு 54) உண்டு. இன்றைய மிகப் பெரிய மாதிரிகளுக்குப் பல GPU-கள் தேவை — ஒரு server-இல், பிறகு ஒரு cluster குறுக்கே — மற்றும் அந்த GPU-கள் ஒருவருக்கொருவர் எப்படிப் பேசுகின்றன என்பது எந்த ஒற்றை GPU-வின் peak specs போலவே உண்மையான throughput-ஐ அடிக்கடி தீர்மானிக்கும்.

> **தமிழ் இடைவெளிக் குறிப்பு:** பல GPU-களில் பயிற்சி (multi-GPU training), data parallelism பற்றித் தமிழில் விளக்கம் இல்லை. இங்கே ஒரு பயிற்சிப் படியின் தொடர்பு நேரத்தை PCIe மற்றும் NVLink எண்களுடன் கணக்கிட்டு, "இணைப்பு ஏன் முதல்தரக் கட்டுப்பாடு" என்பதை எண்களில் காட்டுகிறோம். NVLink எண்கள் NVIDIA Volta whitepaper-இலிருந்து; மாதிரி அளவு, கணக்கு நேரம் போன்றவை எடுத்துக்காட்டு மதிப்புகள்.

## முதலில் சொற்கள்

- **Parameter / weight (அளவுரு / எடை):** ஒரு neural network கற்றுக்கொள்ளும் எண்கள். பெரிய மாதிரிகளில் பில்லியன் கணக்கில்.
- **Gradient (சரிவு):** ஒவ்வொரு parameter-ஐயும் எந்தத் திசையில், எவ்வளவு மாற்றினால் பிழை குறையும் என்று சொல்லும் எண். ஒவ்வொரு parameter-க்கும் ஒரு gradient.
- **Training step (பயிற்சிப் படி):** ஒரு தரவுத் தொகுதியில் (batch) forward கணக்கு, backward கணக்கு (gradient-கள்), பிறகு parameter புதுப்பிப்பு.
- **Data parallelism (தரவு இணைச் செயல்பாடு):** ஒவ்வொரு GPU-விலும் முழு மாதிரியின் நகல்; batch-ஐப் பிரித்து ஒவ்வொன்றும் ஒரு பகுதியைக் கணக்கிடுகிறது.
- **Model parallelism (மாதிரி இணைச் செயல்பாடு):** மாதிரியையே பிரித்து வெவ்வேறு GPU-களில் வைப்பது — ஒரு GPU-வின் நினைவகத்தில் பொருந்தாதபோது.
- **All-reduce (அனைத்தும்-குறை):** எல்லா GPU-களின் gradient-களையும் கூட்டி (அல்லது சராசரி எடுத்து) அந்த விடையை எல்லா GPU-களுக்கும் திருப்பித் தரும் கூட்டுத் தொடர்பு. விரிவான கணக்கு பதிவு 61-இல்.
- **Scaling efficiency (அளவீட்டுத் திறன்):** N GPU-களில் பெற்ற வேகம் ÷ N மடங்கு இலட்சிய வேகம்.

## வேலையைப் பிரிப்பது இலவசம் அல்ல

பதிவு 46 data-parallel மற்றும் model-parallel பிரிவுகள் ஏன் அடிக்கடி அவசியம் என்பதை உள்ளடக்கியது. திறன் GPU-கள் தரவை எவ்வளவு வேகமாகப் பரிமாறிக்கொள்கின்றன என்பதைப் பொறுத்தது. ஒவ்வொரு GPU-வின் compute-க்கு ஒப்பீட்டில் தொடர்பு மெதுவாக இருந்தால், peers ஒருவருக்கொருவர் காத்திருந்து stall ஆகும் — memory wall (பதிவு 35) மீண்டும், CPU-to-DRAM-க்குப் பதிலாக GPU-to-GPU இணைப்புகளுக்குப் பயன்படுத்தப்பட்டது.

## ஒரு Server-க்குள் நேரடி பாதைகள்

பதிவு 37 NVLink-ஐ CPU-மத்தியஸ்த PCIe பாதையைத் தவிர்க்கும் உயர்-bandwidth GPU-to-GPU interconnect-ஆக அறிமுகப்படுத்தியது. ஒரு server-க்குள், NVSwitch அதை all-to-all ஆக்குகிறது: ஒவ்வொரு GPU-வும் மற்ற ஒவ்வொன்றையும் PCIe மற்றும் host வழியாக அல்லாமல் NVLink bandwidth-இல் அடையும். பெரிய gradients-ஐ தொடர்ந்து பரிமாறும் workloads-க்கு, அந்த நேரடி பாதை தனிமைப்படுத்தப்பட்ட peak-FLOPS எண்ணை விட அடையப்பட்ட பயிற்சி throughput-ஐ அடிக்கடி தீர்மானிக்கும்.

## ஒரு Box-க்கு அப்பால்

பெரிய பயிற்சி பல servers குறுக்கே நீளும். பதிவு 42-இன் RDMA கருத்துக்கள் திரும்பும்: GPUDirect RDMA ஒரு network adapter-ஐ host DRAM வழியாக கூடுதல் நகல்கள் இல்லாமல் servers குறுக்கே GPU நினைவகத்தைப் படிக்க அல்லது எழுத அனுமதிக்கும் — அதே "hops குறைக்கவும், நேரடி bandwidth அதிகரிக்கவும்" பந்தயம், இப்போது cluster அளவில்.

## இந்தத் தொடர் தொடர்ந்து பெயரிடும் தத்துவம்

நேரடி GPU-to-GPU பாதைகள், தேவையற்ற hops குறைவு, interconnect முதல்-தர கட்டுப்பாடாக — இந்தத் தொடர் குறிப்பிட்ட தனிப்பயன் GPU memory fabric பின்னால் உள்ள அதே தத்துவம்: ஒரு vendor-இன் stack-க்குள் proprietary GPU fabrics செய்வதற்குத் திறந்த, PCIe-அடிப்படையிலான அணுகுமுறை. Phase 10 நூலை உண்மையான datacenter அளவில் எடுக்கும் — ஒரு box-இல் சில GPU-கள் அல்ல, ஆனால் ஒரு பயிற்சி cluster குறுக்கே ஆயிரக்கணக்கானவை, மொத்த தத்துவார்த்த compute ஒருங்கிணைப்பில் இழக்காதபடி கம்பி இணைக்கப்பட்டவை.

## ஒரு data-parallel பயிற்சிப் படி, படிப்படியாக

N GPU-கள், ஒவ்வொன்றிலும் முழு மாதிரியின் நகல்:

1. Batch-ஐ N பகுதிகளாகப் பிரி; ஒவ்வொரு GPU-வும் தன் பகுதியில் forward, backward கணக்கிட்டு தன் gradient-களைப் பெறுகிறது.
2. **All-reduce:** எல்லா GPU-களின் gradient-களையும் சராசரி எடு; ஒவ்வொரு GPU-வுக்கும் அதே சராசரி கிடைக்கிறது.
3. ஒவ்வொரு GPU-வும் அதே சராசரியால் தன் parameter-களைப் புதுப்பிக்கிறது → நகல்கள் ஒன்றாகவே இருக்கின்றன.

படி 1 N மடங்கு இணையாகிறது. படி 2 **புதிய வேலை** — ஒரு GPU-வில் இது இல்லவே இல்லை. அதன் நேரம் இணைப்பின் bandwidth-ஐப் பொறுத்தது.

## தொடர்பு நேரம்: PCIe எதிர் NVLink

**எடுத்துக்காட்டு மதிப்புகள்:** 100 கோடி (1 billion) parameter-கள் கொண்ட மாதிரி; gradient-கள் FP16 (2 byte) → gradient அளவு S = 2 GB. N = 8 GPU-கள். பதிவு 61-இல் பெறப்போகும் ring all-reduce சூத்திரத்தின்படி, ஒவ்வொரு GPU-வும் அனுப்ப வேண்டியது (பெற வேண்டியதும்) சுமார் 2(N − 1)/N × S:
- 2 × 7 ÷ 8 × 2 GB = **3.5 GB ஒவ்வொரு GPU-வுக்கும், ஒவ்வொரு படியிலும்**

**PCIe 3.0 ×16 வழியாக:** ஒரு lane 8 GT/s, 128b/130b குறியாக்கம், 16 lane-கள்:
1. 8 × 10⁹ × 16 × (128 ÷ 130) ÷ 8 ≈ **15.75 GB/s ஒரு திசைக்கு**
2. 3.5 ÷ 15.75 ≈ **0.222 விநாடி**

**V100 NVLink வழியாக (whitepaper):** ஆறு NVLink இணைப்புகள், ஒவ்வொன்றும் ஒரு திசைக்கு 25 GB/s → ஒரு திசைக்கு 150 GB/s (இரு திசைகளும் சேர்த்து "300 GB/s"). எல்லா இணைப்புகளும் இந்த ஒரு வேலைக்குப் பயன்படும் என்ற இலட்சிய மேல் எல்லையில்:
1. 3.5 ÷ 150 ≈ **0.023 விநாடி (23 ms)**

**Scaling efficiency:** ஒரு GPU-வின் பங்குக் கணக்கு நேரம் ஒரு படிக்கு 0.3 விநாடி என்று கொள்வோம் (எடுத்துக்காட்டு மதிப்பு), தொடர்பும் கணக்கும் ஒன்றன்பின் ஒன்றாக (overlap இல்லாமல்):

| இணைப்பு | ஒரு படி நேரம் | Efficiency = 0.3 ÷ படி நேரம் | 8 GPU-களில் பெறும் வேகம் |
|---|---|---|---|
| PCIe 3.0 ×16 | 0.3 + 0.222 = 0.522 s | 57.5% | 8 × 0.575 ≈ **4.6×** |
| NVLink (இலட்சியம்) | 0.3 + 0.023 = 0.323 s | 92.8% | 8 × 0.928 ≈ **7.4×** |

அதே 8 GPU-கள், அதே peak FLOPS — ஆனால் ஒரு அமைப்பு மற்றதை விட 60% அதிக வேலை செய்கிறது. ஆங்கிலப் பதிவு சொல்வதுபோல, இணைப்பு "தனித்த peak-FLOPS எண்ணை விட அடிக்கடி உண்மையான பயிற்சி வேகத்தைத் தீர்மானிக்கிறது".

**Overlap:** Backward கணக்கு கடைசி layer-இலிருந்து முதல் layer-க்குப் போகிறது. கடைசி layer-களின் gradient-கள் தயாரானவுடன் அவற்றை அனுப்பத் தொடங்கலாம், முதல் layer-களின் கணக்கு நடக்கும்போதே. சரியாகச் செய்தால் தொடர்பு நேரத்தின் பெரும்பகுதி கணக்கின் பின்னால் மறைகிறது — பதிவு 53-இன் latency hiding, cluster அளவில்.

## மாதிரி ஏன் ஒரு GPU-வில் பொருந்தாது: நினைவகக் கணக்கு

Mixed precision-இல் Adam optimizer உடன் பயிற்சி செய்யும்போது ஒவ்வொரு parameter-க்கும் பொதுவாகச் சேமிக்கப்படுபவை (ஒரு பொதுவான அமைப்பு):

| என்ன | byte / parameter |
|---|---|
| FP16 weight | 2 |
| FP16 gradient | 2 |
| FP32 "master" weight நகல் | 4 |
| Adam-இன் இரண்டு FP32 நிலைகள் (momentum, variance) | 4 + 4 = 8 |
| **மொத்தம்** | **16** |

- 100 கோடி parameter-கள் × 16 byte = **16 GB** — V100-இன் முழு 16 GB HBM2, activation-களுக்கு இடமே இல்லாமல்.
- 1,000 கோடி (10 billion) parameter-கள் → 160 GB → குறைந்தது 10 V100-களில் பிரிக்க வேண்டும்.

இங்கே data parallelism மட்டும் போதாது — ஒவ்வொரு GPU-விலும் முழு நகல் பொருந்தாது. மாதிரியின் layer-களை GPU-களுக்கு இடையே பிரிப்பதோ (pipeline), ஒவ்வொரு matrix-ஐயும் பிரிப்பதோ (tensor parallel), optimizer நிலைகளைப் பிரித்துப் பகிர்வதோ தேவை. ஒவ்வொன்றும் **மேலும்** தொடர்பைக் கோருகிறது — சில நேரங்களில் ஒவ்வொரு layer-இலும்.

## ஒரு box-க்கு அப்பால்: copy-களை எண்ணுவோம்

இரண்டு server-களில் உள்ள GPU-களுக்கு இடையே தரவு:

**GPUDirect RDMA இல்லாமல்:**
1. GPU நினைவகம் → host DRAM (copy 1)
2. Host DRAM → network card (copy 2)
3. Network → மறு server-இன் network card
4. Network card → host DRAM (copy 3)
5. Host DRAM → GPU நினைவகம் (copy 4)

**GPUDirect RDMA உடன்:** network card நேரடியாக GPU நினைவகத்தைப் படிக்கிறது/எழுதுகிறது: GPU → NIC → network → NIC → GPU. Host DRAM வழியாகச் செல்லும் இடைநிலை copy-கள் நீங்குகின்றன; CPU-வும் host நினைவக bandwidth-உம் விடுவிக்கப்படுகின்றன. பதிவு 42-இன் RDMA கருத்து — "hop-களைக் குறை, நேரடி bandwidth-ஐ அதிகரி" — GPU அளவில்.

## காகிதப் பயிற்சிகள் (விடைகளுடன்)

1. S = 4 GB gradient, N = 16 GPU-கள். ஒவ்வொரு GPU-வும் ஒரு படிக்கு அனுப்ப வேண்டியது (ring all-reduce)?
   *விடை:* 2 × 15 ÷ 16 × 4 = 7.5 GB.
2. ஒரு திசைக்கு 50 GB/s இணைப்பில் அது எத்தனை நேரம்? கணக்கு நேரம் 0.5 s என்றால் overlap இல்லாத efficiency?
   *விடை:* 7.5 ÷ 50 = 0.15 s; 0.5 ÷ 0.65 ≈ 76.9%.
3. 700 கோடி (7 billion) parameter மாதிரியை மேலே உள்ள 16 byte/parameter கணக்கில் பயிற்சி செய்ய, 80 GB GPU-கள் குறைந்தது எத்தனை தேவை (activation-களைப் புறக்கணித்து)?
   *விடை:* 7 × 10⁹ × 16 = 112 GB → 112 ÷ 80 = 1.4 → குறைந்தது 2 GPU-கள்.
