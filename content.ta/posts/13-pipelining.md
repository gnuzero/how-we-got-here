Single-cycle datapath (பதிவு 12) throughput-ஐ மேசையில் விட்டுவிடுகிறது: ஒவ்வொரு அறிவுறுத்தலும் மிக மெதுவான சாத்தியமான பாதைக்காகக் காத்திருக்கிறது. Pipelining செயல்பாட்டை நிலைகளாகப் பிரித்து, பல அறிவுறுத்தல்கள் வெவ்வேறு நிலைகளை *ஒரே நேரத்தில்* ஆக்கிரமிக்க விடுகிறது.

தமிழில் pipelining-க்கு Anna University பாடத்திட்டக் காணொளிகள் உள்ளன; ஆனால் எழுத்து வடிவில் கிடைப்பது இயந்திர மொழிபெயர்ப்பான MCQ விளக்கங்கள் மட்டுமே (தமிழ் விக்கிப்பீடியாவில் கட்டுரை இல்லை). எனவே இங்கே நேர வரைபடம், வேகக் கணக்கு, ஒவ்வொரு இடர் வகைக்கும் சுழற்சி-வாரியான எடுத்துக்காட்டு ஆகியவற்றைத் தமிழில் முழுமையாகத் தருகிறோம்.

## ஐந்து நிலைகள், மேலெழுதப்பட்டவை

ஒரு செவ்வியல் RISC pipeline:

- **IF** (instruction fetch) — PC சுட்டும் முகவரியிலிருந்து அறிவுறுத்தலை நினைவகத்திலிருந்து எடு.
- **ID** (instruction decode) — opcode-ஐப் புரிந்துகொள், மூலப் பதிவேடுகளைப் படி.
- **EX** (execute) — ALU கணக்கு, அல்லது load/store-க்கான முகவரிக் கணக்கு.
- **MEM** (memory access) — load என்றால் தரவு நினைவகத்திலிருந்து படி, store என்றால் எழுது.
- **WB** (write back) — முடிவை இலக்குப் பதிவேட்டில் எழுது.

நிலைகளுக்கு இடையே **pipeline பதிவேடுகள்** (pipeline registers; பதிவு 9-இன் flip-flop அணிகள்) ஒவ்வொரு clock விளிம்பிலும் முடிவுகளைப் பூட்டுகின்றன, அதனால் ஒவ்வொரு நிலையும் தன் சொந்த அறிவுறுத்தலில் சுதந்திரமாக வேலை செய்கிறது.

**நேர வரைபடம்** (ஐந்து சுதந்திரமான அறிவுறுத்தல்கள்; நெடுவரிசைகள் = clock சுழற்சிகள்):

| | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| i1 | IF | ID | EX | MEM | WB | | | | |
| i2 | | IF | ID | EX | MEM | WB | | | |
| i3 | | | IF | ID | EX | MEM | WB | | |
| i4 | | | | IF | ID | EX | MEM | WB | |
| i5 | | | | | IF | ID | EX | MEM | WB |

சுழற்சி 5-இல் ஐந்து நிலைகளும் ஐந்து வெவ்வேறு அறிவுறுத்தல்களால் நிரம்பியுள்ளன. அதன்பின் ஒவ்வொரு சுழற்சியும் ஒரு புதிய அறிவுறுத்தல் *முடிக்கப்படுகிறது* — ஒவ்வொன்றும் தொடக்கம் முதல் முடிவு வரை இன்னும் ஐந்து சுழற்சிகள் எடுத்தாலும். **Latency** (ஒரு அறிவுறுத்தலின் மொத்த நேரம்) நிலைத்திருக்கிறது; **throughput** (ஒரு நேர அலகில் முடியும் அறிவுறுத்தல்கள்) உயர்கிறது. அந்த வேறுபாடு இதற்குப் பிறகு எல்லா இடத்திலும் தோன்றுகிறது. N அறிவுறுத்தல்களுக்கு k நிலை pipeline எடுக்கும் சுழற்சிகள் = k + (N − 1).

## வேகக் கணக்கு: 5 மடங்கு அல்ல, ஏன்?

Single-cycle இயந்திரத்தில் ஒரு அறிவுறுத்தலுக்கு 1000 ps (மிக மெதுவான அறிவுறுத்தலின் முழுப் பாதை) என்று வைப்போம். அதை ஐந்து நிலைகளாக வெட்டினால் நிலைத் தாமதங்கள் சமமாக வராது: IF 200, ID 150, EX 200, MEM 250, WB 150 ps (மொத்தம் 950). ஒவ்வொரு pipeline பதிவேடும் சுமார் 20 ps கூடுதல் செலவு (பதிவு 9-இன் clock-to-Q + setup).

- Pipeline clock = மிக மெதுவான நிலை + பதிவேட்டுச் செலவு = 250 + 20 = **270 ps**.
- ஒரு தனி அறிவுறுத்தல்: 5 × 270 = 1350 ps — single-cycle-ஐ (1000 ps) விட *மெதுவானது*!
- 1000 அறிவுறுத்தல்கள்: (5 + 999) × 270 = 271,080 ps; single-cycle-இல் 1,000,000 ps. வேகம் ≈ **3.69 மடங்கு**.

இலட்சியம் 5 மடங்கு. இழப்புக்கு இரண்டு காரணங்கள்: நிலைகள் சமநிலையில் இல்லை (clock மிக மெதுவான MEM-க்குக் காத்திருக்கிறது), மற்றும் ஒவ்வொரு நிலைக்கும் பதிவேட்டுச் செலவு. நிலைகளை மேலும் மேலும் வெட்டினால் இந்தச் செலவு பங்கு கூடுகிறது — ஆழம் இலவசம் அல்ல. அதோடு, கீழே வரும் இடர்கள் இன்னும் கணக்கில் இல்லை.

**இப்போது முயல்க.** கீழே உள்ள mini-CPU-வை அறிவுறுத்தல் ஒன்றுக்கு ஒருமுறை **படி (Step)** அழுத்துங்கள் — அது பதிவு 12 காட்டிய single-cycle பழக்கம். Pipelining-இன் உரிமைகோரல் throughput: அதே fetch / decode / execute துண்டுகள் அறிவுறுத்தல்களுக்கு இடையே மேலெழுதல், டிக் ஒன்றுக்கு ஒரு முழு அறிவுறுத்தல் அல்ல. பிறகு இதைச் செய்யுங்கள்:

1. ஏற்கனவே ஏற்றப்பட்ட எட்டு-அறிவுறுத்தல் நிரலை (`LDI 5` … `HLT`) **படி** அழுத்தி, ஒவ்வொரு அறிவுறுத்தலும் நினைவகத்தை *எத்தனை முறை* தொடுகிறது என்று குறியுங்கள்: ஒவ்வொன்றும் fetch-க்கு ஒருமுறை; `STA 14`, `ADD 14`, `STA 15`, `LDA 15` தரவுக்காக இன்னொருமுறை.
2. இந்த நிரலுக்கு மேலே உள்ளதுபோல் ஐந்து நிலை நேர வரைபடத்தைக் காகிதத்தில் வரையுங்கள். எந்தச் சுழற்சிகளில் ஒரு அறிவுறுத்தலின் IF-உம் இன்னொன்றின் MEM-உம் *ஒரே* 16-பைட் நினைவகத்தைக் கேட்கின்றன என்று வட்டமிடுங்கள் — அவைதான் கீழே விளக்கப்படும் structural hazard-கள்.
3. ஒவ்வொரு அறிவுறுத்தலும் A பதிவேட்டைப் படிக்கிறதா, எழுதுகிறதா என்று குறியுங்கள். A-இன் மதிப்பு EX-இல் தயாராகி அடுத்த அறிவுறுத்தலின் EX-இல் தேவைப்படும் இடங்களில் அம்புக்குறி வரையுங்கள் — அவைதான் forwarding பாதைகள்.

## Hazards: சுதந்திரம் உடையும் இடம்

அறிவுறுத்தல்கள் அரிதாகவே சுதந்திரமானவை. **இடர்** (hazard) என்பது அடுத்த அறிவுறுத்தல் தன் திட்டமிட்ட சுழற்சியில் சரியாக ஓட முடியாத நிலை. மூன்று வகைகள்.

### 1. Structural hazard (வள இடர்)

இரண்டு அறிவுறுத்தல்களுக்கு ஒரே சுழற்சியில் ஒரே வன்பொருள் தேவை. செவ்வியல் எடுத்துக்காட்டு: ஒரே ஒரு நினைவக வாயில் (port). மேலே உள்ள வரைபடத்தில் சுழற்சி 4-இல் i1 MEM-இல் (load என்றால் நினைவகம் படிக்கிறது) இருக்கும்போது i4 IF-இல் (அதுவும் நினைவகம் படிக்கிறது). Mini-CPU-இல் நிரலும் தரவும் ஒரே 16-பைட் நினைவகத்தில் வாழ்கின்றன (von Neumann அமைப்பு) — அதை pipeline செய்தால் இந்த மோதல் அடிக்கடி வரும். தீர்வு: அறிவுறுத்தல்களுக்கும் தரவுக்கும் தனித்தனி L1 cache-கள் (பதிவு 15) — இன்றைய CPU-கள் L1-இல் அப்படித்தான் பிரிக்கின்றன.

### 2. Data hazard (தரவு இடர்)

ஒரு அறிவுறுத்தலுக்கு முந்தைய, இன்னும் பறக்கும் அறிவுறுத்தல் எழுதி முடிக்காத மதிப்பு தேவை:

```
add r1, r2, r3     ; r1 ← r2 + r3
sub r4, r1, r5     ; r1 உடனே தேவை
```

`add`-இன் முடிவு EX முடிவில் (சுழற்சி 3) கணக்கிடப்படுகிறது, ஆனால் register file-இல் WB-இல் (சுழற்சி 5) தான் எழுதப்படுகிறது. `sub` தன் ID-இல் (சுழற்சி 3) r1-ஐப் படிக்க விரும்புகிறது — இன்னும் பழைய மதிப்பு. Forwarding இல்லாவிட்டால் `sub` இரண்டு சுழற்சிகள் **stall** (bubble) செய்ய வேண்டும் (register file சுழற்சியின் முதல் பாதியில் எழுதி இரண்டாம் பாதியில் படிக்கும் என்று அனுமானித்து).

**Forwarding** (bypassing): ALU முடிவை EX/MEM pipeline பதிவேட்டிலிருந்து நேரடியாக அடுத்த அறிவுறுத்தலின் ALU உள்ளீட்டுக்குத் திருப்பும் கம்பியும் mux-உம் (பதிவு 8). இப்போது `sub`-இன் EX (சுழற்சி 4) `add`-இன் EX முடிவை (சுழற்சி 3 முடிவில்) நேரடியாகப் பெறுகிறது — **பூஜ்ய stall**.

Forwarding ஒவ்வொரு இடைவெளியையும் மூட முடியாது:

```
lw  r1, 0(r2)      ; load: தரவு MEM முடிவில்தான் வரும்
sub r4, r1, r5
```

Load-இன் தரவு MEM முடிவில் (சுழற்சி 4) தான் கிடைக்கிறது; `sub`-இன் EX-உம் சுழற்சி 4-இல். காலத்தில் பின்னோக்கி forward செய்ய முடியாது — **ஒரு stall** தவிர்க்க முடியாதது. இதுதான் **load-use hazard**. Compiler சார்பில்லாத ஒரு அறிவுறுத்தலை இடையில் நகர்த்தினால் (instruction scheduling) அந்த bubble மறையலாம்.

### 3. Control hazard (கட்டுப்பாட்டு இடர்)

கிளைகள். கிளை EX-இல் தீர்மானமானால், அதற்குள் அடுத்த இரண்டு அறிவுறுத்தல்கள் IF, ID-இல் நுழைந்துவிட்டன; taken ஆனால் அவற்றை flush செய்ய வேண்டும் — 2 சுழற்சி இழப்பு. தவறான பாதையில் செலவழிக்கப்பட்ட சுழற்சிகள் வீணாகின்றன. விரிவான கணக்கு பதிவு 14-இல்.

## எல்லாம் சேர்த்து: CPI கணக்கு

> CPI = 1 + (ஒரு அறிவுறுத்தலுக்குச் சராசரி stall சுழற்சிகள்)

எடுத்துக்காட்டு: 25% அறிவுறுத்தல்கள் load, அவற்றில் பாதியை உடனே சார்ந்த அறிவுறுத்தல் தொடர்கிறது (ஒவ்வொன்றுக்கும் 1 stall) → 0.25 × 0.5 × 1 = 0.125. 20% கிளைகள், "not-taken" என ஊகிப்பு, 60% taken, தண்டனை 2 → 0.20 × 0.60 × 2 = 0.24. மொத்தம் CPI = 1 + 0.125 + 0.24 = **1.365**. அதாவது இலட்சிய pipeline-இன் throughput-இல் சுமார் 73% (1 / 1.365). அந்த 0.24-ஐக் குறைப்பதே branch prediction; அந்த 0.125-ஐக் குறைப்பதே out-of-order execution.

## அந்தச் செலவுகள் அடுத்து எதைக் கட்டாயப்படுத்துகின்றன

Misprediction flush-கள் விலை உயர்ந்தவை — அதனால்தான் branch prediction (பதிவு 14) உள்ளது: முன்கூட்டியே, flush அரிதாகும் அளவுக்குத் துல்லியமாக ஊகிக்க. Load-use stall-தான் out-of-order execution (பதிவு 16) உள்ளதற்குக் காரணம்: காத்திருக்கும் அறிவுறுத்தலை மட்டும் stall செய்து, முழு pipeline-ஐ அல்ல, மற்றும் அதற்குப் பின்னால் உள்ள சுதந்திரமான வேலையை ஓட விடுங்கள்.
