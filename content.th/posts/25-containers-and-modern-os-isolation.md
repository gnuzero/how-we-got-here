หน่วยความจำเสมือน (บทที่ 24) แยกโพรเซสจากหน่วยความจำของกันและกัน มันไม่แยกพวกมันจากการแชร์ระบบไฟล์เดียวกัน เนมสเปซ process ID เดียวกัน หรือการตั้งค่าเครือข่ายเดียวกัน — โพรเซส Unix แบบดั้งเดิมสามารถเห็น (และบางครั้งรบกวน) โพรเซสอื่นบนเครื่องเดียวกันได้หลายทางนอกเหนือจากการเข้าถึงหน่วยความจำดิบ คอนเทนเนอร์ขยายการแยกให้ครอบคลุมพื้นผิวส่วนนั้นมากขึ้น โดยไม่ไปถึงฮาร์ดแวร์ virtualization เต็มรูป

## Full Virtualization: ตัวเลือกหนัก

เครื่องเสมือนแบบดั้งเดิมรัน guest OS แยกทั้งก้อน — เคอร์เนลของตัวเอง ไดรเวอร์อุปกรณ์ของตัวเอง ทุกอย่างของตัวเอง — บน hypervisor ที่เสนอการเข้าถึง CPU หน่วยความจำ ที่เก็บ และเครือข่ายแบบ virtualized (หรือ ด้วยความช่วยเหลือฮาร์ดแวร์สมัยใหม่ ใกล้ native) นี่ให้การแยกแข็งมาก: guest VM มองหรือโต้ตอบกับโพรเซสของโฮสต์หรือ guest อื่นไม่ได้เลย เว้นแต่บั๊กความปลอดภัย hypervisor ร้ายแรง ต้นทุนคือโอเวอร์เฮดจริง — แต่ละ VM ต้องบูทเคอร์เนลเต็มของตัวเอง ใช้ footprint หน่วยความจำสำหรับเคอร์เนลนั้น และโดยทั่วไปเข้าถึงทรัพยากรฮาร์ดแวร์บางอย่างช้ากว่ารันตรงบนโฮสต์

## คอนเทนเนอร์: แชร์เคอร์เนล แยกอย่างอื่นทั้งหมด

คอนเทนเนอร์ใช้แนวทางต่าง: ทุกคอนเทนเนอร์บนโฮสต์แชร์เคอร์เนลพื้นฐาน *เดียวกัน* — ไม่มี guest OS แยกบูทข้างในแต่ละตัว — แต่เคอร์เนลให้กลไกการแยกที่ทำให้มุมมองระบบของแต่ละคอนเทนเนอร์ดูแยกอยู่ดี คุณสมบัติเคอร์เนล Linux สองอย่างทำงานจริงส่วนใหญ่ **Namespaces** แยกมุมมองของโพรเซสต่อทรัพยากรระบบเฉพาะ — PID namespace ทำให้โพรเซสของคอนเทนเนอร์เห็นเฉพาะต้นไม้โพรเซสของตัวเอง (โพรเซส 1 ข้างในคอนเทนเนอร์ไม่ใช่ PID 1 จริงบนโฮสต์); network namespace ให้คอนเทนเนอร์มีอินเทอร์เฟซเครือข่ายและตารางเส้นทางส่วนตัว; mount namespace ให้มุมมองระบบไฟล์ของตัวเอง **Cgroups** (control groups) จำกัดและบัญชีการใช้ทรัพยากร — เวลา CPU หน่วยความจำ แบนด์วิดท์ I/O — เพื่อให้คอนเทนเนอร์หนึ่งไม่ทำให้ตัวอื่นที่แชร์โฮสต์เดียวกันอด

สายเลือดย้อนไกลกว่า "คอนเทนเนอร์" ในฐานะคำฮิตสมัยใหม่ — chroot (เปลี่ยนรากระบบไฟล์ที่ปรากฏของโพรเซส มีตั้งแต่ต้นทศวรรษ 1980) ทำเวอร์ชันจำกัดของการแยกระบบไฟล์มาหลายทศวรรษก่อน; cgroups และการแยก namespace สมัยใหม่ขยายแนวคิดเดียวกันให้ครอบคลุมมุมมองระบบของโพรเซสมากขึ้นมาก

## เหตุใดการแลกเปลี่ยนนี้คุ้ม

เพราะคอนเทนเนอร์แชร์เคอร์เนลโฮสต์แทนที่จะบูทของตัวเอง พวกมันมักเริ่มในเศษเสี้ยววินาที (ไม่มีการบูทเคอร์เนลเลย) แทนหลายวินาทีที่ VM เต็มมักต้องการ และมี footprint หน่วยความจำและที่เก็บต่ออินสแตนซ์เล็กกว่ามาก — ไม่มีอิมเมจเคอร์เนลซ้ำ ไม่มีแคชระดับเคอร์เนลซ้ำ ประสิทธิภาพนั้นคือเหตุผลที่คอนเทนเนอร์กลายเป็นหน่วยแพ็กเกจและดีพลอยเริ่มต้นสำหรับโครงสร้างพื้นฐานคลาวด์สมัยใหม่: คุณรันคอนเทนเนอร์ได้มากกว่า VM มากบนฮาร์ดแวร์กายภาพเดียวกัน ซึ่งสำคัญมหาศาลที่ขนาดที่ระบบกระจาย (เฟส 7) ทำงานจริง

การแลกเปลี่ยนคือความแข็งของการแยก: เพราะคอนเทนเนอร์แชร์เคอร์เนล ช่องโหว่เคอร์เนลที่ร้ายแรงพอสามารถในหลักการถูกใช้เพื่อหลุดจากการแยกคอนเทนเนอร์ในทางที่โครงสร้างยากกว่ามากภายใต้โมเดลเคอร์เนลแยกของฮาร์ดแวร์ virtualization เต็ม ในทางปฏิบัติ ระบบโปรดักชันส่วนใหญ่ยอมรับการแลกเปลี่ยนนี้โดยตั้งใจ บางครั้งซ้อน sandboxing เพิ่มด้านบน — และการอภิปราย Kubernetes ในบทที่ 45 รับตรงจากที่นี่: เมื่อคุณมีหน่วยแยกเบาและเริ่มเร็วอย่างคอนเทนเนอร์ ปัญหาถัดไปคือการ orchestrate พวกมันหลายพันตัวอย่างเชื่อถือได้ข้ามฝูงเครื่อง
