บทที่ 52 ครอบคลุมว่า *เหตุใด* GPU จึงเดิมพัน SIMT ขนานมหาศาล บทนี้คือแผนที่รูปธรรม: Streaming Multiprocessor, warp และ occupancy — ว่าฮาร์ดแวร์ขนานนั้นถูกใช้จริงเต็มแค่ไหน

ทั้งสามคำนี้แทบไม่มีคำอธิบายภาษาไทยที่ลงลึกบนอินเทอร์เน็ต บางหน้าที่แปลด้วยเครื่องถึงกับแปล "warp" ว่า "การบิดเบี้ยว" บทนี้จึงนิยามทุกคำตั้งแต่ต้น และคำนวณตัวเลขให้ดูทีละขั้น

**เธรด** (thread; ศัพท์บัญญัติคือ *สายโยงใย* แต่ในวงการ GPU ใช้คำทับศัพท์ว่าเธรดแทบทั้งหมด บทนี้จึงใช้ *เธรด*) คือลำดับการทำงานหนึ่งสายที่มีค่าเรจิสเตอร์และตัวนับตำแหน่งคำสั่งของตัวเอง ใน CUDA โปรแกรมเมอร์เขียน **เคอร์เนล** (kernel) คือฟังก์ชันหนึ่งฟังก์ชัน แล้วสั่งให้มันรันพร้อมกันเป็นพัน ๆ ถึงล้าน ๆ เธรด เธรดถูกจัดเป็นกลุ่มเรียก **บล็อก** (thread block) และบล็อกทั้งหมดรวมกันเรียก **กริด** (grid) ทุกเธรดรู้ตำแหน่งของตัวเองผ่านตัวแปรอย่าง `threadIdx.x` (ลำดับในบล็อก) และ `blockIdx.x` (ลำดับของบล็อก)

## Streaming Multiprocessor

GPU คือ Streaming Multiprocessor (SM) จำนวนมาก — แต่ละตัวเป็นหน่วยขนานที่ค่อนข้างครบในตัว มี CUDA core ง่าย ๆ หลายเลน (เลนแบบ ALU จงใจซับซ้อนกว่าคอร์ CPU เฟส 3 น้อยมาก: ไม่มีการรันนอกลำดับ ไม่มีการทำนายสาขาซับซ้อนแบบบทที่ 14) มี warp scheduler และ register file ที่แชร์โดยเธรดที่พักอยู่ SM หลายสิบตัวรันค่อนข้างอิสระคือแหล่งความขนานรวมของ GPU เทียบกับคอร์ซับซ้อนกำมือของ CPU

คำว่า "CUDA core" ในสเปกของ NVIDIA ไม่ใช่ "คอร์" ในความหมายของ CPU มันคือ **เลน** (lane) คำนวณเลขทศนิยมหนึ่งช่อง ที่ไม่มีตัวนับตำแหน่งคำสั่งหรือหน่วยดึงคำสั่งของตัวเอง หน่วยที่ใกล้เคียงกับ "คอร์" ของ CPU มากกว่าคือ SM ทั้งตัว

เมื่อเคอร์เนลถูกเรียก บล็อกจะถูกแจกไปยัง SM ต่าง ๆ บล็อกหนึ่งอยู่บน SM เดียวตลอดชีวิต และ SM หนึ่งรับได้หลายบล็อกพร้อมกันถ้าทรัพยากรพอ (ดูหัวข้อ occupancy) เธรดในบล็อกเดียวกันแชร์ **shared memory** (หน่วยความจำร่วมบนชิปของ SM) และรอกันได้ด้วยคำสั่ง `__syncthreads()` ส่วนเธรดต่างบล็อกคุยกันโดยตรงไม่ได้

## Warp: lockstep เป็นหน่วย

เธรดบน SM ถูกจัดเป็น warp — บนฮาร์ดแวร์ NVIDIA เสมอ 32 เธรด (wavefront ของ AMD ในอดีตใช้ 64) Warp คือความละเอียดที่ SIMT ของบทที่ 52 ถูกบังคับใช้: ทั้ง 32 รันคำสั่ง *เดียวกัน* ในรอบ *เดียวกัน* แต่ละเส้นบนข้อมูลของตัวเอง นั่นคือรูปฮาร์ดแวร์ของ "หน่วยควบคุมที่แชร์หนึ่งหน่วย หลายเลน"

คำว่า warp มาจากศัพท์การทอผ้า หมายถึง *เส้นยืน* ชุดเส้นด้ายที่ขึงขนานกันบนกี่ทอแล้วเคลื่อนไปพร้อมกัน ไม่เกี่ยวกับการบิดงอ ภาพนี้ตรงกับความหมายมาก คือ 32 เธรดที่วิ่งขนานไปด้วยกันเป็นชุด

การแบ่ง warp เป็นกลไก ไม่ได้ถามโปรแกรมเมอร์ เธรด 0–31 ของบล็อกเป็น warp ที่ 0 เธรด 32–63 เป็น warp ที่ 1 และต่อไปเรื่อย ๆ ผลที่ตามมามีสองข้อ

- บล็อกขนาด 96 เธรดได้ 96 ÷ 32 = **3 warp** พอดี
- บล็อกขนาด 100 เธรดได้ **4 warp** (ปัดขึ้น) warp สุดท้ายมีเธรดจริงแค่ 4 ตัว อีก 28 เลนว่าง ใช้เลนได้จริง 100 ÷ 128 = **78%** ขนาดบล็อกจึงควรเป็นพหุคูณของ 32 เสมอ

ข้อดีอีกอย่างของ lockstep อยู่ที่หน่วยความจำ ถ้า 32 เธรดใน warp อ่าน `float` ที่เรียงติดกัน (เธรด i อ่านตัวที่ i) ทั้ง warp ต้องการแค่ 32 × 4 = 128 ไบต์ต่อเนื่อง ฮาร์ดแวร์รวมเป็นธุรกรรมหน่วยความจำก้อนเดียวได้ เรียกว่า **coalescing** ถ้าแต่ละเธรดอ่านกระจัดกระจาย ต้องแตกเป็นหลายธุรกรรม (ลำดับชั้นหน่วยความจำของ GPU ที่ธุรกรรมเหล่านี้วิ่งผ่านอยู่ในบทที่ 54)

## Branch Divergence: ที่ที่ lockstep มีราคา

เมื่อเธรด *ภายใน warp เดียว* ไปสาขาต่างกัน ฮาร์ดแวร์รันทั้งสองเส้นทางตามลำดับและ mask ครึ่งที่ไม่ได้ใช้งาน Warp ใช้เวลานานเท่าทั้งสองเส้นทาง แม้แต่ละเธรดต้องการเพียงเส้นทางเดียว — ภาษีตรงของ lockstep เดียวกันที่ทำให้กรณีไม่ divergent ถูก การให้เธรดใน warp อยู่บนเส้นทางเดียวกันจึงเป็นการ optimize จริง ไม่ใช่แค่สไตล์

**มาสก์** (active mask) คือบิต 32 บิต หนึ่งบิตต่อเลน บอกว่าเลนไหน "เปิด" อยู่ในคำสั่งนี้ เลนที่ปิดยังเดินตามคำสั่งไปด้วย แต่ไม่เขียนผล

### ตัวอย่างคำนวณ

```
if (threadIdx.x % 2 == 0)
    ทางA();   // สมมติใช้ 100 รอบ
else
    ทางB();   // สมมติใช้ 100 รอบ
```

ในทุก warp มีเธรดคู่ 16 ตัวและคี่ 16 ตัว ฮาร์ดแวร์จึงรัน ทางA ด้วยมาสก์เปิดเฉพาะเลนคู่ 100 รอบ แล้วรัน ทางB ด้วยมาสก์เปิดเฉพาะเลนคี่อีก 100 รอบ warp ใช้ **200 รอบ** ขณะที่แต่ละเธรดทำงานมีประโยชน์แค่ 100 รอบ ประสิทธิภาพเหลือ **50%**

ลองเปลี่ยนเงื่อนไขเป็น

```
if ((threadIdx.x / 32) % 2 == 0)
```

ผลรวมของงานเท่าเดิม ครึ่งหนึ่งของเธรดยังไปทางA ครึ่งหนึ่งไปทางB แต่คราวนี้เธรดทั้ง 32 ตัวใน warp เดียวกันได้ค่า `threadIdx.x / 32` เท่ากัน ทุก warp จึงไปทางเดียวทั้ง warp ใช้แค่ **100 รอบ** ไม่มี divergence เลย ความเร็วเพิ่มเป็นสองเท่า โดยที่การคำนวณเหมือนเดิมทุกประการ แค่จัดว่า *เธรดไหนทำงานไหน* ให้เข้ากับขอบเขตของ warp

## Occupancy: ซ่อน latency ด้วยงานที่พร้อม

SM มี register และ shared memory จำกัด; ทุก warp ที่พักกินส่วนหนึ่ง Occupancy คือว่ามีกี่ warp ที่พักและมีสิทธิ์รัน เทียบกับที่ฮาร์ดแวร์รองรับได้ Occupancy สูงช่วยซ่อน latency ของหน่วยความจำ (บทที่ 35 อีกครั้ง): ขณะที่ warp หนึ่งค้างรอการเข้าถึงช้า scheduler สลับไป warp ที่พร้อมและเก็บเลนให้ไม่ว่าง

การสลับ warp บน GPU ไม่มีค่าใช้จ่าย ต่างจาก context switch ของ CPU (บทที่ 24) ที่ต้องเซฟเรจิสเตอร์ลงหน่วยความจำ เพราะเรจิสเตอร์ของทุก warp ที่พักอยู่บน SM ถูกจองไว้ใน register file ตลอดเวลาแล้ว scheduler แค่เลือกว่ารอบนี้จะส่งคำสั่งของ warp ไหน นี่คือเหตุผลที่ register file ของ SM ใหญ่มาก และเป็นเหตุผลที่จำนวนเรจิสเตอร์ต่อเธรดกำหนดว่าพักได้กี่ warp

### ต้องมีกี่ warp ถึงจะซ่อนได้

แบบจำลองอย่างง่าย: scheduler ส่งได้หนึ่งคำสั่งต่อรอบ แต่ละ warp มีงานอิสระ W = 10 คำสั่ง แล้วต้องรอหน่วยความจำ L = 400 รอบ ระหว่างที่ warp หนึ่งรอ 400 รอบ ต้องมี warp อื่นป้อนคำสั่งให้ครบ 400 รอบ แต่ละตัวป้อนได้ 10 จึงต้องการอีก 40 ตัว รวมตัวที่รออยู่เป็น **ราว 41 warp** (สูตรประมาณ 1 + L/W) ถ้าเคอร์เนลมีงานอิสระต่อ warp มากขึ้น เช่น W = 40 ก็ต้องการแค่ราว 11 warp ความขนานในระดับคำสั่ง (ILP) ภายใน warp จึงแทน occupancy ได้บางส่วน

### คำนวณ occupancy

ใช้ SM สมมติ (ตัวเลขกลม ๆ เพื่อการเรียนรู้ ไม่ใช่สเปกของชิปรุ่นใด) รองรับได้สูงสุด 2,048 เธรด (= 64 warp) 32 บล็อก มีเรจิสเตอร์ 32 บิต 65,536 ตัว และ shared memory 64 KiB เคอร์เนลใช้บล็อกละ 256 เธรด (= 8 warp)

1. **ใช้ 32 เรจิสเตอร์ต่อเธรด** — บล็อกหนึ่งใช้ 256 × 32 = 8,192 ตัว พักได้ 65,536 ÷ 8,192 = 8 บล็อก = 2,048 เธรด = 64 warp ขีดจำกัดเธรดก็พอดี 2,048 → occupancy **100%**
2. **ใช้ 64 เรจิสเตอร์ต่อเธรด** — บล็อกละ 16,384 ตัว พักได้ 4 บล็อก = 32 warp → **50%**
3. **ใช้ 48 เรจิสเตอร์ต่อเธรด** — บล็อกละ 12,288 ตัว 65,536 ÷ 12,288 = 5.33 ปัดลงเป็น 5 บล็อก = 40 warp → **62.5%** (เรจิสเตอร์เหลือทิ้งไป 4,096 ตัว)
4. **32 เรจิสเตอร์ แต่ใช้ shared memory บล็อกละ 20 KiB** — 64 ÷ 20 = 3.2 ปัดลงเป็น 3 บล็อก = 24 warp → **37.5%** ครั้งนี้ shared memory กลายเป็นคอขวดแทนเรจิสเตอร์

occupancy คือค่าที่ *น้อยที่สุด* ในบรรดาขีดจำกัดทุกตัว (เธรด บล็อก เรจิสเตอร์ shared memory) ฮาร์ดแวร์จริงยังจองเรจิสเตอร์และ shared memory เป็นก้อน ๆ (allocation granularity) ซึ่งทำให้ตัวเลขจริงต่ำกว่าที่คำนวณแบบนี้ได้เล็กน้อย ตัวอย่างข้างบนละเรื่องนี้ไว้เพื่อให้เห็นหลักการ

มันไม่ใช่ "ทำให้สูงสุดแล้วจบ" เคอร์เนลที่ใช้ register หรือ shared memory ต่อเธรดมากกว่าอาจรัน warp น้อยกว่าแล้วยังจบเร็วกว่า หากทรัพยากรนั้นตัดงานซ้ำหรือทราฟฟิกหน่วยความจำ Occupancy กับทรัพยากรต่อเธรดคือ tradeoff จริง — ที่โผล่เมื่อเคอร์เนลเจอซิลิคอนจริง ไม่ใช่เมื่อให้เหตุผลในนามธรรมอย่างเดียว ในกรณีที่ 4 ถ้า shared memory 20 KiB นั้นใช้เก็บไทล์ของเมทริกซ์ที่ทำให้อ่าน DRAM น้อยลงหลายเท่า occupancy 37.5% อาจชนะ 100% ที่ต้องอ่าน DRAM ซ้ำไปมาได้สบาย ๆ
