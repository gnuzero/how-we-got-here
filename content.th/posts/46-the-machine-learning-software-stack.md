เฟส 9 และเฟส 10 ของชุดนี้ครอบคลุมด้านฮาร์ดแวร์ของการคำนวณ AI สมัยใหม่เชิงลึก — GPU, tensor core, systolic array, อินเตอร์คอนเนกต์ระดับศูนย์ข้อมูล ไม่มีฮาร์ดแวร์นั้นถูกโปรแกรมตรงโดยวิศวกร ML ส่วนใหญ่ในแต่ละวัน สแต็กซอฟต์แวร์สำคัญนั่งระหว่าง "นี่คือสถาปัตยกรรมโครงข่ายประสาท" กับ "นี่คือซิลิคอนจริงที่คูณเมทริกซ์" — และการเข้าใจสแต็กนั้นสำคัญต่อการเห็นว่าทุกอย่างอื่นในชุดนี้ถูก *ใช้* จริงในทางปฏิบัติอย่างไร

## รากฐาน: อาร์เรย์และการคำนวณเชิงตัวเลข

ที่ก้นของสแต็กซอฟต์แวร์เชิงปฏิบัติคือการคำนวณเชิงตัวเลขแบบอาร์เรย์ — NumPy ในระบบนิเวศ Python เป็นตัวอย่างที่ครอง การ abstraction หลักคืออาร์เรย์หลายมิติ (เทนเซอร์) และชุดปฏิบัติการแบบ vectorized บนมัน — การบวกทีละองค์ประกอบ การคูณเมทริกซ์ การ reshape — implement ในโค้ดที่ optimize โดยทั่วไประดับ C ใต้ส่วนติดต่อ Python การรันแบบแปลความของ Python เองที่ค่อนข้างช้าไม่ใช่คอขวดสำหรับงานเชิงตัวเลข; งานหนักเกิดในรูทีนที่ compile แล้วถูกเรียก *จาก* Python ไม่ได้รัน *โดย* ลูป interpreter ของ Python

## เฟรมเวิร์ก: PyTorch, TensorFlow และการหาอนุพันธ์อัตโนมัติ

เฟรมเวิร์ก deep learning (PyTorch และ TensorFlow เป็นสองตัวอย่างที่ครอง) สร้างบนรากฐานการคำนวณอาร์เรย์นี้ เพิ่มสองความสามารถสำคัญต่อการฝึกโครงข่ายประสาท ประการแรก **automatic differentiation**: เมื่อมีกราฟการคำนวณ (ลำดับปฏิบัติการที่แปลงข้อมูลอินพุตเป็นคำทำนาย) เฟรมเวิร์กคำนวณ gradient อัตโนมัติได้ — เอาต์พุตเปลี่ยนเทียบกับทุกพารามิเตอร์อย่างไร — โดยไม่ต้องให้มนุษย์ derive แคลคูลัสด้วยมือสำหรับทุกสถาปัตยกรรมใหม่ นั่นคือสิ่งที่ทำให้การฝึกผ่าน gradient descent ใช้ได้จริงที่สเกลและจังหวะที่วิจัย ML สมัยใหม่ดำเนิน

ประการที่สอง เฟรมเวิร์กเหล่านี้ให้ **ชั้น abstraction ของฮาร์ดแวร์**: โค้ดโมเดลเดียวกันโดยหลักการรันบน CPU, GPU ของ NVIDIA (ผ่าน CUDA เชื่อมกับการสนทนา CUDA core ของเฟส 9) หรือตัวเร่งอื่นได้ โดยเฟรมเวิร์กแปลปฏิบัติการเทนเซอร์ระดับสูงเป็นเคอร์เนลระดับต่ำที่ optimize สำหรับแต่ละเป้าหมายฮาร์ดแวร์ — abstraction คล้ายการแยก ISA/microarchitecture จากบทที่ 11 ที่ชั้นซอฟต์แวร์สูงกว่ามาก

## การคอมไพล์และการ optimize กราฟ

ยิ่งขึ้น มีชั้นคอมไพเลอร์ระหว่างปฏิบัติการระดับสูงของเฟรมเวิร์กกับการรันเฉพาะฮาร์ดแวร์ — รับกราฟการคำนวณที่เฟรมเวิร์กสร้าง และใช้การ optimize เช่น operator fusion (รวมหลายปฏิบัติการเป็นเคอร์เนลเดียวที่มีประสิทธิภาพกว่า ลดทราฟฟิกหน่วยความจำระหว่างปฏิบัติการ) ก่อนสร้างโค้ดสำหรับเป้าหมายฮาร์ดแวร์ นี่คือลูกหลานเชิงแนวคิดของการสนทนาคอมไพเลอร์ในบทที่ 28 — lexing และ parsing ไม่ใช่ขั้นที่เกี่ยวข้องที่นี่ แต่ไอเดียหลักของ intermediate representation ที่ถูก optimize และลดลงสู่เป้าหมายฮาร์ดแวร์ทีละขั้น map ตรง นำไปใช้กับกราฟการคำนวณเทนเซอร์แทนโค้ด imperative อเนกประสงค์

## การฝึกแบบกระจาย: Data-Parallel และ Model-Parallel

หน่วยความจำของ GPU เดียว (การสนทนา HBM ของเฟส 9) มักใหญ่ไม่พอที่จะถือโมเดลใหญ่สมัยใหม่ทั้งก้อน แล้วยังฝึกด้วยความเร็วสมเหตุสมผลเพียงลำพัง — การฝึกต้องกระจายข้ามหลาย GPU และมักหลายเครื่อง **Data parallelism** replicate โมเดลเต็มบนแต่ละ GPU แบ่งแบตช์ฝึกข้าม GPU เหล่านั้น และซิงค์ (ผ่าน all-reduce เชื่อมกับการสนทนาอินเตอร์คอนเนกต์ศูนย์ข้อมูลของเฟส 10) การอัปเดต gradient ข้ามทุกเรพลิกาหลังแต่ละขั้น **Model parallelism** ใช้แนวทางตรงข้าม: แบ่งโมเดลเองข้ามหลาย GPU — เลเยอร์ต่างกัน หรือแม้ส่วนของเลเยอร์เดียว บนอุปกรณ์ต่างกัน — เมื่อโมเดลใหญ่เกินกว่าจะพอดีบน GPU ใดเพียงตัวโดยไม่สนขนาดแบตช์ การฝึกขนาดใหญ่จริงมักรวมทั้งสอง และประสิทธิภาพของการประสานนั้นขึ้นตรงกับแบนด์วิดท์และทอโพโลยีอินเตอร์คอนเนกต์ที่บทที่ 37 และ 42 ครอบคลุม — throughput ของงานฝึกมักถูกจำกัดโดยความเร็วที่ GPU แลกข้อมูล gradient และ activation ไม่ใช่โดยความเร็วที่ GPU เดียวคำนวณได้แยกเดี่ยว

## ปิดลูปของเฟสนี้

บทนี้ปิดลูปของเส้น "ระบบกระจาย" ที่เฟสนี้เปิดด้วยสถาปัตยกรรมกระจายศูนย์ของ Usenet: การฝึก ML สมัยใหม่ โดยแก่นแล้ว เป็นปัญหาระบบกระจาย — ประสานหน่วยคำนวณอิสระหลายหน่วย จัดการความล้มเหลวบางส่วนอย่างสง่างาม (สะท้อน GFS และ Kubernetes จากสองบทก่อน) และเคลื่อนข้อมูลมหาศาลระหว่างพวกมันอย่างมีประสิทธิภาพ — ซ้อนทับทุกอย่างที่เฟส 9 และเฟส 10 ครอบคลุมเกี่ยวกับสิ่งที่ฮาร์ดแวร์ชิ้นใดชิ้นหนึ่งทำแยกเดี่ยว ไม่มีครึ่งใดของเรื่อง — ฮาร์ดแวร์ หรือซอฟต์แวร์กระจายที่ประสานมัน — สมบูรณ์โดยไม่มีอีกครึ่ง
