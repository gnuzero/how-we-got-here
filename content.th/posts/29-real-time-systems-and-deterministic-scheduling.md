ทุกอย่างที่กล่าวมาในเฟส 4 จนถึงตอนนี้ — batch processing, time-sharing, หน่วยความจำเสมือน, คอนเทนเนอร์ — optimize เพื่อ throughput ความยุติธรรม หรือการแชร์ทรัพยากรอย่างมีประสิทธิภาพ ไม่มีอย่างใดให้การรับประกันแข็งว่า *เมื่อไหร่* งานชิ้นหนึ่งจะเสร็จแม่นยำ ระบบเรียลไทม์สนใจการรับประกันนั้นพอดี และ "เร็ว" กลายเป็นคุณสมบัติต่างจาก "เรียลไทม์" — ความต่างที่ทำให้คนสะดุดตลอด

## เร็วไม่เหมือนกำหนดได้

ตัวจัดตาราง OS ทั่วไป (ชนิดที่อยู่ใต้ทุกอย่างในบทที่ 21–25) มักถูก optimize เพื่อการตอบสนอง *กรณีเฉลี่ย* ที่ดี และการแชร์ทรัพยากรอย่างยุติธรรมข้ามโพรเซสที่แข่งกันหลายตัว — และมักเร็วพอสมควรในกรณีทั่วไป แต่ "มักเร็ว" ไม่ใช่การรับประกันเดียวกับ "เสร็จเสมอภายในกำหนดเวลาที่ระบุ ไม่มีข้อยกเว้น" ตัวจัดตารางทั่วไปอาจปล่อยให้งานลำดับต่ำรันนานกว่าอุดมคติเป็นครั้งคราว หรือประสบความล่าช้ายาวผิดปกติจากผลแคช การจัดการ interrupt หรือ garbage collection pause (เชื่อมตรงกลับไปการอภิปรายรันไทม์ในบทที่ 28) สำหรับแอปพลิเคชันส่วนใหญ่ ความแปรปรวนเป็นครั้งคราวนั้นไม่สำคัญ สำหรับระบบเรียลไทม์ มันอาจเป็นเกมทั้งก้อน

## Hard Real-Time เทียบ Soft Real-Time

กำหนดเวลาเรียลไทม์แบบ **hard** คือกำหนดที่การพลาดถือเป็นความล้มเหลวระบบทั้งหมด — ไม่ใช่ "ประสิทธิภาพเสื่อม" ความล้มเหลวจริง ลูปเสถียรภาพของระบบควบคุมการบิน หรือตัวควบคุมการปล่อยถุงลมนิรภัย ต้องเสร็จภายในหน้าต่างเวลาที่ระบุทุกครั้ง เพราะกำหนดที่พลาดไม่ใช่ความไม่สะดวกเล็กน้อย มันอาจหายนะ

กำหนดเวลาเรียลไทม์แบบ **soft** คือกำหนดที่การพลาดทำให้คุณภาพเสื่อมแต่ไม่ถือเป็นความล้มเหลวทันที — การเล่นวิดีโอที่ทิ้งเฟรมภายใต้ภาระระบบหนักไม่น่าพอใจแต่รอดได้; ระบบไม่ต้องการการรับประกันที่ฮาร์ดแวร์บังคับ แค่แนวโน้มเชิงปฏิบัติแข็งที่จะถึงกำหนดอย่างเชื่อถือได้

## Rate-Monotonic Scheduling

หนึ่งในแนวทางคลาสสิกที่ศึกษามากต่อการจัดตาราง hard real-time คือ rate-monotonic scheduling: กำหนดลำดับความสำคัญคงที่ให้แต่ละงานแบบคาบ ตามความถี่ที่ต้องรันโดยตรง — งานที่มีคาบสั้นกว่า (ความถี่สูงกว่า) ได้ลำดับสูงกว่า นี่พิสูจน์ได้ว่าเหมาะสมที่สุดในบรรดาอัลกอริทึมจัดตารางลำดับคงที่สำหรับคลาสชุดงานคาบที่กำหนดชัดเจนเฉพาะ: หาก *การกำหนดลำดับคงที่ใด ๆ* สามารถถึงกำหนดของทุกงานสำหรับภาระงานที่กำหนด การกำหนดแบบ rate-monotonic ก็จะได้เช่นกัน นั่นคือการรับประกันทางคณิตศาสตร์แข็ง — ไม่ใช่แค่ "มักทำงานดี" แต่ขอบเขตที่พิสูจน์ได้บน schedulability ซึ่งพอดีคือชนิดของคุณสมบัติทางการที่ระบบ hard real-time ต้องรับรองเทียบกับ

## เหตุใดสิ่งนี้ต้องการ OS คนละชนิด

การถึงการรับประกันเหล่านี้ต้องการ OS ที่ออกแบบรอบจังหวะ worst-case ที่มีขอบเขตและคาดเดาได้ — Real-Time Operating System (RTOS) — แทนการออกแบบที่ optimize เพื่อ throughput และความยุติธรรมของสายเลือดทั่วไปในบทที่ 21–25 ความล่าช้าของการจัดการ interrupt ต้องมีขอบเขตและรู้ล่วงหน้า การจัดสรรหน่วยความจำโดยทั่วไปพึ่งกลไก latency ที่คาดเดาไม่ได้เช่น garbage collector ทั่วไปไม่ได้ แม้สิ่งพื้นฐานอย่าง mutex lock ต้องออกแบบระวัง (โปรโตคอล priority inheritance โดยเฉพาะ) เพื่อหลีกเลี่ยงให้งานลำดับต่ำบล็อกงานลำดับสูงโดยไม่ตั้งใจเป็นเวลาไม่มีขอบเขต — กับดักเรียลไทม์คลาสสิกที่เรียกว่า priority inversion

แล็บ mini-CPU ที่แนบกับบทนี้คุ้มที่จะกลับไปผ่านเลนส์นี้: ก้าวผ่านโปรแกรมเล็ก ๆ และสังเกตว่าบนฮาร์ดแวร์จริงที่เรียบง่าย จังหวะของทุกคำสั่งกำหนดได้และนับได้ — ความคาดเดาได้นั้นพอดีคือสิ่งที่การออกแบบ RTOS จริงกำลังต่อสู้เพื่อรักษาเมื่อระบบซับซ้อนขึ้น บทถัดไปนำหลักการเหล่านี้ออกจากนามธรรมเข้าสู่การดีพลอยคอนกรีต: อากาศยาน การควบคุมอุตสาหกรรม และระบบฝังตัวที่การรับประกันเหล่านี้รับน้ำหนัก ไม่ใช่แค่เชิงวิชาการ
