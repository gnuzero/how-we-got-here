บทที่ 27 กล่าวถึง *เหตุใด* ภาษาระดับสูงจึงมีอยู่ บทนี้กล่าวถึงเครื่องจักรที่ทำให้พวกมันใช้ปฏิบัติได้เลย: คอมไพเลอร์ ซึ่งแปลซอร์สโค้ดเป็นสิ่งที่ CPU จริง (สร้างจากทุกอย่างในเฟส 3) สามารถรันได้จริง

## ไปป์ไลน์คอมไพเลอร์คลาสสิก

คอมไพเลอร์มักทำงานเป็นขั้น **Lexer** แตกข้อความซอร์สดิบเป็นโทเคน — ตัวระบุ คำหลัก ตัวดำเนินการ ค่าคงที่ — ตัดช่องว่างและคอมเมนต์ออก **Parser** รับสตรีมโทเคนนั้นและสร้าง Abstract Syntax Tree (AST) การแทนโครงสร้างของไวยากรณ์โปรแกรม — นิพจน์ใดซ้อนในคำสั่งใด ลำดับความสำคัญของตัวดำเนินการจัดกลุ่มสิ่งต่าง ๆ อย่างไร การวิเคราะห์ความหมายเดินต้นไม้นั้นตรวจสิ่งที่ parser อย่างเดียวจับไม่ได้: ความถูกต้องของชนิด ว่าตัวแปรถูกประกาศก่อนใช้จริงหรือไม่

จากนั้น คอมไพเลอร์จริงส่วนใหญ่ลด AST เป็น Intermediate Representation (IR) — รูปแบบระดับต่ำกว่า สม่ำเสมอกว่า ที่วิเคราะห์และ optimize ง่ายกว่าต้นไม้ไวยากรณ์ระดับซอร์สเดิม แต่ยังอิสระจากชุดคำสั่งของ CPU เป้าหมายใด ๆ **Optimizer** ทำงานบน IR นี้: กำจัดโค้ดตายที่ไม่เคยรันได้ ยกการคำนวณที่ไม่ขึ้นกับลูปออกจากลูปเพื่อไม่ต้องคำนวณซ้ำทุก iteration โดยไม่จำเป็น inline การเรียกฟังก์ชันเล็กเพื่อหลีกเลี่ยงโอเวอร์เฮดการเรียก และการแปลงอื่นอีกหลายสิบอย่าง — ทั้งหมดพิสูจน์ได้ว่าคงพฤติกรรมเดิมของโปรแกรมไว้ขณะลดงานเปล่า สุดท้าย **code generation** แปล IR ที่ optimize แล้วเป็นคำสั่งเครื่องจริงสำหรับ ISA เป้าหมาย จัดการการจัดสรรรีจิสเตอร์ (ตัดสินใจว่าค่าใดอยู่ในชุดรีจิสเตอร์กายภาพที่จำกัด เทียบกับต้อง spill ไปหน่วยความจำ) ไปพร้อมกัน

## Ahead-of-Time เทียบ Just-in-Time

ไปป์ไลน์ทั้งก้อนนี้ รันครั้งเดียวก่อนโปรแกรมรันเลย คือ Ahead-of-Time (AOT) compilation — คอมไพเลอร์ C และ FORTRAN แบบดั้งเดิมทำงานแบบนี้ Just-in-Time (JIT) compilation ที่ภาษาอย่าง Java และ JavaScript ใช้ ใช้แนวทางต่าง: เริ่มรันโค้ดผ่าน interpreter ที่ง่ายกว่า หรือคอมไพเลอร์เบสไลน์เร็วแต่ไม่ optimize แล้ว *ตอนรันไทม์* ระบุเส้นทางโค้ด "ร้อน" — ฟังก์ชันหรือลูปที่ถูกรันบ่อยจริง — และคอมไพล์ใหม่เฉพาะเส้นทางเหล่านั้นด้วยการ optimize หนักและก้าวร้าวกว่า

เหตุผลเบื้องหลัง JIT ฉลาด: คอมไพเลอร์ที่ทำสิ่งนี้ตอนรันไทม์มีข้อมูลที่คอมไพเลอร์ AOT ไม่เคยมี — พฤติกรรม branch ที่สังเกตจริง ชนิดอาร์กิวเมนต์ที่สังเกตจริง เส้นทางร้อนที่สังเกตจริง — ซึ่งสามารถเปิด optimization ที่คอมไพเลอร์ AOT ทำอย่างปลอดภัยไม่ได้โดยไม่มีข้อมูลรันไทม์นั้น ต้นทุนจริง: การคอมไพล์ JIT เองกินรอบ CPU ระหว่างการรันโปรแกรม และวินาทีแรก ๆ ของโปรแกรมมักช้ากว่าสถานะคงที่ ก่อนที่ JIT จะระบุและ optimize เส้นทางร้อน — การแลกเปลี่ยน "JIT warm-up" คลาสสิก

## รันไทม์ภาษา: มากกว่าแค่การคอมไพล์

ภาษาจัดการสมัยใหม่ (Java, C# และในระดับต่าง ๆ JavaScript, Python) จับคู่คอมไพเลอร์กับระบบรันไทม์กว้างกว่า — ที่สำคัญที่สุด การจัดการหน่วยความจำอัตโนมัติผ่าน garbage collection ซึ่งปลดโปรแกรมเมอร์จากการติดตามอายุการจัดสรรทุกชิ้นด้วยมือ (แหล่งบั๊กหลักในภาษาอย่าง C) นี่ย้ายความซับซ้อนจริงเข้าไปในรันไทม์เอง แลกความพยายามจัดการหน่วยความจำด้วยมือกับโอเวอร์เฮดรันไทม์ และอย่างน้อยในประวัติศาสตร์ พฤติกรรม pause ที่คาดเดายากกว่า — การแลกเปลี่ยนที่สำคัญมหาศาลต่อระบบเรียลไทม์ ซึ่งพอดีคือเหตุผลที่บทที่ 29 และ 30 ถือว่า "เรียลไทม์" กับ "รันไทม์จัดการแบบ garbage-collected" มักตึงเครียดกัน
