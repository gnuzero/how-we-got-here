บทที่ 27 ครอบคลุม *เหตุใด* ภาษาระดับสูงจึงมีอยู่ บทนี้คือเครื่องจักรที่ทำให้ใช้ได้: คอมไพเลอร์ ที่แปลซอร์สเป็นสิ่งที่ CPU จริง (เฟส 3) รันได้

คำศัพท์ก่อนเริ่ม (ศัพท์บัญญัติราชบัณฑิตยสภา สาขาคอมพิวเตอร์และเทคโนโลยีสารสนเทศ เว้นแต่ระบุ): **ตัวแปลโปรแกรม** (compiler — ทับศัพท์ว่าคอมไพเลอร์ก็ได้); **ตัวแปลคำสั่ง** (interpreter — โปรแกรมที่อ่านแล้วทำตามทีละคำสั่งโดยไม่สร้างรหัสเครื่องเก็บไว้); **รหัสต้นฉบับ** (source code); **รหัสจุดหมาย** (object code); **รหัสเครื่อง** (machine code); **แอสเซมเบลอร์** (assembler); **การวิเคราะห์ศัพท์** (lexical analysis — งานของ lexer); **ตัวแจงส่วน** (parser); **ทำให้เหมาะที่สุด** (optimize — งานของ optimizer); **เรจิสเตอร์** (register); **จำนวนเต็ม** (integer); **การล้น** (overflow); **ตัวชี้** (pointer); **ฮีป** (heap — พื้นที่หน่วยความจำที่จัดสรรตอนรัน); **กองซ้อน** (stack); **การเก็บขยะ** (garbage collection); **การอัดแน่น** (compaction — การย้ายออบเจ็กต์ที่ยังใช้อยู่มาชิดกัน); และ **วง** (cycle) คำว่า **การจัดสรร** (allocation) พบในสาขาเศรษฐศาสตร์ นิติศาสตร์ และศึกษาศาสตร์ ส่วน **อนิยาม** (undefined) พบในสาขาวิทยาศาสตร์ ผู้เขียนยืมมาใช้ คำต่อไปนี้ยังไม่พบศัพท์บัญญัติ จึงใช้คำอธิบายหรือทับศัพท์: just-in-time (JIT, คอมไพล์ตอนรัน), bytecode (ไบต์โค้ด — ชุดคำสั่งของเครื่องเสมือน), intermediate representation (รูปแทนกลาง), runtime (รันไทม์ — ระบบที่ทำงานร่วมกับโปรแกรมขณะรัน), reference count (ตัวนับการอ้างอิง), inlining, dead code (โค้ดตาย), reachable (เข้าถึงได้) และ tracing (การไล่ตามตัวชี้)

## ไปป์ไลน์คลาสสิก (สั้น)

Lexer → โทเคน Parser → Abstract Syntax Tree การวิเคราะห์เชิงความหมายจับสิ่งที่ไวยากรณ์อย่างเดียวจับไม่ได้ (ชนิด ชื่อที่ยังไม่ประกาศ) คอมไพเลอร์จริงส่วนใหญ่แล้วลดลงเป็น Intermediate Representation (IR) — สม่ำเสมอกว่าไวยากรณ์ซอร์ส ยังอิสระจาก ISA เป้าหมายใด — ที่ซึ่ง **optimizer** ทำงาน: กำจัดโค้ดตาย ยกสิ่งที่ไม่แปรในลูป inlining และการแปลงอื่นอีกหลายสิบที่รักษาพฤติกรรมขณะตัดงานเปล่า **Code generation** ปล่อยคำสั่งเป้าหมายและจัดสรรรีจิสเตอร์ (ค่าใดอยู่รีจิสเตอร์กายภาพที่หายาก เทียบกับการ spill ไปหน่วยความจำ)

นั่นคือกระดูกสันหลัง สารานุกรมของทุก pass ไม่ใช่จุด — ข้อจำกัดคือ: abstraction ของซอร์สรันไม่ได้; ต้องมีอะไรลดพวกมัน และสิ่งนั้นรันได้ *ก่อน* การดำเนินการ หรือ *ระหว่าง* มัน

## ตัวแปลโปรแกรมทำอะไรกับโค้ดจริง: สามกรณีขอบ

"รักษาพฤติกรรม" ในย่อหน้าข้างบนฟังง่าย แต่พฤติกรรมของอะไร? ของ *ภาษา* ไม่ใช่ของความคาดหวังผู้เขียน ผู้เขียนคอมไพล์ฟังก์ชันสี่บรรทัดด้วย gcc 14.2.0 (Debian) บนเครื่อง x86-64 ด้วย `-O2 -S -masm=intel` (ไม่ได้ทำในแล็บ ดูเหตุผลที่หัวข้อ "ดูสด") แล้วอ่าน assembly ที่ได้:

```c
int div2(int x){ return x/2; }
unsigned udiv2(unsigned x){ return x/2; }
int gt(int x){ return x+1 > x; }
long sum(int n){ long s=0; for(int i=0;i<n;i++) s+=i; return s; }
```

**กรณี 1 — หารด้วยสองไม่ใช่แค่เลื่อนบิต:** `udiv2` กลายเป็นสองคำสั่ง `mov eax,edi / shr eax` (คัดลอกแล้วเลื่อนขวาหนึ่งบิต) แต่ `div2` กลายเป็นสี่คำสั่ง `mov eax,edi / shr eax,31 / add eax,edi / sar eax` เหตุผลอยู่ที่ค่าลบ: ภาษา C ปัดผลหารจำนวนเต็มเข้าหาศูนย์ −3/2 จึงต้องได้ −1 แต่การเลื่อนขวาแบบคงเครื่องหมาย (`sar`) ปัดลงเสมอ −3 >> 1 ได้ −2 ตัวแปลโปรแกรมจึงบวกบิตเครื่องหมาย (1 เมื่อลบ 0 เมื่อไม่ลบ) เข้าไปก่อนเลื่อน: (−3 + 1) >> 1 = −1 ผู้เขียนรันจริงได้ `div2(-3)=-1` และ `-3>>1 = -2` สำหรับ x = 0 และค่าบวก บิตที่บวกเป็น 0 คำตอบจึงตรงกับการเลื่อนธรรมดา

**กรณี 2 — การล้นของจำนวนเต็มแบบมีเครื่องหมายเป็นอนิยาม:** `gt` ถูกแปลเป็น `mov eax,1` คือ "คืนค่าจริงเสมอ" โดยไม่บวกหรือเปรียบเทียบเลย และเกิดขึ้นแม้ที่ `-O0` ผลคือ `gt(INT_MAX)` = 1 ทั้งที่ถ้าเครื่องบวกจริง INT_MAX + 1 จะวนกลับเป็นค่าลบที่สุด และคำตอบควรเป็น 0 มาตรฐาน C ถือว่าการล้นของ `int` ไม่เกิดขึ้นในโปรแกรมที่ถูกต้อง ตัวแปลโปรแกรมจึงเลือกคำตอบที่ถูกสำหรับทุก x ที่ไม่ล้น เมื่อสั่ง `-fwrapv` (บอกว่าให้วนกลับแบบเลขฐานสองจริง) ผู้เขียนได้ `gt(INT_MAX)=0` และ `gt(0)=1` ข้อสังเกตเพิ่ม: เมื่อคอมไพล์ด้วย `-fsanitize=undefined` ก็ยังได้ 1 และไม่มีคำเตือน เพราะการบวกถูกพับทิ้งไปก่อนจะมีโค้ดให้ตรวจ

**กรณี 3 — ลูปที่รอบเป็นศูนย์หรือติดลบ:** `sum` ขึ้นต้นด้วย `test edi,edi / jle` คือถ้า n ≤ 0 ข้ามลูปทั้งหมดแล้วคืน 0 จากนั้นลูปถูกคลี่ (unroll) ทำสองรอบต่อการกระโดดหนึ่งครั้ง พร้อมจัดการกรณี n เป็นเลขคี่แยก รันจริงได้ `sum(0)=0`, `sum(-5)=0`, `sum(5)=10` และ `sum(100000)=4999950000` ตรงกับสูตร n(n−1)/2 = 100000 × 99999 / 2 ค่านี้เกิน 2³¹ − 1 = 2,147,483,647 จึงต้องใช้ `long` เก็บผล ถ้าประกาศ `s` เป็น `int` ผลจะล้น

บทเรียนจากสามกรณี: optimizer แปลงโค้ดได้เฉพาะเมื่อพิสูจน์ได้ว่าผลเท่าเดิม *ตามกติกาของภาษา* ซึ่งรวมกรณีขอบที่มนุษย์มักลืม (ค่าลบ ศูนย์ ค่าสูงสุด)

## Ahead-of-Time เทียบ Just-in-Time

รันไปป์ไลน์ทั้งก้อนครั้งเดียวก่อนโปรแกรมรันเลย: Ahead-of-Time (AOT) — C และ FORTRAN แบบดั้งเดิม Just-in-Time (JIT) — Java, JavaScript และเครือญาติ — เริ่มด้วย interpreter หรือคอมไพเลอร์ baseline เร็ว แล้ว *ตอนรันไทม์* หา hot path และคอมไพล์ใหม่ด้วยการ optimize หนักกว่า

ข้อได้เปรียบของ JIT คือข้อมูลที่คอมไพเลอร์ AOT ไม่มี: branch ที่สังเกต ชนิดของอาร์กิวเมนต์ ลูปร้อนจริง — การ optimize ที่ไม่ปลอดภัยที่จะสมมติโดยไม่มีข้อมูลนั้น ต้นทุนจริง: การคอมไพล์เผารอบระหว่างการรัน และวินาทีแรกมักช้ากว่าสถานะคงที่ — warm-up แบบคลาสสิก

## JIT คุ้มเมื่อไร: จุดคุ้มทุนจากหลักการแรก

สมมุติโค้ดส่วนหนึ่งถูกเรียก N ครั้ง ถ้าตีความ (interpret) ใช้เวลา c₁ ต่อครั้ง ถ้าคอมไพล์ต้องจ่ายค่าคอมไพล์ C หนึ่งครั้ง แล้วเหลือ c₂ ต่อครั้ง การคอมไพล์คุ้มเมื่อ C + N·c₂ < N·c₁ หรือ

N > N\* = C / (c₁ − c₂)

กรณีขอบอ่านจากสูตรได้ทันที: ถ้า N = 0 (โค้ดไม่เคยถูกเรียก) การคอมไพล์เสียเปล่าทั้งหมด ถ้า c₁ ≤ c₂ (โค้ดคอมไพล์แล้วไม่เร็วขึ้น) N\* เป็นอนันต์ ไม่มีวันคุ้ม และถ้า C = 0 คุ้มตั้งแต่ครั้งแรก นี่คือเหตุผลที่ JIT *นับ* ก่อนตัดสินใจ: มันไม่รู้ N ล่วงหน้า จึงคอมไพล์เฉพาะโค้ดที่ถูกเรียกบ่อยพอแล้ว (hot path) และพนันว่าจะถูกเรียกต่อ

**วัดจริงบน V8:** ผู้เขียนรันฟังก์ชัน `add(a,b){ return a+b; }` ใน Node.js v20.19.2 (เอนจิน V8) เรียกเป็นชุดละ 200,000 ครั้ง แปดชุด ด้วยแฟล็ก `--trace-opt --trace-deopt` เวลาต่อชุด (มิลลิวินาที วัดครั้งเดียวบนเครื่องของผู้เขียน ตัวเลขจะต่างไปตามเครื่อง) คือ 2.75, 2.15, 1.18, 2.19, 0.72, 0.05, 0.05, 0.05 — ช่วง warm-up ที่ย่อหน้าก่อนพูดถึง ชุดสุดท้ายเร็วกว่าชุดแรกราว 55 เท่า บันทึกของ V8 แสดงว่า `add` ถูกทำเครื่องหมายให้ TurboFan (ตัวแปลโปรแกรมชั้นบนสุดของ V8) ด้วยเหตุผล "small function" และการคอมไพล์ใช้เวลารวมราว 1.8 มิลลิวินาที (0.057 + 1.717 + 0.024) บนเธรดเบื้องหลังพร้อมกับที่โปรแกรมหลักยังรันต่อ ลูปเองก็ถูกคอมไพล์ขณะกำลังวน (on-stack replacement, OSR)

แทนค่าเป็นตัวอย่าง (ค่าประมาณเชิงอนุมาน ไม่ใช่การวัดแยกชั้น): เวลาต่อรอบของชุดแรก 2.75 ms / 200,000 ≈ 13.75 ns ของชุดท้าย ≈ 0.25 ns ได้ N\* ≈ 1.8 × 10⁶ ns / (13.75 − 0.25) ns ≈ 133,000 รอบ — น้อยกว่าจำนวนรอบในชุดแรกชุดเดียว และเนื่องจากงานคอมไพล์ทำบนเธรดอื่น ต้นทุนที่เธรดหลักต้องจ่ายจริงจึงต่ำกว่านี้อีก ส่วน 0.25 ns ต่อรอบสั้นกว่าหนึ่งรอบสัญญาณนาฬิกาของ CPU ทั่วไป จึงน่าจะสะท้อนว่า TurboFan inline `add` เข้าไปในลูปแล้ว ไม่ใช่เวลาเรียกฟังก์ชันจริง

## ชั้นของ JIT และการถอยกลับ (deoptimization)

เอกสารของทีม V8 เล่าว่าจนถึงปี 2021 V8 มีสองชั้น: Ignition (ตัวแปลคำสั่งที่รันไบต์โค้ด) กับ TurboFan (ตัวแปลโปรแกรมที่ทำให้เหมาะที่สุด) จากนั้นเพิ่ม Sparkplug (คอมไพล์เร็วแบบไม่ optimize) และ Maglev (ชั้นกลาง เปิดใน Chrome M117) โค้ด JavaScript ทุกบรรทัดเริ่มจากไบต์โค้ดของ Ignition และระหว่างรัน V8 จดว่าออบเจ็กต์มีรูปร่าง (shape) และชนิดอะไร (feedback) ชั้นบนใช้ข้อมูลนั้นสร้างรหัสเครื่องที่ *สมมุติ* ว่าชนิดจะเหมือนเดิม และใส่การตรวจไว้ ถ้าการตรวจล้มเหลวก็ทิ้งรหัสนั้นแล้วถอยกลับไปชั้นล่าง

ผู้เขียนทดลองทำให้สมมุติฐานพัง:

- หลัง warm-up ด้วยจำนวนเต็ม เรียก `add('a','b')` ครั้งเดียว V8 รายงาน `deopt-eager` ด้วยเหตุผล `not a Smi` (Smi คือจำนวนเต็มเล็กที่ V8 เก็บไว้ในตัวชี้โดยตรง) จากนั้น `add` ถูก optimize ใหม่ ชุดถัดไปใช้ 1.43 ms แทน 0.05 ms
- **กรณีขอบที่ขอบของ Smi:** หลัง warm-up อีกครั้ง `add(2**30-1, 1)` และ `add(2**31-2, 1)` ไม่ทำให้ถอยกลับ แต่ `add(2**31-1, 1)` (ผลลัพธ์ 2³¹ เกินจำนวนเต็ม 32 บิตแบบมีเครื่องหมาย) และ `add(-(2**31), -1)` ทำให้ถอยกลับด้วยเหตุผล `overflow` ในบิลด์ Node นี้ `v8_enable_pointer_compression` = 0 ขอบของ Smi จึงอยู่ที่ 32 บิต ส่วนบทความ Maglev ของทีม V8 เขียนว่า V8 พยายามเก็บตัวเลขเป็นจำนวนเต็มติดป้าย 31 บิต (32 บิตเพราะการบีบตัวชี้) ผู้เขียนจึงอนุมานว่าใน Chrome ขอบจะอยู่ที่ 2³⁰ แทน 2³¹ (ไม่ได้ทดสอบ) — ขอบของการ optimize ขึ้นกับการสร้างเอนจิน ไม่ใช่ตัวภาษา

เทียบกับกรณี 2 ของ gcc: ตัวแปลโปรแกรม AOT ของ C *สมมุติ* ว่าการล้นไม่เกิดแล้วไม่ตรวจ ส่วน JIT ของ JavaScript สมมุติเหมือนกันแต่ *ตรวจ* และถอยกลับเมื่อผิด เพราะภาษา JavaScript กำหนดให้ผลต้องถูกเสมอ (ผลบวกที่เกินจะกลายเป็นเลขทศนิยมลอยตัว)

## รันไทม์: มากกว่าการคอมไพล์

ภาษาที่จัดการ (Java, C# และ JavaScript กับ Python ในระดับต่างกัน) จับคู่คอมไพเลอร์กับรันไทม์กว้างกว่า — ที่สำคัญที่สุดคือการจัดการหน่วยความจำอัตโนมัติผ่าน garbage collection ปลดโปรแกรมเมอร์จากการติดตามอายุของทุกการจัดสรร (แหล่งบั๊กใหญ่ใน C) ความซับซ้อนย้ายเข้าไปในรันไทม์: ความพยายามด้วยมือแลกกับโอเวอร์เฮด และในประวัติ pause ที่คาดเดายากกว่า ความตึงเครียดนั้นพอดีคือเหตุผลที่บทที่ 29–30 ถือ "เรียลไทม์" กับ "รันไทม์ที่จัดการพร้อม GC" เป็นสิ่งที่มักขัดกัน

## การเก็บขยะจากหลักการแรก

ออบเจ็กต์หนึ่งเป็น "ขยะ" เมื่อโปรแกรมไม่มีทางไปถึงมันอีก: ไม่มีตัวแปร ไม่มีเรจิสเตอร์ และไม่มีตัวชี้จากออบเจ็กต์อื่นที่ยังใช้อยู่ชี้มา มีสองวิธีหลักในการรู้เรื่องนี้

**วิธีที่ 1 — นับการอ้างอิง:** ทุกออบเจ็กต์เก็บจำนวนตัวชี้ที่ชี้มาหามัน เมื่อนับลงถึงศูนย์ก็คืนหน่วยความจำได้ทันที CPython ใช้วิธีนี้เป็นหลัก ผู้เขียนทดลองใน CPython 3.13.5:

- ออบเจ็กต์ A ที่ไม่มีวง: `sys.getrefcount(A)` ได้ 2 (ตัวแปร A หนึ่ง และอาร์กิวเมนต์ที่ส่งเข้า `getrefcount` ชั่วคราวอีกหนึ่ง ตรงกับที่เอกสาร Python ระบุว่าค่านี้ "มักสูงกว่าที่คาดหนึ่ง") เมื่อ `del A` ออบเจ็กต์ถูกคืนทันที
- **กรณีขอบ — วง:** B ชี้ไป C และ C ชี้กลับมา B เมื่อ `del B, C` ตัวนับของทั้งคู่ยังเหลือ 1 (จากกันและกัน) จึงไม่ถูกคืน ต้องรอ `gc.collect()` ซึ่งคืนค่า 11 แล้วทั้งคู่จึงหายไป (เอกสารระบุว่าค่านี้คือจำนวนออบเจ็กต์ที่เก็บได้บวกที่เก็บไม่ได้ จึงนับออบเจ็กต์ภายในอื่นที่ติดมากับสคริปต์ทดลองด้วย ไม่ใช่แค่ B กับ C)
- ถ้าปิดตัวเก็บวงด้วย `gc.disable()` ออบเจ็กต์ D ที่ชี้หาตัวเองจะค้างอยู่ตลอด จนกว่าจะ `gc.enable()` แล้ว `gc.collect()` — วงที่ไม่มีใครเก็บคือหน่วยความจำรั่ว
- **กรณีขอบ — ตัวนับที่ไม่ขยับ:** `sys.getrefcount(None)` และ `sys.getrefcount(1)` ได้ 4294967295 = 0xFFFFFFFF เท่ากันทั้งคู่ นี่คือ "ออบเจ็กต์อมตะ" (immortal objects) ที่ PEP 683 เพิ่มใน Python 3.12: ตัวนับของออบเจ็กต์ที่ใช้ร่วมกันมาก ๆ ถูกตรึงไว้ที่ค่าพิเศษ การเพิ่มหรือลดไม่มีผล จึงไม่มีวันถึงศูนย์

PEP 683 ยังพิจารณาเรื่อง "อมตะโดยบังเอิญ" (accidental immortality): ออบเจ็กต์ธรรมดาที่ถูกเพิ่มตัวนับซ้ำ ๆ โดยไม่มีการลด จนตัวนับไปถึงค่าพิเศษที่ใช้ระบุความเป็นอมตะเอง (ไม่ใช่เรื่องตัวนับล้น) บนเครื่อง 64 บิต PEP คำนวณว่าถ้าบิตอมตะอยู่ที่ 2⁶⁰ ต้องใช้ 2⁶⁰ รอบ ซึ่งที่ 5 GHz "ยังต้องใช้เกือบ 250,000,000 วินาที (กว่า 2,500 วัน)" ผู้เขียนคำนวณตาม 2⁶⁰ / (5 × 10⁹) ≈ 2.3 × 10⁸ วินาที ≈ 2,669 วัน ตรงกัน สำหรับเครื่อง 32 บิต PEP สมมุติให้ค่าพิเศษเป็น 2³⁰ และเขียนว่า "ใช้สเปกเดียวกันข้างบน จะใช้เวลาราว 4 วินาที" แต่ถ้าใช้สมมุติฐานเดียวกัน (เพิ่มหนึ่งครั้งต่อรอบที่ 5 GHz) ผู้เขียนคำนวณได้ 2³⁰ / (5 × 10⁹) ≈ 0.21 วินาที ผู้เขียนไม่ทราบที่มาของตัวเลข 4 วินาที ทั้งสองค่าชี้ไปทางเดียวกันคือเร็วมาก และ PEP เองก็สรุปว่าบน 32 บิต แม้เพิ่มค่าช้ากว่านี้มากก็ใช้เวลาไม่นาน แต่ยังถือว่า "แทบเป็นไปไม่ได้" ในสภาพปกติ เพราะต้องเข้าเงื่อนไขพร้อมกันหลายข้อ (ออบเจ็กต์ไม่ใช่อมตะ ส่วนขยายภาษา C เพิ่มตัวนับโดยไม่ลดคืน และไม่มีโค้ดอื่นลดตัวนับของออบเจ็กต์นั้น) ข้อเสนอจึงไม่ถือว่าอมตะโดยบังเอิญเป็นปัญหา

**วิธีที่ 2 — ไล่ตามตัวชี้:** เริ่มจาก "ราก" (ตัวแปร เรจิสเตอร์ กองซ้อน) แล้วตามตัวชี้ทุกเส้น อะไรที่ไปไม่ถึงคือขยะ วงไม่ใช่ปัญหา เพราะวงที่ไม่มีทางมาจากรากก็ไปไม่ถึงเช่นกัน John McCarthy บรรยายวิธีนี้ไว้ในบทความ LISP ปี 1960: ไม่ทำอะไรจนกว่าพื้นที่ว่างจะหมด แล้วทำเครื่องหมายทุกเซลล์ที่เข้าถึงได้จากเรจิสเตอร์ฐาน (โดยเปลี่ยนเครื่องหมายของเซลล์ให้เป็นลบ) ไล่ตามสาย car–cdr จากนั้นกวาดทุกเซลล์ที่ไม่มีเครื่องหมายกลับไปรายการพื้นที่ว่าง McCarthy เขียนว่าขั้นนี้ "ใช้เวลาหลายวินาที" จึงต้องคืนได้อย่างน้อยหลายพันเซลล์ต่อครั้ง ไม่เช่นนั้นโปรแกรมจะเสียเวลาส่วนใหญ่ไปกับการเก็บขยะ นี่คือต้นแบบของ **mark-sweep**

## เก็บขยะแพงแค่ไหน: แบบจำลองงาน

ให้ฮีปมี H ออบเจ็กต์ ยังใช้อยู่ L ตัว (แบบจำลองอย่างง่าย ไม่นับจำนวนตัวชี้):

- **mark-sweep:** ขั้นทำเครื่องหมายแตะเฉพาะ L ตัวที่ยังอยู่ ขั้นกวาดต้องเดินทั้งฮีป H งาน ≈ L + H
- **copying:** ย้ายเฉพาะ L ตัวที่ยังอยู่ไปอีกครึ่งหนึ่งของหน่วยความจำ ขยะไม่ถูกแตะเลย งาน ≈ L แต่ต้องกันพื้นที่ไว้ 2H และได้การอัดแน่นมาฟรี

| H | L | mark + sweep | copying | ได้คืน | งาน copying ต่อหนึ่งออบเจ็กต์ที่ได้คืน |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 + 0 | 0 | 0 | — (ฮีปว่าง ไม่มีอะไรทำ) |
| 1000 | 0 | 0 + 1000 | 0 | 1000 | 0 |
| 1000 | 100 | 100 + 1000 | 100 | 900 | 0.11 |
| 1000 | 900 | 900 + 1000 | 900 | 100 | 9 |
| 1000 | 1000 | 1000 + 1000 | 1000 | 0 | อนันต์ (ทำงานเต็มแต่ไม่ได้อะไรคืน) |

(ตัวเลขสมมุติเพื่ออธิบาย คำนวณด้วยสคริปต์ของผู้เขียน) แถวสุดท้ายคือกรณีขอบที่เจ็บที่สุด: เมื่อทุกอย่างยังใช้อยู่ การเก็บขยะคือเวลาที่เสียไปล้วน ๆ — ตรงกับคำเตือนของ McCarthy และแถวที่สามบอกว่า copying ถูกมากเมื่อออบเจ็กต์ส่วนใหญ่ตายไปแล้ว

## สมมุติฐานเชิงรุ่น (generational hypothesis)

ข้อสังเกตเชิงประจักษ์ที่ว่า "ออบเจ็กต์ส่วนใหญ่ตายตั้งแต่ยังเด็ก" ทำให้แถวที่สามเป็นกรณีปกติ บทความ "Trash talk" ของทีม V8 (2019) อธิบายว่าตัวเก็บขยะ Orinoco แบ่งฮีปเป็นรุ่น: รุ่นเยาว์เป็นแบบ semi-space ที่ครึ่งหนึ่งว่างเสมอ ออบเจ็กต์ที่รอดถูกคัดลอกจาก From-Space ไป To-Space (บทความยอมรับว่า "ในกรณีเลวที่สุดทุกออบเจ็กต์อาจรอด") ส่วนรุ่นเก่าใช้ mark, sweep และ compact ตัวคัดลอกรุ่นเยาว์แบบขนานลดเวลาบนเธรดหลักลง 20–50% และ Orinoco เปลี่ยนตัวเก็บขยะแบบ "หยุดทั้งโลก" ที่ทำงานเป็นลำดับเดียว (sequential) ไปเป็นแบบที่ขนานและทำพร้อมกับโปรแกรมเกือบทั้งหมด โดยมีแบบทำทีละขั้น (incremental) เป็นทางสำรอง — ซึ่งคือการลด pause ที่หัวข้อก่อนพูดถึง

CPython ก็ใช้รุ่นกับตัวเก็บวง: เอกสาร `gc` ของ Python 3.13 ระบุสามรุ่น และตัวเก็บเริ่มทำงานเมื่อจำนวนการจัดสรรลบการคืนเกิน threshold0 บนเครื่องของผู้เขียน `gc.get_threshold()` ได้ (2000, 10, 10) กรณีขอบจากเอกสาร: ตั้ง threshold0 เป็น 0 คือปิดการเก็บ

## ดูสด

เทอร์มินัล VM ด้านล่างคือที่คอมไพล์จริง: ลอง `gcc` กับโปรแกรม C เล็ก ๆ แล้วตรวจ assembly ด้วย `-S` — abstraction จากบทนี้กลายเป็นคำสั่งเครื่องที่จับต้องได้

**หมายเหตุจากการตรวจแล็บ:** ผู้เขียนบูตอิมเมจของเทอร์มินัล VM นี้แล้วตรวจพบว่า *ไม่มี* `gcc`, `cc`, `tcc` หรือ `as` (และไม่มี Python, Perl, Lua) ใน `/bin` กับ `/usr/bin` ซึ่งมีรวม 190 รายการ (73 + 117) ประโยคข้างบนจึงยังทำตามในแล็บไม่ได้ ตัวอย่าง gcc ในบทนี้รันบนเครื่องเดสก์ท็อปของผู้เขียน สิ่งที่มีในแล็บคือ `awk` ของ BusyBox ซึ่งเป็น *ตัวแปลคำสั่ง* ให้ลองเทียบกับกรณีขอบของ C ข้างบน:

- `awk 'BEGIN{print 2147483647+1}'` ได้ 2147483648 ไม่วนกลับ เพราะ awk เก็บตัวเลขเป็นทศนิยมลอยตัว ไม่ใช่ `int` 32 บิต
- `awk 'BEGIN{print 9007199254740992+1}'` ได้ 9007199254740992 — ขอบอีกแบบ: 2⁵³ + 1 เก็บในทศนิยมลอยตัว 64 บิตไม่ได้ การบวก 1 จึงหายไปเงียบ ๆ
- `awk 'BEGIN{print -3/2, int(-3/2)}'` ได้ `-1.5 -1` คือ `int()` ตัดเข้าหาศูนย์ เหมือนการหารจำนวนเต็มของ C ในกรณี 1
- `awk 'BEGIN{printf "%d %d\n", 2147483648, -2147483649}'` ได้ `-2147483648 -2147483648` ทั้งคู่ เมื่อแปลงค่าที่เกินช่วงเป็นจำนวนเต็ม 32 บิต ค่าบวกไม่ได้กลายเป็นค่าบวกสูงสุด และค่าลบก็ไม่ได้วนกลับเป็นบวก (ผู้เขียนอนุมานว่าเป็นเพราะคำสั่งแปลงของ x86 คืนค่า 0x80000000 เมื่อเกินช่วง ภาษา C ถือว่าการแปลงแบบนี้เป็นอนิยาม)
- `awk 'BEGIN{s=0; for(i=0;i<0;i++) s+=i; print s}'` ได้ 0 (ลูปศูนย์รอบ) และลูปเดียวกันกับ 100000 ได้ 4999950000 เท่ากับ `sum(100000)` ของ gcc
- `echo 'x=1+2*3' | awk '{n=split($0,a,""); for(i=1;i<=n;i++) printf "[%s]", a[i]; print ""}'` ได้ `[x][=][1][+][2][*][3]` — การแยกทีละตัวอักษรแบบหยาบที่สุด ซึ่งเป็นก้าวแรกของการวิเคราะห์ศัพท์ (lexer จริงจะรวม `12` เป็นโทเคนเดียว)
