บทที่ 52 ครอบคลุมว่า *เหตุใด* GPU จึงใช้โมเดลการรัน SIMT ขนานมหาศาล บทนี้ครอบคลุมฮาร์ดแวร์รูปธรรมที่โมเดลนั้นแมปลง — Streaming Multiprocessor, warp และเมตริก occupancy ที่กำหนดว่าฮาร์ดแวร์ขนานนั้นถูกใช้โดยโปรแกรมหนึ่งอย่างมีประสิทธิภาพเพียงใด

## Streaming Multiprocessor

GPU ถูกจัดเป็น Streaming Multiprocessor (SM) จำนวนมาก — แต่ละตัวเป็นหน่วยประมวลผลขนานที่ค่อนข้างครบในตัว มี CUDA core แต่ละเลนจำนวนมาก (เลนการรันแบบ ALU ง่าย ๆ จงใจซับซ้อนกว่าคอร์ CPU เดียวจากเฟส 3 น้อยมาก — ไม่มีการรันนอกลำดับ ไม่มีการทำนายสาขาแบบซับซ้อนที่บทที่ 14 ครอบคลุม) มี warp scheduler และ register file ที่แชร์ข้ามเธรดที่พักอยู่บน SM นั้น GPU ระดับสูงสมัยใหม่มี SM เหล่านี้หลายสิบตัว แต่ละตัวรันค่อนข้างอิสระ ซึ่งคือแหล่งของความขนานรวมมหึมาของ GPU เมื่อเทียบกับคอร์ซับซ้อนกำมือของ CPU

## Warp: หน่วยการรัน lockstep จริง

เธรดบน SM ถูกจัดเป็น warp — บน GPU ของ NVIDIA warp หนึ่งมีเสมอ 32 เธรด (CUDA; wavefront ของ AMD ในอดีตใช้ 64) — และ warp คือความละเอียดที่โมเดล SIMT จากบทที่ 52 ถูกบังคับใช้: ทั้ง 32 เธรดใน warp รันคำสั่ง *เดียวกัน* ในรอบคล็อก *เดียวกัน* แต่ละเส้นทำงานบนข้อมูลของตัวเอง นี่คือ implementation ฮาร์ดแวร์ตรงของข้อโต้แย้งประสิทธิภาพ "หน่วยควบคุมที่แชร์หนึ่งหน่วยขับเลนขนานหลายเลน" จากบทก่อน

## Branch Divergence: ที่ที่ประสิทธิภาพของ SIMT พัง

นี่คือขอบคมของโมเดลนี้: จะเกิดอะไรขึ้นเมื่อเธรดต่าง *ภายใน warp เดียวกัน* ต้องไปสาขา if/else ต่างกัน — ข้อมูลของบางเธรดผ่านเงื่อนไข บางเธรดไม่ผ่าน? ฮาร์ดแวร์จัดการได้ แต่ไม่ฟรี: มันรัน *ทั้งสอง* เส้นทางสาขาตามลำดับ โดยเธรดที่ไม่ได้อยู่บนเส้นทางที่กำลังรันถูก mask ออก (ปิดชั่วคราว ไม่มีส่วนร่วมงานมีประโยชน์) ในช่วงนั้น warp ที่มีสาขา divergent จึงใช้เวลานานเท่าการรันทั้งสองเส้นทางต่อกัน แม้ผลของแต่ละเธรดต้องการเพียงเส้นทางเดียว — ต้นทุนประสิทธิภาพจริง และเป็นผลตรงของการรัน lockstep เดียวกันที่ทำให้กรณีไม่ divergent มีประสิทธิภาพสูง การเขียนโค้ด GPU ที่ลด divergence ประเภทนี้ — ให้เธรดใน warp อยู่บนเส้นทางการรันเดียวกันให้มากที่สุด — จึงเป็นการ optimize เชิงปฏิบัติที่สำคัญ

## Occupancy: ฮาร์ดแวร์ถูกใช้จริงเต็มแค่ไหน

SM มีทรัพยากรจำกัด — register file จำกัด shared memory จำกัด — และทุก warp ที่พักบน SM นั้นกินส่วนหนึ่งของทรัพยากรเหล่านั้นตราบที่ยัง active Occupancy วัดว่ามีกี่ warp ที่พักอยู่จริงและมีสิทธิ์รันบน SM ในชั่วขณะหนึ่ง เทียบกับค่าสูงสุดทางทฤษฎีที่ฮาร์ดแวร์รองรับได้ Occupancy สูงโดยทั่วไปช่วยซ่อน latency ของหน่วยความจำ (เชื่อมกลับการสนทนา memory wall ในบทที่ 35): ขณะที่ warp หนึ่งค้างรอการเข้าถึงหน่วยความจำช้า scheduler สามารถสลับไป warp อื่นที่พร้อมได้ แทนที่จะปล่อยหน่วยรันของ SM ว่างระหว่างการค้างนั้น

แต่ occupancy ไม่ใช่แค่ "ทำให้ตัวเลขนี้สูงสุดแล้วจบ" — เคอร์เนลที่ใช้ register หรือ shared memory ต่อเธรดมากกว่าอาจได้ occupancy ต่ำกว่าแต่ยังรันเร็วกว่าโดยรวม หากทรัพยากรต่อเธรดเพิ่มนั้นลดการคำนวณซ้ำหรือทราฟฟิกหน่วยความจำที่อื่นอย่างมีความหมาย การจูน occupancy กับทรัพยากรต่อเธรดคือ tradeoff การ optimize จริงในการโปรแกรม GPU ไม่ใช่เมตริกทำให้สูงสุดแล้วลืม — ความละเอียดที่กลายเป็นเรื่องเมื่อเคอร์เนลจริงถูกเขียนและ profile กับฮาร์ดแวร์จริง แทนที่จะให้เหตุผลเพียงในนามธรรม
