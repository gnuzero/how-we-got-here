    கம்பிக்கு யார் முடிவெடுக்கிறார்கள்

    செப்டம்பர் 6, 2026

    ARPANET (பதிவு 39) மற்றும் TCP/IP (பதிவு 41) packets எப்படி நகரும் என்பதைத் தீர்த்தன. அவை தனியாக அமைதியான கேள்விக்குப் பதிலளிக்கவில்லை: bits என்ன அர்த்தம் எனச் சொல்ல யார் அனுமதி பெறுகிறார்கள்? Port 80, ஒரு IPv4 prefix, .com, ก-க்கான code point — தொலை இயக்குநர்கள் அதே அடையாளங்களை அதே வழியில் கருதாவிட்டால் எதுவும் வேலை செய்யாது. இணையத்தின் ஆளுமைக் கதை அந்த ஒப்பந்தத்தின் கதை: வலையமைப்புக்கு மேல் ஒரு பாராளுமன்றம் அல்ல, ஆனால் எண்கள், பெயர்கள் மற்றும் encodings-க்கான பகிரப்பட்ட பதிவேடுகளின் தொகுப்பு.

    தமிழ் இடைவெளிக் குறிப்பு: IETF/RFC பற்றித் தமிழ் எழுத்து விளக்கம் மெலிதானது; ICANN/IANA பற்றி இல்லை; Unicode பற்றிப் போதுமானது. காணொளிச் சான்று YouTube தேடல் முடிவுகள் மட்டும் — காணொளிகள் பார்க்கப்படவில்லை. கீழே உள்ள எண்கள் முதன்மை ஆவணங்களிலிருந்து சரிபார்க்கப்பட்டவை: IPv4 முகவரி 32 bits (RFC 791), TCP port 16 bits (RFC 793), IANA port பதிவேட்டில் http = 80/tcp, DNS label ≤ 63 octets / பெயர் ≤ 255 octets (RFC 1035), UTF-8 byte வடிவங்கள் (RFC 3629), தமிழ் Unicode block U+0B80–U+0BFF (Unicode Blocks.txt). UTF-8 bytes-ஐ எங்கள் பணிக் கணினியில் Python-இலும் சரிபார்த்தோம். எடுத்துக்காட்டு prefix-கள், domain பெயர்கள் “எடுத்துக்காட்டு மதிப்புகள்”. இந்தப் பதிவுக்கு lab இல்லை; காகிதப் பயிற்சிகள் கீழே.

    முதலில் சொற்கள்#

    • RFC (Request for Comments): இணைய நெறிமுறைகளின் பொது ஆவணத் தொடர்; பல இன்று தரநிலைகள்.
    • Registry (பதிவேடு): ஒவ்வொரு அடையாளமும் ஒரே ஒரு அர்த்தத்துக்கு மட்டும் ஒதுக்கப்படுவதை உறுதிசெய்யும் பொதுப் பட்டியல்.
    • Protocol parameter: port எண், protocol எண், media type போன்ற, நெறிமுறைகள் பயன்படுத்தும் ஒதுக்கப்பட்ட எண் / பெயர்.
    • IP prefix (முகவரி முன்னொட்டு): “/24” போல, முதல் சில bits நிலையான முகவரித் தொகுதி.
    • RIR (பிராந்திய இணையப் பதிவகம்): ஒரு பிராந்தியத்துக்கு IP முகவரித் தொகுதிகளை வழங்கும் அமைப்பு — ARIN, RIPE NCC, APNIC, LACNIC, AFRINIC.
    • Label (DNS லேபிள்): domain பெயரில் புள்ளிகளுக்கு இடையேயான ஒவ்வொரு பகுதி.
    • Code point (குறியீட்டுப் புள்ளி): ஒவ்வொரு எழுத்துக்கும் Unicode வழங்கும் எண், U+0BA4 போல.
    • Encoding (குறியாக்கம்): code point-களை bytes-ஆக மாற்றும் விதி — UTF-8 அதில் ஒன்று.

    நிறுவனங்களுக்கு முன் ஆவணங்கள்#

    முதல் ஒருங்கிணைப்புக் கருவி ஒரு ஆவணத் தொடர். ஏப்ரல் 1969இல், Steve Crocker RFC 1-ஐ வெளியிட்டார் — Host Software — ARPANET ஆராய்ச்சி சமூகத்திற்கான பணிக் குறிப்புகளாக. தொனி முக்கியம்: “Request for Comments,” “ஆணை” அல்ல. Jon Postel கிட்டத்தட்ட மூன்று பத்தாண்டுகள் தொடரைத் தொகுத்து, முறைசாரா மெமோக்களை இணையம் உண்மையில் எப்படி வேலை செய்கிறது என்பதன் நீடித்த பொதுப் பதிவாக மாற்றினார். Door out: RFC Editor history.

    ஆராய்ச்சி சமூகம் தாழ்வாரக் கூட்டங்களைத் தாண்டி வளர்ந்ததும், Internet Engineering Task Force (IETF)-ஐ வளர்த்தது. சுமை தாங்கும் சொற்றொடர் Dave Clark-இன்: rough consensus and running code — தரநிலைகள் வாக்களிப்பால் அல்ல, shipping ஆல் தங்கள் தகுதியை நிரூபிக்கின்றன. IETF இணையத்தைச் சொந்தமாக வைத்திருக்கவில்லை; இயக்குநர்கள் பயன்படுத்தும் ஒன்றாக நெறிமுறைகளை வாதிடும் செயல்முறையைச் சொந்தமாக வைத்திருக்கிறது. Door out: ietf.org.

    எண்கள்: யாராவது அடையாளங்களை வழங்க வேண்டும்#

    Packets protocol numbers, port numbers, address blocks, ASN மதிப்புகள், media types சுமக்கின்றன — இரு குழுக்கள் வெவ்வேறு அர்த்தங்களுக்கு அதே ஒன்றை அச்சிட்டால் மதிப்பில்லாத அடையாளங்கள். ஆண்டுகளாக அந்தப் பதிவேடு ஒரே இடத்தில் வாழ்ந்தது: Internet Assigned Numbers Authority (IANA), UCLA மற்றும் பின்னர் USC/ISI-இல் ஆராய்ச்சி ஒப்பந்தங்களின் கீழ் Jon Postel (நீண்டகால தொடர்புப் புள்ளியாக Joyce Reynolds உடன்) நடைமுறை சேவையாக இயக்கியது. IANA ஒரு வகையின் விதை: implementations இருதரப்பு பேச்சுவார்த்தை இல்லாமல் இடைசெயல்பட protocol parameters-க்கான நடுநிலைப் பதிவேடு.

    வலையமைப்பு ஒரு நபரின் நோட்புக்கைத் தாண்டி அளவிட்டதும், எண் வளங்கள் வகை ஆல் பிரிந்தன. Protocol parameters IANA-வுடன் இருந்தன. IP address இடம் Regional Internet Registries நோக்கி நகர்ந்தது — வட அமெரிக்காவின் பெரும்பகுதிக்கு ARIN (1997); RIPE NCC, APNIC, LACNIC மற்றும் AFRINIC மற்ற பிராந்தியங்களுக்கு அதே வகை, சிலவற்றின் கீழ் அந்தப் பிராந்தியம் தேர்ந்தெடுத்த மாதிரியில் national அல்லது local Internet registries (NIR-கள்). Pattern தான் முக்கியம்: அரிய, தனித்துவ அடையாளங்களுக்கு எல்லோரும் சுட்டிக்காட்டக்கூடிய ஒரு பாதுகாவலர் தேவை. Door out: iana.org, arin.net.

    எண்கள் ஏன் அரியவை — கணக்கில்#

    அடையாளம் அகலம் (மூலம்) சாத்தியமான மதிப்புகள்
    IPv4 முகவரி 32 bits (RFC 791) 2³² = 4,294,967,296
    TCP port 16 bits (RFC 793) 2¹⁶ = 65,536 (0–65,535)

    IPv4 முகவரிகள் நான்கு பில்லியனுக்குச் சற்று மேல் மட்டுமே; ports ஒரு இயந்திரத்துக்கு 65,536. எண்ணிக்கை வரம்புள்ளது, ஒவ்வொன்றும் தனித்துவமாக இருக்க வேண்டும் — அதனால்தான் அவற்றை யாரோ கணக்கு வைத்து வழங்க வேண்டும்.

    Prefix கணக்கு. “/n” என்றால் முதல் n bits நிலையானவை; மீதி 32 − n bits தொகுதிக்குள் மாறுகின்றன:

    Prefix மாறும் bits முகவரிகள்
    /8 24 2²⁴ = 16,777,216
    /22 10 2¹⁰ = 1,024
    /24 8 2⁸ = 256

    ஒரு /8 என்பது முழு IPv4 இடத்தின் 1 ÷ 256 பங்கு (2²⁴ ÷ 2³² = 2⁻⁸).

    Port 80 ஏன் எல்லா இடத்திலும் web? IANA-வின் service name / port number பதிவேட்டில் இன்றும் http, 80, tcp மற்றும் https, 443, tcp என்ற வரிகள் உள்ளன. இரண்டு நிறுவனங்கள் 80-ஐ வெவ்வேறு நெறிமுறைகளுக்குப் பயன்படுத்தினால், எந்த browser-உம் எந்த server-உடனும் பேச முடியாது — பதிவேடுதான் “80 = web” என்ற உடன்பாடு.

    பெயர்கள்: மனிதர்களுக்குச் சொற்கள் தேவை; இயந்திரங்களுக்குத் தனித்துவம் தேவை#

    Paul Mockapetris-இன் DNS விவரக்குறிப்புகள் (RFC 1034, RFC 1035) படிநிலைப் பெயர்களை முகவரி fabric மீது விநியோகிக்கப்பட்ட lookup அமைப்பாக மாற்றின. பெயர்கள் மூல எண்கள் இல்லாத வகையில் அரசியல்: மக்கள் சொற்கள் மீது வாதிடுகின்றனர். Jon Postel-இன் RFC 1591 ஆரம்ப domain கொள்கையைப் பொறுப்பாண்மையாக வரைந்தது.

    DNS பெயர், கம்பியில் எப்படி#

    RFC 1035-இன்படி பெயர் label-களின் வரிசையாகச் செல்கிறது: ஒவ்வொரு label-க்கும் முன் ஒரு நீள byte, இறுதியில் root-க்கான பூஜ்ய நீள byte. நீள byte-இன் மேல் இரண்டு bits பூஜ்யமாக இருக்க வேண்டும்; மீதி ஆறு bits → label அதிகபட்சம் 2⁶ − 1 = 63 octets. முழுப் பெயர் (label-கள் + நீள byte-கள்) 255 octets அல்லது குறைவு.

    www.example.com (எடுத்துக்காட்டுப் பெயர்):

    Byte-கள் பொருள்
    3 w w w 1 + 3 = 4
    7 e x a m p l e 1 + 7 = 8
    3 c o m 1 + 3 = 4
    0 root, 1

    மொத்தம் 4 + 8 + 4 + 1 = 17 octets.

    1990-களின் பிற்பகுதியில் அமெரிக்க அரசு அந்த ஒருங்கிணைப்புச் செயல்பாடுகளை ஒற்றை ஆராய்ச்சி ஒப்பந்தத்திலிருந்து வெளியேற்ற விரும்பியது. ICANN (Internet Corporation for Assigned Names and Numbers) 1998இல் உருவானது — இடைக்காலத் தலைவர் Esther Dyson — IANA அந்தக் குடைக்குக் கீழ் செயல்பாட்டுப் பதிவேடுகளாகத் தொடர, பெயர்கள் மற்றும் எண்கள் கொள்கைக்கான நிறுவன இருக்கையை வைத்திருக்க. ICANN-ஐ மற்றொரு வகையின் விதையாகப் படியுங்கள்: பகிரப்பட்ட namespace-இன் நிலைத்தன்மை மற்றும் தனித்துவமே வேலை, applications இடையே வெற்றியாளர்களைத் தேர்ந்தெடுப்பது அல்ல. Door out: icann.org.

    Encodings: Payload அதே Glyph அர்த்தம் கொள்ள வேண்டும்#

    இரு முனைகளும் ஒரு byte வரிசை என்ன என உடன்படாதபோது இடைசெயல்பாடு அமைதியாகத் தோல்வியடையும். Unicode Consortium (1991இல் நிறுவப்பட்டது; ஒற்றை character set தேவைப்பட்ட நிறுவனங்கள் குறுக்கே Joe Becker, Mark Davis மற்றும் பிறரின் ஆரம்ப வேலை) சுருக்க எழுத்துகளிலிருந்து code points-க்குப் பகிரப்பட்ட மேப்பிங்கைப் பராமரிக்கிறது — ஒவ்வொரு application-உம் தன் alphabet அட்டவணையைக் கண்டுபிடிக்காமல் தமிழ், Latin மற்றும் emoji ஒரே கம்பியைப் பகிரக் காரணம். UTF-8 பிறகு அந்த repertoire-க்கு மேலாதிக்க on-the-wire encoding ஆனது. Door out: unicode.org, Unicode Standard.

    UTF-8 கையால் — “த”#

    RFC 3629-இன் UTF-8 அட்டவணை:

    Code point வரம்பு UTF-8 byte வடிவம் Byte-கள்
    U+0000–U+007F 0xxxxxxx 1
    U+0080–U+07FF 110xxxxx 10xxxxxx 2
    U+0800–U+FFFF 1110xxxx 10xxxxxx 10xxxxxx 3
    U+10000–U+10FFFF 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx 4

    தமிழ் block U+0B80–U+0BFF, அதனால் ஒவ்வொரு தமிழ் code point-உம் 3 bytes. “த” = U+0BA4 = binary 0000 1011 1010 0100.

    • 16 bits-ஐ 4 + 6 + 6 ஆகப் பிரி: 0000 | 101110 | 100100
    • வடிவத்தில் நிரப்பு: 1110 0000 | 10 101110 | 10 100100
    • Hex: E0 AE A4

    Python-இல் 'த'.encode() அதே E0 AE A4 தந்தது. மேலும் சில (எங்கள் கணினியில் சரிபார்த்தவை):

    உரை Code points UTF-8 bytes
    A U+0041 41 (1 byte)
    é U+00E9 C3 A9 (2)
    ก (Thai) U+0E01 E0 B8 81 (3)
    தமிழ் U+0BA4 U+0BAE U+0BBF U+0BB4 U+0BCD 5 code points × 3 = 15 bytes
    😀 U+1F600 F0 9F 98 80 (4)

    கவனிக்கவும்: திரையில் “தமிழ்” மூன்று எழுத்துகளாகத் தெரிந்தாலும் அது ஐந்து code points (த, ம, ி உயிர்க்குறி, ழ, ் புள்ளி). Encoding-இல் இருமுனைகளும் உடன்படாவிட்டால், இந்த 15 bytes வேறு மொழியின் குப்பை எழுத்துகளாகத் தோன்றும் — “அமைதியான தோல்வி”.

    அதே வகையின் உறவினர்கள்#

    சில peers ஒரு வாக்கியம் சம்பாதிக்கின்றன — அதே வகை பகிரப்பட்ட அர்த்தம், தரநிலை-அமைப்பு சுற்றுலா அல்ல:

    • W3C மற்றும் WHATWG — Tim Berners-Lee World Wide Web Consortium-ஐ (1994) web platform தரநிலைகளைப் பராமரிக்க நிறுவினார்; browser vendors வேகமான iteration பாதை தேவைப்பட்டபோது WHATWG பின்னர் living HTML/DOM specs சுமந்தது. அதே வகை: browser-இல் ஒரு ஆவணம் மற்றும் API என்ன அர்த்தம் என வரையறுக்க யார் அனுமதி.
    • IEEE — IEEE 802 ஏன் Ethernet (பதிவு 40) மற்றும் Wi-Fi link அடுக்கில் proprietary தீவு பேச்சுவழக்குகள் அல்ல.
    • ISO மற்றும் peers — கொள்முதல், பாதுகாப்பு அல்லது தேசிய அமைப்புகள் கோரும் இடத்தில் முறைசார்ந்த சர்வதேச தரநிலைகள் RFC உலகத்திற்கு அருகில் அமர்கின்றன; இணையம் பெரும்பாலும் முதலில் RFCs-இல் shipping செய்து பின்னர் இசைவுபடுத்தியது.

    இது ஏன் பயணத்தில் சேர்கிறது#

    பதிவுகள் 39–41 பொறியியல் பந்தயம்: packets, அடுக்குகள், நம்பகமற்ற substrate. இந்தப் பதிவு அவற்றின் கீழ் குடியியல் பந்தயம்: பகிரப்பட்ட அர்த்தம் உள்கட்டமைப்பு. யாராவது (மற்றும் சில செயல்முறை) எண்கள், பெயர்கள் மற்றும் encodings முடிவெடுக்காவிட்டால், ஒவ்வொரு புதிய வலையமைப்பும் தனிப்பட்ட மொழி. மேலேயுள்ள கதவுகள் முதன்மை மூலங்கள் — RFCs, பதிவேடுகள், consortium பக்கங்கள்.

    இங்கிருந்து விருப்பப் பக்கப் பாதைகள்: அந்தப் பகிரப்பட்ட கம்பியில் மக்கள் எப்படி கண்டுபிடித்தார்கள் மற்றும் பேசினார்கள் (பதிவு 43), அல்லது போர்க்கால crypto இரகசியங்களை வைத்திருக்கக்கூடிய இயந்திரங்களை எப்படிக் கட்டாயப்படுத்தியது (பதிவு 66). முக்கிய spine packets → அமைப்புகள் → சிலிகான் → attention ஆகவே இருக்கும்; இது நீங்கள் எடுக்கலாம் அல்லது தவிர்க்கலாம் என்ற lens-ஐ விரிவாக்கும் துடிப்பு.

    காகிதப் பயிற்சிகள் (விடைகளுடன்)#

    1. “ம” = U+0BAE. UTF-8-இல் கையால் encode செய்யுங்கள். விடை: binary 0000 1011 1010 1110 → 0000 | 101110 | 101110 → 11100000 10101110 10101110 = E0 AE AE.

    2. “அம்மா” UTF-8-இல் எத்தனை bytes? விடை: code points அ U+0B85, ம U+0BAE, ் U+0BCD, ம U+0BAE, ா U+0BBE = 5; 5 × 3 = 15 bytes.

    3. ஒரு /20 prefix-இல் எத்தனை IPv4 முகவரிகள்? விடை: 32 − 20 = 12 bits; 2¹² = 4,096.

    4. DNS label ஏன் 63 octets-இல் நிற்கிறது, 255 அல்ல? விடை: நீள byte-இன் 8 bits-இல் மேல் இரண்டு பூஜ்யமாக இருக்க வேண்டும் (RFC 1035); மீதி 6 bits → அதிகபட்சம் 2⁶ − 1 = 63.

    5. tamil.example.org (எடுத்துக்காட்டுப் பெயர்) கம்பியில் எத்தனை octets? விடை: (1 + 5) + (1 + 7) + (1 + 3) + 1 = 6 + 8 + 4 + 1 = 19.

    6. TCP port 16 bits. ஒரு இயந்திரத்தில் எத்தனை port எண்கள் சாத்தியம்? இரு குழுக்கள் 80-ஐ வேறு வேறு நெறிமுறைகளுக்கு எடுத்தால் என்ன ஆகும்? விடை: 2¹⁶ = 65,536 (0–65,535). ஒரு client “80-இல் web” என்று எதிர்பார்த்து வேறு நெறிமுறையைச் சந்திக்கும் — அதனால்தான் IANA பதிவேடு.
