    Google-இன் Big Data Infrastructure — அவர்கள் ஏன் வென்றார்கள்

    ஜனவரி 1, 2026

    1990களின் இறுதியில் பல நிறுவனங்கள் web தேடலைக் கட்டின. Google ranking நுணுக்கத்தால் மட்டும் வெல்லவில்லை — PageRank முக்கியம், ஆனால் நீடித்த நன்மை infrastructure: ஒரு இயந்திரம் ஒருபோதும் போதாதபோது தொடர்ந்து மாறும் web-ஐச் சேமித்துச் செயலாக்க முடியும் அமைப்புகள்.

    தமிழ் இடைவெளிக் குறிப்பு: GFS, Bigtable இரண்டுக்கும் தமிழில் எழுத்தும் காணொளியும் இல்லை; MapReduce-க்குத் தமிழ் எழுத்து விளக்கம் இல்லை; காணொளிச் சான்று YouTube தேடல் முடிவுகள் மட்டும் — காணொளிகள் பார்க்கப்படவில்லை. இங்குள்ள உண்மை எண்கள் ஆங்கிலப் பதிவு “Door out”-இல் பெயரிடும் மூன்று மூலக் கட்டுரைகளிலிருந்தே நேரடியாகச் சரிபார்க்கப்பட்டவை: GFS (SOSP 2003) — 64 MB chunk, இயல்பாக 3 நகல்கள், ஒரு chunk-க்கு 64 byte-க்குக் குறைவான master metadata, chunkserver மீட்புச் சோதனை; MapReduce (OSDI 2004) — word count எடுத்துக்காட்டு, 1 TB grep அளவீடு; Bigtable (OSDI 2006) — com.cnn.www webtable எடுத்துக்காட்டு. இயந்திரத் தோல்வி விகிதம் போன்றவை “எடுத்துக்காட்டு மதிப்புகள்”. இந்தப் பதிவுக்கு lab இல்லை; காகிதப் பயிற்சிகள் கீழே.

    முதலில் சொற்கள்#

    • Commodity இயந்திரம் (சாதாரணச் சந்தைக் கணினி): சிறப்பு நம்பகத்தன்மை இல்லாத, மலிவான, பெருமளவில் கிடைக்கும் சேவையகம்.
    • Chunk (துண்டு): GFS கோப்பைப் பிரிக்கும் நிலைத்த அளவுப் பகுதி (64 MB).
    • Replica (நகல்): அதே chunk-இன் இன்னொரு இயந்திரத்தில் உள்ள பிரதி; ஒன்று இறந்தாலும் தரவு பிழைக்கிறது.
    • Master / chunkserver: chunk-கள் எங்கே உள்ளன என்ற metadata-வை வைத்திருக்கும் ஒற்றை ஒருங்கிணைப்பாளர் / chunk-களை உண்மையில் சேமிக்கும் இயந்திரங்கள்.
    • Map / reduce: ஒரு record-இலிருந்து (key, value) இணைகளை வெளியிடும் செயல்கூறு / ஒரே key கொண்ட values-ஐத் தொகுக்கும் செயல்கூறு.
    • Shuffle (கலைத்து அடுக்குதல்): map வெளியீடுகளை key வாரியாகப் பிரித்து, சரியான reduce-க்கு அனுப்பி வரிசைப்படுத்தும் படி.
    • Sparse table (அரிதான அட்டவணை): பெரும்பாலான கலங்கள் காலியாக உள்ள அட்டவணை; காலியானவற்றுக்கு இடம் செலவாகாது.
    • Moat (அகழி): போட்டியாளர்கள் எளிதில் நகலெடுக்க முடியாத நீடித்த நன்மை.

    கட்டுப்பாடு: Web ஒற்றை Box-ஐ விஞ்சினது#

    “முழு web”-ஐ index செய்வது என்பது எந்த ஒற்றை disk அல்லது memory-ஐயும் விடப் பெரிய dataset — ஒருமுறை எடுக்கப்பட்ட snapshot அல்ல, தொடர்ந்து வருவது. Phase 3 ஒரு இயந்திரத்தை வேகமாக்கியது. இந்தப் பிரச்சனை வேறு: பல இயந்திரங்களை ஒருங்கிணைத்து, எந்த ஒன்றிற்கும் மிகப் பெரிய ஒன்றை அவை கூட்டாக வைத்துச் செயலாக்கச் செய்யுங்கள்.

    Failure சாதாரணம் — எனவே Storage அதைக் கருத வேண்டியிருந்தது#

    Google File System (Ghemawat, Gobioff, மற்றும் Leung, SOSP 2003) பெரும்பாலான filesystems இன்னும் விதிவிலக்காகக் கருதிய வடிவமைப்பு அனுமானத்திலிருந்து தொடங்கியது: ஆயிரக்கணக்கான commodity இயந்திரங்களுடன், வன்பொருள் failure வழக்கம். கோப்புகளைப் பெரிய chunks-ஆகப் பிரிங்கள், ஒவ்வொரு chunk-ஐயும் chunkservers குறுக்கே replicate செய்யுங்கள், மற்றும் chunks எங்கே வாழ்கின்றன என master கண்காணிக்கட்டும் — எனவே ஒரு இயந்திரத்தை இழப்பது தானாக உறிஞ்சப்படுகிறது, நெருக்கடியாகக் கையாளப்படுவதில்லை. அது பதிவு 42-இன் fabric பணி datacenter-க்குள் செய்யும் அதே வகை பந்தயம்: பகுதி failure-இன் பொதுவான வழக்கிற்குப் பொறியியல் செய்யுங்கள்.

    “தோல்வி வழக்கம்” என்பதன் கணக்கு (எடுத்துக்காட்டு மதிப்புகள்): ஒவ்வொரு இயந்திரமும் சராசரியாக 1,000 நாட்களுக்கு ஒருமுறை (சுமார் மூன்று ஆண்டுகள்) செயலிழக்கிறது என்றால்:

    இயந்திரங்கள் ஒரு நாளில் எதிர்பார்க்கும் தோல்விகள்
    1 1 ÷ 1,000 = 0.001
    1,000 1,000 ÷ 1,000 = 1
    10,000 10,000 ÷ 1,000 = 10

    ஒரு கணினிக்கு “அரிதான விபத்து”, ஆயிரம் கணினிகளுக்கு “தினசரி நிகழ்வு”.

    GFS-இன் எண்கள், கட்டுரையிலிருந்து#

    GFS கட்டுரை: chunk அளவு 64 MB; இயல்பாக ஒவ்வொரு chunk-க்கும் 3 நகல்கள்; master ஒவ்வொரு 64 MB chunk-க்கும் 64 byte-க்குக் குறைவான metadata-வை நினைவகத்தில் வைக்கிறது. 1 TB கோப்புக்குக் கணக்கு (1 TB = 1,048,576 MB):

    • Chunk-கள் = 1,048,576 ÷ 64 = 16,384
    • நகல்கள் உட்பட சேமிப்பு = 3 × 1 TB = 3 TB; chunk நகல்கள் = 3 × 16,384 = 49,152
    • Master metadata < 16,384 × 64 byte = 1,048,576 byte = 1 MB — ஒரு TB தரவுக்கு ஒரு MB நினைவகம். அதனால்தான் ஒற்றை master போதுமானது.

    மீட்பு, கட்டுரையின் சொந்தச் சோதனை: cluster B-இல் சுமார் 15,000 chunk-கள், 600 GB தரவு கொண்ட ஒரு chunkserver வேண்டுமென்றே நிறுத்தப்பட்டது. ஒரே நேரத்தில் 91 நகலெடுப்புகள் (chunkserver-களில் 40%), ஒவ்வொன்றும் அதிகபட்சம் 6.25 MB/s என்று வரம்பிடப்பட்டது; எல்லா chunk-களும் 23.2 நிமிடங்களில் மீட்கப்பட்டன, பயனுள்ள வீதம் 440 MB/s.

    • வரம்பு: 91 × 6.25 = 568.75 MB/s அதிகபட்சம்; அடைந்தது 440 MB/s ≈ 77%.
    • சரிபார்ப்பு: 600 GB ≈ 614,400 MB; ÷ 440 MB/s ≈ 1,396 s ≈ 23.3 நிமிடம் — கட்டுரையின் 23.2-உடன் ஒத்துப்போகிறது.

    ஒரு இயந்திர இழப்பு: யாரும் அழைக்கப்படவில்லை, அரை மணிக்குள் முழு நகல் நிலை மீண்டது.

    Cluster-ஐ மீண்டும் கண்டுபிடிக்காமல் செயலாக்கம்#

    சேமிப்பு மட்டும் போதாது. அந்த அளவில் செயலாக்கத்திற்கு ஒவ்வொரு பொறியாளரும் distribution மற்றும் recovery-ஐ மீண்டும் கண்டுபிடிக்காதபடி ஒரு நிரலாக்க மாதிரி தேவைப்பட்டது. MapReduce (Dean மற்றும் Ghemawat, OSDI 2004) இரண்டு hooks கொடுத்தது — ஒரு record-இலிருந்து key-value pairs வெளியிடும் map, மற்றும் ஒரு key பகிரும் values-ஐத் தொகுக்கும் reduce — மற்றும் அமைப்பு split, parallel map, key-ஆல் shuffle/sort, parallel reduce, மற்றும் தோல்வியுற்ற tasks-இன் retry-ஐக் கையாண்டது. கட்டுப்பாடு இயற்பியல் சார்ந்தது போலவே அறிவுசார்ந்ததும் கூட: cluster-ஐ மறைத்து வேலையின் தர்க்கம் சிறியதாக இருக்கட்டும்.

    MapReduce, கையால் ஒருமுறை#

    கட்டுரையின் முதல் எடுத்துக்காட்டு word count: map ஒவ்வொரு சொல் w-க்கும் (w, "1") வெளியிடுகிறது; reduce ஒரு சொல்லின் எல்லா 1-களையும் கூட்டுகிறது. இரண்டு சிறு ஆவணங்களுடன் (எடுத்துக்காட்டு உள்ளீடு):

    • ஆவணம் 1: கணினி நினைவகம் கணினி
    • ஆவணம் 2: நினைவகம் வலை கணினி
    படி வெளியீடு
    Map (ஆவணம் 1) (கணினி,1) (நினைவகம்,1) (கணினி,1)
    Map (ஆவணம் 2) (நினைவகம்,1) (வலை,1) (கணினி,1)
    Shuffle / sort (key வாரியாக) கணினி → [1,1,1]; நினைவகம் → [1,1]; வலை → [1]
    Reduce (கணினி,3) (நினைவகம்,2) (வலை,1)

    நிரலாளர் எழுதியது map-உம் reduce-உம் மட்டும்; பிரித்தல், இயந்திரங்களுக்கு அனுப்புதல், shuffle, தோல்வியுற்ற task-ஐ மீண்டும் ஓட்டுதல் — அமைப்பின் வேலை.

    அளவில், கட்டுரையின் grep அளவீடு: 10¹⁰ record-கள் × 100 byte = 10¹² byte ≈ 1 TB; உள்ளீடு சுமார் 64 MB துண்டுகளாக, M = 15,000 map task-கள் (10¹² ÷ 15,000 ≈ 66.7 MB — “சுமார் 64 MB” உடன் ஒத்தது); சுமார் 1,800 இயந்திரங்கள்; 1,764 worker-கள் ஒதுக்கப்பட்டபோது உச்ச வேகம் 30 GB/s-க்கு மேல்; மொத்தம் சுமார் 150 வினாடிகள், அதில் சுமார் ஒரு நிமிடம் தொடக்கச் செலவு. ஒரு இயந்திரம் 100 MB/s-இல் படித்தால் (எடுத்துக்காட்டு மதிப்பு) அதே 1 TB-க்கு 10¹² ÷ 10⁸ = 10,000 s ≈ 2.8 மணி நேரம்.

    மலிவான Bytes மீது அமைப்பு#

    Bigtable (Chang et al., OSDI 2006) தொடர்புடைய தேவைக்குப் பதிலளித்தது: web அளவில் sparse structured storage — rows URLs ஆக, columns crawled versions அல்லது metadata ஆக, பெரும்பாலான cells காலி — அடியில் GFS மீது கட்டப்பட்டது. வடிவமைப்பு தொழில் பின்னர் NoSQL என அழைத்ததில் பெரும்பகுதியை வடிவமைத்தது; இணைப்புத் திசு ஒன்றுதான்: failure-tolerant bulk storage மற்றும் batch நிரலாக்க மாதிரி இருந்தவுடன், structured அணுகல் அடுத்த கட்டாய அடுக்கு ஆகிறது.

    Bigtable-இன் webtable, கட்டுரையிலிருந்து#

    Bigtable கட்டுரையின் எடுத்துக்காட்டு: row key com.cnn.www (URL பின்னோக்கி — அதே domain-இன் பக்கங்கள் அருகருகே வரிசைப்படும்); contents: column பக்க உள்ளடக்கத்தை மூன்று பதிப்புகளாக (நேரமுத்திரைகள் t3, t5, t6) வைக்கிறது; anchor:cnnsi.com, anchor:my.look.ca columns அந்தப் பக்கத்தைச் சுட்டும் பிற தளங்களின் இணைப்பு உரையை வைக்கின்றன.

    Sparse ஏன் முக்கியம் (எடுத்துக்காட்டு மதிப்புகள்): 1,000,000 பக்கங்கள் (rows); சுட்டும் தளங்களின் மொத்த எண்ணிக்கை 100,000 (சாத்தியமான anchor: columns); ஒவ்வொரு பக்கத்தையும் சராசரியாக 10 தளங்கள் சுட்டுகின்றன.

    • சாத்தியமான கலங்கள் = 1,000,000 × 100,000 = 10¹¹
    • நிரம்பியவை = 1,000,000 × 10 = 10⁷
    • நிரம்பிய பங்கு = 10⁷ ÷ 10¹¹ = 0.0001 = 0.01%

    ஒவ்வொரு கலத்துக்கும் இடம் ஒதுக்கும் சாதாரண அட்டவணை 99.99% காலியாக இருக்கும்; Bigtable நிரம்பிய கலங்களை மட்டுமே சேமிக்கிறது.

    இது ஏன் Moat ஆனது#

    போட்டியாளர்கள் ranking கருத்துகளை நகலெடுக்க முடியும். Commodity வன்பொருளில் முழு web-ஐச் சேமித்து, செயலாக்கி, தொடர்ந்து மீண்டும் index செய்யும் திறனை — இயந்திர இறப்பை சாதாரணமாகக் கருதி — பிரதிபண்ணுவது மிகக் கடினம். Hadoop மற்றும் பிந்தைய “big data” stack Google-இன் உள் code இல்லாமலே வெளியிடப்பட்ட papers-ஐப் பின்தொடர்ந்தன: papers அந்த வகைப் பிரச்சனையை எப்படித் தீர்ப்பது எனக் காட்டின.

    Batch map/reduce சக்திவாய்ந்ததும் நெகிழ்வற்றதும். அடுத்த பதிவு செயலாக்கும் விநியோகிக்கப்பட்ட தரவிலிருந்து, முதிர்ந்த விநியோகிக்கப்பட்ட அமைப்பு ஆன பல சேவைகளை deploy செய்து குணப்படுத்துவதற்கு திரும்புகிறது.

    காகிதப் பயிற்சிகள் (விடைகளுடன்)#

    1. 10 TB தரவு GFS-இல், 64 MB chunk-கள், 3 நகல்கள். எத்தனை chunk-கள்? மொத்த வட்டு இடம்? Master metadata-வின் மேல் வரம்பு? விடை: 10 × 1,048,576 ÷ 64 = 163,840 chunk-கள்; 3 × 10 = 30 TB; < 163,840 × 64 byte = 10,485,760 byte = 10 MB.

    2. கட்டுரையின் மீட்புச் சோதனையில் வரம்பு 91 × 6.25 MB/s. அதே 600 GB-ஐ அந்த முழு வரம்பில் மீட்டிருந்தால் எவ்வளவு நேரம்? விடை: 614,400 MB ÷ 568.75 MB/s ≈ 1,080 s ≈ 18 நிமிடம் (உண்மையில் 23.2 நிமிடம் ஆனது).

    3. ஆவணங்கள்: “அ ஆ அ”, “ஆ இ”, “அ”. Word count-இன் reduce வெளியீடு என்ன? Map எத்தனை (key, value) இணைகளை வெளியிட்டது? விடை: (அ,3) (ஆ,2) (இ,1); map இணைகள் = 3 + 2 + 1 = 6.

    4. 5,000 இயந்திரங்கள், ஒவ்வொன்றும் சராசரியாக 1,000 நாட்களுக்கு ஒருமுறை தோல்வி (எடுத்துக்காட்டு மதிப்புகள்). ஒரு வாரத்தில் எத்தனை தோல்விகள் எதிர்பார்க்கலாம்? விடை: ஒரு நாளுக்கு 5,000 ÷ 1,000 = 5; ஒரு வாரம் 5 × 7 = 35.

    5. Hadoop Google-இன் குறியீடு இல்லாமல் எப்படி உருவானது? விடை: ஆங்கிலப் பதிவு சொல்வதுபடி, Google வெளியிட்ட GFS, MapReduce கட்டுரைகள் அந்த வகைப் பிரச்சினையை எப்படித் தீர்ப்பது — பெரிய chunk-கள், நகல்கள், map/reduce, தோல்வியுற்ற task-களை மீண்டும் ஓட்டுதல் — என்று காட்டின; குறியீடு இல்லாமலும் வடிவமைப்பை மீண்டும் உருவாக்க முடிந்தது.

    Door out: Sanjay Ghemawat, Howard Gobioff, மற்றும் Shun-Tak Leung, “The Google File System” (SOSP 2003); Jeffrey Dean மற்றும் Sanjay Ghemawat, “MapReduce: Simplified Data Processing on Large Clusters” (OSDI 2004); Fay Chang et al., “Bigtable: A Distributed Storage System for Structured Data” (OSDI 2006) — இந்த infrastructure கதையின் பின்னால் உள்ள மூன்று முதன்மைகள்.
