    Out-of-Order Execution

    ஜனவரி 1, 2026

    பதிவு 13-இன் load-use hazard ஒரு in-order pipeline-ஐ ஒரு காத்திருக்கும் அறிவுறுத்தலுக்குப் பின்னால் stall செய்கிறது — பிந்தைய அறிவுறுத்தல்கள் சுதந்திரமாகவும் தயாராகவும் இருந்தாலும். Out-of-order execution அந்தக் கட்டுப்பாட்டிற்குப் பதிலளிக்கிறது: operands தயாரானபோதெல்லாம் சுதந்திரமான வேலையை ஓட்டுங்கள்; கட்டமைப்பு தேவைப்படும் இடங்களில் மட்டும் நிரல் வரிசையை அமலாக்குங்கள்.

    Out-of-order execution, Tomasulo algorithm, register renaming — இம்மூன்றுக்கும் தமிழில் எழுத்து விளக்கமோ தமிழ் YouTube விளக்கமோ இந்தத் தணிக்கையில் கிடைக்கவில்லை. எனவே இந்தப் பக்கம் ஒரே நான்கு-அறிவுறுத்தல் எடுத்துக்காட்டை முழுவதும் பின்தொடர்ந்து, ஒவ்வொரு இயந்திரப் பகுதியையும் அது ஏன் தேவை என்பதிலிருந்து கட்டுகிறது.

    ஓடும் எடுத்துக்காட்டு#

    ஒரு சாதாரண பதிவேட்டு இயந்திரத்தில் (register machine) இந்த நான்கு அறிவுறுத்தல்கள்:

    I1:  R1 ← MEM[R2]      ; load — cache miss, மெதுவானது
I2:  R3 ← R1 + R4      ; I1-இன் R1 தேவை
I3:  R1 ← R5 + R6      ; R1-ஐ மீண்டும் எழுதுகிறது (தொடர்பில்லாத புதிய மதிப்பு)
I4:  R7 ← R1 + R5      ; I3-இன் R1 தேவை

    In-order இயந்திரத்தில் I1 நினைவகத்துக்குக் காத்திருக்கும்போது I2 நிற்கிறது (அதற்கு R1 வேண்டும்) — அதனால் I3, I4-உம் அதன் பின்னால் நிற்கின்றன, அவற்றுக்கு I1-இடம் எதுவும் தேவையில்லை என்றாலும். ALU சும்மா இருக்கிறது.

    மூன்று வகைச் சார்புகள்#

    இரண்டு அறிவுறுத்தல்கள் ஒரே பதிவேட்டைத் தொடும்போது மூன்று வகை உறவுகள் உண்டு:

    • RAW (read after write) — உண்மைச் சார்பு (true dependency): பிந்தையது முந்தையது எழுதிய மதிப்பைப் படிக்கிறது. I1 → I2 (R1), I3 → I4 (R1). மதிப்பு உண்மையில் ஓடுகிறது; தவிர்க்க முடியாது.
    • WAR (write after read) — எதிர்ச் சார்பு (anti-dependency): பிந்தையது, முந்தையது இன்னும் படிக்க வேண்டிய பதிவேட்டை மேலெழுதுகிறது. I2 R1-ஐப் படிக்க வேண்டும்; I3 R1-ஐ எழுதுகிறது. I3 முன்னால் ஓடிவிட்டால் I2 தவறான மதிப்பைப் படிக்கும்.
    • WAW (write after write) — வெளியீட்டுச் சார்பு (output dependency): இரண்டும் ஒரே பதிவேட்டை எழுதுகின்றன. I1, I3 இரண்டும் R1. I3 முதலில் முடிந்து, மெதுவான I1 பிறகு எழுதினால், R1-இல் பழைய (தவறான) மதிப்பு தங்கும்.

    WAR, WAW இரண்டும் பெயர்ச் சார்புகள் (name / false dependencies): அவற்றுக்கிடையே மதிப்பு எதுவும் ஓடவில்லை — ISA-க்கு வெறும் சில architectural பதிவேட்டு பெயர்கள் மட்டுமே உள்ளன, compiler ஒரு பெயரை மீண்டும் பயன்படுத்தியது, அவ்வளவுதான்.

    Register Renaming: பெயர்களை மாற்றிச் சண்டையை நிறுத்துதல்#

    Register renaming CPU-க்கு ISA வெளிப்படுத்தும் அளவை விட அதிக physical பதிவேடுகளைக் கொடுத்து, ஒவ்வொரு எழுத்தையும் decode-இல் ஒரு புதிய, காலியான physical பதிவேட்டிற்கு மேப் செய்கிறது. இதற்கு இரண்டு அமைப்புகள்:

    • Register alias table (RAT, மறுபெயர் அட்டவணை) — ஒவ்வொரு architectural பதிவேடும் இப்போது எந்த physical பதிவேட்டில் வாழ்கிறது.
    • Free list (காலிப் பட்டியல்) — பயன்படாத physical பதிவேடுகள்.

    தொடக்கம்: R1→P1, R2→P2, …, R7→P7; காலிப் பட்டியல்: P10, P11, P12, P13. ஒவ்வொரு அறிவுறுத்தலுக்கும் விதி ஒன்றே: மூலங்களை (sources) RAT-இல் பார்த்து மாற்று; இலக்குக்கு (destination) காலிப் பட்டியலிலிருந்து புதியது கொடு, RAT-ஐப் புதுப்பி.

    அறிவுறுத்தல் மூலங்கள் → இலக்கு → மறுபெயரிட்ட வடிவம் RAT மாற்றம்
    I1: R1 ← MEM[R2] R2→P2 R1→P10 P10 ← MEM[P2] R1 = P10
    I2: R3 ← R1 + R4 R1→P10, R4→P4 R3→P11 P11 ← P10 + P4 R3 = P11
    I3: R1 ← R5 + R6 R5→P5, R6→P6 R1→P12 P12 ← P5 + P6 R1 = P12
    I4: R7 ← R1 + R5 R1→P12, R5→P5 R7→P13 P13 ← P12 + P5 R7 = P13

    மறுபெயரிட்ட வடிவத்தைப் பாருங்கள்: I2 படிப்பது P10; I3 எழுதுவது P12 — வெவ்வேறு பதிவேடுகள், எனவே WAR இல்லை. I1 எழுதுவது P10, I3 எழுதுவது P12 — WAW இல்லை. எஞ்சியவை உண்மைச் சார்புகள் மட்டும்: I1 → I2 (P10) மற்றும் I3 → I4 (P12). இப்போது I3, I4 இரண்டும் I1 காத்திருக்கும்போதே ஓடலாம்.

    (P1 எப்போது விடுவிக்கப்படும்? R1-இன் பழைய மதிப்பைப் படிக்கக்கூடிய எல்லா அறிவுறுத்தல்களும் உறுதியான பின் — அதாவது R1-ஐ மேலெழுதிய அறிவுறுத்தல் commit ஆகும்போது. அதனால்தான் physical பதிவேடுகளின் எண்ணிக்கை, “பறக்கும்” அறிவுறுத்தல்களின் எண்ணிக்கைக்கு ஒரு வரம்பாகிறது.)

    தயாரானபோது Issue: Reservation Stations மற்றும் Common Data Bus#

    Renamed அறிவுறுத்தல்கள் உண்மையான operands வரும் வரை reservation stations-இல் (காத்திருப்பு நிலையங்கள்) காத்திருக்கின்றன. ஒவ்வொரு station பதிவிலும்: செயல் (op), இரண்டு operand இடங்கள் — ஒவ்வொன்றும் ஒன்று மதிப்பு (value) அல்லது அந்த மதிப்பைத் தயாரிக்கும் அறிவுறுத்தலின் குறிச்சொல் (tag). ஒரு execution unit முடித்ததும், முடிவையும் அதன் tag-ஐயும் common data bus (CDB) மூலம் எல்லோருக்கும் ஒலிபரப்புகிறது. அந்த tag-க்காகக் காத்திருந்த ஒவ்வொரு station-உம் மதிப்பைப் பிடித்துக்கொள்கிறது. இரண்டு operands-உம் மதிப்பானதும், அறிவுறுத்தல் execution unit-க்கு issue ஆகிறது — அசல் நிரல் வரிசையைப் பொருட்படுத்தாமல். அதுதான் out-of-order பகுதி.

    Architectural விளைவுகள் வரிசையில்: Reorder Buffer#

    வெளியே தெரியும் நிலை — பதிவேடுகள், நினைவகம், exceptions — இன்னும் நிரல் வரிசையில் நடந்ததுபோல் தோன்ற வேண்டும். Reorder buffer (ROB) ஒரு வட்ட வரிசை (circular queue): decode ஆகும் ஒவ்வொரு அறிவுறுத்தலும் வாலில் (tail) சேர்கிறது; தலையில் (head) உள்ளது முடிந்திருந்தால் மட்டுமே commit (retire) ஆகி architectural நிலைக்கு எழுதப்படுகிறது. இது இரண்டு விஷயங்களை இலவசமாகத் தருகிறது:

    • துல்லியமான விதிவிலக்குகள் (precise exceptions) — I1 ஒரு page fault-ஐ (பதிவு 24) எழுப்பினால், I3, I4 ஏற்கனவே கணக்கிட்டு முடித்திருந்தாலும் இன்னும் commit ஆகவில்லை; அவற்றின் முடிவுகள் நிராகரிக்கப்படுகின்றன. இயக்க அமைப்புக்கு “I1-க்கு முன் உள்ள அனைத்தும் முடிந்தது, பின் உள்ள எதுவும் நடக்கவில்லை” என்ற சுத்தமான படம் கிடைக்கிறது.
    • தவறான கிளை ஊகத்திலிருந்து மீட்பு — பதிவு 14-இன் misprediction-இல், அந்தக் கிளைக்குப் பின்னால் உள்ள ROB பதிவுகள் அனைத்தும் அழிக்கப்படுகின்றன, RAT பழைய நிலைக்குத் திரும்புகிறது.

    ஒரு சுழற்சி-வாரியான சுவடு#

    அனுமானங்கள்: ஒரு சுழற்சிக்கு ஒரு அறிவுறுத்தல் issue; load (miss) execute-க்கு 4 சுழற்சிகள், கூட்டல் 1; முடிவு அடுத்த சுழற்சியில் CDB-இல்; commit ஒரு சுழற்சிக்கு 4 வரை, ஆனால் வரிசையில் மட்டும்.

    அறிவுறுத்தல் Issue Execute CDB-இல் முடிவு Commit
    I1 (load) 1 2–5 6 7
    I2 (P10 தேவை) 2 7 8 9
    I3 (சுதந்திரம்) 3 4 5 9
    I4 (P12 தேவை) 4 6 7 9

    I3, I4 இரண்டும் I1 நினைவகத்துக்குக் காத்திருக்கும் போதே கணக்கிட்டு முடிக்கின்றன (சுழற்சி 4, 6), ஆனால் I2 commit ஆகும் சுழற்சி 9 வரை வரிசையில் காத்திருந்து, அதே சுழற்சியில் commit ஆகின்றன. ஒப்பீட்டுக்கு, அதே விதிகளுடன் in-order இயந்திரத்தில் I2 சுழற்சி 7-இல், I3 8-இல் execute ஆகும்; I4 I3-இன் முடிவுக்காக (CDB-இல் 9) காத்திருந்து 10-இல் execute ஆகி, அதன் முடிவு 11-இல் வரும். இங்கே சேமிப்பு மூன்று சுழற்சிகள்தான் (கடைசி முடிவு சுழற்சி 8 எதிர் 11) — ஆனால் miss 4 சுழற்சிகள் அல்ல, DRAM-க்கு 100-க்கு மேல் சுழற்சிகள் (பதிவு 35) என்றால், அந்த நேரத்தில் பின்னால் உள்ள டஜன் கணக்கான சுதந்திர அறிவுறுத்தல்கள் முடிந்துவிடும். அதனால்தான் நவீன CPU-களின் ROB-கள் நூற்றுக்கணக்கான பதிவுகள் கொண்டவை: miss-இன் நிழலில் முடிந்தவரை அதிக வேலையை ஒளித்துவைக்க.

    Tomasulo-வின் மைய யோசனை#

    “தயாரானபோதெல்லாம் execute” — reservation stations, tag-கள், common data bus — IBM System/360 Model 91 floating-point unit-க்கான Robert Tomasulo-வின் algorithm (1967-இல் வெளியிடப்பட்டது). மூல Tomasulo வடிவமைப்பில் reorder buffer இல்லை, எனவே அதன் விதிவிலக்குகள் துல்லியமற்றவை; “கண்டிப்பாக வரிசையில் commit” என்ற பாதி பின்னர் சேர்ந்தது — J. E. Smith மற்றும் A. R. Pleszkun-இன் 1985 precise-interrupts ஆய்வு reorder buffer யோசனையை முன்வைத்தது. இரண்டும் சேர்ந்ததே அதன்பிறகு கிட்டத்தட்ட ஒவ்வொரு உயர்-செயல்திறன் out-of-order CPU-இன் கருத்தியல் மையம். அது விலை உயர்ந்ததும்: renaming அட்டவணைகள், reservation stations, மற்றும் ROB பரப்பும் மின்சாரமும் செலவாகும். அந்த இயந்திரத்தை மேலும் சேர்ப்பது குறைந்துவரும் வருவாயைக் கொடுக்கிறது — அடுத்த பதிவு நேருக்கு நேர் மோதும் சுவர்.

    இப்போது முயல்க. கீழே உள்ள mini-CPU in-order, single-cycle இயந்திரம் — ஆனால் சார்புகளைப் பார்க்க அது சிறந்த இடம், ஏனெனில் அதில் ஒரே ஒரு பணிப் பதிவேடு A (accumulator) தான் உள்ளது. ஏற்கனவே ஏற்றப்பட்ட நிரல்:

    0: LDI 5    ; A ← 5
1: STA 14   ; mem[14] ← A
2: LDI 8    ; A ← 8
3: ADD 14   ; A ← A + mem[14]
4: STA 15   ; mem[15] ← A
5: LDA 15   ; A ← mem[15]
6: OUT
7: HLT
    1. Step-ஐ இரண்டு முறை அழுத்தி mem[14] = 5 ஆனதைப் பாருங்கள்; நான்காவது Step-க்குப் பின் A = 0D (hex, = 13).
    2. காகிதத்தில் ஒவ்வொரு ஜோடிக்கும் சார்பு வகையைக் குறியுங்கள்: 0→1 RAW (A); 1→2 WAR (STA 14 A-ஐப் படிக்கிறது, LDI 8 A-ஐ மேலெழுதுகிறது); 0→2 WAW (இரண்டும் A-ஐ எழுதுகின்றன); 1→3 RAW நினைவகம் வழியாக (mem[14]); 2→3 RAW (A).
    3. இப்போது A-ஐ மறுபெயரிடுங்கள்: 0 எழுதுவது A→P1, 2 எழுதுவது A→P2, 3 எழுதுவது A→P3, 5 எழுதுவது A→P4. மறுபெயரிட்ட பின், அறிவுறுத்தல் 2 (P2 ← 8) அறிவுறுத்தல் 0, 1 உடன் ஒரே நேரத்தில் ஓடலாம் என்பதைக் காணுங்கள் — பெயர்ச் சண்டைகள் மறைந்தன; உண்மைச் சார்புகள் மட்டும் எஞ்சுகின்றன — பதிவேடு வழியாக 0→1 (P1), 2→3 (P2), மற்றும் நினைவகம் வழியாக 1→3 (mem[14]).
    4. பாடம்: ஒரே accumulator கொண்ட ISA-வில் கிட்டத்தட்ட ஒவ்வொரு அறிவுறுத்தலும் A-இன் பெயரில் மோதுகிறது. பல பதிவேடுகள் கொண்ட ISA-களும் (பதிவு 11), வன்பொருள் renaming-உம் இந்த மோதல்களை நீக்கவே.
