    x86 vs RISC பிளவு

    ஜனவரி 1, 2026

    பதிவு 11 CISC மற்றும் RISC-ஐ தத்துவங்களாகப் பெயரிட்டது. இந்தப் பதிவு அவை வணிகரீதியாகப் போட்டியிட்டபோது என்ன நடந்தது — மற்றும் ஏன் “சுத்தமான” ISA வெறுமனே வெல்லவில்லை.

    தமிழ் இடைவெளிக் குறிப்பு: x86, RISC பற்றித் தமிழில் எழுத்து விளக்கம் கிடைக்கவில்லை; காணொளிச் சான்று YouTube தேடல் முடிவுகள் மட்டும் — காணொளிகள் பார்க்கப்படவில்லை. RISC தரப்பின் வாதம் “அனுபவ ரீதியானது” என்று ஆங்கிலப் பதிவு சொல்கிறது; அதை இங்கே ஒரு உண்மையான நிரலின் instruction எண்ணிக்கையால் சோதிக்கிறோம்: எங்கள் பணிக் கணினியில் (Linux, x86-64) உள்ள /bin/ls (x86-64) நிரலை objdump மூலம் disassemble செய்து எண்ணியது. x86 குறியாக்கங்கள் capstone disassembler மூலம் சரிபார்க்கப்பட்டவை; mini-CPU நிரல் lab-இன் simulator-இல் ஓட்டப்பட்டது. “எடுத்துக்காட்டு மதிப்பு” என்று குறிக்கப்பட்டவை கணக்குக்காகத் தேர்ந்தெடுத்தவை.

    முதலில் சொற்கள்#

    • x86: Intel 8086-இலிருந்து வந்த CISC ISA குடும்பம்; இன்றைய 64-பிட் வடிவம் x86-64.
    • RISC வரிசை: MIPS, SPARC, PowerPC போன்ற நிலைத்த-நீள, load/store ISA-கள்.
    • Micro-operation, µop (நுண்செயல்): CPU-க்குள் decoder உருவாக்கும் எளிய, நிலைத்த-வடிவ உள் செயல்; ISA-வுக்குத் தெரியாதது.
    • Decoder (குறிவிலக்கி): x86 byte-களைப் படித்து µop-களாக மாற்றும் முன்முனை.
    • பின்னோக்கு இணக்கம் (backward compatibility): புதிய chip பழைய binary-களை மாற்றமின்றி ஓட்ட வேண்டும் என்ற கட்டுப்பாடு.
    • நிறுவப்பட்ட அடித்தளம் (installed base): ஏற்கனவே பயன்பாட்டில் உள்ள மென்பொருளும் கணினிகளும்.
    • Instruction கலவை (instruction mix): ஒரு நிரலில் எந்த வகை instruction-கள் எவ்வளவு பங்கு என்பது.

    RISC வாதம்#

    1980களின் ஆரம்பம்: CISC சிக்கலுக்கு எதிர்வினையாக RISC — Berkeley வேலை SPARC நோக்கி, Stanford MIPS நோக்கி, POWER/PowerPC-க்கு உணவளித்த IBM வேலை. கூற்று அனுபவபூர்வமானது: சிக்கலான CISC ops தொகுக்கப்பட்ட குறியீட்டில் அடிக்கடி அரிதாகவே பயன்படுத்தப்பட்டன, அவை தேவைப்பட்ட decode வன்பொருள் சிலிகானை எரித்து இந்தக் கட்டம் ஏற்கனவே உள்ளடக்கிய pipeline-களைச் சிக்கலாக்கியது. ISA-ஐ எளிய, நிலைத்த-நீள, சீரான அறிவுறுத்தல்களுக்குச் சுருக்குங்கள்; சிலிகானைப் பதிவேடுகள், வேகமான pipeline-கள், சிறந்த cache-களுக்குச் செலவழிக்கவும்.

    MIPS, SPARC, மற்றும் PowerPC அனைத்தும் வெளியிடப்பட்டன. ஒரு காலத்திற்கு அவை தூய compute benchmark-களில் x86-ஐ வென்றன, குறிப்பாக workstations மற்றும் சேவையகங்களில்.

    அனுபவச் சோதனை: ஒரு உண்மையான நிரலில் எந்த instruction-கள்?#

    RISC தரப்பின் கூற்று: compiler உருவாக்கும் குறியீட்டில் சிக்கலான CISC செயல்கள் அரிதாகவே வருகின்றன. சோதிப்போம். objdump -d /bin/ls — எங்கள் பணிக் கணினியில் (Linux, x86-64) உள்ள 158,632 byte x86-64 நிரல் — 22,874 instruction-கள். அதிகம் வரும் mnemonic-கள் (objdump-இன் AT&T பெயர்களில்; jmp எண்ணிக்கையில் 11 notrack jmp-உம் அடங்கும்):

    Mnemonic எண்ணிக்கை பங்கு வகை
    mov 5,913 25.9% தரவு நகர்த்தல்
    jmp 1,286 5.6% தாவல்
    call 1,261 5.5% அழைப்பு
    cmp 1,199 5.2% ஒப்பீடு
    je 1,127 4.9% நிபந்தனைத் தாவல்
    test 1,051 4.6% ஒப்பீடு
    lea 954 4.2% முகவரிக் கணக்கு
    jne 822 3.6% நிபந்தனைத் தாவல்
    pop / push 813 / 742 3.6% / 3.2% stack நகர்த்தல்
    xor 754 3.3% பதிவேட்டைப் பூஜ்ஜியமாக்கல் (754-இல் 720, xor %eax,%eax போல ஒரு பதிவேட்டைத் தன்னுடனேயே)
    add / sub 658 / 587 2.9% / 2.6% கணக்கு

    கூட்டிப் பார்ப்போம்:

    • தரவு நகர்த்தல் (mov + push + pop + lea): 5,913 + 813 + 742 + 954 = 8,422 → 8,422 ÷ 22,874 ≈ 37%
    • தாவல்/அழைப்பு (jmp + call + je + jne): 4,496 → ≈ 20%; ஒப்பீடு (cmp + test): 2,250 → ≈ 10%
    • rep முன்னொட்டு கொண்ட string செயல் (ஒரே instruction நினைவகத் தொகுதியை நகர்த்தும் CISC பாணி): முழு நிரலில் 1 மட்டும்.

    ஒரு நிரல் ஒரு மாதிரி மட்டுமே, ஆனால் வடிவம் தெளிவு: பெரும்பகுதி எளிய நகர்த்தல், ஒப்பீடு, தாவல். அவற்றை வேகமாக்குவதில் silicon-ஐச் செலவிடு — 1980-இல் RISC தரப்பு வைத்த வாதம் இதுதான்.

    நீளங்களும் அதே கதை சொல்கின்றன. அதே நிரலில் instruction நீளப் பரவல் (objdump வெளியீட்டிலிருந்து):

    நீளம் (byte) 1 2 3 4 5 6 7 அல்லது அதிகம்
    பங்கு 5.2% 17.9% 22.7% 13.2% 20.0% 9.9% 11.1%

    சராசரி ≈ 4.08 byte (93,406 byte ÷ 22,874). அதாவது x86 குறியீடு சராசரியாக ஒரு RISC-V instruction-இன் 4 byte அளவுதான் — ஆனால் ஒவ்வொரு instruction-இன் எல்லையும் decode செய்த பிறகே தெரியும் (பதிவு 11).

    x86 ஏன் தரையை வைத்திருந்தது#

    x86-இன் விளிம்பு ஒருபோதும் நேர்த்தி அல்ல — அது ஏற்கனவே IBM PC இணக்கத்தன்மையில் அமர்ந்திருந்த மென்பொருள். அது desktop தரநிலையாக மாறியதும், மிகப்பெரிய நிறுவப்பட்ட அடித்தளம் x86-இல் மட்டுமே ஓடியது. பின்னோக்கு இணக்கத்தன்மை ஒரு அகழி ஆனது: புதிய சிப்கள் பழைய binaries-ஐ ஓட்ட வேண்டும், எனவே ISA-வை RISC-பாணியில் சுத்தமாக மறுவடிவமைக்க முடியவில்லை — wart-க்கு wart நீட்டிக்க மட்டுமே, Intel மற்றும் பின்னர் AMD மேற்பரப்பு இருந்தாலும் implementation-ஐ வேகமாக்கியபோது.

    உண்மையான தீர்வு: நவீன x86 CISC ops-ஐ out-of-order core-இல் நேரடியாகச் செயல்படுத்துவதில்லை. ஒரு decoder ஒவ்வொரு x86 அறிவுறுத்தலையும் ஒன்று அல்லது அதற்கு மேற்பட்ட நிலைத்த-வடிவ உள் micro-operations (µops) ஆக மொழிபெயர்க்கிறது — RISC-போன்றவை — மற்றும் அவை பதிவு 16-இன் reservation stations, ROB, மற்றும் execution units வழியாக ஓடுகின்றன. வெளியே: CISC-இணக்கமானது. உள்ளே: மொழிபெயர்ப்பு அடுக்கின் கீழ் RISC-பாணி pipeline.

    உள்ளே RISC: ஒரு instruction µop-களாக#

    add dword ptr [rbx], eax (byte-கள் 01 03, capstone சரிபார்த்தது) — நினைவகத்தில் உள்ள எண்ணுடன் eax-ஐக் கூட்டி அங்கேயே சேமி. ஒரு out-of-order core-க்குள் இது கருத்தளவில் மூன்று எளிய செயல்கள் (சரியான பிரிவும் எண்ணிக்கையும் ஒவ்வொரு CPU வடிவமைப்புக்கும் மாறும் — இது விளக்கத்துக்கான பிரிப்பு):

    µop செயல் RISC-V-இல் ஒத்தது
    1 tmp ← நினைவகம்[rbx] (load) lw
    2 tmp ← tmp + eax (ALU) add
    3 நினைவகம்[rbx] ← tmp (store) sw

    பதிவு 11-இல் RISC-V-க்கு எழுதிய மூன்று instruction-கள் இவைதான். வித்தியாசம்: RISC-V-இல் compiler இந்த மூன்றையும் நிரலிலேயே எழுதுகிறது (12 byte); x86-இல் நிரலில் 2 byte, மூன்றாகப் பிரிப்பது decoder-இன் வேலை. பதிவு 16-இன் reservation station-களும் ROB-உம் பார்ப்பது µop-களை மட்டுமே.

    பதிவேடுகள்: x86-64 16 பொதுப் பதிவேடுகள் (rax … r15). பழைய 8-க்கு மேல் உள்ளவற்றை அணுக ஒரு முன்னொட்டு byte (REX) தேவை: add eax, ebx = 01 D8 (2 byte), ஆனால் add r8, r15 = 4D 01 F8 (3 byte) — பழைய குறியாக்கத்தை உடைக்காமல் நீட்டியதன் விலை (capstone சரிபார்த்தது). RISC-V 32 பதிவேடுகளையும் முதலிலிருந்தே 5-பிட் புலங்களில் வைத்தது (பதிவு 11). “நீட்டப்பட்டது, மரு மருவாக” என்று ஆங்கிலப் பதிவு சொல்வதன் ஒரு சிறு உதாரணம்.

    இணக்கத்தின் பொருளாதாரம், ஒரு கணக்கில்#

    ஒரு நிறுவனத்திடம் x86-க்கு மட்டும் compile செய்த 200 நிரல்கள்; ஒவ்வொன்றையும் வேறு ISA-க்கு மாற்றிச் சோதிக்க சராசரி 3 வாரம் (எடுத்துக்காட்டு மதிப்புகள்). புதிய RISC கணினி 30% வேகம் என்றாலும், மாற்றச் செலவு 200 × 3 = 600 வார உழைப்பு. ஒரு x86 chip அடுத்த ஆண்டே 30% வேகமாக வந்தால் அந்தச் செலவு பூஜ்ஜியம். ஆயிரக்கணக்கான நிறுவனங்களில் இதே கணக்கு — அதுதான் “moat”.

    வைத்திருக்க வேண்டிய முறை#

    வெல்லும் ISA-கள் அரிதாகவே தொழில்நுட்பத் தகுதியால் மட்டும் வெல்கின்றன. இணக்கத்தன்மை, ecosystem lock-in, மற்றும் உற்பத்தி அளவு வழக்கமாகச் சுத்தமான காகிதக் கட்டமைப்பை வெல்கின்றன. அதே இயக்கம் அடுத்து ARM-இன் licensing மாதிரிக்கு எதிராக RISC-V-இன் திறந்த ISA-வுடன் தோன்றுகிறது — ஒரு அறிவுறுத்தல் தொகுப்பைச் சுற்றிய வணிக மாதிரி குறியாக்கத்தைப் போலவே முக்கியமாக இருக்கலாம்.

    இப்போது முயல்க: CISC instruction-ஐ RISC படிகளாக விரியுங்கள். Mini-CPU-க்கு “நினைவகம்[15] ← நினைவகம்[15] + நினைவகம்[14]” போன்ற ஒரே CISC instruction இல்லை. ஒரு x86 decoder செய்வதுபோல அதை எளிய படிகளாக நீங்களே விரியுங்கள். மூல உரையை இப்படி மாற்றுங்கள்:

    LDI 5
STA 14
LDI 8
STA 15
LDA 15
ADD 14
STA 15
LDA 15
OUT
HLT

    முதல் நான்கு வரிகள் தரவை அமைக்கின்றன (mem[14] = 5, mem[15] = 8). அடுத்த மூன்று (LDA 15, ADD 14, STA 15) தான் அந்த ஒரே “CISC” செயலின் load / ALU / store µop-கள். Assemble, பிறகு Run: பத்து படிகளில் HALT, Output 13; Step செய்தால் IR வரிசை 55 4E 58 4F 1F 2E 4F 1F E0 F0 (simulator-இல் சரிபார்த்தது). பிறகு மேலே உள்ள /bin/ls அட்டவணையைப் போல எண்ணுங்கள்: பத்தில் எத்தனை தரவு நகர்த்தல் (LDI, LDA, STA)? (விடை: 7 — மீதி ADD, OUT, HLT.)
