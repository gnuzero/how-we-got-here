    Virtual Memory மற்றும் Multitasking

    ஜனவரி 1, 2026

    Time-sharing (பதிவு 22) பல process-கள் ஒரே இயந்திரத்தில் — தோற்றத்தில் ஒரே நேரத்தில் — ஓட வேண்டும். உடனடி பிரச்சினை: ஒவ்வொரு process-ம் எந்த physical முகவரியையும் சுதந்திரமாகப் படித்து எழுத முடிந்தால், ஒரு பிழை அல்லது தீங்கிழைக்கும் நிரல் மற்றொன்றின் தரவை, அல்லது OS தன்னைக் கெடுக்கலாம். Virtual memory ஒவ்வொரு process-க்கும் முழு address space-ஐச் சொந்தமாக்கிய மாயையைக் கொடுத்து அதைத் தடுக்கிறது, OS கீழே உண்மையை நிர்வகிக்கும்போது.

    தமிழில் இந்தத் தலைப்புக்குக் கிடைப்பது பெரும்பாலும் “நினைவக மேலாண்மை”, “page” என்ற அறிமுக வரையறைகள் மட்டுமே (பள்ளிப் பாடநூலின் ஒரு பகுதி, தமிழ் விக்கிப்பீடியாவில் “page” பற்றிய ஒரு சிறு கட்டுரை). ஒரு முகவரி எப்படி மொழிபெயர்க்கப்படுகிறது, page table ஏன் பல நிலைகளாக அமைகிறது, TLB ஏன் தேவை, page fault-இன்போது உண்மையில் என்ன நடக்கிறது, context switch என்ன செலவாகிறது — இவற்றுக்கு எண்களோடு கூடிய தமிழ் எழுத்து விளக்கம் இந்தத் தணிக்கையில் கிடைக்கவில்லை. இந்தப் பக்கம் அவற்றை அடிப்படையிலிருந்து விளக்குகிறது.

    மைய மாயை#

    ஒவ்வொரு process-ம் முழு virtual address space-ஐப் பார்க்கிறது — 64-பிட் அமைப்பில், physical RAM-ஐ விட மிகப் பெரியது. அது ஒரு virtual முகவரியைக் குறிப்பிடும்போது, வன்பொருள் (Memory Management Unit, அல்லது MMU) OS பராமரிக்கும் page table வழியாக physical முகவரிக்கு மொழிபெயர்க்கிறது. இரண்டு process-களும் “virtual முகவரி 0x1000”-ஐக் குறிப்பிட்டு இரண்டு வெவ்வேறு physical frame-களைத் தாக்கலாம் — ஒன்று மற்றொன்றின் நினைவகத்தைப் பார்க்க முடியாது, ஒவ்வொரு process-இன் உள்ளேயிருந்தும் சாதாரண, தனிப்பட்ட உரிமை போல் தெரிந்தாலும்.

    முதலில் சொற்கள்#

    • முகவரி (address) — நினைவகத்தில் ஒரு பைட்டின் இடத்தைக் குறிக்கும் எண். 32-பிட் முகவரி 2³² = 4,294,967,296 வெவ்வேறு பைட்டுகளைக் குறிக்க முடியும் (4 GiB).
    • முகவரி வெளி (address space) — ஒரு process பயன்படுத்தக்கூடிய எல்லா முகவரிகளின் தொகுப்பு.
    • Virtual முகவரி (மெய்நிகர் முகவரி) — நிரல் தன் அறிவுறுத்தல்களில் பயன்படுத்தும் முகவரி. Physical முகவரி (இயல் முகவரி) — RAM சிப்களுக்கு உண்மையில் அனுப்பப்படும் முகவரி.
    • Page (பக்கம்) — virtual முகவரி வெளியின் நிலையான அளவுத் துண்டு; frame (சட்டகம்) — physical RAM-இன் அதே அளவுத் துண்டு. ஒரு page ஒரு frame-இல் “அமர்கிறது”.
    • Page table (பக்க அட்டவணை) — “இந்த virtual page எந்த frame-இல் உள்ளது” என்று சொல்லும், OS பராமரிக்கும் அட்டவணை. ஒவ்வொரு வரியும் ஒரு PTE (page table entry).
    • MMU (Memory Management Unit, நினைவக மேலாண்மை அலகு) — ஒவ்வொரு நினைவக அணுகலிலும் virtual முகவரியை physical முகவரியாக மாற்றும் CPU-க்குள் உள்ள வன்பொருள்.

    முக்கியமான பிரிவு: கொள்கை (எந்த page எந்த frame-இல், யாருக்கு அனுமதி) OS-இன் வேலை; ஒவ்வொரு அணுகலுக்குமான மொழிபெயர்ப்பு வன்பொருளின் வேலை. மென்பொருள் ஒவ்வொரு load/store-ஐயும் சரிபார்த்தால் இயந்திரம் நின்றுவிடும்; அதனால்தான் MMU.

    ஒரு முகவரியை மொழிபெயர்த்தல்: படிப்படியாக#

    32-பிட் virtual முகவரிகள், 4 KiB (4096 பைட்) pages என்று எடுத்துக்கொள்வோம். 4096 = 2¹², எனவே ஒரு page-க்குள் எந்த பைட் என்பதைச் சொல்ல கீழ் 12 பிட்கள் போதும் — அதுவே offset (இடப்பெயர்ச்சி). மீதமுள்ள மேல் 20 பிட்கள் எந்த page என்று சொல்லும் — VPN (virtual page number).

    எடுத்துக்காட்டு (எண்கள் விளக்கத்துக்கான எடுத்துக்காட்டு மதிப்புகள்): virtual முகவரி 0x00403A7C.

    0x00403A7C = 0000 0000 0100 0000 0011 | 1010 0111 1100
             <------ VPN (20 பிட்) --->  <- offset (12) ->
VPN    = 0x00403 = 1027
offset = 0xA7C   = 2684

    Page table-இல் வரி 1027-ஐப் பார்க்கிறோம். அங்கே “frame 0x1F2” (= 498) என்று இருக்கிறது என்று வைத்துக்கொள்வோம். Physical முகவரி = frame எண்ணை offset-க்கு முன் ஒட்டுவது:

    physical = 0x1F2 × 4096 + 0xA7C
         = 498 × 4096 + 2684
         = 2,039,808 + 2684 = 2,042,492 = 0x1F2A7C

    Offset மாறவே இல்லை என்பதைக் கவனியுங்கள் — மொழிபெயர்ப்பு page எண்ணை மட்டுமே மாற்றுகிறது. அதனால்தான் page அளவு 2-இன் அடுக்காக இருக்கிறது: பிரிப்பதும் ஒட்டுவதும் வெறும் பிட் வெட்டுதல், வகுத்தல் அல்ல.

    இப்போது இரண்டு process-கள். A-வின் page table-இல் VPN 1027 → frame 498; B-யின் page table-இல் VPN 1027 → frame 7301 (எடுத்துக்காட்டு மதிப்புகள்). இரண்டும் “0x00403A7C” என்று எழுதுகின்றன; A-வின் எழுத்து physical 0x1F2A7C-க்குச் செல்கிறது, B-யினுடையது முற்றிலும் வேறு இடத்துக்கு. இதுதான் மேலே சொன்ன “மாயை” — ஒவ்வொரு process-க்கும் சொந்த page table, எனவே சொந்த உலகம். Context switch-இன்போது OS செய்வது, MMU எந்த அட்டவணையைப் பார்க்க வேண்டும் என்று சொல்லும் ஒரு பதிவேட்டை (x86-இல் CR3) மாற்றுவது.

    Page table எவ்வளவு பெரியது? பலநிலை அட்டவணைகள்#

    தட்டையான (flat) அட்டவணை: 20-பிட் VPN → 2²⁰ = 1,048,576 வரிகள்; ஒவ்வொரு PTE-யும் 4 பைட் என்றால் 4 MiB ஒரு process-க்கு — நிரல் மூன்றே page-களைப் பயன்படுத்தினாலும். 100 process-கள் = 400 MiB வெறும் அட்டவணைகளுக்கு. ஏற்க முடியாது.

    தீர்வு: அட்டவணையையே pages-ஆக வெட்டி, பயன்படாத பகுதிகளை உருவாக்காமலே விடுவது. செவ்வியல் 32-பிட் x86 திட்டம் (PAE இல்லாமல்) 20-பிட் VPN-ஐ 10 + 10 ஆகப் பிரிக்கிறது:

    | 10 பிட்: directory index | 10 பிட்: table index | 12 பிட்: offset |

    மேல் நிலை page directory 1024 வரிகள் × 4 பைட் = 4 KiB; ஒவ்வொரு வரியும் ஒரு இரண்டாம் நிலை page table-ஐச் சுட்டுகிறது (அதுவும் 4 KiB, 1024 PTE-கள், மொத்தம் 1024 × 4 KiB = 4 MiB virtual வெளியை உள்ளடக்கும்). நம் VPN 0x00403 = 0000000001 0000000011 → directory index 1, table index 3 (சரிபார்ப்பு: 1 × 1024 + 3 = 1027 ✓).

    குறியீடு கீழ் முகவரிகளிலும், stack மேல் முகவரிகளிலும் உள்ள ஒரு சிறிய நிரலுக்கு: 1 directory + 2 page tables = 3 × 4 KiB = 12 KiB — 4 MiB-க்குப் பதிலாக. பயன்படாத directory வரிகள் “not present” என்று இருக்கின்றன; அவற்றுக்கு அட்டவணையே இல்லை.

    64-பிட் x86 (x86-64) இதையே ஆழமாக்குகிறது: பொதுவான அமைப்பில் 48-பிட் virtual முகவரி = 9 + 9 + 9 + 9 + 12. ஒவ்வொரு நிலை அட்டவணையும் 512 வரிகள் × 8 பைட் = 4096 பைட் — சரியாக ஒரு page. 2⁴⁸ பைட் = 256 TiB virtual வெளி. விலை: ஒரு மொழிபெயர்ப்புக்கு நான்கு அட்டவணைகளைப் படிக்க வேண்டும் — page walk — அதாவது ஒரு load-க்கு நான்கு கூடுதல் நினைவக அணுகல்கள்.

    TLB: மொழிபெயர்ப்புக்கான Cache#

    ஒவ்வொரு load-க்கும் நான்கு கூடுதல் அணுகல்கள் என்றால் நினைவகம் ஐந்து மடங்கு மெதுவாகும். பதில் பதிவு 15-இன் அதே யோசனை: அண்மையில் பயன்பட்ட மொழிபெயர்ப்புகளை ஒரு சிறிய, வேகமான cache-இல் வையுங்கள். அதன் பெயர் TLB (translation lookaside buffer). TLB hit ஆனால் page walk இல்லை.

    கணக்கு (எடுத்துக்காட்டு மதிப்புகள்): ஒரு நினைவக அணுகல் 100 ns; TLB தேடல் நேரம் புறக்கணிக்கத்தக்கது; miss-இல் 4-நிலை walk (4 × 100 ns) பிறகு உண்மையான அணுகல் (100 ns).

    சராசரி = hit விகிதம் × 100 + miss விகிதம் × (400 + 100)

    • TLB இல்லை: ஒவ்வொரு அணுகலும் 500 ns.
    • 99% hit: 0.99 × 100 + 0.01 × 500 = 99 + 5 = 104 ns — walk-இன் செலவு கிட்டத்தட்ட மறைகிறது.

    TLB reach (TLB ஒரே நேரத்தில் உள்ளடக்கும் நினைவகம்) = வரிகள் × page அளவு. 64 வரிகள் (எடுத்துக்காட்டு மதிப்பு) × 4 KiB = 256 KiB மட்டுமே. அதே 64 வரிகள் 2 MiB huge pages-உடன் = 128 MiB. பெரிய தரவுத்தளங்களும் அறிவியல் கணக்குகளும் huge pages கேட்பதற்கு இதுவே காரணம்.

    TLB-இல் ஒரு சிக்கல்: context switch-இல் page table மாறுகிறது, எனவே பழைய process-இன் மொழிபெயர்ப்புகள் தவறாகிவிடும். எளிய தீர்வு TLB-ஐ முழுவதும் அழிப்பது (flush) — புதிய process மீண்டும் miss-களிலிருந்து தொடங்குகிறது. நவீன CPU-கள் ஒவ்வொரு TLB வரியிலும் ஒரு process அடையாளக் குறியை (ASID; x86-இல் PCID) வைத்து அந்த flush-ஐத் தவிர்க்கின்றன.

    PTE-க்குள் என்ன இருக்கிறது#

    ஒரு PTE frame எண்ணை மட்டுமல்ல, சில கொடிப் பிட்களையும் (flag bits) சுமக்கிறது. x86-இல் முக்கியமானவை:

    பிட் பொருள் யார் பயன்படுத்துகிறார்
    Present இந்த page இப்போது RAM-இல் உள்ளதா 0 என்றால் அணுகல் → page fault
    Read/Write எழுத அனுமதி உண்டா குறியீட்டு pages-ஐப் படிக்க-மட்டும் ஆக்க
    User/Supervisor சாதாரண நிரல் அணுகலாமா kernel நினைவகத்தைப் பாதுகாக்க
    Accessed அண்மையில் தொடப்பட்டதா எந்த page-ஐ வெளியேற்றலாம் என OS தீர்மானிக்க
    Dirty எழுதப்பட்டதா swap-க்கு எழுத வேண்டுமா என்று அறிய
    NX (no-execute) இதை அறிவுறுத்தலாக ஓட்டலாமா தரவுப் பகுதியில் தீங்குக் குறியீடு ஓடுவதைத் தடுக்க

    கீழே உள்ள “Isolation பாதுகாப்பாக” பகுதி பேசும் வன்பொருள் சரிபார்ப்பு இதுதான்: அனுமதி இல்லாத ஒவ்வொரு அணுகலையும் MMU அதே கணத்தில் பிடித்து OS-க்கு trap செய்கிறது.

    Pages, Faults, Swap#

    நினைவகம் நிலையான அளவு pages-ஆகப் பிரிக்கப்படுகிறது (பல கட்டமைப்புகளில் பொதுவாக 4 KB; பெரிய “huge pages” உள்ளன). Page table virtual pages-ஐ physical frames-க்கு வரைபடமாக்குகிறது. முக்கியமாக, ஒவ்வொரு virtual page-க்கும் எல்லா நேரத்திலும் frame தேவையில்லை — “not present” எனக் குறிக்கவும், குறிப்பு page fault ஆக OS-க்குள் trap ஆகும். OS பக்கத்தை disk-இலிருந்து ஏற்றலாம் (குறியீடு மற்றும் தரவின் lazy கொண்டுவருதல்), அல்லது உண்மையான பிழையாகக் கருதலாம் (ஒருபோதும் வழங்கப்படாத நினைவகத்தை அணுகுதல் — segmentation fault-க்கு ஒரு பொதுவான பாதை).

    அதே பொறிமுறை swapping-ஐ இயக்குகிறது: நினைவக அழுத்தத்தின் கீழ், குளிர்ந்த page-ஐ disk-இல் எழுதி, not-present எனக் குறித்து, frame-ஐ விடுவிக்கவும். அமைப்பு physically இருப்பதை விட அதிக RAM இருப்பது போல் நடந்துகொள்கிறது — அந்த page மீண்டும் தொடப்பட்டால் disk-வேகம் செலவில். ஏராளமான RAM கனமான swapping-ஐ முன்பு இருந்ததை விடக் குறைவாக ஆக்குகிறது; பொறிமுறை அடிப்படையாகவே இருக்கிறது.

    Page Fault: ஒரு படிப்படியான சுவடு#

    நிரல் ஒரு முகவரியைத் தொடுகிறது; அதன் PTE-இல் Present = 0. என்ன நடக்கிறது:

    படி யார் என்ன
    1 CPU அறிவுறுத்தல் virtual முகவரியை அணுக முயல்கிறது
    2 MMU TLB miss → page walk → PTE-இல் Present = 0
    3 CPU அறிவுறுத்தலை நடுவில் நிறுத்தி, page fault trap மூலம் kernel-க்குள் தாவுகிறது
    4 Kernel இந்த முகவரி process-க்கு ஒதுக்கப்பட்ட பகுதியா என்று தன் பதிவுகளில் சரிபார்க்கிறது
    5a Kernel (செல்லுபடி) ஒரு frame-ஐ ஒதுக்கி, தேவைப்பட்டால் disk-இலிருந்து உள்ளடக்கத்தைப் படித்து, PTE-ஐ நிரப்பி Present = 1 ஆக்குகிறது
    5b Kernel (செல்லாதது) process-க்கு segmentation fault சமிக்ஞை (Linux-இல் SIGSEGV) — பொதுவாக நிரல் முடிகிறது
    6 CPU அதே அறிவுறுத்தலை மீண்டும் ஓட்டுகிறது — இம்முறை வெற்றி

    படி 6 நுட்பமானது: fault-க்குப் பிறகு அறிவுறுத்தல் எதுவும் நடக்காதது போல் மீண்டும் தொடங்க வேண்டும். அதற்கு CPU துல்லியமான விதிவிலக்குகளை (precise exceptions, பதிவு 16) வழங்க வேண்டும்.

    Disk படிப்பு தேவைப்படும் fault major fault; frame மட்டும் ஒதுக்கினால் போதுமானது (எடுத்துக்காட்டாக முதன்முறை தொடப்படும் பூஜ்ய நினைவகம், அல்லது ஏற்கனவே RAM-இல் உள்ள பகிரப்பட்ட நூலகப் பக்கம்) minor fault.

    Page fault எவ்வளவு விலை? (எடுத்துக்காட்டு மதிப்புகள்) நினைவக அணுகல் 100 ns; disk-இலிருந்து page கொண்டுவர 8 ms = 8,000,000 ns. ஒரு லட்சம் அணுகல்களுக்கு ஒருமுறை (p = 1/100,000) major fault என்றால்:

    சராசரி = 100 + p × 8,000,000 = 100 + 80 = 180 ns

    ஒரு லட்சத்தில் ஒன்று என்ற “அரிய” நிகழ்வே நினைவகத்தை 80% மெதுவாக்குகிறது. மந்தநிலையை 10%-க்குள் (110 ns) வைக்க: p × 8,000,000 ≤ 10 → p ≤ 1 / 800,000. அதனால்தான் RAM போதாதபோது இயந்திரம் திடீரென ஊர்ந்து செல்கிறது — thrashing: நேரம் முழுவதும் page-களை உள்ளும் வெளியும் நகர்த்துவதில் போகிறது.

    Demand paging இதன் நல்ல பக்கம்: ஒரு நிரல் தொடங்கும்போது அதன் முழுக் குறியீடும் ஏற்றப்படுவதில்லை; முதன்முறை தொடப்படும் page மட்டும் fault வழியாக வருகிறது. Copy-on-write இன்னொரு பயன்: Unix fork() பெற்றோர் process-இன் pages-ஐ நகலெடுக்காமல், இரு process-களின் PTE-களையும் அதே frames-க்கு, படிக்க-மட்டும் என்று அமைக்கிறது; யாராவது எழுத முயலும்போது மட்டும் fault வந்து அந்த ஒரு page நகலெடுக்கப்படுகிறது.

    Multitasking: Context Switch என்ன செலவாகிறது#

    Process என்பது ஓடும் நிரல் + அதன் நிலை. அந்த நிலை — context — பதிவேடுகள், நிரல் கவுண்டர் (PC), stack pointer, மற்றும் page table-இன் அடிப்படை முகவரி. ஒரு CPU core ஒரு கணத்தில் ஒரு process-ஐ மட்டுமே ஓட்டுகிறது. Context switch: ஒரு process-இன் context-ஐச் சேமித்து மற்றொன்றினுடையதை ஏற்றுவது.

    யார் தூண்டுகிறார்கள்? ஒரு timer interrupt — வன்பொருள் கடிகாரம் சீரான இடைவெளியில் CPU-வை kernel-க்குள் இழுக்கிறது; kernel-இன் scheduler அடுத்து யார் என்று தீர்மானிக்கிறது. ஒரு process-க்கு ஒருமுறைக்குக் கிடைக்கும் நேரம் time slice (quantum).

    Round-robin சுவடு (எடுத்துக்காட்டு மதிப்புகள்): P1-க்கு 3 slices வேலை, P2-க்கு 1, P3-க்கு 2.

    Slice 1 2 3 4 5 6
    ஓடுவது P1 P2 P3 P1 P3 P1
    முடிந்தது — P2 — — P3 P1

    வெளியிலிருந்து பார்த்தால் மூன்றும் “ஒரே நேரத்தில்” முன்னேறுகின்றன — பதிவு 22-இன் time-sharing மாயை.

    செலவுக் கணக்கு (எடுத்துக்காட்டு மதிப்புகள்): ஒரு switch = 5 µs (பதிவேடுகளைச் சேமித்தல், scheduler, page table மாற்றம், பிறகு குளிர்ந்த cache/TLB-இன் miss-கள்). Overhead = switch / (slice + switch):

    • slice 10 ms: 5 / (10,000 + 5) ≈ 0.05% — கண்ணுக்குத் தெரியாது.
    • slice 50 µs: 5 / (50 + 5) ≈ 9.1% — CPU நேரத்தில் பத்தில் ஒரு பங்கு வெறும் மாற்றங்களுக்கு.

    சிறிய slice = விரைவான பதிலளிப்பு (தட்டச்சு செய்தவுடன் எழுத்து தோன்றும்); பெரிய slice = குறைந்த வீணடிப்பு. ஒவ்வொரு scheduler-உம் இந்த இரண்டுக்கும் இடையே சமரசம் செய்கிறது. நேரடிச் செலவைவிட மறைமுகச் செலவு பெரும்பாலும் பெரியது: புதிய process-இன் தரவு cache-இலும் TLB-இலும் இல்லை, எனவே அது முதல் சில நூறு மைக்ரோவிநாடிகள் miss-களோடு தவழ்கிறது.

    Isolation பாதுகாப்பாக#

    Multitasking-ஐ இயக்குவதற்கு அப்பால், மொழிபெயர்ப்பு ஒரு பாதுகாப்பு எல்லை. ஒரு process-க்கு மற்றொரு process-இன் physical நினைவகத்தை முகவரியிட பொறிமுறை இல்லை — அதன் page table-இல் அங்கே வரைபடமாகும் செல்லுபடியான virtual முகவரி இல்லை. நன்கு நடந்துகொள்ளும், sandboxed process ஒன்றில் நினைவகக் கெடுதல் (கொள்கையளவில்) தொடர்பில்லாத process-ஐப் படிக்கவோ கெடுக்கவோ விடாது; isolation வன்பொருள்-சரிபார்க்கப்பட்ட முகவரி மொழிபெயர்ப்பு, மரபு அல்ல.

    இது எங்கே போகிறது#

    Virtual memory ஒவ்வொரு process-க்கும் தனிப்பட்ட address space கொடுக்கிறது — வலுவான உத்தரவாதம், மற்றும் கனமான ஒன்று: சொந்த kernel கட்டமைப்புகள், சொந்த page tables, அவற்றுக்கிடையே முழு context-switch செலவு. Containers (அடுத்த பதிவு) கேட்கின்றன: ஒவ்வொரு tenant-க்கும் முழு தனி kernel செலுத்தாமல், process-களுக்குத் தேவையான பெரும்பாலான நடைமுறை isolation-ஐப் பெற முடியுமா?

    இப்போது முயல்க. கீழே உள்ள lab உங்கள் browser-க்குள் ஒரு உண்மையான 32-பிட் x86 Linux-ஐ (uname -m → i686) ஓட்டுகிறது. Boot VM அழுத்தி, prompt (~%) வந்ததும் கருப்புத் திரையைக் கிளிக் செய்து தட்டச்சு செய்யுங்கள். கீழே காட்டப்படும் வெளியீடுகள் இந்த lab-இன் அதே image-ஐ ஓட்டிப் பெற்றவை; முகவரிகளும் எண்ணிக்கைகளும் ஒவ்வொரு boot-இலும் சற்று மாறலாம்.

    1. ஒரு process-இன் முகவரி வெளியைப் பாருங்கள்: cat /proc/self/maps. ஒவ்வொரு வரியும் ஒரு virtual பகுதி: முகவரி வரம்பு, அனுமதிகள் (r படி, w எழுது, x ஓட்டு, p தனிப்பட்டது), பிறகு எந்தக் கோப்பிலிருந்து. முதல் வரி ஏறக்குறைய இப்படி இருக்கும்: 
      08048000-080d8000 r-xp 00000000 00:01 6450       /bin/busybox
      இது நிரலின் குறியீடு: படிக்கலாம், ஓட்டலாம், எழுத முடியாது (w இல்லை — மேலே உள்ள அட்டவணையின் Read/Write பிட்). அளவைக் கணக்கிடுங்கள்: 0x080d8000 − 0x08048000 = 0x90000 = 589,824 பைட் = 576 KiB = 144 pages. கடைசி வரிகளில் [stack] 0xbf… பகுதியில் இருக்கும் — 32-பிட் Linux-இல் பயனர் நினைவகம் 0xC0000000-க்குக் கீழே.
    2. Page அளவை உறுதிசெய்யுங்கள்: grep -i pagesize /proc/self/smaps → KernelPageSize: 4 kB மற்றும் MMUPageSize: 4 kB. (getconf PAGESIZE → 4096.)
    3. Virtual எதிர் உண்மையில் RAM-இல் இருப்பது: grep -E "VmSize|VmRSS|VmExe" /proc/self/status. எங்கள் ஓட்டத்தில் VmSize: 1348 kB ஆனால் VmRSS: 188 kB — process-இன் virtual வெளி 1348 KiB, ஆனால் இப்போது RAM frame-களில் இருப்பது 188 KiB மட்டுமே. மீதி இன்னும் தொடப்படவில்லை: demand paging-இன் நேரடிச் சான்று. VmExe: 576 kB படி 1-இல் நீங்கள் கணக்கிட்ட அதே எண் என்பதைக் கவனியுங்கள்.
    4. Page fault-களை எண்ணுங்கள்: grep pgfault /proc/vmstat, பிறகு ls / > /dev/null, பிறகு மீண்டும் grep pgfault /proc/vmstat. எண்ணி ஏறும் (எங்கள் ஓட்டத்தில் 1190 → 1333). புதிதாகத் தொடங்கிய ஒவ்வொரு process-உம் (ls, grep கூட) தன் pages-ஐ fault வழியாகவே பெறுகிறது. pgmajfault 0-இலேயே இருக்கும்: இந்த VM-இன் கோப்புகள் ஏற்கனவே RAM-இல் உள்ளன, எனவே disk படிப்பு இல்லை — எல்லாம் minor faults.
    5. இரண்டு process-கள், ஒரே virtual முகவரிகள்: sleep 300 & (பின்னணியில் ஒரு process), பிறகு head -3 /proc/$!/maps மற்றும் head -3 /proc/self/maps. இரண்டிலும் /bin/busybox அதே 08048000-இல்! ஒவ்வொன்றுக்கும் சொந்த page table இருப்பதால் இது மோதல் அல்ல; படிக்க-மட்டும் குறியீட்டுப் pages-ஐ OS ஒரே physical frames-இல் பகிரலாம்.
    6. முகவரி சீரற்றாக்கம் (ASLR): cat /proc/sys/kernel/randomize_va_space → 2 (இயக்கத்தில்). grep stack /proc/self/maps-ஐ மூன்று முறை ஓட்டுங்கள் — ஒவ்வொரு முறையும் [stack] வேறு முகவரியில் (எங்களுக்கு bfbf4000, bf80f000, bf91a000). தாக்குபவர் முகவரிகளை முன்கூட்டியே ஊகிக்க முடியாமல் செய்ய இது.
    7. Swap: free → Swap: 0 0 0. இந்த VM-க்கு swap இல்லை; எனவே இங்கே page-களை disk-க்குத் தள்ளும் “Pages, Faults, Swap” பொறிமுறையைப் பார்க்க முடியாது — ஆனால் அதே PTE Present பிட்தான் அதை இயக்குகிறது.
