    TCP/IP மற்றும் நவீன இணைய Stack

    ஜனவரி 1, 2026

    ARPANET (பதிவு 39) packet switching-ஐ நிரூபித்தது. Ethernet (பதிவு 40) உள்ளூர் கம்பியைத் தரநிலைப்படுத்தியது. எதுவும் தனியாக வெவ்வேறு வலையமைப்புகளை — வெவ்வேறு ஊடகங்கள், வெவ்வேறு முகவரி — எந்த இரண்டு இயந்திரங்களும் பயன்படுத்தக்கூடிய ஒரே internetwork-ஆக எப்படித் தைக்க வேண்டும் எனச் சொல்லாது. Vint Cerf மற்றும் Bob Kahn-இன் TCP/IP suite அதைத் தீர்த்தது; நவீன இணையம் இன்னும் ஓடும் அடித்தளம் அது.

    தமிழ் இடைவெளிக் குறிப்பு: TCP/IP அடுக்குகள் பற்றித் தமிழில் பாடநூல் அறிமுகமும் ஒரு நூலும் உண்டு (கீழே மேலும் படிக்க); காணொளிச் சான்று YouTube தேடல் முடிவுகள் மட்டும் — காணொளிகள் பார்க்கப்படவில்லை. Header-களின் byte கணக்கு, sequence எண்கள் handshake-இல் எப்படி நகர்கின்றன, window அளவு வேகத்தை எப்படிக் கட்டுப்படுத்துகிறது — இவை எண்களுடன் விளக்கப்பட்டதாகத் தெரியவில்லை. Header அளவுகளும் handshake விதிகளும் RFC 791, RFC 793 உரைகளிலிருந்து சரிபார்க்கப்பட்டவை; lab முயற்சி கீழே உள்ள அதே Linux VM-இல் ஓட்டிச் சரிபார்க்கப்பட்டது. “எடுத்துக்காட்டு மதிப்பு” என்று குறிக்கப்பட்டவை கணக்குக்காகத் தேர்ந்தெடுத்தவை.

    முதலில் சொற்கள்#

    • நெறிமுறை (protocol): இரண்டு தரப்பும் ஒப்புக்கொண்ட செய்தி வடிவமும் நடத்தை விதிகளும்.
    • அடுக்கு (layer): ஒரு வேலையை மட்டும் செய்து, மேலே உள்ள அடுக்குக்கு ஒரு சேவை தரும் பகுதி.
    • Header (தலைப்பு): ஒவ்வொரு அடுக்கும் தரவுக்கு முன் சேர்க்கும் கட்டுப்பாட்டுத் தகவல் (முகவரிகள், port-கள், எண்கள்).
    • Encapsulation (உறையிடல்): மேல் அடுக்கின் முழுச் செய்தியையும் கீழ் அடுக்கு தன் payload ஆக வைத்து, தன் header-ஐச் சேர்ப்பது.
    • Segment / packet / frame: முறையே TCP, IP, link அடுக்குகளின் தரவு அலகுகள்.
    • Port: ஒரே கணினிக்குள் எந்த நிரலுக்குத் தரவு போக வேண்டும் என்று சொல்லும் 16-பிட் எண்.
    • Sequence number (வரிசை எண்): TCP ஒவ்வொரு byte-க்கும் தரும் எண்; வரிசையைச் சரிசெய்யவும் இழப்பைக் கண்டுபிடிக்கவும்.
    • ACK (acknowledgment, ஒப்புகை): “இந்த எண் வரை பெற்றேன்; அடுத்தது இதை எதிர்பார்க்கிறேன்” என்ற செய்தி.
    • Window (சாளரம்): ACK வரும் முன் அனுப்பலாம் என்று பெறுநர் அனுமதிக்கும் byte-களின் எண்ணிக்கை.
    • RTT (round-trip time, சுற்றுப் பயண நேரம்): ஒரு செய்தி போய் அதன் பதில் திரும்பும் நேரம்.

    அடுக்கு மாதிரி#

    TCP/IP கவலைகளை PCIe-இன் stack பிரிக்கும் விதத்தில் பிரிக்கிறது (பதிவு 33), internetworking அளவில். Link உள்ளூர் hop-ஐக் கையாளும் — Ethernet, Wi-Fi, fiber. Internet (IP) அந்த இணைப்புகளுக்கு குறுக்கே உலகளாவிய முகவரி மற்றும் routing தரும்; ஒரு IP packet அதைச் சுமக்கும் ஊடகம் என்னவெனப் பொருட்படுத்தாது. Transport (TCP அல்லது UDP) IP மீது நம்பக வரிசைப்படுத்தப்பட்ட வழங்கல் (TCP) அல்லது குறைந்த-overhead best-effort (UDP) வழங்குகிறது. Application HTTP, DNS, SMTP மற்றும் உறவினர்கள் அமர்வது, பொருத்தமான transport-ஐத் தேர்ந்தெடுத்து.

    Encapsulation#

    கீழே நகரும் தரவு ஒவ்வொரு அடுக்கிலும் ஒரு header பெறுகிறது — application bytes TCP/UDP கீழ், அந்த segment IP கீழ், அந்த packet ஒரு link header (மற்றும் அடிக்கடி trailer) கீழ். தொலை முனையில் செயல்முறை தலைகீழ்: ஒவ்வொரு அடுக்கும் தன் header-ஐ உரித்து, அது படித்ததை (ports, முகவரிகள்) பயன்படுத்தி மீதியை மேலே ஒப்படைக்கும்.

    உறையிடல், byte-களில்#

    RFC 791-இன்படி IPv4 header குறைந்தது 5 × 32-பிட் word-கள் = 20 byte; RFC 793-இன்படி TCP header-உம் குறைந்தது 5 word-கள் = 20 byte (options இருந்தால் அதிகம்).

    அடுக்கு அது சேர்ப்பது அதன் முக்கிய முகவரி / எண்
    Application தரவு (எ.கா. HTTP கோரிக்கை) —
    Transport (TCP) 20+ byte header port-கள் (16 பிட் → 2^16 = 65,536 மதிப்புகள்), sequence, ACK, window
    Internet (IP) 20+ byte header IPv4 முகவரிகள் (32 பிட் → 2^32 = 4,294,967,296 மதிப்புகள்)
    Link (எ.கா. Ethernet) தன் header, trailer (பதிவு 40) MAC முகவரி (48 பிட்)

    எடுத்துக்காட்டு 1 — சிறிய கோரிக்கை. 100 byte HTTP கோரிக்கை (எடுத்துக்காட்டு மதிப்பு):

    1. TCP: 100 + 20 = 120 byte segment
    2. IP: 120 + 20 = 140 byte packet
    3. பயனுள்ள பங்கு: 100 ÷ 140 ≈ 71% — link header சேர்க்கும் முன்பே 29% header.

    எடுத்துக்காட்டு 2 — முழு packet. இந்தப் பதிவின் lab VM-இன் Ethernet இடைமுகம் MTU:1500 காட்டுகிறது: ஒரு IP packet அதிகபட்சம் 1,500 byte.

    1. 1,500 − 20 (IP) − 20 (TCP) = 1,460 byte தரவு ஒரு packet-இல்
    2. பயனுள்ள பங்கு: 1,460 ÷ 1,500 ≈ 97.3%

    சிறிய செய்திகளுக்கு header செலவு பெரியது; பெரிய பரிமாற்றங்களுக்குச் சிறியது. பெறும் முனையில் IP header-இன் “protocol” புலம் “இது TCP” என்றும், TCP header-இன் இலக்கு port “இது port 5000-இல் கேட்கும் நிரலுக்கு” என்றும் சொல்லி, ஒவ்வொரு அடுக்கும் தன் header-ஐ உரித்து மேலே அனுப்புகிறது.

    நம்பகமற்ற Substrate மீது TCP#

    IP வெளிப்படையாக best-effort — வழங்கல் வாக்குறுதி இல்லை, வரிசை வாக்குறுதி இல்லை, drops அனுமதிக்கப்பட்டவை. TCP sequence numbers மற்றும் acknowledgments (மற்றும் ACK-கள் வராதபோது retransmission) மூலம் மீது ஒரு நம்பக வரிசைப்படுத்தப்பட்ட byte stream கட்டுகிறது — பதிவு 33-இன் PCIe data-link அடுக்கின் அதே நம்பகத்தன்மை வகை, ஒரே அர்ப்பணிக்கப்பட்ட இணைப்புக்குப் பதிலாக முழு நம்பகமற்ற internetwork குறுக்கே நீட்டப்பட்டது.

    ஒரு connection மூன்று-வழி handshake-ஆல் தொடங்குகிறது: SYN (client ஒரு sequence number முன்மொழிகிறது), SYN-ACK (server ஒப்புக்கொண்டு தன் சொந்தத்தை முன்மொழிகிறது), இறுதி ACK. அதற்குப் பிறகுதான் application தரவு ஓடும் — இரு பக்கங்களும் முதலில் ஒத்திசைக்கப்பட்ட நிலையைப் பகிரும் சிறிய வேண்டுமென்ற செலவு.

    Handshake, எண்களுடன்#

    RFC 793-இன் Figure 7 அதே எண்களைப் பயன்படுத்துகிறது: A தன் தொடக்க வரிசை எண்ணாக 100, B 300.

    படி திசை கொடிகள் SEQ ACK பொருள்
    1 A → B SYN 100 — “என் byte-கள் 100-இலிருந்து எண்ணப்படும்”
    2 B → A SYN, ACK 300 101 “உன் 100 கிடைத்தது; 101 எதிர்பார்க்கிறேன். என்னுடையது 300-இலிருந்து”
    3 A → B ACK 101 301 “உன் 300 கிடைத்தது; 301 எதிர்பார்க்கிறேன்”
    4 A → B ACK + தரவு 101 301 முதல் தரவு byte-இன் எண் 101

    ACK 101 ஏன், 100 அல்ல? RFC 793: SYN ஒரு வரிசை எண்ணை “ஆக்கிரமிக்கிறது” — அது முதல் உண்மைத் தரவு byte-க்கு முன் நிகழ்வதாகக் கருதப்படுகிறது. அதனால் SYN = 100 என்றால் முதல் தரவு byte = 101.

    தரவு நகர்வு (எடுத்துக்காட்டு மதிப்புகள்): படி 4-இல் A 200 byte அனுப்பினால், அவை 101 முதல் 300 வரை எண்ணப்படுகின்றன. B-இன் ACK = 301 (“300 வரை எல்லாம் வந்தது”). அடுத்து A-வின் SEQ = 301.

    இழப்பு, ஒரு கணக்கில்: A மூன்று segment-கள் அனுப்புகிறது: 101–300, 301–500, 501–700. இரண்டாவது தொலைகிறது. B-க்கு 101–300 வந்தது, பிறகு 501–700 — இடைவெளி. B-இன் ACK 301-இலேயே நிற்கிறது. 301-க்கான ACK நேரத்துக்குள் முன்னேறாததால் A 301–500-ஐ மீண்டும் அனுப்புகிறது; அது வந்ததும் B ACK 701 அனுப்புகிறது — எல்லாம் வரிசைப்படி. IP இதில் எதையும் அறியாது; முழு நம்பகத்தன்மையும் இரண்டு முனைகளின் TCP-இல்.

    Window: வேகத்தின் மறைந்த வரம்பு#

    RFC 793-இல் window புலம் 16 பிட் → அதிகபட்சம் 65,535 byte. அனுப்புநர் ACK வராமல் அதற்கு மேல் அனுப்ப முடியாது. அதனால் ஒரு RTT-க்கு அதிகபட்சம் ஒரு window:

    அதிகபட்ச வேகம் ≈ window ÷ RTT

    RTT (எடுத்துக்காட்டு மதிப்பு) கணக்கு அதிகபட்சம்
    100 ms (கண்டம் தாண்டி) 65,535 byte ÷ 0.1 s 655,350 byte/s ≈ 5.2 Mbit/s
    10 ms (அதே நகரம்) 65,535 byte ÷ 0.01 s ≈ 52 Mbit/s

    Link 1 Gbit/s ஆக இருந்தாலும், 100 ms தூரத்தில் இந்த 16-பிட் window-உடன் ஒரு TCP இணைப்பு சுமார் 5 Mbit/s-ஐத் தாண்டாது. தூரம் (RTT) வேகத்தின் பகுதி — அதனால்தான் பிற்கால TCP நீட்டிப்புகள் window-ஐப் பெரிதாக்கும் வழிகளைச் சேர்த்தன.

    ஒரு வலையமைப்பின் நெறிமுறைகளிலிருந்து ஒரு Stack-க்கு#

    ARPANET முதலில் தன் சொந்த host-to-host நெறிமுறையை (NCP) பேசியது, TCP/IP அல்ல. Cerf மற்றும் Kahn-இன் பந்தயம் பெரியது: பல packet வலையமைப்புகளை internet செய்யக்கூடிய ஒரு protocol stack — எனவே transport மற்றும் உள்ளூர் கம்பி தனித்தனியாக பரிணமிக்க முடியும். ARPANET-இல் நடைமுறை மாற்றம் ஜனவரி 1, 1983 “flag day” — NCP அணைக்கப்பட்டு TCP/IP கட்டாயமானது — அடுக்குக் கதையை கட்டமைப்பு மட்டும் அல்லாமல் செயல்பாட்டுக்குக் கொண்டுவந்த அரிதான கடின வெட்டு.

    Application நெறிமுறைகள் பிறகு அடுக்கியது அந்த substrate இருந்ததால். DNS (பதிவு 64-இன் கதவுகள்: RFC 1034 / RFC 1035) பெயர்களை அளவில் பயன்படுத்தக்கூடியதாக்கியது; mail மற்றும் வலை (SMTP, HTTP மற்றும் உறவினர்கள்) முகவரி மற்றும் retransmission-ஐ மீண்டும் கண்டுபிடிக்காமல் நம்பக stream-இன் clients ஆக TCP மீது ஏறின. முறைதான் பொருள்: ஒவ்வொரு அடுக்கும் ஒரு கட்டுப்பாட்டை வாங்கி மேலே உள்ளது அதைக் கருத அனுமதிக்கிறது. அது அடுக்குதல் பற்றிய கதை, ஒவ்வொரு RFC-இன் பட்டியல் அல்ல.

    இந்த வடிவமைப்பு ஏன் வென்றது#

    சுமை தாங்கும் கருதுகோள் அடிப்படை வலையமைப்பு பன்முகமும் நம்பகமற்றதும், எனவே உத்தரவாதங்கள் ஒவ்வொரு இயற்பியல் இணைப்பிலும் அல்லாமல் உயர் அடுக்கில் இருக்க வேண்டும். அது பத்தாண்டுகளாக வெவ்வேறு தொழில்நுட்பங்களிலிருந்து, ஒரு இயற்பியல் தரநிலையில் ஒருபோதும் ஒப்புக்கொள்ளாத நிறுவனங்களால் தைக்கப்பட்ட உலகளாவிய internetwork-க்குப் பொருந்தியது — அதனால்தான் TCP/IP இன்னும் கிட்டத்தட்ட முழு நவீன இணையத்திற்கும் கீழே அமர்ந்திருக்கிறது, அடுத்த datacenter வலையமைப்புகள் உட்பட.

    Door out: RFC 791 (Internet Protocol) மற்றும் RFC 793 (Transmission Control Protocol) — இந்த stack-இன் முகவரி/routing மற்றும் நம்பக-transport பாதிகளுக்கான முதன்மை விவரக்குறிப்புகள் (Cerf/Kahn வம்சாவளி; இந்த செப்டம்பர் 1981 உரைகளுக்கு RFC editor ஆக Postel).

    இப்போது முயல்க: ஒரு TCP இணைப்பை எண்ணுங்கள். கீழே உள்ள terminal-இல் ஒரு சிறிய Linux கணினி. அதற்குள்ளேயே (loopback, 127.0.0.1) ஒரு server-ஐயும் client-ஐயும் ஓட்டி, kernel-இன் TCP எண்ணிகளைப் பார்க்கலாம். (எல்லாப் படிகளும் இதே VM-இல் ஓட்டிச் சரிபார்க்கப்பட்டவை; port எண் 45324 போன்ற client port ஓட்டத்துக்கு ஓட்டம் மாறும்.)

    1. Loopback-ஐ இயக்குங்கள்: ifconfig lo 127.0.0.1 up
    2. ஒரு echo server: echo "5000 stream tcp nowait root /bin/cat cat" > /tmp/inetd.conf பிறகு inetd /tmp/inetd.conf. இப்போது port 5000-க்கு வரும் ஒவ்வொரு இணைப்பும் cat நிரலுடன் இணைக்கப்படும் — அனுப்பியதைத் திருப்பி அனுப்பும்.
    3. netstat -tln → 0.0.0.0:5000 … LISTEN
    4. grep Tcp: /proc/net/snmp — இரண்டு வரிகள்: பெயர்கள், எண்கள். முதல் நான்கு (RtoAlgorithm 1, RtoMin 200, RtoMax 120000, MaxConn -1) அமைப்பு மதிப்புகள், எண்ணிகள் அல்ல; ActiveOpens முதல் மீதி எல்லா எண்ணிகளும் 0 — இன்னும் எந்த TCP இணைப்பும் இல்லை.
    5. இணையுங்கள்: (echo hello-tcp; sleep 4) | telnet 127.0.0.1 5000 & → hello-tcp திரும்பி வரும் (server-இன் echo).
    6. உடனே netstat -tn → இரண்டு ESTABLISHED வரிகள்: 127.0.0.1:45324 → 127.0.0.1:5000, 127.0.0.1:5000 → 127.0.0.1:45324. ஒரே இணைப்பின் இரண்டு முனைகள், இரண்டும் இந்தக் கணினியில்.
    7. மீண்டும் grep Tcp: /proc/net/snmp → எங்கள் ஓட்டத்தில் ActiveOpens 1 (client பக்கம் SYN அனுப்பியது), PassiveOpens 1 (server பக்கம் SYN ஏற்றது), CurrEstab 2, InSegs 7, OutSegs 7.
    8. நான்கு விநாடி கழித்து (telnet முடிந்ததும்) netstat -tn -a → client வரி இப்போது TIME_WAIT — முதலில் மூடிய பக்கம் சற்று நேரம் பழைய segment-களுக்காகக் காத்திருக்கிறது. grep Tcp: /proc/net/snmp → CurrEstab 0, InSegs 10, OutSegs 10.
    9. ifconfig lo | grep packets → எங்கள் ஓட்டத்தில் RX/TX packets 10, bytes 558.

    எண்ணிப் பாருங்கள்: 10 segment-களில் 3 handshake (SYN, SYN-ACK, ACK), 3 மூடல் (படி 7-இன் 7-இலிருந்து 10 வரை). மீதி 4 தரவையும் அதன் echo-வையும் அவற்றின் ஒப்புகைகளையும் சுமந்தன (இந்தப் பிரிவு ஓட்டத்துக்கு ஓட்டம் சற்று மாறலாம்). 558 ÷ 10 ≈ 56 byte சராசரி — IP 20 + TCP 20 = 40 byte header மட்டுமே பெரும்பகுதி; “hello-tcp” போன்ற சிறு தரவுக்கு header-தான் பெரிய செலவு (மேலே உள்ள எடுத்துக்காட்டு 1).

    மூடிய port-ஐ முயன்றால்? telnet 127.0.0.1 6000 → Connection refused; எண்ணிகளில் AttemptFails, OutRsts ஒவ்வொன்றும் 1 ஏறும் — kernel SYN-க்கு RST (reset) மூலம் “இங்கே யாரும் கேட்கவில்லை” என்று பதிலளித்தது.
