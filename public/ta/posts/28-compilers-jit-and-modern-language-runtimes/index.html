    Compilers, JIT, மற்றும் நவீன மொழி Runtimes

    ஜனவரி 1, 2026

    பதிவு 27 உயர்நிலை மொழிகள் ஏன் உள்ளன என்பதை உள்ளடக்கியது. இந்தப் பதிவு அவற்றைப் பயன்படுத்தக்கூடியதாக்கும் இயந்திரம்: compiler, மூலத்தை உண்மையான CPU (Phase 3) இயக்கக்கூடிய ஒன்றாக மொழிபெயர்ப்பது.

    தமிழ் இடைவெளிக் குறிப்பு: compiler, JIT, garbage collection பற்றித் தமிழ் எழுத்து விளக்கம் மெலிதானது (JIT-க்கு எதுவுமில்லை); காணொளிச் சான்று YouTube தேடல் முடிவுகள் மட்டும் — காணொளிகள் பார்க்கப்படவில்லை. இங்குள்ள optimizer எடுத்துக்காட்டு எங்கள் பணிக் கணினியில் (Linux, x86-64) GCC 14.2 மூலம் உண்மையில் compile செய்து பெற்றது; VM பயிற்சியின் வெளியீடுகள் உண்மையில் ஓட்டிப் பெற்றவை. கவனிக்க: கீழே உள்ள VM-இல் gcc இல்லை (gcc: not found — ஓட்டிச் சரிபார்த்தது); அதற்கேற்ப இப்போது முயல்க பகுதி மாற்றி அமைக்கப்பட்டுள்ளது. “எடுத்துக்காட்டு மதிப்பு” என்று குறிக்கப்பட்டவை கணக்குக்காகத் தேர்ந்தெடுத்தவை.

    முதலில் சொற்கள்#

    • Compiler (தொகுப்பி): மூல நிரலை இலக்கு இயந்திரக் குறியீடாக மொழிபெயர்க்கும் நிரல்.
    • Token (சொல்லலகு): lexer பிரிக்கும் சிறிய அர்த்த அலகு — பெயர், எண், செயற்குறி, நிறுத்தற்குறி.
    • AST (Abstract Syntax Tree, சுருக்கத் தொடரியல் மரம்): நிரலின் அமைப்பை மரமாகக் காட்டும் parser-இன் வெளியீடு.
    • IR (இடைநிலை வடிவம்): மூல மொழிக்கும் இலக்கு ISA-வுக்கும் இடையிலான சீரான உள் வடிவம்; optimizer இங்கே வேலை செய்கிறது.
    • Optimizer (உகப்பாக்கி): நடத்தையை மாற்றாமல் வேலையைக் குறைக்கும் மாற்றங்களின் தொகுப்பு.
    • AOT (முன்கூட்டியே தொகுத்தல்): நிரல் ஓடுவதற்கு முன் முழுமையாக compile செய்வது.
    • JIT (ஓடும்போது தொகுத்தல்): ஓடும்போதே அடிக்கடி ஓடும் பகுதிகளைக் கண்டு compile செய்வது.
    • Interpreter (விளக்கி): நிரலை இயந்திரக் குறியீடாக மாற்றாமல், ஒவ்வொரு படியையும் படித்து நேரடியாகச் செய்யும் நிரல்.
    • Garbage collection (நினைவகச் சுத்திகரிப்பு): இனிப் பயன்படாத நினைவகத்தை runtime தானாக மீட்பது.

    செவ்வியல் Pipeline (சுருக்கம்)#

    Lexer → tokens. Parser → Abstract Syntax Tree. Semantic analysis இலக்கணம் மட்டும் பிடிக்க முடியாதவற்றைப் பிடிக்கிறது (types, அறிவிக்கப்படாத பெயர்கள்). பெரும்பாலான உண்மையான compilers பிறகு Intermediate Representation (IR)-க்குத் தாழ்த்துகின்றன — மூல தொடரியலை விட ஒரேமாதிரியானது, இன்னும் எந்த இலக்கு ISA-விலிருந்தும் சுயாதீனம் — அங்கு optimizer வேலை செய்கிறது: dead-code elimination, loop-invariant hoisting, inlining, மற்றும் நடத்தையைப் பாதுகாத்து வீணான வேலையை வெட்டும் டஜன் கணக்கான பிற மாற்றங்கள். Code generation இலக்கு அறிவுறுத்தல்களை வெளியிட்டு register allocation செய்கிறது (எந்த மதிப்புகள் குறைவான physical பதிவேடுகளில் வாழ்கின்றன எதிராக நினைவகத்திற்கு spilling).

    அதுதான் முதுகெலும்பு. ஒவ்வொரு pass-இன் கலைக்களஞ்சியம் புள்ளி அல்ல — கட்டுப்பாடு: மூல abstractions ஓடாது; ஏதோ ஒன்று அவற்றைத் தாழ்த்த வேண்டும், மற்றும் அது இயக்கத்திற்கு முன் அல்லது போது ஓடலாம்.

    ஒரு வரி, pipeline வழியே#

    C வரி s += i; எடுத்துக்கொள்வோம்.

    கட்டம் வெளியீடு
    Lexer 4 token-கள்: பெயர் s, செயற்குறி +=, பெயர் i, நிறுத்தற்குறி ;
    Parser AST: += கணு, இடக்கிளை s, வலக்கிளை i
    Semantic analysis s, i இரண்டும் அறிவிக்கப்பட்டவையா? இரண்டும் long — கூட்டல் சரி
    IR / optimizer சுற்றுப்புறத்தைப் பார்த்து மாற்றலாம் (கீழே உண்மையான எடுத்துக்காட்டு)
    Code generation x86-64-இல் add instruction, s-ஐ ஒரு register-இல் அல்லது நினைவகத்தில் வைத்து

    Optimizer வேலை செய்வதைப் பாருங்கள் (உண்மையான GCC வெளியீடு)#

    இந்தச் சிறிய function 1 முதல் 1,000,000 வரை கூட்டுகிறது:

    long sum(void) {
    long s = 0;
    for (long i = 1; i <= 1000000; i++)
        s += i;
    return s;
}

    எங்கள் பணிக் கணினியில் gcc -O0 -S -masm=intel (உகப்பாக்கம் இல்லை) தந்த assembly-இல் 13 instruction-கள்; loop-இன் உடல் ஒவ்வொரு சுற்றுக்கும் 5 instruction-கள் (mov, add, add, cmp, jle), s-உம் i-உம் stack நினைவகத்தில்:

        mov  rax, QWORD PTR -16[rbp]      ; i-ஐ ஏற்று
    add  QWORD PTR -8[rbp], rax       ; s += i
    add  QWORD PTR -16[rbp], 1        ; i++
    cmp  QWORD PTR -16[rbp], 1000000
    jle  .L3                          ; i <= 1000000 என்றால் மீண்டும்

    அதே மூலத்துக்கு gcc -O2:

        movabs rax, 500000500000
    ret

    கணக்கு: 1 + 2 + … + n = n(n+1)/2 = 1,000,000 × 1,000,001 / 2 = 500,000,500,000 — optimizer loop-இன் இறுதி மதிப்பை compile நேரத்திலேயே கணக்கிட்டு, loop-ஐ நீக்கி முடிவை மட்டும் மாறிலியாக வைத்துவிட்டது (constant folding). ஓடும் நேர வேலை:

    பதிப்பு loop-இல் ஓடும் instruction-கள்
    -O0 5 × 1,000,000 = 5,000,000 (+ முன்பின் சில)
    -O2 0 — மொத்தம் 2 instruction-கள்

    நடத்தை ஒன்றே (அதே மதிப்பு திரும்புகிறது); வேலை மட்டும் மறைந்தது. இதுதான் ஆங்கிலப் பதிவு சொல்லும் “நடத்தையைப் பாதுகாத்து வீணான வேலையை வெட்டுதல்”.

    Ahead-of-Time எதிர் Just-in-Time#

    நிரல் எப்போதும் இயங்குவதற்கு முன் முழு pipeline-ஐ ஒருமுறை ஓட்டுங்கள்: Ahead-of-Time (AOT) — C மற்றும் பாரம்பரிய FORTRAN. Just-in-Time (JIT) — Java, JavaScript, மற்றும் உறவினர்கள் — interpreter அல்லது வேகமான baseline compiler-உடன் தொடங்கி, பிறகு runtime-இல் hot paths கண்டுபிடித்து கனமான optimization-உடன் மீண்டும் தொகுக்கிறது.

    JIT-இன் நன்மை AOT compiler-க்கு ஒருபோதும் இல்லாத தகவல்: கவனிக்கப்பட்ட branches, argument types, உண்மையான hot loops — அந்தத் தரவு இல்லாமல் கருத பாதுகாப்பற்ற optimizations. செலவு உண்மையானது: compilation இயக்கத்தின் போது சுழற்சிகளை எரிக்கிறது, மற்றும் முதல் வினாடிகள் அடிக்கடி steady state-ஐ விட மெதுவாக ஓடுகின்றன — செவ்வியல் warm-up.

    JIT warm-up, ஒரு கணக்கில்#

    JIT எப்போது பலன் தரும்? எல்லாம் எடுத்துக்காட்டு மதிப்புகள்: ஒரு loop சுற்று interpreter-இல் 100 ns, JIT-compile செய்த பிறகு 5 ns; அந்த loop-ஐ compile செய்ய 20 ms (= 20,000,000 ns) ஆகிறது.

    • ஒவ்வொரு சுற்றிலும் சேமிப்பு: 100 − 5 = 95 ns
    • சமநிலைப் புள்ளி: 20,000,000 ÷ 95 ≈ 210,526 சுற்றுகள்
    சுற்றுகள் interpreter மட்டும் JIT (compile + ஓட்டம்) எது வேகம்?
    10,000 1 ms 20 + 0.05 = 20.05 ms interpreter
    210,526 ≈ 21.05 ms ≈ 20 + 1.05 = 21.05 ms சமம்
    10,000,000 1,000 ms 20 + 50 = 70 ms JIT (≈ 14 மடங்கு)

    அதனால்தான் JIT “hot” பகுதிகளை மட்டும் compile செய்கிறது, முதல் சில விநாடிகள் மெதுவாக இருக்கின்றன (warm-up). இன்னொரு உண்மை: கீழே உள்ள VM-ஐ ஓட்டும் v86 emulator-உம் ஒரு JIT — அதன் README சொல்வதுபடி, x86 இயந்திரக் குறியீடு ஓடும்போதே WebAssembly module-களாக மொழிபெயர்க்கப்படுகிறது.

    Runtimes: Compilation-ஐ விட அதிகம்#

    Managed மொழிகள் (Java, C#, மற்றும் பல்வேறு அளவுகளில் JavaScript மற்றும் Python) compiler-ஐ பரந்த runtime-உடன் இணைக்கின்றன — மிக முக்கியமாக garbage collection வழியாகத் தானியங்கி நினைவக மேலாண்மை, நிரலாளர்களை ஒவ்வொரு allocation-இன் lifetime கண்காணிப்பிலிருந்து விடுவிக்கிறது (C-இல் முக்கிய பிழை மூலம்). சிக்கல் runtime-க்குள் மாறுகிறது: கையேடு முயற்சி overhead-க்கு மற்றும், வரலாற்றுரீதியாக, குறைந்த கணிக்கக்கூடிய இடைநிறுத்தங்களுக்கு வர்த்தகம். அந்தப் பதற்றம்தான் பதிவுகள் 29–30 “real-time” மற்றும் “garbage-collected managed runtime”-ஐ அடிக்கடி முரண்பாடாகக் கருதக் காரணம்.

    நேரடியாகப் பாருங்கள்#

    கீழே உள்ள VM terminal ஒரு உண்மையான Linux அமைப்பு, ஆனால் அதில் C compiler இல்லை — gcc ஓட்டினால் gcc: not found என்று வரும். எனவே அங்கே C நிரலை compile செய்ய முடியாது. மேலே உள்ள உண்மையான GCC -O0 / -O2 வெளியீடுகள் இந்தப் பதிவின் abstractions உறுதியான machine அறிவுறுத்தல்களாக மாறுவதைக் காட்டுகின்றன; VM-இல் என்ன முயலலாம் என்பதற்குக் கீழே உள்ள “இப்போது முயல்க” பகுதியைப் பாருங்கள் — அங்கே ஏற்கனவே compile ஆன ஒரு binary-ஐயும் interpret ஆகும் ஒரு நிரலையும் ஒப்பிடுகிறோம்.

    இப்போது முயல்க: compile ஆன ஒன்றும் interpret ஆகும் ஒன்றும். இந்த VM-இல் gcc இல்லை (gcc: not found). அதனால் இவற்றை ஓட்டுங்கள் (எல்லாம் ஓட்டிச் சரிபார்த்தவை):

    1. gcc → -/bin/sh: gcc: not found. இங்கே compiler இல்லை — ஆனால் compile ஆன வெளியீடுகள் இருக்கின்றன.
    2. hexdump -C /bin/busybox | head -2 → முதல் byte-கள் 7f 45 4c 46 01 01 01 …: 7f + “ELF” = compiler/linker உருவாக்கும் இயக்கக்கூடிய கோப்பு வடிவம்; அடுத்த 01 = 32-பிட், அதற்கடுத்த 01 = little-endian. இரண்டாம் வரியில் 03 00 = x86 (i386) இலக்கு. இது AOT: நிரல் ஓடுவதற்கு முன்பே — 2018-இல், வேறொரு கணினியில் — compile செய்யப்பட்டது.
    3. echo 'BEGIN{s=0; for(i=1;i<=1000000;i++) s+=i; print s}' > /tmp/sum.awk பிறகு time awk -f /tmp/sum.awk → 500000500000, எங்கள் ஓட்டங்களில் real சுமார் 6 விநாடி (6.06 s, 6.45 s; உங்கள் உலாவியில் வேறுபடும்). awk ஒரு interpreter: மேலே GCC -O2 ஒரே constant ஆக்கிய அதே கூட்டலை, இங்கே ஒவ்வொரு சுற்றையும் ஓடும்போது படித்துச் செய்கிறது — ஒரு சுற்றுக்குச் சுமார் 6 s ÷ 1,000,000 ≈ 6 µs.
