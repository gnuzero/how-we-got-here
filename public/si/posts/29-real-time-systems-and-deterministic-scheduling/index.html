    දුරුතු 1, 2026

    Phase 4 හි මෙතෙක් සියල්ල — batch, time-sharing, අතථ්‍ය මතකය, containers — throughput, සාධාරණත්වය, හෝ කාර්යක්ෂම බෙදාගැනීම සඳහා ප්‍රශස්තකරණය කරයි. ඒවායින් කිසිවක් දී ඇති කාර්ය කොටසක් කවදාද අවසන් වේද යන්න දැඩිව සහතික නොකරයි. තත්‍ය කාල පද්ධති එම සහතිකය ගැන සැලකිලිමත් වේ. “වේගවත්” යනු “තත්‍ය කාල” ට වඩා වෙනස් ගුණයකි — මිනිසුන් නිරන්තරයෙන් පැටලෙන වෙනස්කමකි.

    වේගවත් යනු නිශ්චයාත්මක නොවේ#

    සාමාන්‍ය-අරමුණු scheduler එකක් (Posts 21–25) හොඳ සාමාන්‍ය-අවස්ථා ප්‍රතිචාරශීලීත්වය සහ සාධාරණ බෙදාගැනීම සඳහා ප්‍රශස්තකරණය කරයි — සාමාන්‍ය අවස්ථාවේදී බොහෝ විට තරමක් වේගවත්ය. “සාමාන්‍යයෙන් වේගවත්” යනු “සෑම විටම නිශ්චිත deadline එකක් ඇතුළත අවසන් වේ, ව්‍යතිරේක නැත” නොවේ. Cache බලපෑම්, interrupt හැසිරවීම, හෝ garbage-collection pauses (Post 28) ප්‍රමාදයක් දිගු කළ හැක. බොහෝ apps සඳහා, ඉඳහිට විචලනය වැදගත් නොවේ. තත්‍ය කාල පද්ධතියක් සඳහා, එය සම්පූර්ණ ක්‍රීඩාව විය හැක.

    දැඩි එදිරිව මෘදු#

    දැඩි deadline එකක්: එය මග හැරීම සම්පූර්ණ පද්ධති අසාර්ථකත්වයකි — පහත වැටුණු කාර්ය සාධනය නොවේ. ගුවන්-පාලන ස්ථායීකරණය, airbag යෙදවීම — සෑම විටම, කවුළුව ඇතුළත, නැතහොත් අසාර්ථකත්වය විනාශකාරී විය හැක.

    මෘදු deadline එකක්: එය මග හැරීම ගුණාත්මකභාවය පහත හෙළයි නමුත් සෘජු අසාර්ථකත්වයක් නොවේ — බර යටතේ මඟ හැරුණු වීඩියෝ frame එකක් අප්‍රසන්නය, සහතික අර්බුදයක් නොවේ. Deadlines වෙත ළඟා වීමට ශක්තිමත් ප්‍රායෝගික ප්‍රවණතාවයක්; දෘඪාංග-බලාත්මක සහතිකයක් නොවේ.

    Rate-Monotonic Scheduling#

    දැඩි තත්‍ය කාලය සඳහා එක් සම්භාව්‍ය ප්‍රවේශයක්: rate-monotonic scheduling — එක් එක් ආවර්තිත කාර්යයට එය කොපමණ නිතර ධාවනය විය යුතුද යන්නෙන් ස්ථිර priority එකක් පවරන්න; කෙටි කාල පරිච්ඡේදය → ඉහළ priority. ආවර්තිත කාර්ය කට්ටලවල හොඳින් අර්ථ දක්වන ලද පන්තියක් සඳහා ස්ථිර-priority ඇල්ගොරිතම අතර ඔප්පු කළ හැකි ලෙස ප්‍රශස්තය: එම workload සඳහා කිසියම් ස්ථිර-priority පැවරුමකට සෑම deadline එකක්ම සපුරාලිය හැකි නම්, rate-monotonic ද එසේ කරයි. ගණිතමය schedulability බැඳීමක් — දැඩි තත්‍ය කාල පද්ධති සහතික කිරීමට අවශ්‍ය ආකාරයේ විධිමත් ගුණයම.

    වෙනස් වර්ගයේ OS එකක් ඇයි#

    මෙම සහතික සපුරාලීමට බැඳුණු නරකම-අවස්ථා කාලය වටා නිර්මාණය කළ OS එකක් අවශ්‍යය — Real-Time Operating System (RTOS) — Posts 21–25 හි throughput/සාධාරණත්ව පෙළපත නොවේ. Interrupt latency බැඳුණු සහ දන්නා විය යුතුය. මතක allocation සාමාන්‍යයෙන් සාමාන්‍ය-අරමුණු GC වැනි පුරෝකථනය කළ නොහැකි-latency යාන්ත්‍රණ මත රඳා නොපවතී. Mutex එකකටත් ප්‍රවේශම් සහගත නිර්මාණය අවශ්‍යය (priority inheritance) එවිට අඩු-priority කාර්යයකට ඉහළ-priority එකක් අසීමිත කාලයක් අවහිර කළ නොහැක — priority inversion, සම්භාව්‍ය තත්‍ය කාල අන්තරායක්.

    මෙම කාචය හරහා mini-CPU lab එක නැවත බලන්න: සරල දෘඪාංගය මත, සෑම උපදෙසක කාලය නිශ්චයාත්මක සහ ගණන් කළ හැකිය — පද්ධති වඩාත් සංකීර්ණ වන විට RTOS නිර්මාණය සුරැකීමට සටන් කරන පුරෝකථනය කළ හැකි බව. ඊළඟ පෝස්ට් එක මෙම මූලධර්ම avionics, කාර්මික පාලනය, සහ සහතික බර දරන embedded යෙදවුම් වෙත ගෙන යයි.

    Lab එක නව tab එකක විවෘත කරන්න ↗

    ගැඹුරින්: deadline සහතික කිරීම අතින් — rate-monotonic බැඳීම, EDF, සහ උපදෙස් ගණන් කිරීම#

    සිංහල මූලාශ්‍ර පිළිබඳ සටහන: si.wikipedia හි “තථ්‍ය කාල මෙහෙයුම් පද්ධති” ලිපිය (~6.6 KB) RTOS සංකල්පය හඳුන්වා දෙයි. එහි schedulability බැඳීම, වැඩ කළ උදාහරණ හෝ EDF ගණනය කිරීම් නැත. මෙම කොටස ඒවා Liu සහ Layland ගේ මුල් පත්‍රිකාවෙන් අතින් ගණනය කරයි.

    1. මූලික පද#

    • ආවර්තිත කාර්යය (periodic task): සෑම T කාල ඒකකයකටම වරක් නැවත පැමිණෙන වැඩය. τ (tau) ලෙස ලියයි.
    • කාල පරිච්ඡේදය (period) T: නැවත පැමිණීම් අතර කාලය. මෙහිදී deadline එකද ඊළඟ පැමිණීමයි.
    • ධාවන කාලය (execution time) C: එක් වටයකට අවශ්‍ය CPU කාලය. සහතික කිරීම සඳහා නරකම අවස්ථාවේ ධාවන කාලය (worst-case execution time, WCET) යොදයි.
    • භාවිතය (utilization) U: U = Σ Cᵢ / Tᵢ. CPU කාලයෙන් කොටස.
    • Rate-monotonic (RM): කෙටි T → ඉහළ ස්ථිර priority.
    • Earliest deadline first (EDF): එම මොහොතේ ළඟම deadline ඇති කාර්යය ධාවනය කිරීම (priority වෙනස් වේ).
    • Preemption (preemption): ඉහළ priority කාර්යයක් පැමිණි විට පහළ එක නවතා එය ධාවනය කිරීම.

    2. Liu සහ Layland ඔප්පු කළ දේ#

    C. L. Liu සහ James W. Layland, Journal of the ACM 20(1), 1973 ජනවාරි (පිටු 46–61):

    • ප්‍රමේයය 2 (Theorem 2), පිටුව 51: කාර්ය කට්ටලයකට කිසියම් ස්ථිර priority පැවරුමක් ක්‍රියා කරයි නම්, rate-monotonic පැවරුමද ක්‍රියා කරයි.
    • ප්‍රමේයය 5, පිටුව 54: කාර්ය m ක් සඳහා RM ට සහතික කළ හැකි අවම භාවිත බැඳීම U = m(2^{1/m} − 1). m = 3 විට ≈ 0.78 බවත්, m විශාල වන විට ln 2 වෙත ළඟා වන බවත් පත්‍රිකාව කියයි.
    • ප්‍රමේයය 7, පිටුව 56: deadline ගතික ලෙස පවරන (EDF) ඇල්ගොරිතමයට කට්ටලය schedule කළ හැක්කේ Σ C/T ≤ 1 නම් සහ එසේ නම් පමණි.

    3. වැඩ කළ උදාහරණ (ආදර්ශ කාර්ය කට්ටල)#

    පහත කාර්ය කට්ටල අපි ගොඩනැගූ ආදර්ශ (illustrative) අංක වේ. කාලරේඛාවේ එක් අක්ෂරයක් = කාල ඒකක 1. අංකය = ධාවනය වන කාර්යය, - = CPU නිෂ්ක්‍රීය (idle).

    උදාහරණය A — බැඳීමට පහළින්: τ1 = (C 1, T 3), τ2 = (C 2, T 5). U = 1/3 + 2/5 = 0.7333 < 0.8284 → RM සහතිකයි. ගණනය නොකර පවා. කාලරේඛාව (0–15): 1221-212-1221--. සෑම deadline එකක්ම සපුරයි.

    • RM (τ1 ට ඉහළ priority): 1122211. t = 5 දී τ1 නැවත පැමිණ τ2 නවතයි. t = 7 වන විට τ2 ධාවනය කළේ ඒකක 3 ක් පමණි → deadline 7 මග හැරේ.
    • EDF: t = 5 දී τ1 හි deadline 10, τ2 හි deadline 7 → τ2 දිගටම යයි: 1122221…. t = 6 දී τ2 අවසන්. සාර්ථකයි.

    (අපි මෙම කාලරේඛා කුඩා simulator එකකින්ද පරීක්ෂා කළෙමු.)

    4. C (WCET) ලැබෙන්නේ කොහෙන්ද: mini-CPU මත උපදෙස් ගණන් කිරීම#

    ඉහත සියල්ල C දන්නා බව උපකල්පනය කරයි. සරල දෘඪාංගයක C ගණන් කළ හැකිය. ඉහත lab එකේ මෙම countdown වැඩසටහන ටයිප් කරන්න (ලේබල නැත, ලිපින අංක පමණි):

    LDI 1     ; 0
STA 15    ; 1: mem[15] = 1
LDI 5     ; 2: n = 5
OUT       ; 3
SUB 15    ; 4: A = A - 1
JZ 7      ; 5
JMP 3     ; 6
OUT       ; 7: 0 පෙන්වයි
HLT       ; 8

    Output 5, 4, 3, 2, 1, 0. Steps 24 (lab එකේ මූලාශ්‍ර කේතය ධාවනය කර පරීක්ෂා කළා). සාමාන්‍යයෙන් steps = 4n + 4 (n = 1: 8, n = 3: 16, n = 15: 64). n ⩽ 15 නම් නරකම අවස්ථාව n = 15: 64 steps. එය WCET වේ.

    උගුලක්: LDI 0 (n = 0) දුන්නොත්, පළමු SUB එක 0 − 1 = 255 කරයි. Loop එක 255 සිට 0 දක්වා ගොස් steps 1,028 ක් ගනී. වලංගු නොවන ආදානයක් (invalid input) WCET 16 ගුණයකින් වැඩි කරයි. සහතික කිරීමේදී ආදාන පරාසය (input range) සීමා කළ යුත්තේ මේ නිසාය.

    Cache, pipeline සහ interrupts ඇති නූතන CPU එකක මෙතරම් සරල ගණනයක් කළ නොහැක. මෙම පිටුවේ ප්‍රධාන පෙළ කියන “සරල දෘඪාංගය මත ගණන් කළ හැකි” කාලය යන්නෙහි තේරුම මෙයයි.

    5. Priority inversion: ආදර්ශ කාලරේඛාවක්#

    ඉහළ (H), මධ්‍යම (M) සහ පහළ (L) priority කාර්ය තුනක්. L සහ H එකම mutex (අන්‍යෝන්‍ය බැහැර කිරීමේ lock) එකක් භාවිත කරයි. ආදර්ශ අනුපිළිවෙල:

    1. t = 0: L mutex එක ගනී.
    2. t = 1: H පැමිණ, L නවතා, mutex ඉල්ලයි → අවහිරයි (blocked). L ට නැවත ධාවනය කළ යුතුය.
    3. t = 2: M පැමිණේ. M > L නිසා M ධාවනය වේ. L ට mutex මුදා හැරිය නොහැක. H, M සඳහා බලා සිටී, M H හා කිසිදු සම්බන්ධයක් නැතත්.

    විසඳුම priority inheritance (priority උරුම කිරීම): H අවහිර වූ විට, L තාවකාලිකව H හි priority ලබයි. M ට L නවතා දැමිය නොහැක. L mutex මුදා හරියි, H වහාම ධාවනය වේ. මෙය සැබෑ ලෝකයේ සිදු වූ ආකාරය ඊළඟ පෝස්ට් එකේ (Pathfinder) පෙනේ.

    6. පැන්සලෙන් අභ්‍යාසය#

    1. τ1 = (1, 2), τ2 = (1, 5). U සොයා RM බැඳීමෙන් සහතිකද කියන්න.
    2. කාර්ය 5 ක් සඳහා RM බැඳීම දශමස්ථාන 2 කට ගණනය කරන්න (2^{0.2} ≈ 1.1487).
    3. උදාහරණය C හි τ2 = (3, 7) ලෙස වෙනස් කළොත් RM සාර්ථකද? කාලරේඛාව (0–7) අඳින්න.
    4. Countdown වැඩසටහනේ n = 10 ට steps කීයද?
    5. U = 1.05 ක කාර්ය කට්ටලයක් EDF මගින් schedule කළ හැකිද?
