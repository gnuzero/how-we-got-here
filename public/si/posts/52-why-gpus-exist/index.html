    GPU පවතින්නේ ඇයි

    දුරුතු 1, 2026

    Phase 3 හි සෑම CPU එකක්ම උපකල්පනය කරන්නේ උපදෙස් ප්‍රමාණවත් තරම් ස්වාධීන සහ අනපේක්ෂිත බවයි — එබැවින් යන්ත්‍රණය සාමාන්‍ය-අරමුණු විය යුතුය: branch prediction, out-of-order execution, ගැඹුරු caches, අත්තනෝමතික අනුක්‍රමික කේතය වේගයෙන් ධාවනය කිරීමට. GPU ආරම්භ වන්නේ වෙනස් උපකල්පනයකින් — ඒවායේ මුල් workload එකෙන් මුල් බැස ගත්: එකම මෙහෙයුම විශාල දත්ත ලක්ෂ්‍ය ගණනකට ස්වාධීනව එකවර යෙදීම.

    Graphics Parallelism පැහැදිලි කළේය#

    3D scene එකක් render කිරීම යනු මිලියන ගණනක් vertices පරිවර්තනය කිරීම සහ මිලියන ගණනක් pixels shade කිරීමයි — එක එකකට එකම ගණිතය, pixel (100, 200) සහ pixel (100, 201) අතර අර්ථවත් රඳා පැවැත්මක් නැත. ප්‍රමාණවත් lanes තිබේ නම්, ඒ සියල්ල එකවර ධාවනය වේ.

    එය Phase 3 ගොඩනැගූ හැඩයට වඩා වෙනස් ය. CPU එකක් මෙවැනි නොපෙනෙන parallelism කේතයෙන් උපුටා ගනී. Graphics ට එම යන්ත්‍රණය අවශ්‍ය නැත: parallelism සැඟවී නැත — ආරම්භයේ සිටම පැහැදිලි සහ විශාල ය.

    SIMD / SIMT: එක් උපදෙසක්, බොහෝ Lanes#

    SIMD එක උපදෙසක් බොහෝ දත්ත මූලද්‍රව්‍ය හරහා එකවර යොදයි. GPU ඉතා සමීප ආකෘතියක් ක්‍රියාත්මක කරයි — SIMT: බොහෝ සමාන්තර threads, එක එකක් තමන්ගේ දත්ත මත (තමන්ගේ pixel, තමන්ගේ vertex), දෘඪාංගය සරල lanes හරහා ඒවා කණ්ඩායම් වශයෙන් lockstep ධාවනය කරයි.

    ප්‍රතිලාභය සෘජු ය: කණ්ඩායමක සෑම lane එකක්ම එකම උපදෙස එකම මොහොතේ ධාවනය කරයි, එබැවින් CPU එකක් core එකකට pipeline යන්ත්‍රණය අනුපිටපත් කරන ආකාරයෙන් lane එකකට fetch, decode, සහ control අනුපිටපත් නොකරයි. එක් බෙදාගත් control unit එකක් බොහෝ lanes ධාවනය කරයි — embarrassingly parallel, එකම-මෙහෙයුම-බොහෝ-දත්ත වැඩ සඳහා ප්‍රදේශය සහ බල ජයග්‍රහණයක්, අනපේක්ෂිත අනුක්‍රමික කේතයට නරක ගැලපීමක්. එබැවින් CPU සහ GPU හුවමාරු කළ නොහැකි ය, සහ සැබෑ පද්ධති සාමාන්‍යයෙන් දෙකම තබා ගනී.

    Graphics සිට සාමාන්‍ය Compute දක්වා#

    කර්මාන්තය හැඩගැස්වූ අවබෝධය: එම SIMT හැඩයම triangles ඉක්මවා බොහෝ පුළුල් පන්තියකට ගැලපේ — ගණිතය විශාල පරිමාණයෙන් සමාන්තර සහ නිත්‍ය වන විට. Neural-network training සහ inference බොහෝ දුරට එම වර්ගයේ matrix සහ vector වැඩෙන් ගොඩනැගේ — එබැවින් rendering සඳහා උපන් දෘඪාංගය ප්‍රමුඛ AI compute පදනම බවට පත් වූයේය, සහ මෙම අදියරේ ඉතිරිය එම සමාන්තර ගෘහ නිර්මාණය ක්‍රමලේඛනය කිරීම සහ පෝෂණය කිරීම ගැන ය, graphics ගැන විශේෂයෙන් නොවේ.

    ගැඹුරින්: GPU එකක් ප්‍රමාදය නොව ප්‍රතිදානය ඉලක්ක කරන්නේ ඇයි — අංකවලින්#

    සිංහල මූලාශ්‍ර පිළිබඳ සටහන: NIE 12 ශ්‍රේණිය ICT ගුරු මාර්ගෝපදේශය (PDF) PDF p.59 හි GPU එක එක් වාක්‍යයකින් අර්ථ දක්වයි: සංදර්ශකයක් සඳහා රූප නිර්මාණය වේගවත් කිරීමට සැලසුම් කළ විශේෂිත විද්‍යුත් පරිපථයක් ලෙස. si.wikipedia හි “ග්‍රැෆික් කාඩ්” ලිපිය (අක්ෂර ~9.7k) කාඩ්පතේ කොටස්, සම්බන්ධක සහ නිෂ්පාදකයින් විස්තර කරයි. Anytiplk වීඩියෝව (YT JKPH9DeROek) CUDA cores සහ AMD stream processors මිලදී ගන්නාගේ මට්ටමින් සසඳයි. අප වීඩියෝව හඳුනා ගත්තේ මාතෘකාවෙන් පමණි.

    ඒවා GPU එක කුමක්ද යන්න කියයි. නමුත් එහි හැඩය ඇයි එසේ වූයේද යන්න ගැන සිංහලෙන් අපට කිසිවක් හමු නොවීය: pixel ගණන කොපමණ වැඩ ප්‍රමාණයක්ද, SIMD පළල ALU ගණන වැඩි කරන්නේ කෙසේද, branch එකක් ඒ ලාභය අඩු කරන්නේ කොපමණද, සහ මතකය බලා සිටින කාලය thread මාරු කිරීමෙන් සඟවන්නේ කෙසේද. මෙම කොටස ඒවා අංකවලින් පෙන්වයි. Warp සහ occupancy Post 53 හි ද, මතක bandwidth Post 54 හි ද, tensor cores Post 55 හි ද, matrix ගුණ කිරීම Post 57 හි ද ඇත.

    1. මූලික පද#

    • ප්‍රමාදය (latency): එක් කාර්යයක් ආරම්භයේ සිට අවසානය දක්වා ගන්නා කාලය.
    • ප්‍රතිදානය (throughput): ඒකක කාලයකදී අවසන් කරන කාර්ය ගණන.
    • ගණිත-තාර්කික ඒකකය (arithmetic logic unit, ALU): එකතු කිරීම, ගුණ කිරීම වැනි එක් මෙහෙයුමක් කරන පරිපථය (Post 08).
    • SIMD පළල (SIMD width, S): එක් උපදෙසක් එකවර ක්‍රියාත්මක කරන ALU ගණන. එක් එක් ALU එක lane එකකි.
    • ක්‍රියාත්මක සන්දර්භය (execution context): Thread එකක program counter, registers ආදී තත්ත්වය.
    • නැවතීම (stall): ඊළඟ උපදෙසට අවශ්‍ය දත්ත (උදා. මතකයෙන්) තවම නොපැමිණි නිසා thread එකට ඉදිරියට යා නොහැකි වීම.
    • Fragment: Triangle එකක් screen එක මත ආවරණය කරන එක් නියැදි ලක්ෂ්‍යයක්. එය pixel එකක අගයට දායක විය හැක.
    • Shader: සෑම vertex එකකටම හෝ fragment එකකටම වෙන වෙනම ධාවනය වන කුඩා වැඩසටහන.

    2. වැඩ ප්‍රමාණය: pixel කීයක්ද?#

    ආදර්ශ ගණනය:

    • 1920 × 1080 තිරය = 2,073,600 pixels. තත්පරයට රාමු (frames) 60 ක් නම්: 2,073,600 × 60 = 124,416,000 pixels/s.
    • 3840 × 2160 (4K) = 8,294,400 pixels. × 60 = 497,664,000 pixels/s.

    දැන් එක් pixel එකකට shader උපදෙස් 100 ක් යැයි සිතමු (ආදර්ශ අගයකි). 1080p හිදී එය තත්පරයට උපදෙස් 124,416,000 × 100 ≈ 1.24 × 10¹⁰ කි. Cycle එකකට එක් උපදෙසක් කරන 3 GHz core එකකට pixel එකක් සඳහා ඇත්තේ 3 × 10⁹ ÷ 124,416,000 ≈ 24 cycles පමණි. උපදෙස් 100 කට එය මදි. එක් වේගවත් core එකක් වෙනුවට බොහෝ ALUs අවශ්‍ය වන්නේ එබැවිනි. Pixel එකිනෙක ස්වාධීන නිසා (ඉහත “Graphics Parallelism” කොටස) ඒවා බෙදා දීම පහසුය.

    3. NVIDIA ගේ නිල විස්තරය#

    CUDA Programming Guide (v13.4.2), §1.1.1 සහ §1.1.2 මෙසේ කියයි:

    • GPU එක ආරම්භ වූයේ ත්‍රිමාණ graphics සඳහා ස්ථාවර-කාර්ය දෘඪාංගයක් (fixed-function hardware) ලෙසය. 2003 වන විට graphics pipeline හි සමහර අදියර සම්පූර්ණයෙන් ක්‍රමලේඛනය කළ හැකි විය. 2006 දී NVIDIA, graphics API නොමැතිව ඕනෑම ගණනයකට GPU භාවිතා කිරීමට CUDA හඳුන්වා දුන්නේය.
    • CPU එකක් එක් thread එකක් හැකි තරම් වේගයෙන් ධාවනය කිරීමට සැලසුම් කර ඇති අතර එවැනි threads “දුසිම් කිහිපයක්” (a few tens) සමාන්තරව ධාවනය කළ හැක. GPU එකක් threads දහස් ගණනක් සමාන්තරව ධාවනය කරයි. ඒ සඳහා එක් thread එකක වේගය කැප කරයි.
    • GPU එක transistors වැඩි ප්‍රමාණයක් දත්ත සැකසීමට (ALUs) යොදයි. CPU එක transistors වැඩි ප්‍රමාණයක් දත්ත cache කිරීමට සහ පාලන ප්‍රවාහයට (flow control) යොදයි.

    4. අදහස 1: බොහෝ cores + පුළුල් SIMD = ALU විශාල ගණනක්#

    Kayvon Fatahalian සහ Mike Houston ගේ 2008 ලිපිය “A Closer Look at GPUs” (Communications of the ACM) මෙම හැඩය අදහස් තුනකින් පැහැදිලි කරයි. පළමුවැන්න: fetch/decode කොටස එකක් ALU රාශියක් අතර බෙදා ගැනීම (SIMD).

    ලිපියේ අංක (p.54): 3 GHz Intel Core 2 Quad එකේ cores 4 ක් ඇත. එක් core එකක SIMD floating-point ALUs 8 බැගින් ඇත. එබැවින් උපරිම වේගය:

    4 × 8 × 3 × 10⁹ = 96 × 10⁹ FLOPS (96 GFLOPS)

    ලිපිය එම යුගයේ NVIDIA GeForce GTX 280 GPU එකේ උපරිම වේගය 933 GFLOPS ලෙස දෙයි. (සටහන: ලිපියේ පෙළ GTX 280 හි “480 ALUs” 1.3 GHz දී ඇති බව කියයි. නමුත් එම ලිපියේම Table 1 අනුව cores 30 × SIMD ALUs 8 = 240 කි. මෙම වෙනස ලිපිය පැහැදිලි නොකරයි. එබැවින් 933 අගය අපි ලිපියෙන් උපුටා දක්වමු; CPU අගය මෙන් cores × ALUs × GHz ලෙස ගණනය නොකළෙමු.) එය 933 ÷ 96 ≈ 9.7 ගුණයකි.     5. SIMD හි මිල: branch වෙන් වීම#

    Lanes 32 ම එකම උපදෙස කරයි. එසේනම් if එකක lanes සමහරක් එක් මාර්ගයකුත් අනෙක් ඒවා අනෙක් මාර්ගයකුත් ගත්තොත් කුමක් වේද? ලිපිය (p.54) කියන්නේ කණ්ඩායම මාර්ග දෙකම ධාවනය කරන බවයි. අදාළ නොවන lanes ලිවීම් වසා (write-mask) නිකරුණේ සිටී. පළල S නම්, නරකම අවස්ථාවේ වේගය උපරිමයෙන් 1/S කි. S = 32 නම් 1/32 ≈ 3.1%.

    ආදර්ශ උදාහරණය: Lanes 32. if මාර්ගය A = උපදෙස් 10, else මාර්ගය B = උපදෙස් 30.

    තත්ත්වය කණ්ඩායම ධාවනය කරන උපදෙස් ප්‍රයෝජනවත් lane-උපදෙස් කාර්යක්ෂමතාව
    lanes 32 ම A 10 32 × 10 = 320 320 ÷ 320 = 100%
    16 A, 16 B 10 + 30 = 40 16 × 10 + 16 × 30 = 640 640 ÷ (32 × 40) = 50%

    Pixels ආසන්න වශයෙන් එකම මාර්ගය ගන්නා නිසා graphics වලදී මෙය බොහෝ විට හොඳින් ක්‍රියා කරයි. අක්‍රමවත් branches ඇති කේතය GPU එකට නරක ගැලපීමක් වන්නේ මේ නිසාය.

    6. අදහස 2: thread මාරු කර මතක ප්‍රමාදය සැඟවීම#

    Texture එකක් මතකයෙන් කියවීමට cycles සිය ගණනක් ගත විය හැකි බව ලිපිය (p.54) කියයි. CPU එකක් එම ප්‍රමාදය විශාල caches සහ out-of-order execution මඟින් වළක්වා ගැනීමට උත්සාහ කරයි. GPU එකක් එය සඟවයි: core එකට ධාවනය කළ හැකි ප්‍රමාණයට වඩා බොහෝ thread සන්දර්භ chip එක මත තබා ගෙන, එක් thread එකක් නැවතුණු විගස තවත් එකකට මාරු වේ. මෙය දෘඪාංග multithreading (hardware multithreading) ලෙස හැඳින්වේ.

    ලිපියේ උදාහරණය (p.55 පෙට්ටිය): එක් core එකක lanes 32. Threads 4 (T0–T3). Texture කියවීම් අතර ගණිත උපදෙස් 20 ක්. Texture ප්‍රමාදය උපරිම cycles 50.

    cycles 0–20 20–40 40–60 60–80 80–100
    T0 ධාවනය නැවතී නැවතී නැවතී (70 සිට සූදානම්) ධාවනය
    T1 සූදානම් ධාවනය නැවතී නැවතී නැවතී (90 සිට සූදානම්)
    T2 සූදානම් සූදානම් ධාවනය නැවතී නැවතී
    T3 සූදානම් සූදානම් සූදානම් ධාවනය නැවතී

    T0 cycle 20 දී නවතී. T1, T2, T3 එකිනෙක cycles 20 බැගින් ධාවනය වේ. T0 ගේ දත්ත cycle 70 දී ලැබේ. T3 cycle 80 දී නවතින විට T0 නැවත ආරම්භ වේ. ALUs කිසි විටෙක නිකරුණේ නොසිටී.

    අවශ්‍ය thread ගණන (උදාහරණයෙන් අප ව්‍යුත්පන්න කළ නීතිය): එක් thread එකක් නැවතී සිටින කාලය L, අනෙක් threads වල වැඩ වලින් පිරවිය යුතුය: (T − 1) × C ≥ L. මෙහි C = නැවතීම් අතර උපදෙස් ගණනය.

    • L = 50, C = 20: T = 3 නම් 2 × 20 = 40 < 50 (මදි). T = 4 නම් 3 × 20 = 60 ≥ 50. එබැවින් T = 4. ලිපියේ පිළිතුරද එයයි.
    • Fragments: threads 4 × lanes 32 = 128 (ලිපිය: “4*32=128”).
    • ලිපිය මෙය cores 16 කට සහ core එකකට සන්දර්භ 16 කට විහිදුවයි: 16 × 16 × 32 = 8,192 fragments එකවර අවශ්‍ය වේ. GPU වේගය සමාන්තර වැඩ බහුල වීම මත රඳා පවතින්නේ මේ නිසාය.

    ලිපියේ Table 1 අනුව, ධාවනය කළ හැකි threads වලට සාපේක්ෂව chip එක මත තබා ගත හැකි සන්දර්භ අනුපාතය (Max T) GTX 280 එකේ 128 කි. Core 2 Quad එකේ 1 කි. Sun UltraSPARC T2 එකේ 4 කි. NVIDIA ගේ threads 32 කණ්ඩායම් (warps) සහ Little’s නියමයෙන් “warps කීයක් අවශ්‍යද” යන්න Post 53 හි ඇත.

    7. ප්‍රමාදය සහ ප්‍රතිදානය අතර හුවමාරුව#

    ලිපිය (p.55) කියන්නේ: නැවතීම් නැති විට multithreading ALU ගණන වැඩි නොකරයි. එය පවතින ALUs වඩා හොඳින් භාවිතා කරයි. උපරිම වේගයෙන් ධාවනය වන core එකක් එක් thread එකක් කාලයෙන් 1/T ක් පමණක් ධාවනය කරයි.

    ආදර්ශ ගණනය (ඉහත උදාහරණය දිගු කිරීම): සෑම thread එකකටම උපදෙස් 20, texture, උපදෙස් 20 යැයි සිතමු.

    • Thread එකක් තනිව: 20 + 50 + 20 = cycles 90. එයින් ALUs වැඩ කළේ cycles 40 යි: 40 ÷ 90 ≈ 44%.
    • Threads 4 එකින් එක: 4 × 90 = cycles 360.
    • Threads 4 මාරුවෙන් මාරුවට: T0 0–20, T1 20–40, T2 40–60, T3 60–80, T0 80–100, T1 100–120, T2 120–140, T3 140–160. සෑම thread එකකම දත්ත, එය නැවත ආරම්භ වීමට පෙර ලැබේ (T1: 40 + 50 = 90 ≤ 100). මුළු කාලය cycles 160, ALUs 100% කාර්යබහුලය.

    ප්‍රතිදානය 360 ÷ 160 = 2.25 ගුණයකින් වැඩි විය. නමුත් T0 අවසන් වූයේ cycle 100 දීය (තනිව 90). T3 අවසන් වූයේ 160 දීය. එක් එක් thread එකේ ප්‍රමාදය වැඩි විය. GPU එක දිනන්නේ මේ හුවමාරුවෙනි.
