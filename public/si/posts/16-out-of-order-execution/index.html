    Out-of-Order Execution

    දුරුතු 1, 2026

    Post 13 හි load-use hazard එක in-order pipeline එකක් රැඳෙන එක් උපදෙස් එකක් පසුපසින් stall කරයි — පසු උපදෙස් ස්වාධීන සහ සූදානම් වුවද. Out-of-order execution එම සීමාවට පිළිතුරු දෙයි: operands සූදානම් වූ සෑම විටම ස්වාධීන වැඩ ධාවනය කරන්න; වැඩසටහන් අනුපිළිවෙල බලාත්මක කරන්නේ ගෘහ නිර්මාණයට අවශ්‍ය තැන්වල පමණි.

    ව්‍යාජ Dependencies සහ Register Renaming#

    සෑම “dependency” එකක්ම සැබෑ නොවේ. උපදෙස් A R1 ලියයි සහ පසු උපදෙස් Bද අදාළ නොවන ප්‍රතිඵලයක් සඳහා R1 ලියයි නම්, ඒවා අතර අගයක් ගලන්නේ නැත — ISA එකට හුදෙක් අඩු ගෘහ නිර්මාණ register නම් ඇත, සහ සම්පාදකය එකක් නැවත භාවිතා කළේය. එය name (ව්‍යාජ) dependency එකකි, සැබෑ data dependency එකක් නොවේ.

    Register renaming CPU එකට ISA එක හෙළිදරව් කරනවාට වඩා බොහෝ physical registers ලබා දෙයි, සහ decode වේලාවේ සෑම ලිවීමක්ම නව physical register එකකට සිතියම් කරයි. A ගේ “R1” P17 වේ; B ගේ පසු “R1” P42 වේ. ව්‍යාජ ගැටුමක් නැත; දෙකම ඉදිරියට යා හැක.

    සූදානම් වූ විට Issue කරන්න, අනුපිළිවෙලින් Commit කරන්න#

    Rename කළ උපදෙස් සැබෑ operands පැමිණෙන තුරු reservation stations වල රැඳෙයි (අගයෙන් හෝ තවමත් ගුවන්ගතව ඇති producer එකකින් tag එකකින්). Operands සූදානම් වූ මොහොතේ, උපදෙස් එකක් execution unit එකකට issue කළ හැක — මුල් වැඩසටහන් අනුපිළිවෙල නොසලකා. එය out-of-order කොටසයි.

    ගෘහ නිර්මාණ බලපෑම් තවමත් in-order ලෙස පෙනිය යුතුය: දෘශ්‍ය registers, මතකය, exceptions. Reorder buffer (ROB) සෑම ගුවන්ගත උපදෙස් එකක්ම වැඩසටහන් අනුපිළිවෙලින් ලුහුබඳියි සහ ප්‍රතිඵල retire කරන්නේ එම අනුපිළිවෙලින් පමණක් ගෘහ නිර්මාණ තත්ත්වයට — ක්‍රියාත්මක කිරීම විවිධ වේලාවල අවසන් වුවද.

    “සූදානම් වූ විට ක්‍රියාත්මක කරන්න, දැඩි ලෙස අනුපිළිවෙලින් commit කරන්න” — බොහෝ විට Robert Tomasulo ගේ IBM System/360 Model 91 floating-point unit සඳහා වූ ඇල්ගොරිතමයට (1967 දී ප්‍රකාශිත) ආරෝපණය කෙරෙන රටාව — එතැන් සිට ප්‍රායෝගිකව සෑම ඉහළ-කාර්ය සාධන out-of-order CPU එකකම සංකල්පීය හරයයි. එය මිල අධිකද වේ: renaming tables, reservation stations, සහ ROB එකට ප්‍රදේශය සහ බලය වැය වේ. එම යන්ත්‍රෝපකරණ තවත් එකතු කිරීමට අඩුවන ප්‍රතිලාභ ඇත — ඊළඟ පෝස්ට් එක හිසෙන් හැපෙන බිත්තිය.

    Lab එක නව tab එකක විවෘත කරන්න ↗

    ගැඹුරින්: අනුපිළිවෙළින් තොර ක්‍රියාත්මක කිරීම (out-of-order execution) පියවරෙන් පියවර#

    සිංහල මූලාශ්‍ර පිළිබඳ සටහන: 2026 සැප්තැම්බරයේ සමීක්ෂණයේදී out-of-order execution, register renaming හෝ reorder buffer ගැන සිංහල පැහැදිලි කිරීමක් (ලිඛිත හෝ වීඩියෝ) අපට හමු නොවීය; සිංහල විකිපීඩියාවේ CPU ලිපියේ සඳහන් වන්නේ out-of-order execution යන නම පමණි (“ක්‍රියා විරහිත සම්පාදනය” ලෙස); register renaming සහ reorder buffer කිසිසේත් සඳහන් නොවේ. එබැවින් මෙහි සෑම පදයක්ම නිර්වචනය කර, කුඩා උදාහරණයකින් ගණනය කර පෙන්වමු.

    1. පරායත්තතා (dependencies) වර්ග තුන#

    උපදෙස් දෙකක් අතර පරායත්තතාවක් (dependency) ඇත්තේ එකක ප්‍රතිඵලය හෝ එක් රෙජිස්ටරයක් භාවිතය අනෙකට බලපාන විටය. රෙජිස්ටර් R1, R2… ලෙස නම් කර, වර්ග තුන බලමු:

    වර්ගය ඉංග්‍රීසි නම උදාහරණය සැබෑද?
    කියවීමට පෙර ලිවීම RAW (read after write) — සැබෑ දත්ත පරායත්තතාව R1 ← … පසුව … ← R1 + R3 ඔව් — අගයක් එකකින් අනෙකට ගලයි
    ලිවීමට පෙර කියවීම WAR (write after read) — ප්‍රති-පරායත්තතාව … ← R1 + R3 පසුව R1 ← … නැත — රෙජිස්ටර් නම පමණක් බෙදා ගනී
    ලිවීමට පසු ලිවීම WAW (write after write) — ප්‍රතිදාන පරායත්තතාව R1 ← … පසුව නැවත R1 ← … නැත — රෙජිස්ටර් නම පමණක් බෙදා ගනී

    RAW පමණක් සැබෑ දත්ත ගලායාමකි: දෙවන උපදෙසට පළමු උපදෙසේ ප්‍රතිඵලය නැතිව ආරම්භ කළ නොහැක. WAR සහ WAW නාම පරායත්තතා (name dependencies) ය — ISA එකට ඇත්තේ සීමිත රෙජිස්ටර් නම් ගණනක් නිසා සම්පාදකය එකම නම නැවත භාවිත කිරීමෙන් ඇති වන ඒවාය. මෙම පෝස්ට් එකේ ඉහත “ව්‍යාජ dependencies” කියන්නේ මේවාටයි.

    2. වැඩ කළ උදාහරණයක්#

    උපදෙස් පහක කුඩා වැඩසටහනක් ගනිමු:

    I1: LOAD R1 ← mem[A]     ; මතකයෙන් කියවීම — cache miss (පහත බලන්න)
I2: ADD  R2 ← R1 + R3    ; I1 ගේ R1 අවශ්‍යයි (RAW)
I3: MUL  R4 ← R5 × R6    ; ස්වාධීනයි
I4: ADD  R7 ← R4 + R5    ; I3 ගේ R4 අවශ්‍යයි (RAW)
I5: SUB  R1 ← R8 − R9    ; R1 නැවත ලියයි: I1 සමඟ WAW, I2 සමඟ WAR

    ඉගැන්වීම සඳහා සරල උපකල්පන (සැබෑ CPU එකක නිශ්චිත අගයන් නොවේ): චක්‍රයකට ක්‍රියාත්මක කිරීම ආරම්භ කළ හැක්කේ එක් උපදෙසකට පමණි; ADD/SUB චක්‍ර 1; MUL චක්‍ර 3; LOAD එක cache එකේ නැති නිසා (cache miss) චක්‍ර 10ක්; ප්‍රතිඵලයක් ඊළඟ චක්‍රයේ සිට භාවිත කළ හැක.

    (අ) අනුපිළිවෙළින් (in-order): උපදෙසක් ආරම්භ කළ හැක්කේ ඊට පෙර ඇති සියල්ල ආරම්භ වූ පසුව පමණි; operands නොමැති නම් එතැනම නැවතී, පිටුපස ඇති සියල්ල ද රඳවා තබයි.

    උපදෙස ක්‍රියාත්මක වන චක්‍ර හේතුව
    I1 1–10 cache miss
    I2 11 R1 සූදානම් වන තුරු රැඳුණි
    I3 12–14 ස්වාධීන වුවත් I2 පිටුපස හිරවී සිටියේය
    I4 15 R4 සඳහා
    I5 16 අනුපිළිවෙළ

    මුළු කාලය: චක්‍ර 16. 2 සිට 10 දක්වා චක්‍ර 9ක් පුරා කිසිදු නව උපදෙසක් ආරම්භ නොවීය — I3, I4, I5 සූදානම්ව තිබියදීත් (load එක මතකය එනතුරු රැඳී සිටියා පමණි).

    (ආ) අනුපිළිවෙළින් තොරව (out-of-order), register renaming සමඟ: operands සූදානම් වූ ඕනෑම උපදෙසක් ආරම්භ කළ හැක.

    උපදෙස ක්‍රියාත්මක වන චක්‍ර හේතුව
    I1 1–10 cache miss
    I3 2–4 ස්වාධීනයි — කෙලින්ම යයි
    I5 3 renaming නිසා R1 ගැටුමක් නැත (පහත බලන්න)
    I4 5 R4 (I3 ගෙන්) දැන් සූදානම්
    I2 11 R1 (I1 ගෙන්) දැන් සූදානම්

    මුළු කාලය: චක්‍ර 11 — 16/11 ≈ 1.45 ගුණයක වේගයක්, කිසිදු උපදෙසක් වේගවත් නොකර. වැඩ ප්‍රමාණය එකමයි; වෙනස් වූයේ රැඳී සිටීම සමඟ වැඩ අතිච්ඡාදනය (overlap) කිරීම පමණි. Post 35 හි මතක බිත්තිය සඟවන්නේ මෙලෙසිනි.

    3. I5 ට කලින් යා හැක්කේ ඇයි? — register renaming#

    Renaming නොමැතිව I5 කලින් ක්‍රියාත්මක කිරීම භයානකයි. I5 R1 ට ලියයි; I1 ද R1 ට ලියයි (WAW), නමුත් I1 අවසන් වන්නේ 10 වන චක්‍රයේය. I5 3 වන චක්‍රයේ R1 ලියා, පසුව I1 10 වන චක්‍රයේ R1 ලිව්වොත්, වැඩසටහන අවසානයේ R1 හි ඇත්තේ වැරදි අගයයි (I5 ගේ අගය තිබිය යුතුය). එමෙන්ම I2 ට අවශ්‍ය I1 ගේ R1 මිස I5 ගේ R1 නොවේ (WAR).

    Register renaming මෙය විසඳයි. CPU එක ඇතුළත ISA එකේ නම්වලට වඩා බොහෝ භෞතික රෙජිස්ටර් (physical registers) — P1, P2, … — ඇත. Decode කරන විට නැවත නම් කිරීමේ වගුවක් (rename table) මඟින් සෑම ලිවීමක්ම නව භෞතික රෙජිස්ටරයකට යොමු කරයි:

    උපදෙස ලියන්නේ කියවන්නේ නම් කිරීමෙන් පසු
    I1 R1 → P1 — P1 ← mem[A]
    I2 R2 → P2 R1 = P1, R3 P2 ← P1 + R3
    I3 R4 → P3 R5, R6 P3 ← R5 × R6
    I4 R7 → P4 R4 = P3, R5 P4 ← P3 + R5
    I5 R1 → P5 R8, R9 P5 ← R8 − R9

    දැන් I1 P1 ට ද I5 P5 ට ද ලියයි — ගැටුමක් නැත. I2 P1 කියවයි, එබැවින් I5 කුමක් කළත් I2 ට නිවැරදි අගය ලැබේ. ඉතිරි වූයේ සැබෑ RAW පරායත්තතා දෙක පමණි (I1→I2, I3→I4). වැඩසටහන අවසානයේ, “R1” යන නමට අදාළ වන්නේ P5 බව වගුව මතක තබා ගනී.

    4. රැඳවුම් ස්ථාන සහ නැවත පිළිවෙළ කිරීමේ බෆරය#

    • රැඳවුම් ස්ථාන (reservation stations): Rename කළ උපදෙස් operands එනතුරු මෙහි රැඳේ. සෑම operand එකක්ම එක්කෝ අගයක්, නැතිනම් “P1 එනතුරු රැඳී සිටින්න” වැනි tag එකකි. ක්‍රියාත්මක කිරීමේ ඒකකයක් ප්‍රතිඵලයක් නිකුත් කළ විට (උදා. “P1 = 42”) එය බස් එකක් මඟින් සියලු රැඳවුම් ස්ථාන වෙත විකාශනය වේ; P1 බලාපොරොත්තුවෙන් සිටි I2 එය අල්ලා ගෙන සූදානම් වේ.
    • නැවත පිළිවෙළ කිරීමේ බෆරය (reorder buffer, ROB): සියලු උපදෙස් මුල් වැඩසටහන් අනුපිළිවෙළින් පෝලිමක තබයි. ක්‍රියාත්මක කිරීම අවසන් වන්නේ ඕනෑම අනුපිළිවෙළකින් වුවත්, ප්‍රතිඵල ගෘහ නිර්මාණ තත්ත්වයට commit (retire) වන්නේ පෝලිමේ හිසින් පමණි — එනම් අනුපිළිවෙළින්ම.

    අපේ උදාහරණයේ I3, I5, I4 කලින් අවසන් වුවද ඒවා ROB එකේ රැඳේ. I1 (චක්‍රය 10 අවසානයේ) commit වේ; ඉන්පසු I2 (චක්‍රය 11); ඉන්පසු I3, I4, I5 පිළිවෙළින් — ඒවා දැනටමත් අවසන් නිසා වහාම.

    ඇයි මෙතරම් කරදරයක්? නිවැරදි ව්‍යතිරේක (precise exceptions) සඳහායි. I1 ගේ මතක ලිපිනය වලංගු නැතැයි සිතමු (උදා. page fault — Post 24). ROB නොමැතිව, I3–I5 ගේ ප්‍රතිඵල දැනටමත් රෙජිස්ටරවලට ලියා තිබිය හැක — මෙහෙයුම් පද්ධතියට පෙනෙන්නේ “I1 අසාර්ථක වූ නමුත් පසු උපදෙස් කොටසක් ක්‍රියාත්මක වූ” අවුල් තත්ත්වයකි. ROB සමඟ, I1 හිසට ආ විට දෝෂය හඳුනාගෙන, ROB හි ඇති පසු සියලු ප්‍රතිඵල ඉවත දමයි. මෙහෙයුම් පද්ධතියට පෙනෙන්නේ වැඩසටහන හරියටම I1 හිදී නැවතුණු ලෙසයි. Post 14 හි වැරදි ශාඛා අනාවැකියකින් පසු අනුමාන උපදෙස් ඉවත් කරන්නේද මෙම යාන්ත්‍රණයෙනිමය.

    5. දැන්ම උත්සාහ කරන්න: Mini-CPU වැඩසටහනක පරායත්තතා සොයන්න#

    ඉහත Mini-CPU lab එකේ පෙරනිමියෙන් පූරණය වී ඇති වැඩසටහන බලන්න:

    0: LDI 5     ; A ← 5
1: STA 14    ; mem[14] ← A
2: LDI 8     ; A ← 8
3: ADD 14    ; A ← A + mem[14]
4: STA 15    ; mem[15] ← A
5: LDA 15    ; A ← mem[15]
6: OUT
7: HLT

    Step ඔබමින් යමින්, සෑම උපදෙස් යුගලයක් අතරම ඇති පරායත්තතාව ලියන්න. උදාහරණ: 0→1 RAW (STA 14 ට LDI 5 ගේ A අවශ්‍යයි); 1→2 WAR (STA 14 A කියවයි, ඉන්පසු LDI 8 A ලියයි); 0→2 WAW (දෙකම A ලියයි); 1→3 මතකය හරහා RAW (ADD 14 ට STA 14 ලියූ mem[14] අවශ්‍යයි).

    මෙම යන්ත්‍රයේ රෙජිස්ටරය එකක් පමණි (A — “accumulator”). එබැවින් සෑම උපදෙසක්ම පාහේ අනෙක් සියල්ලට ගැට ගැසී ඇත — එයින් බොහොමයක් සැබෑ දත්ත ගලායාමක් නොව නාම ගැටුම් පමණි. LDI 8 ට 5 දැනගත යුතු නැත; එය ප්‍රමාද වන්නේ A යන නම බෙදා ගන්නා නිසා පමණි. නවීන ISA වල සාමාන්‍ය කාර්ය රෙජිස්ටර් 16–32ක් පමණ ඇත්තේත්, ඊටත් වඩා භෞතික රෙජිස්ටර් ඇතුළත සඟවා renaming කරන්නේත් එබැවිනි: සැබෑ පරායත්තතා පමණක් ඉතිරි කර, අනෙක් සියල්ල සමාන්තරව දුවවන්නට.

    පිටවීමේ දොර: R. M. Tomasulo, “An Efficient Algorithm for Exploiting Multiple Arithmetic Units” (IBM Journal of Research and Development, 1967) — නවීන out-of-order issue සහ rename පිටුපස ප්‍රාථමික පත්‍රය.
