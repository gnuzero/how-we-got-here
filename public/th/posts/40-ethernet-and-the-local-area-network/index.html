    Ethernet และเครือข่ายท้องถิ่น

    มกราคม 1, 2026

    ARPANET (บทที่ 39) แก้การสลับแพ็กเก็ตระยะไกลระหว่างไซต์ห่าง ในอาคารเดียว การ routing แบบ IMP สำหรับสายไม่กี่สิบเมตรคือเครื่องมือผิด Ethernet ที่เริ่มที่ Xerox PARC ปี 1973 โดย Robert Metcalfe และ David Boggs กลายเป็นคำตอบท้องถิ่นที่ครอง

    คำศัพท์ก่อนเริ่ม (ศัพท์บัญญัติราชบัณฑิตยสภา สาขาคอมพิวเตอร์และเทคโนโลยีสารสนเทศ เว้นแต่ระบุ): อีเทอร์เน็ต (Ethernet); บัส (bus); ทอพอโลยี (topology); กลุ่มข้อมูล (packet); กรอบ หรือ กรอบความ (frame — ในบทนี้ใช้คู่กับคำทับศัพท์ “เฟรม”); ส่วนหัว (header); เลขที่อยู่ (address); เกณฑ์วิธี หรือ โพรโทคอล (protocol); การแพร่สัญญาณ (broadcast); แพร่สัญญาณเฉพาะกลุ่ม (multicast); คลื่นพาห์ (carrier); สายโคแอ็กซ์ (coaxial cable); เครื่องรับส่ง (transceiver); เครื่องทวนสัญญาณ (repeater); ฮับ (hub); บริดจ์ (bridge); สวิตช์ (switch); และ แผ่นวงจรต่อประสานเครือข่าย (network interface card — การ์ดเครือข่าย) จากสาขาวิทยาศาสตร์และคณิตศาสตร์: สุ่ม (random) และ ความน่าจะเป็น (probability) คำต่อไปนี้ยังไม่พบศัพท์บัญญัติในความหมายนี้ จึงใช้คำอธิบายพร้อมคำอังกฤษ: local area network หรือ LAN (เครือข่ายท้องถิ่น), collision (การชน — ศัพท์บัญญัติ “การโดนกัน” มีเฉพาะสาขาประกันภัยและนิติศาสตร์), carrier sense (การฟังคลื่นพาห์), unicast (ส่งถึงปลายทางเดียว), preamble (ส่วนนำ), backoff (การถอยรอ), slot time (ช่วงเวลาหนึ่งช่อง) และ cyclic redundancy check หรือ CRC (รหัสตรวจสอบส่วนซ้ำแบบวน)

    ปัญหาสื่อร่วม#

    Ethernet ยุคแรกวางหลายสถานีบนสายร่วมหนึ่งเส้น — ทอโพโลยีบัส ชนิด ความแย่งเดียวกับที่บทที่ 31 เผชิญในเครื่อง ตอนนี้บน LAN ทุกสถานีส่งได้; ทุกสถานีได้ยินทุกการส่ง สองตัวส่งพร้อมกันแล้วทั้งสองเสีย

    บทความของ Metcalfe และ Boggs (1976) ที่ประตูออกของบทนี้บรรยายระบบทดลองที่ใช้งานอยู่จริงในตอนนั้น: 100 สถานีบนสายโคแอ็กซ์ยาวราวหนึ่งกิโลเมตร “Ether” เป็นสื่อแพร่สัญญาณแบบพาสซีฟที่ไม่มีการควบคุมจากศูนย์กลาง ผู้เขียนบทความเลือกพารามิเตอร์ 1 กิโลเมตร 3 เมกะบิตต่อวินาที และ 256 สถานี (เลขที่อยู่ปลายทางและต้นทางยาวอย่างละ 8 บิต = 256 ค่า) และย้ำว่าพารามิเตอร์สามตัวนี้ “ไม่ใช่ข้อจำกัดตายตัวที่จำเป็นต่อแนวคิด Ethernet” นอกจากนี้ระบบทดลองมี CRC 16 บิตต่อท้าย และจำกัดความยาวกลุ่มข้อมูลในซอฟต์แวร์ไว้ราว 4,000 บิต — Ethernet ปัจจุบันเปลี่ยนเกือบทุกตัว แต่หลักการยังเหมือนเดิม

    CSMA/CD: ฟัง ส่ง ตรวจ ถอย#

    คำตอบของ Ethernet คือ CSMA/CD Carrier Sense: ฟังก่อน; ส่งเฉพาะเมื่อสื่อดูว่าง Multiple Access: สถานีใดก็ได้ลอง — ไม่มี grant ศูนย์กลาง ต่างจาก request/grant บนบัสระบบ (บทที่ 31) Collision Detection: ฟังต่อขณะส่ง; หากมีการชน หยุด รอ backoff สุ่ม แล้วลองใหม่

    การสุ่มคือกลเม็ดที่รับน้ำหนัก Backoff คงที่เหมือนกันจะชนตลอด การรอสุ่มต่างกันให้สถานีหนึ่งสำเร็จก่อนอีกตัวลองใหม่ — ความแย่งแบบกระจายโดยไม่มีผู้ตัดสิน

    ทำไมเฟรมต้องยาวอย่างน้อย 512 บิต#

    การตรวจการชนมีเงื่อนไขซ่อนอยู่: ผู้ส่งต้อง ยังส่งอยู่ ตอนที่สัญญาณชนเดินทางกลับมาถึง คิดกรณีเลวที่สุดจากหลักการแรก (ตามหนังสือ Computer Networks: A Systems Approach ของ Peterson และ Davie): สถานี A กับ B อยู่คนละปลายสาย ให้ d คือเวลาที่สัญญาณเดินทางจากปลายหนึ่งไปอีกปลาย

    • เวลา t: A เริ่มส่ง
    • เวลาเกือบ t + d: บิตแรกของ A ยังไม่ถึง B ฝั่ง B เห็นสายว่างจึงเริ่มส่ง แล้วชนทันที B ส่งสัญญาณรบกวน (jam) 32 บิตแล้วหยุด
    • เวลา t + 2d: สัญญาณชนจาก B เดินทางกลับถึง A

    A จึงต้องส่งต่อเนื่องอย่างน้อย 2d ถ้าเฟรมสั้นกว่านั้น A ส่งจบไปแล้วก่อนรู้ว่าชน และจะเข้าใจผิดว่าส่งสำเร็จ หนังสือระบุว่า Ethernet 10 Mb/s ที่ยาวสูงสุด 2,500 เมตร มีเครื่องทวนสัญญาณได้ถึงสี่ตัว กำหนดเวลาไปกลับไว้ที่ 51.2 µs ซึ่งที่ 10 Mb/s เท่ากับ 512 บิต เฟรมทุกเฟรมจึงต้องยาวอย่างน้อย 512 บิต = 64 ไบต์ = ส่วนหัว 14 + ข้อมูล 46 + CRC 4 และผู้ส่งที่ชนจะส่งออกไปอย่างน้อย 96 บิต (ส่วนนำ 64 + jam 32)

    ผู้เขียนตรวจตัวเลข: 512 บิต ÷ 10⁷ บิต/วินาที = 51.2 µs ถ้าสมมุติว่าสัญญาณในสายวิ่งราว 2 × 10⁸ m/s (ค่าประกอบการอธิบาย ความเร็วจริงขึ้นกับชนิดสาย) เวลาเที่ยวเดียว 25.6 µs เท่ากับสายเปล่า ๆ ราว 5,120 เมตร ตัวเลข 2,500 เมตรจึงเหลือเวลาไว้ให้ความหน่วงของเครื่องทวนสัญญาณและเครื่องรับส่ง (ข้อนี้เป็นการอนุมานของผู้เขียน)

    กรณีขอบเมื่อความเร็วเพิ่ม: ถ้ายังใช้เฟรมขั้นต่ำ 512 บิตเท่าเดิม ที่ 100 Mb/s เวลาส่ง 512 บิตเหลือ 5.12 µs และที่ 1 Gb/s เหลือ 0.512 µs — ความยาวเครือข่ายที่ตรวจการชนได้จะหดลงราวสิบเท่าในแต่ละขั้น (อนุมานจากสูตรเดียวกัน ผู้เขียนไม่ได้เปิดมาตรฐานของความเร็วเหล่านั้น) นี่เป็นอีกเหตุผลที่ย่อหน้า “จากบัสร่วมสู่ดาวแบบสวิตช์” ข้างล่างพูดถึง: เมื่อลิงก์มีแค่สองปลายและส่งสวนกันได้ ปัญหานี้หายไปทั้งหมด

    Backoff แบบเลขชี้กำลังคู่: ตัวเลขและกรณีขอบ#

    “การรอสุ่มต่างกัน” ในย่อหน้าข้างบนมีสูตรชัดเจน หนังสือของ Peterson และ Davie ระบุว่า หลังการชนครั้งที่ n ตัวส่งสุ่ม k จาก 0 ถึง 2ⁿ − 1 แล้วรอ k × 51.2 µs โดย n ถูกจำกัดไม่เกิน 10 และตัวส่งมักลองได้ไม่เกิน 16 ครั้งก่อนรายงานข้อผิดพลาด:

    การชนครั้งที่ n k สุ่มจาก รอนานสุด
    1 0–1 51.2 µs
    2 0–3 153.6 µs
    3 0–7 358.4 µs
    10 0–1023 52.38 ms
    11–15 (กรณีขอบ: ช่วงไม่ขยายอีก) 0–1023 52.38 ms
    16 — เลิกและรายงานข้อผิดพลาด

    สองสถานี: ถ้าสองสถานีชนกันและอยู่ที่ครั้งที่ n เท่ากัน จะชนซ้ำเมื่อสุ่มได้ k เท่ากัน ความน่าจะเป็น 1/2ⁿ: ครั้งแรก 1/2 ครั้งที่สอง 1/4 … ผู้เขียนคูณความน่าจะเป็นที่ชนซ้ำทุกครั้งจนถึงครั้งที่ 15 (ช่วงหยุดขยายที่ n = 10) ได้ราว 2⁻¹⁰⁵ — สองสถานีแทบไม่มีทางเลิกเพราะชนกันเอง

    หลายสถานี: ผู้เขียนจำลองแบบง่าย (ทุกสถานีเริ่มส่งพร้อมกันแล้วชน จากนั้นใช้ backoff ข้างบน นับช่องเวลาจนมีสถานีแรกส่งสำเร็จ แบบจำลองอุดมคติ ไม่ใช่การวัดจริง):

    จำนวนสถานีที่พร้อมส่ง ช่องเวลาเฉลี่ยจนมีผู้สำเร็จคนแรก
    1 (กรณีขอบ: ไม่มีใครชน) 0
    2 2.7
    10 6.6
    50 22.5
    200 64.6

    ในการจำลองนี้ไม่มีสถานีใดถึงขีด 16 ครั้งก่อนมีคนแรกสำเร็จ แต่เวลารอโตตามจำนวนผู้แย่ง — ไม่มีผู้ตัดสินกลาง ราคาที่จ่ายคือช่องเวลาที่เสียไปกับการชน

    ต้นฉบับปี 1976: Metcalfe และ Boggs บรรยายหลักเดียวกันด้วยคำอื่น: ช่วงรอเป็นจำนวนเท่าของ “ช่อง” (slot) ซึ่งเท่ากับเวลาไปกลับหนึ่งรอบ ครั้งแรกค่าเฉลี่ยของช่วงรอคือหนึ่งช่อง และทุกครั้งที่ชน ค่าเฉลี่ยเพิ่มเป็นสองเท่า — ที่บทความเรียกว่า Binary Exponential Backoff

    ประสิทธิภาพตามแบบจำลองของ Metcalfe และ Boggs#

    บทความให้สูตรสำหรับเครือข่ายที่มี Q สถานีพร้อมส่งตลอด แต่ละช่องทุกสถานีส่งด้วยความน่าจะเป็น 1/Q:

    • ความน่าจะเป็นที่ช่องหนึ่งมีผู้ส่งคนเดียว (ยึดสายได้): A = (1 − 1/Q)^(Q−1)
    • จำนวนช่องเฉลี่ยที่เสียไปก่อนยึดได้: W = (1 − A) / A
    • ประสิทธิภาพ: E = (P/C) / ((P/C) + W·T) เมื่อ P คือความยาวกลุ่มข้อมูลเป็นบิต C = 3 Mb/s และ T = 16 µs

    ผู้เขียนคำนวณซ้ำด้วยค่าเหล่านี้ ได้ตรงกับตาราง I ของบทความ (Q = 1 ถึง 256) ถึงทศนิยมตำแหน่งที่สี่ในทุกช่องที่อ่านได้จากสำเนา ยกเว้นช่องเดียวคือ Q = 3, P = 4096 ที่ต่างกันหนึ่งหน่วยในหลักที่สี่ (ผู้เขียนได้ 0.98556 ปัดเป็น 0.9856 ขณะที่ตารางพิมพ์ 0.9857 ส่วนช่องอื่นของแถว Q = 3 ตรงกัน):

    กรณีขอบสามข้อ: Q = 1 สูตรกลายเป็น 0⁰ ซึ่งต้องตีความเป็น 1 จึงได้ A = 1 W = 0 และ E = 1 (สถานีเดียวไม่มีใครชนด้วย) P = 48 คือกลุ่มข้อมูลที่ยาวเท่าหนึ่งช่องพอดี (3 × 10⁶ × 16 × 10⁻⁶ = 48 บิต) เมื่อ Q โตขึ้น A เข้าใกล้ 1/e จึงได้ E เข้าใกล้ 1/e ≈ 0.368 ตามที่บทความเขียนว่าเข้าใกล้ “ประสิทธิภาพเชิงเส้นกำกับของเครือข่าย slotted Aloha” และ P ยาว บทความรายงานว่ากลุ่มข้อมูลยาวเกิน 4,000 บิตให้ประสิทธิภาพ “สูงกว่า 95 เปอร์เซ็นต์” — เวลาที่เสียไปกับการแย่งคงที่ ยิ่งส่งนานต่อครั้งยิ่งคุ้ม นี่คือเหตุผลเชิงตัวเลขของเฟรมยาวสูงสุด 1,500 ไบต์กับเฟรมสั้นที่ไม่ควรสั้นเกินไป

    เฟรม#

    Ethernet พกข้อมูลในเฟรม: ที่อยู่ MAC ต้นทางและปลายทาง (ที่อยู่ฮาร์ดแวร์ ต่ำกว่ที่อยู่ IP ในบทที่ 41) ฟิลด์ type สำหรับโปรโตคอลชั้นสูง payload และ CRC — ชนิด ความเชื่อถือได้เดียวกับการตรวจ data-link ของ PCIe (บทที่ 33) บนสื่อต่างกัน

    เฟรมเป็นไบต์#

    ตามหนังสือของ Peterson และ Davie: ส่วนนำ 64 บิต (8 ไบต์ สลับ 0 กับ 1 ให้ผู้รับจับจังหวะ) เลขที่อยู่ปลายทาง 6 ไบต์ เลขที่อยู่ต้นทาง 6 ไบต์ type 2 ไบต์ ข้อมูล 46–1500 ไบต์ (สั้นกว่า 46 ต้องเติมให้ครบ) CRC 32 บิต และทุกสถานีรอ 9.6 µs หลังจบเฟรมก่อนส่งเฟรมถัดไป ซึ่งที่ 10 Mb/s เท่ากับ 96 บิต = 12 ไบต์ ส่วนหัว 14 ไบต์ที่โฮสต์เห็นจึงเป็นเพียงส่วนหนึ่งของสิ่งที่วิ่งบนสาย ผู้เขียนคำนวณประสิทธิภาพ (ข้อมูลที่ต้องการส่ง ÷ ไบต์ทั้งหมดบนสาย):

    ข้อมูลที่ต้องการส่ง (ไบต์) ข้อมูลในเฟรมหลังเติม ไบต์บนสายต่อเฟรม ประสิทธิภาพ เฟรมต่อวินาทีที่ 10 Mb/s

    ข้อมูล 0 ถึง 46 ไบต์ใช้เวลาบนสายเท่ากันทุกประการ — ส่งหนึ่งไบต์ก็จ่ายเท่ากับส่ง 46 ไบต์

    ขอบเขตในเคอร์เนล Linux: ไฟล์ include/uapi/linux/if_ether.h กำหนด ETH_ZLEN = 60 (เฟรมสั้นสุดไม่นับ FCS = 64 − 4), ETH_DATA_LEN = 1500, ETH_FRAME_LEN = 1514 (สูงสุดไม่นับ FCS = 14 + 1500), ETH_FCS_LEN = 4 และ ETH_MIN_MTU = 68 พร้อมคำอธิบายว่ามาจาก RFC 791 ซึ่งกำหนดว่าทุกโมดูลอินเทอร์เน็ตต้องส่งต่อ datagram ขนาด 68 octet ได้โดยไม่ต้องแบ่งเพิ่ม เพราะส่วนหัว IP ยาวได้ถึง 60 octet และชิ้นส่วนที่เล็กที่สุดคือ 8 octet (60 + 8 = 68)

    เลขที่อยู่ MAC 48 บิต: หนังสือของ Peterson และ Davie อธิบายว่าผู้ผลิตแต่ละรายได้รับคำนำหน้า 24 บิตไม่ซ้ำกัน เลขที่อยู่ที่เป็น 1 ทุกบิตคือการแพร่สัญญาณถึงทุกสถานี และเลขที่อยู่ที่บิตแรกเป็น 1 (แต่ไม่ใช่ 1 ทุกบิต) คือการแพร่สัญญาณเฉพาะกลุ่ม ในโค้ดของ Linux (include/linux/etherdevice.h) “บิตแรก” นี้คือบิต 0x01 ของไบต์แรก และบิต 0x02 ของไบต์แรกหมายถึงเลขที่อยู่ที่กำหนดเองในท้องถิ่น (ไม่ได้มาจากผู้ผลิต) ตัวอย่างที่ผู้เขียนคำนวณ:

    เลขที่อยู่ บิต 0x01 (กลุ่ม) บิต 0x02 (ท้องถิ่น) ความหมาย
    00:22:15:cf:be:a9 0 0 ส่งถึงปลายทางเดียว แบบที่ผู้ผลิตกำหนด
    02:00:00:00:00:01 0 1 ส่งถึงปลายทางเดียว กำหนดเองในท้องถิ่น
    01:00:5e:00:00:01 1 0 แพร่สัญญาณเฉพาะกลุ่ม
    ff:ff:ff:ff:ff:ff 1 1 แพร่สัญญาณถึงทุกสถานี (ตามคำอธิบายในโค้ด ถือเป็นกลุ่มด้วย)

    กรณีขอบในโค้ดเดียวกัน: is_valid_ether_addr ถือว่า 00:00:00:00:00:00 ไม่ใช่ เลขที่อยู่ที่ใช้ได้ เช่นเดียวกับเลขที่อยู่กลุ่มและ ff:ff:ff:ff:ff:ff และ eth_random_addr ที่สุ่มเลขที่อยู่ให้การ์ดจะล้างบิต 0x01 และตั้งบิต 0x02 เสมอ

    CRC-32 ตรวจอะไรได้: หนังสือเล่มเดียวกันให้พหุนาม CRC-32 ที่ Ethernet ใช้ (x³² + x²⁶ + x²³ + x²² + x¹⁶ + x¹² + x¹¹ + x¹⁰ + x⁸ + x⁷ + x⁵ + x⁴ + x² + x + 1) และระบุว่าจับได้ทุกความผิดพลาดบิตเดียว และทุกความผิดพลาดต่อเนื่องที่สั้นกว่า 32 บิต ผู้เขียนเขียนการหารพหุนามนี้เองใน Python แล้วได้ค่าตรงกับ zlib.crc32 (เช่น “123456789” ได้ 0xCBF43926) จากนั้นทดลองกับเฟรม 60 ไบต์บวก CRC 4 ไบต์ = 512 บิต:

    • พลิกบิตทีละหนึ่งบิต ครบ 512 แบบ: ตรวจพบทั้ง 512
    • พลิกสองบิตพร้อมกัน ครบ 130,816 คู่: ตรวจพบทั้งหมด
    • สุ่มทำให้เสีย 200,000 แบบ: ตรวจพบทั้งหมด (คาดว่าจะหลุดราว 200,000 / 2³² ≈ 0.00005 ครั้ง)
    • กรณีขอบ: CRC ของข้อมูลว่างคือ 0 และถ้าคำนวณ CRC ของ “ข้อมูล + CRC ของมัน” จะได้ 0x2144DF1C เสมอไม่ว่าข้อมูลเป็นอะไร (ผู้เขียนลองข้อมูลว่าง 60 ไบต์ศูนย์ 768 ไบต์ และ “hello”) ผู้รับจึงตรวจทั้งเฟรมรวม CRC แล้วเทียบกับค่าคงที่ค่าเดียวได้

    CRC ตรวจได้ แต่แก้ไม่ได้ และตรวจเฉพาะความเสียหายบนสาย Metcalfe และ Boggs เขียนไว้ตั้งแต่ปี 1976 ว่า CRC ของฮาร์ดแวร์ “ป้องกันเฉพาะความผิดพลาดใน Ether” ไม่ป้องกันส่วนขนานภายในสถานี และแนะนำให้มี checksum ในซอฟต์แวร์เพิ่มเมื่อต้องการความน่าเชื่อถือสูงกว่า

    จากบัสร่วมสู่ดาวแบบสวิตช์#

    Ethernet มีสายสมัยใหม่ส่วนใหญ่ทิ้งสายร่วมไปหาสวิตช์ที่ให้แต่ละสถานีมีลิงก์จุดต่อจุดของตัวเอง — ทางหนีจากร่วมสู่จุดต่อจุดเดียวกับที่ PCIe ทำเทียบกับบัสขนานเก่า (บทที่ 32) บนสวิตช์ที่เหมาะสม การชน CSMA/CD คลาสสิกหายเกือบหมด: แต่ละลิงก์มีสองปลาย ไอเดียยังสำคัญทางประวัติศาสตร์ และ Wi-Fi ยุคแรก — ยังเป็นสื่อวิทยุร่วม — ต้องแก้ข้อจำกัดการชนเดียวกัน

    สิ่งนี้นำไปที่ใด#

    Ethernet ท้องถิ่นบวกการกำหนดเส้นทางแพ็กเก็ตระยะไกลยังทิ้งช่องว่าง: แบบแผน addressing และ routing สากล ที่มัดเทคโนโลยีพื้นฐานต่างกันเข้าเป็นอินเตอร์เน็ตเวิร์กเดียว นั่นคือ TCP/IP — ถัดไป

    ประตูออก: Robert M. Metcalfe และ David R. Boggs, “Ethernet: Distributed Packet Switching for Local Computer Networks” (Communications of the ACM, 1976) — เปเปอร์ปฐมภูมิที่ระบุ LAN สื่อร่วมและการออกแบบ CSMA/CD

    ลองในเทอร์มินัล VM ด้านล่าง: เครื่องในแล็บมีการ์ดเครือข่าย eth0 (ไดรเวอร์ ne2k-pci เลียนแบบการ์ด NE2000) ผู้เขียนบูตอิมเมจแล้วสั่งตามนี้ ผลที่ได้:

    • cat /sys/class/net/eth0/address ได้เลขที่อยู่ที่ขึ้นต้นด้วย 00:22:15 เสมอ แต่สามไบต์ท้ายเปลี่ยนทุกครั้งที่บูต — สี่ครั้งที่ผู้เขียนบูตได้ …:1d:f1:2a, …:cf:be:a9, …:98:50:52 และ …:24:af:e8 ซอร์สของตัวจำลองในแล็บสร้างเลขที่อยู่เป็น [0, 34, 21, 255*Math.random()|0, …] (34 = 0x22, 21 = 0x15) กรณีขอบในบรรทัดนั้น: 255*Math.random()|0 ให้ค่า 0 ถึง 254 จึง ไม่มีวัน ได้ 0xFF ในสามไบต์ท้าย และมีเลขที่อยู่ที่เป็นไปได้ 255³ = 16,581,375 แบบ ถ้าเปิดแล็บพร้อมกันหลายเครื่องบนเครือข่ายเดียว โอกาสที่สองเครื่องได้เลขซ้ำ (ปัญหาวันเกิด ผู้เขียนประมาณด้วย 1 − e^(−n(n−1)/2N)) คือ 0 เมื่อ n = 1, ราว 0.03% เมื่อ n = 100, ราว 3% เมื่อ n = 1,000 และถึง 50% ที่ราว 4,795 เครื่อง บิต 0x02 ของไบต์แรกเป็น 0 แม้เลขจะสุ่มขึ้น ต่างจาก eth_random_addr ของ Linux ข้างบน
    • cat /sys/class/net/eth0/mtu ได้ 1500 ลอง ip link set eth0 mtu 1501 ถูกปฏิเสธ (เคอร์เนลรายงาน hw max 1500) mtu 9000 ถูกปฏิเสธเช่นกัน mtu 67 ถูกปฏิเสธ (hw min 68) และ mtu 68 ผ่าน — ตรงกับ ETH_MIN_MTU และ ETH_DATA_LEN ข้างบนทุกขอบ อย่าลืมตั้งกลับเป็น 1500
    • ก่อนเปิดใช้ operstate เป็น down และ statistics/tx_packets กับ rx_packets เป็น 0 หลัง ip link set eth0 up อ่าน carrier ได้ 1 และ operstate เป็น unknown แต่ speed และ duplex อ่านไม่ได้ (“Invalid argument”) — ผู้เขียนอนุมานว่าไดรเวอร์ของการ์ดจำลองไม่รายงานความเร็วลิงก์ และในการทดลองนี้การ์ดไม่ได้ต่อกับเครือข่ายภายนอก

    ในซอร์สเดียวกัน ฟังก์ชันรับเฟรมของการ์ดจำลองรับเฟรมเมื่อ (1) เปิดโหมดรับทุกเฟรม หรือ (2) เป็นเลขที่อยู่ ff:ff:ff:ff:ff:ff และเปิดรับการแพร่สัญญาณ หรือ (3) ตรงกับเลขที่อยู่ของตัวเองทั้งหกไบต์ ส่วนเฟรมที่บิต 0x01 ของไบต์แรกเป็น 1 (แพร่สัญญาณเฉพาะกลุ่ม) เมื่อเปิดรับกลุ่มไว้ ตัวจำลองกลับ ทิ้ง เฟรมนั้น (ซอร์สต้นฉบับของ v86 ใน src/ne2k.js มีหมายเหตุ XXX ตรงนั้น แสดงว่ายังทำไม่เสร็จ) — จึงตรงกับกฎของหนังสือ Peterson และ Davie สามข้อจากสี่ ยกเว้นข้อ multicast และเฟรมที่สั้นกว่า 60 ไบต์จะถูกจองที่ในบัฟเฟอร์อย่างน้อย 60 ไบต์ (Math.max(60, a.length) บวกส่วนหัว 4 ไบต์ของบัฟเฟอร์รับ) ซึ่ง 60 คือ ETH_ZLEN นั่นเอง
