    อินเตอร์คอนเนกต์ในระดับสเกล

    มกราคม 1, 2026

    เฟสนี้จนถึงตอนนี้เชื่อมส่วนประกอบ ภายใน เครื่องเดียว — CPU กับหน่วยความจำ CPU กับอุปกรณ์ เมื่อ workload ต้องการหลาย GPU หรือหลายเครื่อง คำถามเปลี่ยน: หน่วยเหล่านั้นคุยกัน เอง เร็วพอที่การสื่อสารเพิ่มจะไม่กิน compute เพิ่มหรือไม่?

    เส้นทางปริยายคือภาษี#

    หากไม่มีเส้นทาง peer GPU A เขียนผ่านหน่วยความจำระบบ และ GPU B อ่านกลับ — ฮอปเพิ่ม latency เพิ่ม แบนด์วิดท์ PCIe เผาไปกับการคัดลอก แม้บน PCIe อย่างเดียว GPUDirect P2P ก็ DMA GPU↔GPU ได้โดยไม่ต้อง stage ที่โฮสต์ (ยังที่อัตรา PCIe) ข้อจำกัดที่เหลือคือแบนด์วิดท์และทอโพโลยี: fabric ขยายร่วมไม่เคยออกแบบเป็น mesh หลาย GPU

    คำศัพท์ (ศัพท์บัญญัติราชบัณฑิตยสภา; สาขาระบุในวงเล็บเมื่อไม่ใช่คอมพิวเตอร์และเทคโนโลยีสารสนเทศ): แบนด์วิดท์ (bandwidth); เวลาแฝง (latency); เชื่อมโยง (link); บัส (bus); หน่วยความจำ และ แคช (memory, cache); กลุ่มข้อมูล (packet); ปริมาณงาน (throughput); ทอพอโลยี (topology — วิทยาศาสตร์/คณิตศาสตร์); สวิตช์ (switch — วิศวกรรมไฟฟ้า) ไม่พบศัพท์บัญญัติสำหรับ cache coherence, interconnect, fabric, peer-to-peer, memory pooling, shared memory และ direct memory access ในความหมายนี้ (coherence มีศัพท์บัญญัติสาขาวิศวกรรมไฟฟ้าว่า ความอาพันธ์ ซึ่งเป็นเรื่องคลื่น ไม่ใช่แคช) บทนี้จึงใช้คำอธิบายภาษาไทยคู่กับคำอังกฤษ เช่น ความสอดคล้องของแคช (cache coherence) และการรวมหน่วยความจำเป็นพูล (memory pooling)

    ราคาของการคัดลอก: แบบจำลองเวลาถ่ายโอน#

    ให้เวลาส่งข้อมูลขนาด S ผ่านเส้นทางหนึ่งเป็น T = α + S/B โดย α คือเวลาแฝงคงที่ต่อการส่ง และ B คือแบนด์วิดท์ต่อทิศ (แบบจำลองจากหลักการแรก) ใช้ตัวเลขสมมติ α = 10 µs ทุกเส้นทาง และ B ของ PCIe 5.0 x16 = 64 GB/s ต่อทิศ (32 GT/s × 16 lane ÷ 8 บิต ยังไม่หักโอเวอร์เฮดของการเข้ารหัสสาย; ตัวเลข 32 GT/s อนุมานจากที่ PCI-SIG เขียนว่า PCIe 6.0 ที่ 64 GT/s “เพิ่มอัตราเป็นสองเท่าของ PCIe 5.0”)

    เส้นทาง สูตร S = 1 GB S = 64 KB S = 0
    ผ่านหน่วยความจำโฮสต์ (คัดลอกสองครั้งต่อกัน) 2α + 2S/B 31.3 ms 22 µs 20 µs
    GPUDirect P2P บน PCIe (ครั้งเดียว) α + S/B 15.6 ms 11 µs 10 µs
    NVLink รุ่นที่ 4 (450 GB/s ต่อทิศ, ดูข้างล่าง) α + S/B 2.2 ms 10.1 µs 10 µs

    อ่านตาราง: ข้อความใหญ่ถูกกำหนดด้วยแบนด์วิดท์ ข้อความเล็กถูกกำหนดด้วยเวลาแฝง จุดเปลี่ยนที่สองพจน์เท่ากันคือ S = α × B ซึ่งเท่ากับ 10 µs × 64 GB/s = 640 KB สำหรับ PCIe และ 4.5 MB สำหรับ 450 GB/s กรณีขอบ S = 0 ทุกเส้นทางเหลือแต่ α ลิงก์ที่เร็วกว่าไม่ช่วยอะไร เส้นทางผ่านโฮสต์ยังเสียเปรียบสองเท่าเพราะนับ α สองครั้ง (ในทางปฏิบัติอาจแบ่งเป็นชิ้นแล้วส่งซ้อนกันเพื่อลดเวลารวม แต่ข้อมูลยังข้ามหน่วยความจำโฮสต์สองครั้ง)

    ลิงก์เฉพาะ หน่วยความจำที่สอดคล้อง คัดลอกน้อยลง#

    NVLink ของ NVIDIA เป็นอินเตอร์คอนเนกต์ GPU-ถึง-GPU ที่สร้างเพื่องานนี้ — CPU และหน่วยความจำระบบอยู่นอกการถ่ายโอน NVSwitch ทำให้ทุก GPU ในโหนดถึงทุกอันอื่นได้ ที่แบนด์วิดท์สูงกว่าเส้นทาง PCIe-และ-CPU มาก สำหรับการแลกเปลี่ยนขนาดใหญ่บ่อย — รูปแบบที่การฝึกระดับใหญ่กลับมาในเฟส 7 และ 10 — เส้นทางตรงนั้นเป็นอันดับหนึ่ง ไม่ใช่การปรับแต่ง

    ตัวเลขของ NVLink จากหน้าผลิตภัณฑ์ของ NVIDIA (เปิดเมื่อ 26 กันยายน 2026; NVIDIA ระบุว่าค่าของรุ่นที่ 6 เป็น “ข้อกำหนดเบื้องต้น อาจเปลี่ยนแปลงได้”):

    รุ่น NVLink สถาปัตยกรรม แบนด์วิดท์ต่อ GPU ลิงก์สูงสุดต่อ GPU ต่อลิงก์ (ผู้เขียนหาร) แบนด์วิดท์รวมของโดเมน
    4 Hopper 900 GB/s 18 50 GB/s 7.2 TB/s (8 GPU)
    5 Blackwell 1,800 GB/s 18 100 GB/s 130 TB/s (NVL72)
    6 Vera Rubin 3,000 GB/s 36 83.3 GB/s 216 TB/s (NVL72)

    ตรวจตัวเลขของผู้ผลิตเอง: 8 × 900 GB/s = 7.2 TB/s ตรง; 72 × 1.8 TB/s = 129.6 TB/s ซึ่งปัดเป็น 130; 72 × 3 TB/s = 216 TB/s ตรง หน้าเดียวกันเขียนว่ารุ่นที่ 6 ได้ “1.7 เท่าของรุ่นก่อน” (3,000 / 1,800 = 1.67) และ “12 เท่าของ PCIe Gen6” ซึ่งตรวจได้กับตัวเลขของ PCI-SIG: PCIe 6.0 x16 ได้สูงสุด 256 GB/s สองทิศรวมกัน และ 3,000 / 256 = 11.7 ≈ 12 ข่าวประชาสัมพันธ์ Blackwell (18 มีนาคม 2024) ระบุว่า 1.8 TB/s เป็นปริมาณงาน สองทิศรวมกัน ต่อ GPU และเชื่อมได้สูงสุด 576 GPU ตัวเลข 450 GB/s ต่อทิศของรุ่นที่ 4 ในตารางก่อนหน้าจึงมาจากการหาร 900 ด้วยสองโดยสมมติว่าสองทิศเท่ากัน (อนุมาน) ข้อสังเกต: ต่อลิงก์ของรุ่นที่ 6 ต่ำกว่ารุ่นที่ 5 แต่จำนวนลิงก์เพิ่มเป็นสองเท่า แบนด์วิดท์ต่อ GPU จึงยังโต

    all-reduce: ทำไมแบนด์วิดท์ระหว่าง GPU จึงเป็นอันดับหนึ่ง#

    การฝึกแบบขนานข้อมูลต้องรวม gradient จากทุก GPU หลังทุกขั้น วิธีแบบวงแหวน (ring all-reduce) คิดได้จากหลักการแรก:

    1. แบ่งข้อมูลขนาด S ของแต่ละ GPU เป็น N ชิ้น ชิ้นละ S/N
    2. ช่วง reduce-scatter: N − 1 รอบ แต่ละรอบทุก GPU ส่งชิ้นหนึ่งให้เพื่อนถัดไปพร้อมบวกสะสม จบแล้วแต่ละ GPU ถือผลรวมสมบูรณ์หนึ่งชิ้น
    3. ช่วง all-gather: อีก N − 1 รอบ ส่งผลรวมที่สมบูรณ์ต่อกันจนทุก GPU มีครบ
    4. แต่ละ GPU ส่งทั้งหมด 2(N − 1) × S/N ไบต์ และใช้เวลา T = 2(N − 1)·α + 2(N − 1)/N × S/B

    กรณีขอบ: N = 1 ไม่ต้องส่งอะไร (T = 0); N = 2 แต่ละ GPU ส่ง S พอดี; N → ∞ ปริมาณต่อ GPU เข้าใกล้ 2S แต่ไม่เกิน ส่วนพจน์เวลาแฝง 2(N − 1)α โตตาม N เรื่อย ๆ ข้อความเล็กในวงแหวนใหญ่จึงถูกเวลาแฝงกิน และ S = 0 เหลือแต่ 2(N − 1)α

    ตัวอย่างสมมติ: gradient 10 GB (เช่นพารามิเตอร์ 5 พันล้านตัว ตัวละ 2 ไบต์), ไม่นับ α:

    ระบบ (สมมติ) N B ต่อทิศ เวลา all-reduce หนึ่งครั้ง
    8 GPU บน PCIe 5.0 x16 8 64 GB/s 2 × 7/8 × 10 / 64 = 273 ms
    8 GPU บน NVLink รุ่นที่ 4 8 450 GB/s 38.9 ms
    72 GPU บน NVLink รุ่นที่ 5 72 900 GB/s 2 × 71/72 × 10 / 900 = 21.9 ms

    ความต่างราวเจ็ดเท่าระหว่างสองแถวแรกเกิดซ้ำทุกขั้นของการฝึก ซึ่งคือความหมายของ “ภาษี” ในหัวข้อข้างบน (วงแหวนเป็นเพียงอัลกอริทึมหนึ่ง ระบบจริงอาจใช้แบบต้นไม้หรือให้สวิตช์ช่วยรวม ตัวเลขนี้จึงใช้เทียบสัดส่วน ไม่ใช่ทำนายเวลาจริง)

    CXL (Compute Express Link) ตอบข้อจำกัดข้างเคียง: การเข้าถึงที่สอดคล้องแคชข้ามไดย์เดียว และต่อไป หน่วยความจำแบบพูลที่ไม่ได้ติดกับซ็อกเก็ตเดียว ความจุย้ายระหว่างโหนดคำนวณได้แทนการแช่แข็งกับสล็อต DIMM ที่มันลง — ความยืดหยุ่นที่ DDR (บทที่ 34) หรือ PCIe ดิบไม่ให้

    CXL ทีละรุ่น (จากเอกสาร “Compute Express Link 3.0” ของ CXL Consortium เขียนโดย Debendra Das Sharma และ Ishwar Agarwal, หน้า “About CXL” ของ consortium และเอกสาร Linux kernel):

    รุ่น สิ่งที่เพิ่ม
    CXL 1.0 (มีนาคม 2019) สลับโปรโตคอลสามชุดบนลิงก์เดียว: CXL.io (อิงบน PCIe), CXL.cache และ CXL.memory โดยคงพื้นที่หน่วยความจำที่สอดคล้องกันระหว่าง CPU กับหน่วยความจำบนอุปกรณ์
    CXL 2.0 (พฤศจิกายน 2020) สวิตช์ชั้นเดียว, หน่วยความจำถาวร, การรวมหน่วยความจำเป็นพูล และความปลอดภัย; เข้ากันได้กับ PCIe 5.0
    CXL 3.0 อิงบน PCIe 6.0 ที่ 64 GT/s “แบนด์วิดท์ดิบรวมสูงสุด 256 GB/s สำหรับ x16”; flit ขนาด 256 ไบต์; flit แบบลดเวลาแฝงที่ตัด CRC เป็นชิ้น 128 ไบต์ ลดเวลาแฝงได้ 2–5 ns; back-invalidate แคชของโฮสต์; แชร์หน่วยความจำข้ามหลายโฮสต์อย่างสอดคล้อง; fabric ที่ไม่ใช่ต้นไม้ได้สูงสุด 4,096 โหนด
    CXL 4.0 เพิ่มเป็น 128 GT/s คง flit 256 ไบต์ เพิ่ม bundled port และเข้ากันได้ย้อนหลังถึง 1.0 (หน้า About CXL)

    อุปกรณ์สามชนิดตามเอกสาร Linux kernel: Type-1 รองรับ CXL.io และ CXL.cache มีแคชที่สอดคล้องเต็มรูปแต่ไม่มีหน่วยความจำที่โฮสต์จัดการ เช่น Smart NIC ที่อยากเขียนกลุ่มข้อมูลลงหน่วยความจำโฮสต์โดยตรง; Type-2 รองรับทั้งสามโปรโตคอล มักเป็นตัวเร่งที่มีหน่วยความจำแบนด์วิดท์สูงของตัวเอง; Type-3 รองรับ CXL.io และ CXL.mem เช่นตัวขยายหน่วยความจำที่ CPU เข้าถึงได้เหมือนหน่วยความจำปกติ การ “ย้ายความจุระหว่างโหนด” ในย่อหน้าข้างบนคือการรวมอุปกรณ์ Type-3 เป็นพูลผ่านสวิตช์ของ CXL 2.0 ขึ้นไป

    ตรวจตัวเลข 256 GB/s ของ CXL 3.0 จากหลักการแรก: 64 GT/s × 16 lane ÷ 8 = 128 GB/s ต่อทิศ สองทิศรวมกัน 256 GB/s ตรงกับตัวเลขของ PCIe 6.0 เพราะใช้ชั้นกายภาพเดียวกัน คำว่า “ดิบ” หมายถึงยังไม่หักส่วนหัวของ flit และการแก้ข้อผิดพลาด

    GPUDirect RDMA ให้ NIC อ่านหรือเขียนหน่วยความจำ GPU โดยตรง หากไม่มี การถ่ายโอน GPU-ถึง-GPU ข้ามเครือข่ายคือ GPU → หน่วยความจำระบบ → NIC → หน่วยความจำระบบไกล → GPU ไกล — การคัดลอกที่กิน latency และแบนด์วิดท์หน่วยความจำ ยุบเหลือ GPU → เครือข่าย → GPU ด้วยเหตุผลเดียวกับที่ RDMA (บทที่ 42) ชนะในที่เก็บและข้อความ: คัดลอกน้อยลง CPU น้อยลงคอยเฝ้าการย้าย

    สิ่งที่เอกสารของ NVIDIA บอกเรื่อง GPUDirect RDMA: เป็นเทคโนโลยีที่เริ่มใน GPU รุ่น Kepler กับ CUDA 5.0 ให้เส้นทางตรงระหว่าง GPU กับอุปกรณ์ของผู้ผลิตอื่น (เช่นการ์ดเครือข่าย อุปกรณ์จับภาพ ตัวแปลงสตอเรจ) โดยใช้คุณสมบัติมาตรฐานของ PCI Express ข้อจำกัดสำคัญที่สุดคือสองอุปกรณ์ต้องอยู่ใต้ root complex ต้นทางเดียวกัน และเอกสารแบ่งสามกรณีตามสิ่งที่อยู่ระหว่างทาง: มีแต่สวิตช์ PCIe ดีที่สุด; ผ่าน CPU/IOH หนึ่งตัว ใช้ได้แต่ช้ากว่า (แบนด์วิดท์การอ่านแบบ peer-to-peer “ถูกจำกัดอย่างมาก” บนสถาปัตยกรรมโปรเซสเซอร์บางแบบ); ข้ามลิงก์ QPI/HT ระหว่างซ็อกเก็ต อาจช้ามากหรือทำงานไม่เสถียร ทอพอโลยีภายในเครื่องจึงสำคัญเท่ากับการมีฟีเจอร์

    นับการข้ามหน่วยความจำโฮสต์จากหลักการแรก (สำหรับข้อความขนาด S ฝั่งละเครื่อง): เส้นทางแบบเดิม GPU → หน่วยความจำระบบ → NIC ทำให้ DRAM ของโฮสต์ถูกเขียน S และอ่าน S (รวม 2S) ในเครื่องส่ง และอีก 2S ในเครื่องรับ รวม 4S ส่วน GPUDirect RDMA ไม่ผ่าน DRAM ของโฮสต์เลย (0) ส่งข้อความ 1 GB จึงประหยัดการใช้หน่วยความจำโฮสต์ 4 GB ต่อครั้ง ไม่นับเวลาที่ CPU ต้องคอยสั่งการ

    ปัญหาเดียวกัน ฮาร์ดแวร์เปิด#

    นี่คือรากฐานแนวคิดใต้ GPU memory fabric กำหนดเองที่ชุดบทความชี้ไปเรื่อย ๆ: ทำให้หน่วยความจำ GPU ระยะไกล address ได้โดยไม่มี CPU อเนกประสงค์ในเส้นทาง NVLink และ GPUDirect แก้ภายในสแต็กของผู้ขายรายเดียว ทางเลือกเปิดบน PCIe ต้องลบ inefficiency เดียวกัน — นั่นคือเหตุผลที่เส้นทาง peer ระดับ TLP ในบทที่ 32–33 และ “เหตุใดลิงก์เฉพาะจึงมีอยู่” ในบทนี้ เป็นเรื่องเดียวกัน
