    TCP/IP และสแตกอินเทอร์เน็ตสมัยใหม่

    มกราคม 1, 2026

    ARPANET (บทที่ 39) พิสูจน์ packet switching Ethernet (บทที่ 40) ทำให้สายท้องถิ่นเป็นมาตรฐาน ไม่มีอย่างใดเพียงอย่างเดียวที่บอกวิธีเย็บเครือข่าย ต่างกัน — สื่อต่างกัน addressing ต่างกัน — ให้เป็นอินเตอร์เน็ตเวิร์กเดียวที่เครื่องสองเครื่องใด ๆ ใช้ได้ ชุด TCP/IP ของ Vint Cerf และ Bob Kahn แก้ปัญหานั้น; มันยังเป็นรากฐานที่อินเทอร์เน็ตสมัยใหม่รันอยู่

    แบบจำลองแบบชั้น#

    TCP/IP แยกข้อกังวลแบบที่สแตกของ PCIe ทำ (บทที่ 33) ในระดับอินเตอร์เน็ตเวิร์ก Link จัดการฮอปท้องถิ่น — Ethernet, Wi-Fi, ไฟเบอร์ Internet (IP) ให้ addressing และ routing สากล ข้าม ลิงก์เหล่านั้น; แพ็กเก็ต IP ไม่สนใจว่าสื่ออะไรพา Transport (TCP หรือ UDP) ให้การส่งมอบที่เชื่อถือได้มีลำดับ (TCP) หรือ best-effort overhead ต่ำ (UDP) ทับ IP Application คือที่ HTTP, DNS, SMTP และเครือญาติอยู่ เลือก transport ที่เหมาะ

    Encapsulation#

    ข้อมูลที่เคลื่อนลงได้ header ในแต่ละชั้น — ไบต์แอปใต้ TCP/UDP, segment นั้นใต้ IP, แพ็กเก็ตนั้นใต้ link header (และมัก trailer) ที่ปลายทางกระบวนการย้อนกลับ: แต่ละชั้นลอก header ของตัวเองและใช้สิ่งที่เพิ่งอ่าน (พอร์ต, ที่อยู่) เพื่อส่งส่วนที่เหลือขึ้น

    TCP บนพื้นผิวที่ไม่เชื่อถือได้#

    IP เป็น best-effort อย่างชัด — ไม่มีสัญญาการส่งมอบ ไม่มีสัญญาลำดับ ทิ้งได้ TCP สร้างกระแสไบต์ที่เชื่อถือได้มีลำดับทับด้วยหมายเลขลำดับและการยืนยัน (และการส่งซ้ำเมื่อ ACK ไม่มา) — ชนิด ความเชื่อถือได้เดียวกับ data-link ของ PCIe (บทที่ 33) ยืดข้ามอินเตอร์เน็ตเวิร์กที่ไม่เชื่อถือได้ทั้งก้อนแทนลิงก์เฉพาะเส้น

    การเชื่อมต่อเริ่มด้วย three-way handshake: SYN (ไคลเอนต์เสนอหมายเลขลำดับ), SYN-ACK (เซิร์ฟเวอร์ยืนยันและเสนอของตัวเอง), ACK สุดท้าย แล้วข้อมูลแอปจึงไหล — ต้นทุนเล็กน้อยโดยเจตนาเพื่อให้ทั้งสองฝั่งมีสถานะซิงค์ก่อน

    เมื่อเครือข่ายแน่น: การควบคุมความคับคั่ง#

    ความเชื่อถือได้ของ TCP ตอบคำถามว่า “ข้อมูลถึงครบไหม” แต่ยังมีอีกคำถามที่สำคัญพอกัน: ควรส่งเร็วแค่ไหน ถ้าผู้ส่งทุกรายอัดข้อมูลเต็มที่ เราเตอร์ตรงกลางจะล้น ทิ้งแพ็กเก็ต ผู้ส่งก็ส่งซ้ำ เครือข่ายยิ่งแน่น — วงจรป้อนกลับที่พังตัวเอง

    นี่ไม่ใช่ทฤษฎี Van Jacobson เล่าไว้ในบทความปี 1988 ว่าในเดือนตุลาคม 1986 อินเทอร์เน็ตเกิด “การล่มจากความคับคั่ง” (congestion collapse) ครั้งแรกในชุดหนึ่ง: ปริมาณข้อมูลระหว่าง LBL กับ UC Berkeley ซึ่งห่างกันราว 400 หลาและผ่าน IMP สองฮอป ตกจาก 32 kbps เหลือ 40 bps — ลดลงราวพันเท่า สาเหตุไม่ใช่สายเสีย แต่เป็น TCP เองที่ส่งซ้ำอย่างไม่ยั้งเข้าไปในเครือข่ายที่แน่นอยู่แล้ว

    คำว่า congestion ยังไม่พบศัพท์บัญญัติ บทนี้เรียก ความคับคั่ง และ การควบคุมความคับคั่ง (congestion control) ขอนิยามคำอื่นที่ต้องใช้ก่อน:

    • กลุ่มข้อมูล (packet, ศัพท์บัญญัติ; ทับศัพท์ว่าแพ็กเก็ต) และ ส่วน (segment, ศัพท์บัญญัติ “ส่วน, เซกเมนต์”) — หน่วยข้อมูลของชั้น IP และชั้น TCP ตามลำดับ ขนาดข้อมูลสูงสุดต่อ segment เรียกว่า MSS ในตัวอย่างใช้ 1,460 ไบต์ (ขนาดที่พบบ่อยบน Ethernet เป็นตัวเลขประกอบการอธิบาย)
    • การตอบรับ (acknowledgement: ACK, ศัพท์บัญญัติ) — ข้อความจากผู้รับว่า “ได้ถึงไบต์นี้แล้ว”
    • เวลาไปกลับ (round-trip time: RTT; ยังไม่พบศัพท์บัญญัติ) — เวลาตั้งแต่ส่ง segment จนได้ ACK ของมันกลับมา
    • หน้าต่าง (window, ศัพท์บัญญัติ) — จำนวนไบต์ที่ส่งออกไปแล้วแต่ยังไม่ได้ ACK ได้มากที่สุด TCP มีหน้าต่างสองบาน: บานที่ ผู้รับ ประกาศว่ามีที่พักข้อมูล (buffer, ศัพท์บัญญัติ “ที่พัก(ข้อมูล)”) เหลือเท่าไร ซึ่งเป็น การควบคุมสายงาน (flow control, ศัพท์บัญญัติ) กับบานที่ ผู้ส่ง ประเมินเองว่าเครือข่ายรับไหวเท่าไร เรียกว่า หน้าต่างความคับคั่ง (congestion window: cwnd) ผู้ส่งใช้บานที่เล็กกว่า

    ทำไมต้องเป็นหน้าต่าง: ผลคูณแบนด์วิดท์กับเวลาแฝง#

    ผู้ส่งที่มีหน้าต่าง W ไบต์ ส่ง W ไบต์ออกไป แล้วต้องรอ ACK ซึ่งใช้เวลาหนึ่ง RTT ปริมาณงานสูงสุดจึงเป็น W / RTT กลับด้าน: ถ้าจะใช้ลิงก์ความจุ B ให้เต็ม หน้าต่างต้องใหญ่อย่างน้อย B × RTT ค่านี้เรียกว่า ผลคูณแบนด์วิดท์กับเวลาแฝง (bandwidth-delay product: BDP) — คือจำนวนไบต์ที่ “ลอยอยู่ในสาย” ได้พร้อมกัน

    ตัวอย่าง (ตัวเลขประกอบการอธิบาย): ลิงก์ 100 Mb/s, RTT 40 ms

    • BDP = 100 × 10⁶ × 0.040 / 8 = 500,000 ไบต์ ≈ 342 segment ขนาด 1,460 ไบต์
    • ถ้าหน้าต่างติดที่ 65,535 ไบต์ (ค่าสูงสุดของช่อง Window ขนาด 16 บิตในส่วนหัวของ TCP ตาม RFC 793 ในประตูออกด้านล่าง) ปริมาณงานสูงสุด = 65,535 / 0.040 ≈ 1.64 MB/s ≈ 13 Mb/s — ใช้ลิงก์ได้แค่ 13% ไม่ว่าลิงก์จะว่างแค่ไหน

    ข้อสรุปแรก: บนเส้นทางไกลและเร็ว หน้าต่าง ไม่ใช่ความเร็วสาย คือสิ่งที่จำกัดปริมาณงาน และคำถามของการควบคุมความคับคั่งจึงกลายเป็น: ผู้ส่งจะหาค่า cwnd ที่ถูกต้องได้อย่างไร ในเมื่อไม่มีใครบอก BDP ของเส้นทางให้

    เริ่มช้า: ค้นหาความจุแบบทวีคูณ#

    คำตอบของ Jacobson ซึ่ง RFC 5681 เขียนเป็นมาตรฐาน มีสองโหมด โหมดแรกเรียกว่า slow start (ยังไม่พบศัพท์บัญญัติ แปลตามตัวว่า “เริ่มช้า”) เริ่มจากหน้าต่างเริ่มต้น (initial window: IW) แล้ว เพิ่ม cwnd หนึ่ง segment ต่อทุก ACK ที่ได้รับ เพราะในหนึ่ง RTT จะมี ACK กลับมาเท่ากับจำนวน segment ที่ส่งไป ผลคือ cwnd เพิ่มเป็นสองเท่าทุก RTT ชื่อ “ช้า” ฟังดูขัดกับการโตแบบทวีคูณ แต่มันช้าเมื่อเทียบกับของเดิมก่อนปี 1988 ที่ส่งหน้าต่างเต็มออกไปทันที

    RFC 5681 กำหนดเพดาน IW ไว้ 2–4 segment ตามขนาด segment ต่อมา RFC 6928 (ฉบับทดลอง) เสนอให้เพิ่มเป็น 10 segment (ไม่เกิน 14,600 ไบต์) ลองไล่ด้วย IW = 10 บนลิงก์ตัวอย่างเดิม ส่งไฟล์ 1 MB (≈ 685 segment) โดยสมมุติว่าไม่มีการสูญหาย:

    RTT ที่ ส่งในรอบนี้ (segment) สะสม
    1 10 10
    2 20 30
    3 40 70
    4 80 150
    5 160 310
    6 320 630
    7 342 (ชนเพดาน BDP) 972 ≥ 685 เสร็จ

    รวม 7 RTT บวก three-way handshake อีกหนึ่ง RTT = 8 × 40 ms = 320 ms ทั้งที่เวลาส่งบิตล้วน ๆ ที่ 100 Mb/s คือ 8 × 10⁶ / 10⁸ = 80 ms สำหรับไฟล์ขนาดเล็กถึงกลาง เวลาแฝง ไม่ใช่แบนด์วิดท์ คือคอขวด นี่คือเหตุที่การเพิ่ม IW จาก 3 เป็น 10 ถูกผลักดัน และเหตุที่การเปิดการเชื่อมต่อใหม่บ่อย ๆ นั้นแพง

    หลีกเลี่ยงความคับคั่ง: บวกทีละหนึ่ง หารครึ่ง#

    เมื่อ cwnd ถึงเกณฑ์ที่เรียกว่า ssthresh (slow start threshold) ผู้ส่งเปลี่ยนเป็นโหมด congestion avoidance ซึ่ง RFC 5681 ให้เพิ่ม cwnd ราว หนึ่ง segment ต่อ RTT (สูตรต่อ ACK คือ cwnd += SMSS × SMSS / cwnd) — โตแบบเส้นตรงแทนทวีคูณ

    แล้วรู้ได้อย่างไรว่าแน่นแล้ว? อินเทอร์เน็ตไม่มีใครส่งสัญญาณบอก TCP จึงถือว่า การสูญหายของแพ็กเก็ตคือสัญญาณความคับคั่ง (เราเตอร์ทิ้งแพ็กเก็ตเมื่อที่พักข้อมูลเต็ม) มีสองระดับ:

    • ได้ ACK ซ้ำ 3 ครั้ง (duplicate ACK) — ผู้รับยังได้ segment หลังจากช่องที่หายไป แปลว่าเครือข่ายยังส่งได้ แค่หายไปตัวหนึ่ง RFC 5681 ให้ส่ง segment นั้นซ้ำทันที (fast retransmit) และตั้ง ssthresh = max(FlightSize/2, 2 × SMSS) โดย FlightSize คือข้อมูลที่ยังไม่ได้ ACK — คือ ลดหน้าต่างลงครึ่งหนึ่ง
    • หมดเวลารอ (timeout, ศัพท์บัญญัติ) ACK ไม่มาเลย — สัญญาณหนักกว่า RFC 5681 ให้ลด cwnd เหลือไม่เกิน “หน้าต่างสูญหาย” (loss window) ซึ่งเท่ากับ 1 segment เต็ม แล้วเริ่ม slow start ใหม่

    กติกา “บวกทีละน้อยเมื่อทุกอย่างดี ลดแบบคูณเมื่อเจอสัญญาณ” เรียกว่า AIMD (additive increase, multiplicative decrease) ทำให้ cwnd เป็นรูปฟันเลื่อย ถ้าหน้าต่างสูงสุดก่อนสูญหายคือ W มันจะไต่จาก W/2 ขึ้นไป W เป็นเส้นตรง ค่าเฉลี่ยของฟันเลื่อยจึงอยู่ที่ราว 3W/4 (การคำนวณของผู้เขียนจากรูปทรง) เหตุผลที่ต้องลด แบบคูณ ไม่ใช่ลบทีละน้อย: เมื่อมีหลายการเชื่อมต่อแชร์ลิงก์เดียว การลดตามสัดส่วนทำให้ตัวที่ใหญ่ลดมากกว่าตัวที่เล็ก การเชื่อมต่อจึงค่อย ๆ ลู่เข้าหาส่วนแบ่งที่ใกล้เคียงกัน

    ทำไม AIMD แบบเดิมไม่พอ: ท่อยาวและอ้วน#

    การฟื้นหลังสูญหายหนึ่งครั้งใช้ W/2 RTT บนลิงก์ตัวอย่าง (W ≈ 342) ใช้ 171 RTT × 40 ms ≈ 6.8 วินาที พอรับได้ แต่ RFC 9438 (CUBIC, 2023) ยกกรณีลิงก์ 10 Gb/s ที่ RTT 0.1 วินาที แพ็กเก็ต 1,500 ไบต์: หน้าต่างเฉลี่ยต้องเป็น 10¹⁰ × 0.1 / (1,500 × 8) ≈ 83,333 แพ็กเก็ต และตารางใน RFC บอกว่า Reno (AIMD แบบเดิม) จะทำความเร็วนี้ได้ก็ต่อเมื่ออัตราสูญหายไม่เกิน 2 × 10⁻¹⁰ — หายไม่เกินหนึ่งแพ็กเก็ตในห้าพันล้าน ผู้เขียนคำนวณต่อ: ถ้าหายครั้งเดียว การไต่กลับจาก 41,667 ไป 83,333 ทีละหนึ่งต่อ RTT ใช้ 41,667 × 0.1 ≈ 4,167 วินาที หรือราว 69 นาที

    CUBIC ซึ่งเป็นอัลกอริทึมที่เคอร์เนล Linux ในแล็บด้านล่างใช้อยู่ แก้ด้วยการให้หน้าต่างเป็นฟังก์ชันของ เวลา ตั้งแต่การสูญหายครั้งล่าสุด ไม่ใช่จำนวน RTT:

    W(t) = C × (t − K)³ + W_max

    โดย W_max คือหน้าต่างก่อนสูญหาย RFC 9438 ให้ลดหน้าต่างเหลือ β = 0.7 ของเดิมเมื่อสูญหาย (ไม่ใช่ 0.5) และ C = 0.4 ส่วน K คือเวลาที่ใช้ไต่กลับถึง W_max ได้จาก K = ∛(W_max × (1 − β) / C) รูปกราฟลูกบาศก์ทำให้หน้าต่างโตเร็วตอนไกลจาก W_max ชะลอ ใกล้ W_max (ซึ่งเป็นระดับที่เคยแน่น) แล้วค่อยเร่งอีกครั้งถ้าผ่านไปได้โดยไม่สูญหาย แทนตัวเลข (การคำนวณของผู้เขียน):

    • W_max = 342: K = ∛(342 × 0.3 / 0.4) ≈ 6.4 วินาที — ใกล้กับ 6.8 วินาทีของ Reno บนลิงก์ขนาดนี้ทั้งสองแบบพอ ๆ กัน
    • W_max = 83,333: K = ∛(83,333 × 0.3 / 0.4) = ∛62,500 ≈ 40 วินาที เทียบกับ 69 นาทีของ Reno

    K ไม่ขึ้นกับ RTT นี่คือทางเลือกออกแบบที่ทำให้ CUBIC ใช้ท่อยาวได้ดี และ RFC ยังมี “ช่วงเป็นมิตรกับ Reno” (Reno-friendly region) ที่ทำให้ CUBIC ได้ปริมาณงานใกล้เคียง Reno ในสภาพที่ Reno ทำงานได้ดีอยู่แล้ว (RTT สั้น BDP เล็ก)

    จากโปรโตคอลของเครือข่ายเดียวสู่สแตก#

    ARPANET เดิมพูดโปรโตคอล host-to-host ของตัวเอง (NCP) ไม่ใช่ TCP/IP เดิมพันของ Cerf และ Kahn ใหญ่กว่า: สแตกโปรโตคอล ที่อินเตอร์เน็ตเครือข่ายแพ็กเก็ต หลาย เครือข่ายได้ เพื่อให้ transport กับสายท้องถิ่นวิวัฒนาการแยกกัน การตัดจริงบน ARPANET เองคือ “flag day” 1 มกราคม 1983 เมื่อ NCP ถูกปิดและ TCP/IP กลายเป็นบังคับ — การตัดแข็งที่หายากซึ่งทำให้เรื่องแบบชั้นเป็นปฏิบัติการ ไม่ใช่แค่สถาปัตยกรรม

    โปรโตคอลแอปแล้วซ้อน เพราะ พื้นผิวนี้มีอยู่ DNS (ประตูในบทที่ 64: RFC 1034 / RFC 1035) ทำให้ชื่อใช้ได้ในระดับใหญ่; เมลและเว็บ (SMTP, HTTP และเครือญาติ) ขี่ TCP ในฐานะไคลเอนต์ของกระแสที่เชื่อถือได้ แทนการประดิษฐ์ addressing และการส่งซ้ำใหม่ รูปแบบคือจุดสำคัญ: แต่ละชั้นซื้อข้อจำกัดหนึ่งอย่างเพื่อให้ชั้นบนสมมติได้ นั่นคือเรื่องของการซ้อน ไม่ใช่แคตตาล็อกทุก RFC

    เหตุใดการออกแบบนี้ชนะ#

    สมมติฐานรับน้ำหนักคือเครือข่ายพื้นฐานต่างชนิดและไม่เชื่อถือได้ ดังนั้นการรับประกันอยู่ชั้นสูงกว่า แทนที่จะอยู่ในทุกลิงก์กายภาพ นั่นเข้ากับอินเตอร์เน็ตเวิร์กโลกที่เย็บมานานหลายทศวรรษจากเทคโนโลยีต่างกันโดยองค์กรที่ไม่เคยตกลงมาตรฐานกายภาพเดียว — ซึ่งคือเหตุผลที่ TCP/IP ยังนั่งใต้เกือบทั้งอินเทอร์เน็ตสมัยใหม่ รวมเครือข่ายศูนย์ข้อมูลถัดไป

    ประตูออก: RFC 791 (Internet Protocol) และ RFC 793 (Transmission Control Protocol) — สเปกหลักสำหรับครึ่ง addressing/routing และครึ่ง reliable-transport ของสแตกนี้ (สายเลือด Cerf/Kahn; Postel เป็นบรรณาธิการ RFC ของข้อความกันยายน 1981 เหล่านี้)

    ลองตอนนี้. แล็บด้านล่างบูต Linux จริง (เคอร์เนล 4.16) ในเบราว์เซอร์ เครื่องจำลองมีการ์ด Ethernet จำลอง (eth0) แต่ไม่ได้ต่อกับเครือข่ายภายนอก จึงส่งข้อมูลออกนอกเครื่องไม่ได้ และตอนบูตแม้แต่อินเทอร์เฟซวนกลับ (loopback, lo) ก็ยังไม่เปิด (ping 127.0.0.1 จึงตอบว่า Network is unreachable จนกว่าจะสั่ง ifconfig lo 127.0.0.1 up หลังจากนั้นจึงตอบกลับตามปกติ) แต่ส่วน TCP ของเคอร์เนลยังอยู่ครบ และเปิดให้ดูผ่าน /proc ได้ ผู้เขียนลองคำสั่งต่อไปนี้ในอิมเมจของแล็บนี้แล้ว:

    • cat /proc/sys/net/ipv4/tcp_congestion_control — ได้ cubic คืออัลกอริทึมที่ใช้อยู่
    • cat /proc/sys/net/ipv4/tcp_available_congestion_control — ได้ reno cubic คือสองอัลกอริทึมที่เคอร์เนลนี้มี
    • sysctl -w net.ipv4.tcp_congestion_control=reno — เปลี่ยนเป็น AIMD แบบเดิม แล้ว cat ซ้ำเพื่อยืนยัน (การเปลี่ยนมีผลในเครื่องจำลองเท่านั้น กด Restart เพื่อกลับสภาพเดิม)
    • cat /proc/sys/net/ipv4/tcp_rmem — ได้ค่าทำนอง 4096 87380 908384 คือขนาดที่พักข้อมูลขารับ ต่ำสุด ตั้งต้น และสูงสุด เป็นไบต์ (ค่าสูงสุดเปลี่ยนเล็กน้อยทุกครั้งที่บูต เพราะเคอร์เนลคำนวณจากหน่วยความจำว่างตอนบูต ผู้ตรวจบูตสามครั้งได้ 908,288 ถึง 908,544 ไบต์ แต่ราว 908 KB เสมอ) ลองคิด: ถ้าหน้าต่างขารับถูกจำกัดที่ราว 908 KB บนเส้นทาง RTT 40 ms ปริมาณงานสูงสุดคือ 908,384 / 0.040 ≈ 22.7 MB/s หรือราว 182 Mb/s — สูตร W / RTT เดียวกับข้างบน (เป็นขอบบนคร่าว ๆ ค่าที่ใช้ได้จริงขึ้นกับการตั้งค่าอื่นของเคอร์เนลด้วย)
    เปิดแล็บในแท็บใหม่ ↗
