    เหตุใด GPU จึงมีอยู่

    มกราคม 1, 2026

    ทุก CPU ในเฟส 3 สมมติว่าคำสั่งเป็นอิสระและคาดเดายากพอที่เครื่องจักรต้องเป็นอเนกประสงค์ — การทำนายสาขา การรันนอกลำดับ แคชลึก ทั้งหมดเพื่อรันโค้ดลำดับ ใดก็ได้ ให้เร็ว GPU เริ่มจากสมมติฐานต่าง ที่รากใน workload ดั้งเดิม: ปฏิบัติการ เดียวกัน นำไปใช้กับจุดข้อมูลจำนวนมหาศาลพร้อมกันอย่างอิสระ

    คำศัพท์ก่อนเริ่ม (ศัพท์บัญญัติราชบัณฑิตยสภา สาขาคอมพิวเตอร์และเทคโนโลยีสารสนเทศ เว้นแต่ระบุ): การประมวลผลแบบขนาน (parallel processing); ภาพกราฟิกส์ (graphics); จุดภาพ (pixel — จุดเล็กที่สุดของภาพบนจอ); จุดยอด (vertex — มุมของรูปสามเหลี่ยมที่ประกอบเป็นวัตถุสามมิติ); เวกเตอร์ (vector, สาขาวิทยาศาสตร์/คณิตศาสตร์ — ชุดตัวเลขเรียงกัน); คำสั่ง (instruction); หน่วยประมวลผล (processor); แตกกิ่ง (branch — จุดที่โปรแกรมเลือกทางตามเงื่อนไข); ปริมาณงาน (throughput) และ เวลาแฝง (latency); thread มีศัพท์บัญญัติว่า สายโยงใย แต่บทนี้ใช้คำทับศัพท์ “เธรด” ตามต้นฉบับ (หมายถึงลำดับคำสั่งหนึ่งสายที่รันอิสระ) ส่วน SIMD (single instruction, multiple data — คำสั่งเดียว ข้อมูลหลายชุด), SIMT (single instruction, multiple threads — คำสั่งเดียว หลายเธรด), warp, lane (ช่องทำงานหนึ่งช่องในกลุ่ม) และ speedup (อัตราเร่ง) ยังไม่พบศัพท์บัญญัติ

    กราฟิกทำให้ความขนานชัด#

    การเรนเดอร์ฉาก 3D คือการแปลงจุดยอดนับล้านและการ shade พิกเซลนับล้าน — คณิตศาสตร์เดียวกันบนแต่ละจุด โดยไม่มีการพึ่งพาที่มีความหมายระหว่างพิกเซล (100, 200) กับพิกเซล (100, 201) หากมีเลนพอ พวกมันทั้งหมดรันพร้อมกันได้

    ตัวเลขให้เห็นขนาด: จอ 1920 × 1080 มี 2,073,600 จุดภาพ ที่ 60 เฟรมต่อวินาทีต้องคำนวณสีราว 124 ล้านจุดภาพต่อวินาที จอ 4K (3840 × 2160) มี 8,294,400 จุดภาพ หรือราว 498 ล้านจุดภาพต่อวินาทีที่ 60 เฟรม — และนี่คือขั้นต่ำ เพราะหนึ่งจุดภาพอาจถูกคำนวณหลายครั้งเมื่อวัตถุซ้อนกัน งานแต่ละชิ้นเล็ก เหมือนกัน และไม่ต้องรอกัน

    นั่นคือรูปทรงต่างจากที่เฟส 3 ถูกสร้างมาจัดการ CPU สกัดความขนานซ่อนจากโค้ดที่ ไม่มี หน้าตาแบบนี้ กราฟิกไม่ต้องการเครื่องจักรนั้น: ความขนานไม่ได้ซ่อน — มันชัดและมหาศาลตั้งแต่ต้น

    ขอบเขตของความขนาน: กฎของแอมดาห์ล#

    ความขนานช่วยได้แค่ไหนคำนวณได้จากหลักการพื้นฐาน สมมุติงานใช้เวลา 1 หน่วยบนหน่วยประมวลผลเดียว ส่วน p ของงานแบ่งทำพร้อมกันได้ ส่วน 1 − p ต้องทำทีละขั้น เมื่อมี N หน่วย เวลาเหลือ (1 − p) + p/N ดังนั้น

    อัตราเร่ง = 1 / ((1 − p) + p/N) และเมื่อ N โตไม่จำกัด อัตราเร่งเข้าหา 1 / (1 − p)

    ความสัมพันธ์นี้รู้จักกันในชื่อกฎของแอมดาห์ล (Amdahl’s law) ผู้เขียนคำนวณ:

    ส่วนที่ขนานได้ p N = 8 N = 32 N = 1,000 เพดานเมื่อ N → ∞
    0 1.00 1.00 1.00 1
    0.5 1.78 1.94 2.00 2
    0.9 4.71 7.80 9.91 10
    0.95 5.93 12.55 19.63 20
    0.99 7.48 24.43 90.99 100
    1 8.00 32.00 1,000 ไม่มีเพดาน

    กรณีขอบ อธิบายเหตุผลของบทนี้ทั้งบท: ที่ p = 0 หน่วยประมวลผลพันตัวก็ไม่ช่วยเลย (ต้องการ CPU ที่รันเธรดเดียวให้เร็วที่สุด) ส่วนเกือบ p = 1 ตัวส่วน (1 − p) หายไป อัตราเร่งโตตาม N ตรง ๆ แถว p = 0.99 บอกว่าแม้ส่วนลำดับเหลือเพียง 1% ก็ตัดอัตราเร่งจาก 1,000 เหลือราว 91 งานกราฟิกและงานเมทริกซ์อยู่ใกล้ปลาย p ≈ 1 มาก จึงคุ้มที่จะสร้างฮาร์ดแวร์ที่มีเลนหลายพันเลน

    ทำไมต้องรวมหน่วยประมวลผลเป็นแบบเดียว#

    บทความของ Lindholm และคณะ (IEEE Micro, 2008) อธิบายว่า GPU ยุคก่อนมีหน่วยประมวลผลสองชนิดแยกกัน: หน่วยจุดยอด (vertex processors) กับหน่วยจุดภาพ (pixel-fragment processors) และเพราะจุดภาพมีมากกว่าจุดยอด หน่วยจุดภาพจึงมีมากกว่าราวสามต่อหนึ่ง แต่งานจริงไม่สมดุล: สามเหลี่ยมใหญ่ทำให้หน่วยจุดยอดว่าง สามเหลี่ยมเล็กทำให้หน่วยจุดภาพว่าง สถาปัตยกรรม Tesla (GeForce 8800, พฤศจิกายน 2006) จึงรวมเป็นหน่วยประมวลผลแบบเดียวเพื่อ “กระจายภาระแบบพลวัต”

    ตัวอย่างที่คำนวณได้ (ตัวเลขประกอบการอธิบาย: GPU แบบแยกมีหน่วยจุดภาพ 96 หน่วยกับหน่วยจุดยอด 32 หน่วยตามอัตรา 3 : 1 เทียบกับแบบรวม 128 หน่วย เวลาของแบบแยกคือค่าที่มากกว่าระหว่าง งานจุดยอด / 32 กับ งานจุดภาพ / 96):

    สัดส่วนงานจุดยอด ตัวอย่างฉาก แบบรวมเร็วกว่า
    25% ตรงกับอัตรา 3 : 1 พอดี 1.00 เท่า (ไม่ได้อะไรเลย)
    10% สามเหลี่ยมใหญ่ 1.20 เท่า
    60% สามเหลี่ยมเล็กจำนวนมาก 2.40 เท่า
    0% ไม่มีงานจุดยอดเลย 1.33 เท่า (หน่วยจุดยอด 32 หน่วยว่างทั้งหมด)
    100% มีแต่งานจุดยอด 4.00 เท่า (หน่วยจุดภาพ 96 หน่วยว่างทั้งหมด)

    แถวแรกคือกรณีขอบที่สำคัญ: ถ้างานสมดุลตรงกับอัตราที่ออกแบบไว้พอดี การรวมไม่ช่วยเลย ประโยชน์ทั้งหมดมาจากงานที่ ไม่ ตรงกับที่ผู้ออกแบบเดาไว้ และหน่วยที่รวมเป็นแบบเดียวนี้เองที่ “เปิดประตูสู่การคำนวณขนานบน GPU แบบใหม่ทั้งหมด” ตามที่บทความระบุ

    SIMD / SIMT: คำสั่งเดียว หลายเลน#

    SIMD นำคำสั่งเดียวไปใช้ข้ามองค์ประกอบข้อมูลหลายชิ้นพร้อมกัน GPU implement โมเดลที่เกี่ยวข้องใกล้ — SIMT: เธรดขนานหลายเส้น แต่ละเส้นบนข้อมูลของตัวเอง (พิกเซลของตัวเอง จุดยอดของตัวเอง) ฮาร์ดแวร์รันกลุ่มของพวกมันแบบ lockstep ข้ามเลนง่าย ๆ

    ผลตอบแทนตรง: ทุกเลนในกลุ่มรันคำสั่ง เดียวกัน ในชั่วขณะเดียวกัน จึงไม่ต้อง duplicate การดึง decode และควบคุมต่อเลนแบบที่ CPU duplicate เครื่องจักรท่อต่อคอร์ หน่วยควบคุมที่แชร์หนึ่งหน่วยขับหลายเลน — ชัยชนะด้านพื้นที่และพลังงาน สำหรับ งาน embarrassingly parallel ปฏิบัติการเดียว-ข้อมูลหลายชิ้น และพอดีแย่กับโค้ดลำดับที่คาดเดายาก นั่นคือเหตุผลที่ CPU กับ GPU ใช้แทนกันไม่ได้ และระบบจริงมักมีทั้งสอง

    SIMD บน CPU: ความกว้างคงที่และ “เศษ” ท้ายลูป#

    รีจิสเตอร์ SIMD กว้าง 256 บิตบรรจุจำนวนทศนิยม 32 บิตได้ 256 / 32 = 8 ตัว คำสั่งบวกเวกเตอร์หนึ่งคำสั่งจึงบวกได้ 8 คู่พร้อมกัน ลูปบวกเวกเตอร์ยาว n จึงแบ่งเป็น n ÷ 8 รอบเต็ม บวกกับ เศษ n mod 8 ตัวที่ต้องทำแยก ผู้เขียนไล่กรณีขอบ:

    n รอบ SIMD เต็ม เศษที่ต้องทำแยก
    0 0 0 (ลูปต้องไม่รันเลย)
    1 0 1
    7 0 7 (SIMD ไม่ได้ใช้เลย)
    8 1 0
    9 1 1
    1,003 125 3
    1,024 128 0

    ความกว้างคงที่นี้คือจุดต่างที่ NVIDIA CUDA Programming Guide เน้น: ใน SIMD การทำงานเดินตามเส้นทางควบคุมเดียว ส่วนใน SIMT แต่ละเธรดเลือกเส้นทางของตัวเองได้ “SIMT จึงไม่มีความกว้างข้อมูลตายตัวแบบ SIMD” โปรแกรมเมอร์เขียนโค้ดสำหรับ หนึ่งเธรด แล้วให้ฮาร์ดแวร์จัดกลุ่มเอง

    SIMT บน GPU: warp, การแตกกิ่ง และเลนที่ว่าง#

    คู่มือ CUDA ระบุว่าเธรดถูกจัดเป็นกลุ่มละ 32 เรียกว่า warp (ชื่อมาจากการทอผ้า ตามบทความของ Lindholm) ทุกเธรดใน warp รันคำสั่งเดียวกันพร้อมกัน ถ้าบางเธรด แตกกิ่ง ไปทางหนึ่งและบางเธรดไปอีกทาง เธรดที่ไม่ได้ไปทางนั้นจะถูก “ปิดบัง” (masked off) ระหว่างที่อีกกลุ่มรัน เรียกว่า warp divergence

    ตัวอย่างที่คำนวณได้ (สมมุติว่ากิ่ง if มี 10 คำสั่ง กิ่ง else มี 30 คำสั่ง; จำลองด้วยสคริปต์ 4 warp รวม 128 เธรด):

    เงื่อนไขของเธรด i เวลาต่อ warp (คำสั่ง) เหตุผล
    จริงทุกเธรด 10, 10, 10, 10 ไม่มีใครไป else
    i % 2 == 0 (ตัวอย่างในรูปที่ 7 ของคู่มือ) 40, 40, 40, 40 ทุก warp มีทั้งสองแบบ ต้องรันทั้งสองกิ่ง
    i < 16 40, 30, 30, 30 มีเพียง warp แรกที่แตก
    i == 0 เท่านั้น 40, 30, 30, 30 เธรดเดียวก็ทำให้ทั้ง warp จ่ายราคาเต็ม
    (i / 32) % 2 == 0 10, 30, 10, 30 เงื่อนไขเหมือนกันทั้ง warp จึงไม่แตก

    แถว i == 0 คือกรณีขอบที่น่าจำ: เธรดเดียวใน 32 ที่ไปคนละทาง ทำให้ warp นั้นเสียเวลาเท่ากับรันทั้งสองกิ่ง ส่วนแถวสุดท้ายแสดงว่าการแตกกิ่ง ระหว่าง warp ไม่มีราคา — ตรงกับที่ Lindholm เขียนว่า “การแตกกิ่งเกิดเฉพาะภายใน warp; warp ต่างกันทำงานอิสระ” และเป็นเหตุผลที่ warp กว้าง 32 ของ Tesla “มีประสิทธิภาพกับโค้ดที่มีการแตกกิ่งมากกว่า” SIMD ที่กว้างกว่าของ GPU รุ่นก่อน

    ดัชนีและการตรวจขอบเขต: คู่มือ CUDA ให้เคอร์เนลบวกเวกเตอร์ที่แต่ละเธรดคำนวณ workIndex = threadIdx.x + blockDim.x × blockIdx.x และทำงานเฉพาะเมื่อ workIndex < vectorLength จำนวนบล็อกคำนวณด้วยการหารปัดขึ้น blocks = (vectorLength + threads − 1) / threads ผู้เขียนไล่กรณีด้วย 256 เธรดต่อบล็อก:

    • n = 1,000: ได้ 4 บล็อก = 1,024 เธรด ใช้งานจริง 1,000 (97.7%) มี warp ที่ไม่เต็มเพียงตัวเดียว คือ warp สุดท้ายซึ่งมีเธรดทำงาน 8 จาก 32 — ตรงกับที่คู่มือเตือนว่าเมื่อจำนวนเธรดไม่ใช่พหุคูณของ 32 “warp สุดท้ายจะมีเลนที่ไม่ได้ใช้ตลอดการทำงาน” ถ้าไม่มีการตรวจ workIndex < n เธรด 1,000 ถึง 1,023 จะเขียนเลยท้ายอาเรย์
    • n = 0: ได้ 0 บล็อก คือไม่มีงานให้ทำ โปรแกรมควรตรวจกรณีนี้และไม่เรียกเคอร์เนลเลย (คู่มือเองแนะนำให้หลีกเลี่ยงการเรียกบล็อกที่ไม่มีเธรดใดทำงาน)
    • n ใกล้ค่าสูงสุดของ int 32 บิต (2,147,483,647): นิพจน์ n + 255 ล้น (overflow) ผู้เขียนจำลองเลขจำนวนเต็ม 32 บิตแบบมีเครื่องหมาย: n = 2,147,483,392 ยังได้ 8,388,607 บล็อกถูกต้อง แต่ตั้งแต่ n = 2,147,483,393 ขึ้นไป n + 255 วนไปเป็นเลขลบ ได้จำนวนบล็อกติดลบ (−8,388,608 ที่ n = 2,147,483,393 และ −8,388,607 ที่ n = 2,147,483,647 เมื่อหารแบบปัดเข้าหาศูนย์) ทางแก้ที่ไม่ล้นคือ blocks = n / 256 + (n % 256 ≠ 0 ? 1 : 0) (คู่มือแนะนำ cuda::ceil_div เป็นอีกทางหนึ่ง) ตรวจต่อ: เมื่อ n = 2,147,483,647 ได้ 8,388,608 บล็อก และดัชนีสูงสุด 8,388,608 × 256 − 1 = 2,147,483,647 พอดีเท่าค่าสูงสุดของ int จึงไม่ล้น

    จากกราฟิกสู่ compute ทั่วไป#

    การตระหนักที่เปลี่ยนอุตสาหกรรม: รูปทรง SIMT เดียวกันพอดีกับคลาสที่กว้างกว่าสามเหลี่ยมมาก เมื่อคณิตศาสตร์ขนานมหาศาลและสม่ำเสมอ การฝึกและ inference โครงข่ายประสาทสร้างเกือบทั้งหมดจากงานเมทริกซ์และเวกเตอร์แบบนั้น — ซึ่งคือเหตุผลที่ฮาร์ดแวร์เกิดมาเพื่อเรนเดอร์กลายเป็น substrate คำนวณ AI ที่ครอง และเหตุผลที่ส่วนที่เหลือของเฟสนี้เกี่ยวกับการโปรแกรมและป้อนสถาปัตยกรรมขนานนั้น ไม่ใช่กราฟิกโดยเฉพาะ

    ตัวเลขสองจุดบนเส้นทาง#

    คู่มือ CUDA สรุปความต่างว่า CPU ออกแบบให้รันลำดับคำสั่งหนึ่งสายให้เร็วที่สุดและรันพร้อมกันได้ “ไม่กี่สิบเธรด” ส่วน GPU ออกแบบให้รัน “หลายพันเธรด” พร้อมกัน โดยยอมให้แต่ละเธรดช้าลงเพื่อแลกกับปริมาณงานรวม และ “GPU ใช้ทรานซิสเตอร์ไปกับหน่วยประมวลผลข้อมูลมากกว่า ขณะที่ CPU ใช้ทรานซิสเตอร์ไปกับแคชและการควบคุมลำดับงานมากกว่า” คู่มือยังระบุว่า NVIDIA เปิดตัว CUDA ในปี 2006 เพื่อให้งานคำนวณใด ๆ ใช้ปริมาณงานของ GPU ได้โดยไม่ต้องผ่าน API กราฟิก ลองคำนวณยอดสูงสุดจากโครงสร้างจริงสองรุ่น:

    • GeForce 8800 Ultra (2006–2007, Lindholm และคณะ): 16 SM แต่ละ SM มีหน่วยคูณ-บวก (MAD) 8 หน่วย (2 FLOP ต่อรอบต่อหน่วย) และหน่วย SFU 2 หน่วยที่มีตัวคูณหน่วยละ 4 ตัว ที่ 1.5 GHz: (8 × 2 + 2 × 4) × 1.5 = 36 GFLOPS ต่อ SM ตรงกับที่บทความระบุ และ × 16 = 576 GFLOPS ตรงกับยอดรวมในบทความ บนทรานซิสเตอร์ 681 ล้านตัว
    • A100 (2020, whitepaper ของ NVIDIA): 108 SM × 64 แกน FP32 × 2 FLOP × 1.41 GHz ≈ 19.5 TFLOPS FP32 ตรงกับตัวเลขใน whitepaper

    19,500 / 576 ≈ 34 เท่าในราวสิบสามถึงสิบสี่ปีสำหรับ FP32 ธรรมดา (ยังไม่นับ tensor core ที่บทหลังของเฟสนี้จะพูดถึง) — และทั้งสองรุ่นได้มาจากสูตรเดียวกัน: จำนวนเลน × งานต่อเลนต่อรอบ × ความถี่
