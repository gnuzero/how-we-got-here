    แคช

    มกราคม 1, 2026

    บทที่ 10 วางลำดับชั้นหน่วยความจำไว้แล้ว: รีจิสเตอร์, แคช SRAM, DRAM, ดิสก์ — แลกความจุกับความเร็วทุกขั้น แคชคือจุดที่การแลกเปลี่ยนนั้นแบกรับประสิทธิภาพของ CPU ทุกตัว สมมติฐานวางบนข้อเท็จจริงเชิงประจักษ์เกี่ยวกับโปรแกรมจริงข้อเดียว: locality

    บทนี้จะไล่ตั้งแต่ต้น ว่าแคชตัดสินใจอย่างไรว่าข้อมูลอยู่ในแคชหรือไม่ วางข้อมูลไว้ช่องไหน ไล่อะไรออกเมื่อเต็ม และหลายคอร์ตกลงกันอย่างไรว่าค่าไหนคือค่าล่าสุด ทุกขั้นมีตัวเลขให้คำนวณตามได้

    หน่วยความจำแคช (cache memory, ศัพท์บัญญัติ; ในบทนี้เรียกสั้น ๆ ว่า แคช) คือหน่วยความจำขนาดเล็กที่เร็วมาก วางอยู่ระหว่างตัวประมวลผลกับหน่วยความจำหลัก (DRAM) เก็บสำเนาของข้อมูลบางส่วนจากหน่วยความจำหลัก ถ้าข้อมูลที่ต้องการอยู่ในแคช เรียกว่า hit (พบ) ถ้าไม่อยู่ เรียกว่า miss (พลาด) และต้องไปดึงจากชั้นที่ช้ากว่า

    เหตุใดแคชจึงใช้ได้เลย#

    Temporal locality (ความใกล้เชิงเวลา) — ตำแหน่งที่เพิ่งแตะมีแนวโน้มจะถูกแตะอีกในไม่ช้า (ตัวแปรลูป โค้ดร้อน) Spatial locality (ความใกล้เชิงพื้นที่) — ตำแหน่งใกล้เคียงมีแนวโน้มถูกแตะถัดไป (อาร์เรย์ การดึงคำสั่งตามลำดับ) แคชเก็บข้อมูลที่ใช้ล่าสุดไว้ใกล้ และเมื่อ miss จะดึง line (บางตำราเรียก block) ทั้งก้อน มักขนาด 64 ไบต์ เดิมพันว่าข้อมูลข้างเคียงจะถูกใช้ในไม่ช้า

    ตัวอย่างแรก วนอ่านอาร์เรย์ int (ตัวละ 4 ไบต์) เรียงกันไปทีละตัว line 64 ไบต์บรรจุได้ 16 ตัว การอ่านตัวแรกของแต่ละ line จะ miss แล้วดึง line ทั้งก้อนมา อีก 15 ตัวถัดไป hit หมด อัตรา hit จึงเป็น 15/16 = 93.75% ทั้งที่โปรแกรมไม่เคยอ่านซ้ำตัวไหนเลย spatial locality ล้วน ๆ

    ถามแคชอย่างไร: tag, index, offset#

    แคชต้องตอบให้ได้ในหนึ่งถึงไม่กี่รอบว่าเลขที่อยู่ที่ส่งมาอยู่ในแคชหรือไม่ มันจึงแบ่งเลขที่อยู่เป็นสามท่อน

    • offset (ระยะเลื่อน) — ไบต์ไหนภายใน line
    • index (ดรรชนี) — line นี้ต้องอยู่ใน set ไหน (set คือกลุ่มช่องที่ line หนึ่งมีสิทธิ์ลงได้)
    • tag (ป้ายระบุ) — บิตที่เหลือด้านบน เก็บไว้คู่กับข้อมูล ใช้ตรวจว่า line ที่อยู่ใน set นั้นเป็น line ที่เราต้องการจริง ไม่ใช่ line อื่นที่ดรรชนีตรงกัน

    แต่ละช่องมี valid bit (บิตบอกว่าช่องนี้มีข้อมูลจริง) และถ้าเป็นแคชแบบ write-back ก็มี dirty bit (บิตบอกว่าข้อมูลถูกแก้ไขแล้วแต่ยังไม่ได้เขียนกลับ)

    ตัวอย่างคำนวณ#

    แคชข้อมูลระดับ 1 ขนาด 32 KiB, line 64 ไบต์, 8-way set associative (set ละ 8 ช่อง), เลขที่อยู่ 32 บิต

    1. จำนวน line ทั้งหมด = 32,768 ÷ 64 = 512 line
    2. จำนวน set = 512 ÷ 8 = 64 set
    3. offset ต้องชี้ได้ 64 ไบต์ → log₂ 64 = 6 บิต
    4. index ต้องชี้ได้ 64 set → log₂ 64 = 6 บิต
    5. tag = 32 − 6 − 6 = 20 บิต

    ลองแยกเลขที่อยู่ 0x12345678

    • offset = 6 บิตล่าง = 0x38 = 56 (ไบต์ที่ 56 ของ line)
    • index = 6 บิตถัดไป = 25 (ไปดู set ที่ 25)
    • tag = 20 บิตบน = 0x12345

    ฮาร์ดแวร์อ่านทั้ง 8 ช่องของ set 25 พร้อมกัน เทียบ tag ทั้ง 8 ตัวกับ 0x12345 พร้อมกันด้วยวงจรเปรียบเทียบ 8 ชุด ถ้าตัวไหนตรงและ valid = 1 ก็คือ hit แล้วใช้มัลติเพล็กเซอร์ (อุปกรณ์สหสัญญาณ) เลือกข้อมูลจากช่องนั้นออกมา

    ราคาของการเก็บ tag: แต่ละช่องต้องเก็บ tag 20 บิต + valid 1 บิต + dirty 1 บิต = 22 บิต × 512 ช่อง = 11,264 บิต = 1,408 ไบต์ คิดเป็นราว 4.3% ของความจุข้อมูล 32 KiB นี่คือต้นทุนแฝงที่ตัวเลข “32 KiB” บนสเปกไม่ได้บอก

    ข้อสังเกตที่จะสำคัญในบทที่ 24: index + offset = 12 บิต = 4 KiB พอดีกับขนาด หน้า (page) ของหน่วยความจำเสมือน แปลว่าแคชเลือก set ได้จากบิตที่ไม่ถูกแปลงเลขที่อยู่ จึงอ่าน set ไปพร้อมกับที่ TLB กำลังแปลงเลขที่อยู่ได้ ไม่ต้องรอ เป็นเหตุผลหนึ่งที่แคช L1 จำนวนมากมีขนาดเท่ากับ (ขนาดหน้า × จำนวน way)

    Line อยู่ได้ที่ไหน#

    Direct-mapped (จับคู่ตรง) — หนึ่งช่องที่เป็นไปได้ต่อเลขที่อยู่ ตรวจเร็วเพราะเทียบ tag แค่ตัวเดียว แต่เกิด conflict miss (miss จากการชนกัน) เมื่อเลขที่อยู่ที่ใช้บ่อยสองตำแหน่งได้ index เดียวกันแล้วไล่กันออกไปมา

    Fully associative (เชื่อมโยงเต็ม) — line ใดลงช่องใดก็ได้ ไม่มี conflict miss แต่ทุกการค้นต้องเทียบ tag ทุกช่อง วงจรเปรียบเทียบจึงบานตามจำนวนช่อง ใช้ได้แค่กับโครงสร้างเล็กมาก เช่น TLB บางระดับ

    Set-associative (เชื่อมโยงแบบกลุ่ม) — จุดกลางเชิงปฏิบัติ: index เลือก set เล็ก ๆ (เช่น 8 way) แล้วตรวจ tag เฉพาะในนั้น ได้ความยืดหยุ่นเกือบทั้งหมด ด้วยฮาร์ดแวร์น้อยกว่าการสแกนเต็มมาก แคชจริงเกือบทุกตัวอยู่ตรงนี้ direct-mapped คือกรณี 1-way และ fully associative คือกรณีที่มี set เดียว

    ตัวอย่าง: ชนกันแบบ direct-mapped#

    แคช 32 KiB line 64 ไบต์แบบ direct-mapped มี 512 ช่อง ดรรชนี = (เลขที่อยู่ ÷ 64) mod 512 เลขที่อยู่ 0x10000 ได้ดรรชนี 1024 mod 512 = 0 และ 0x18000 ได้ 1536 mod 512 = 0 เช่นกัน เพราะทั้งคู่ห่างกัน 0x8000 = 32 KiB พอดี ถ้าลูปอ่านสองตำแหน่งนี้สลับกัน ทุกการอ่านจะ miss เพราะแต่ละตัวเตะอีกตัวออก แคชแบบ 8-way ขนาดเท่ากันก็ส่งทั้งคู่ไป set 0 เหมือนกัน แต่ set นั้นมี 8 ช่อง จึงเก็บได้ทั้งสองตัว หลังโหลดครั้งแรกทุกการอ่านจะ hit

    ตัวอย่าง: ลำดับการวนลูปเปลี่ยนทุกอย่าง#

    อาร์เรย์ int a[1024][1024] เก็บแบบแถวต่อแถว (row-major แบบภาษา C) หนึ่งแถวยาว 1024 × 4 = 4,096 ไบต์

    • วน ตามแถว (for i … for j … a[i][j]): อ่านเรียงติดกัน miss หนึ่งครั้งทุก 16 ตัว hit 93.75%
    • วน ตามคอลัมน์ (for j … for i … a[i][j]): แต่ละครั้งกระโดดไป 4,096 ไบต์ ได้ line ใหม่ทุกครั้ง ยิ่งกว่านั้น 4,096 ÷ 64 = 64 line ซึ่งเท่ากับจำนวน set พอดี ทุกตัวในคอลัมน์จึงลง set เดียวกัน ที่มีแค่ 8 ช่อง พอวนกลับมาคอลัมน์ถัดไป line เก่าถูกไล่ออกไปนานแล้ว ผลคือ miss ทุกครั้ง

    โค้ดสองแบบนี้คำนวณผลเดียวกันทุกประการ แต่ต่างกันที่ว่ารู้จักแคชหรือไม่

    เวลาเข้าถึงเฉลี่ย (AMAT)#

    ตัวชี้วัดหลักคือ เวลาเข้าถึงหน่วยความจำเฉลี่ย (average memory access time, AMAT)

    AMAT = เวลา hit + อัตรา miss × ค่าปรับเมื่อ miss

    ตัวอย่าง: L1 hit ใช้ 1 ns, miss 5%, ไปถึง DRAM ใช้ 80 ns → AMAT = 1 + 0.05 × 80 = 5 ns แม้ 95% ของการเข้าถึงจะใช้แค่ 1 ns แต่ค่าเฉลี่ยกลับเป็นห้าเท่า เพราะ miss ส่วนน้อยนั้นแพงมาก

    เติม L2 ที่ hit ใน 4 ns และพลาด 20% ของการเข้าถึงที่มาถึงมัน (local miss rate) ค่าปรับของ L1 ตอนนี้คือ AMAT ของ L2 เอง = 4 + 0.20 × 80 = 20 ns ดังนั้น AMAT รวม = 1 + 0.05 × 20 = 2 ns ลดลงเหลือ 40% ของเดิม นี่คือเหตุผลที่ชิปยอมเสียพื้นที่มหาศาลให้แคชหลายชั้น

    เมื่อเต็มต้องไล่ใครออก และเขียนแล้วทำอย่างไร#

    นโยบายแทนที่ (replacement policy) — เมื่อ set เต็มและต้องนำ line ใหม่เข้า ต้องเลือกเหยื่อ วิธีคลาสสิกคือ LRU (least recently used) ไล่ตัวที่ไม่ได้ใช้นานที่สุด ซึ่งอาศัย temporal locality ตรง ๆ แต่การจำลำดับที่แท้จริงของ 8 ช่องแพง ฮาร์ดแวร์จริงจึงมักใช้ตัวประมาณ (pseudo-LRU) ที่ใช้บิตน้อยกว่า

    นโยบายการเขียน มีสองแบบหลัก

    • Write-through (เขียนทะลุ) — เขียนทั้งในแคชและชั้นล่างทุกครั้ง ชั้นล่างมีค่าล่าสุดเสมอ แต่กินแบนด์วิดท์มาก มักใช้คู่กับที่พักข้อมูลการเขียน (write buffer)
    • Write-back (เขียนกลับ) — เขียนเฉพาะในแคชแล้วตั้ง dirty bit จะเขียนกลับลงชั้นล่างเมื่อ line นั้นถูกไล่ออกเท่านั้น ถ้าลูปเขียนตัวแปรเดิมหนึ่งล้านครั้ง ก็เขียนกลับ DRAM แค่ครั้งเดียว แคชระดับบนของซีพียูสมัยใหม่ส่วนใหญ่เป็นแบบนี้

    Multicore: Coherence เป็นข้อจำกัดใหม่#

    คอร์เดียว แคชส่วนตัวหนึ่ง: ใช้ได้ หลายคอร์ แต่ละตัวมีแคช: คอร์ A เขียน line ที่คอร์ B ยังถือ — หากไม่มีโปรโตคอล B อ่านค่าเก่าตลอดไป ความสอดคล้องของแคช (cache coherence) คือข้อตกลงว่า การอ่านต้องเห็นค่าที่เขียนล่าสุด ไม่ว่าจะเขียนจากคอร์ไหน

    MESI คือคำตอบคลาสสิก ทุก line ในทุกแคชติดสถานะหนึ่งในสี่

    สถานะ ความหมาย
    M (Modified) มีที่นี่ที่เดียว และถูกแก้แล้ว หน่วยความจำหลักถือค่าเก่า
    E (Exclusive) มีที่นี่ที่เดียว ค่าตรงกับหน่วยความจำหลัก
    S (Shared) อาจมีหลายแคชถือสำเนา ทุกสำเนาตรงกัน อ่านได้อย่างเดียว
    I (Invalid) ใช้ไม่ได้ ถือว่าไม่มี

    ไล่ตามทีละขั้น กับตัวแปร X ใน line เดียว

    1. คอร์ A อ่าน X ไม่มีใครถือ → A ได้ E
    2. คอร์ B อ่าน X → A เห็นคำขอ (ผ่านการสอดแนมบัส หรือ bus snooping หรือผ่าน directory) ทั้งสองลดเป็น S
    3. คอร์ B เขียน X → B ต้องประกาศขอสิทธิ์เขียน ทำให้สำเนาของ A กลายเป็น I และ B เป็น M
    4. คอร์ A อ่าน X อีก → miss เพราะเป็น I B ส่งค่าล่าสุดมาให้ (และเขียนกลับหน่วยความจำหลัก) ทั้งคู่กลับเป็น S

    ประโยชน์ของ E: ถ้าคอร์ A ใน E เขียน X มันเปลี่ยนเป็น M ได้เองเงียบ ๆ ไม่ต้องประกาศบนบัส เพราะรู้อยู่แล้วว่าไม่มีใครถือสำเนา โปรแกรมแบบเธรดเดียวจึงไม่เสียค่าโปรโตคอลเลย

    False sharing: ไม่ได้แชร์ แต่จ่ายเหมือนแชร์#

    coherence ทำงานระดับ line ไม่ใช่ระดับตัวแปร ถ้าเธรดสองตัวบนสองคอร์ต่างเพิ่มค่าตัวนับของตัวเอง แต่ตัวนับทั้งสองบังเอิญอยู่ใน line 64 ไบต์เดียวกัน ทุกการเขียนของ A จะทำให้สำเนาของ B เป็น I และกลับกัน line นี้เด้งไปมาระหว่างสองคอร์ตลอดเวลา ทั้งที่ข้อมูลไม่ได้แชร์กันจริงเลย เรียกว่า false sharing ทางแก้คือจัดให้ตัวแปรที่เธรดต่างกันเขียนอยู่คนละ line (เช่น เติมช่องว่างให้ครบ 64 ไบต์)

    Coherence ไม่ฟรี และต้นทุนโตตามจำนวนคอร์ — เหตุผลหนึ่งที่ “แค่เพิ่มคอร์” (บทที่ 17) มีผลตอบแทนลดลงของตัวเอง แยกจากขีดจำกัด ILP

    ลองบนเครื่องตัวเอง#

    บนลินุกซ์ส่วนใหญ่ คำสั่ง getconf LEVEL1_DCACHE_LINESIZE บอกขนาด line ของแคชข้อมูล L1 และ lscpu บอกขนาดแคชแต่ละระดับ ลองนำตัวเลขจริงของเครื่องคุณมาคำนวณจำนวน set และความยาวของ tag ตามตัวอย่างข้างบน (บางเครื่องหรือบางเวอร์ชันอาจแสดงค่า 0 หรือไม่รองรับบางตัวแปร)

    ประตูออก: M. V. Wilkes, “Slave Memories and Dynamic Storage Allocation” (IEEE Transactions on Electronic Computers, 1965) — คำแถลงยุคแรกของแนวคิดแคชในฐานะ slave store ที่เร็วข้างหน่วยความจำหลักที่ช้ากว่า
