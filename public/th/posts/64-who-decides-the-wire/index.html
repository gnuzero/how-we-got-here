    ARPANET (บทที่ 39) และ TCP/IP (บทที่ 41) แก้ปัญหาว่าแพ็กเก็ตเคลื่อนที่อย่างไร แต่เพียงลำพังไม่ได้ตอบคำถามเงียบกว่า: ใครมีสิทธิ์บอกว่าบิตเหล่านั้นหมายความว่าอะไร? พอร์ต 80, คำนำหน้า IPv4, .com, code point ของ ก — ไม่มีอันใดใช้ได้ เว้นแต่ผู้ปฏิบัติการที่อยู่ห่างกันจะปฏิบัติต่อตัวระบุเดียวกันในทางเดียวกัน เรื่องการกำกับดูแลอินเทอร์เน็ตคือเรื่องของข้อตกลงนั้น: ไม่ใช่รัฐสภาเหนือเครือข่าย แต่เป็นชุดบัญชีแชร์สำหรับ หมายเลข, ชื่อ, และ การเข้ารหัส

    เอกสารก่อนสถาบัน#

    เครื่องมือประสานงานชิ้นแรกคือชุดเอกสาร ในเมษายน 1969 Steve Crocker ตีพิมพ์ RFC 1 — Host Software — เป็นบันทึกทำงานสำหรับชุมชนวิจัย ARPANET น้ำเสียงสำคัญ: “Request for Comments” ไม่ใช่ “คำสั่ง” Jon Postel บรรณาธิการชุดนี้เกือบสามทศวรรษ เปลี่ยนบันทึกไม่เป็นทางการให้เป็นบันทึกสาธารณะที่ยั่งยืนว่าอินเทอร์เน็ตทำงานจริงอย่างไร ประตูออก: ประวัติ RFC Editor

    เมื่อชุมชนวิจัยโตเกินการประชุมในทางเดิน มันเติบโตเป็น Internet Engineering Task Force (IETF) วลีที่รับน้ำหนักคือของ Dave Clark: rough consensus and running code — มาตรฐานพิสูจน์ตัวด้วยการเผยแพร่ออกไปใช้งานจริง ไม่ใช่ด้วยการลงคะแนน IETF ไม่ได้เป็นเจ้าของอินเทอร์เน็ต; มันเป็นเจ้าของกระบวนการถกโปรโตคอลให้กลายเป็นสิ่งที่ผู้ปฏิบัติการจะนำไปใช้ ประตูออก: ietf.org

    หมายเลข: ต้องมีใครแจกตัวระบุ#

    แพ็กเก็ตพกหมายเลขโปรโตคอล หมายเลขพอร์ต บล็อกที่อยู่ ค่า ASN ประเภทสื่อ — ตัวระบุที่ไร้ค่าหากสองกลุ่มสร้างตัวเดียวกันสำหรับความหมายต่างกัน เป็นปี ๆ บัญชีนั้นอยู่ที่เดียว: Internet Assigned Numbers Authority (IANA) บริหารเป็นบริการปฏิบัติโดย Jon Postel (พร้อม Joyce Reynolds เป็นจุดติดต่อยาวนาน) ภายใต้สัญญาวิจัยที่ UCLA และต่อมา USC/ISI IANA คือเมล็ดของ ชนิด: ทะเบียนกลางสำหรับพารามิเตอร์โปรโตคอล เพื่อให้การอิมพลีเมนต์ทำงานร่วมกันได้โดยไม่ต้องเจรจาคู่ต่อคู่

    เมื่อเครือข่ายขยายเกินสมุดบันทึกของคนคนเดียว ทรัพยากรตัวเลขแยกตาม ชนิด พารามิเตอร์โปรโตคอลอยู่กับ IANA พื้นที่ที่อยู่ IP เคลื่อนไปสู่ Regional Internet Registries — ARIN (1997) สำหรับส่วนใหญ่ของอเมริกาเหนือ; RIPE NCC, APNIC, LACNIC และ AFRINIC คือ ชนิด เดียวกันสำหรับภูมิภาคอื่น โดยมี national หรือ local Internet registries (NIRs) อยู่ใต้บางแห่งเมื่อภูมิภาคเลือกแบบนั้น รูปแบบคือจุดสำคัญ: ตัวระบุที่หายากและไม่ซ้ำต้องการผู้ดูแลที่ทุกคนชี้ได้ ประตูออก: iana.org, arin.net

    ชื่อ: มนุษย์ต้องการคำ; เครื่องต้องการความไม่ซ้ำ#

    ข้อกำหนด DNS ของ Paul Mockapetris (RFC 1034, RFC 1035) เปลี่ยนชื่อแบบลำดับชั้นให้เป็นระบบค้นหาแบบกระจายบนผ้าที่อยู่ ชื่อเป็นการเมืองในทางที่ตัวเลขดิบไม่ใช่: คนถกเถียงเรื่องคำ RFC 1591 ของ Jon Postel วางกรอบนโยบายโดเมนยุคแรกในฐานะการดูแล

    ชื่อบนสายยังเป็น ASCII: RFC 1035 หัวข้อ 2.3.4 จำกัด ป้าย (label — ส่วนระหว่างจุด) ไว้ที่ 63 ออกเต็ตหรือน้อยกว่า และทั้งชื่อไว้ที่ 255 ออกเต็ตหรือน้อยกว่า เลข 63 ไม่ได้ตั้งลอย ๆ: ในรูปแบบข้อความ DNS ป้ายแต่ละป้ายนำหน้าด้วยออกเต็ตความยาวหนึ่งออกเต็ต สองบิตบนสงวนไว้ (RFC 1035 ใช้ค่า 11 สำหรับการบีบอัดชื่อ) เหลือหกบิต 2⁶ − 1 = 63 เมื่อ ชื่อโดเมน (domain name — ศัพท์บัญญัติ: ชื่อเขต, ชื่อโดเมน) ต้องเป็นภาษาไทย ระบบจึงไม่เปลี่ยน DNS แต่แปลงป้ายภาษาไทยให้เป็นป้าย ASCII ที่ขึ้นต้นด้วย xn-- ก่อนส่ง รายละเอียดและตัวอย่างที่คำนวณด้วยมืออยู่ในส่วน “เจาะลึก” ท้ายหัวข้อการเข้ารหัสด้านล่าง

    ปลายทศวรรษ 1990 รัฐบาลสหรัฐต้องการย้ายฟังก์ชันประสานงานเหล่านั้นออกจากสัญญาวิจัยเดียว ICANN (Internet Corporation for Assigned Names and Numbers) ก่อตั้งปี 1998 — ประธานชั่วคราว Esther Dyson — เพื่อถือที่นั่งสถาบันสำหรับนโยบายชื่อและหมายเลข ในขณะที่ IANA ยังทำงานเป็นทะเบียนปฏิบัติภายใต้ร่มนั้น อ่าน ICANN เป็นเมล็ดอีกอันของ ชนิด: องค์กรหลายฝ่ายมีส่วนได้ส่วนเสียที่งานคือความเสถียรและความไม่ซ้ำของเนมสเปซแชร์ ไม่ใช่การเลือกผู้ชนะในแอปพลิเคชัน ประตูออก: icann.org

    การเข้ารหัส: เพย์โหลดต้องหมายถึงอักษรเดียวกัน#

    การทำงานร่วมกันพังเงียบเมื่อสองปลายไม่เห็นด้วยว่าลำดับไบต์ คืออะไร Unicode Consortium (ก่อตั้ง 1991; งานต้นจาก Joe Becker, Mark Davis และคนอื่นข้ามบริษัทที่ต้องการชุดอักขระเดียว) ดูแลการแมปแชร์จากอักขระนามธรรมสู่ code point — เหตุผลที่ไทย ละติน และอีโมจิแชร์สายเดียวกันได้โดยไม่ให้แต่ละแอปประดิษฐ์ตารางอักษรของตัวเอง UTF-8 จึงกลายเป็นการเข้ารหัส บนสาย ที่ครองสำหรับคลังนั้น ประตูออก: unicode.org, Unicode Standard

    เจาะลึก: อักษรไทยกลายเป็นไบต์ได้อย่างไร#

    บทนี้เปิดด้วย “code point ของ ก” ส่วนนี้ตามรอย ก และเพื่อนร่วมอักษรตั้งแต่ตารางมาตรฐานลงไปจนถึงไบต์บนสาย ตัวเลขทุกตัวในส่วนนี้ผู้เขียนตรวจเองด้วยการรันโค้ดจริง (Python 3.13 กับแพ็กเกจ idna 3.10, Node 20.19.2 ที่มาพร้อม ICU 76.1 และ BusyBox ในแล็บ) หรือเปิดอ่านจากแหล่งปฐมภูมิที่ระบุท้ายส่วน ข้อความใดเป็นการอนุมานหรือตัวอย่างสมมติของผู้เขียนจะมีป้ายบอกไว้

    คำศัพท์ก่อนเริ่ม#

    ศัพท์บัญญัติราชบัณฑิตยสภา สาขาคอมพิวเตอร์และเทคโนโลยีสารสนเทศ เว้นแต่ระบุ: อักขระ (character); ชุดอักขระ (character set); รหัส (code); รหัสอักขระ (character code); การเข้ารหัส (encoding — สาขาภาษาศาสตร์ประยุกต์); บิต (bit); ไบต์ (byte); ฐานสิบหก (hexadecimal); สายอักขระ (string); เรียงลำดับ (sort); ชุดแบบอักษร (font); แผงแป้นอักขระ (keyboard); ชื่อเขต, ชื่อโดเมน (domain name); เกณฑ์วิธี, โพรโทคอล (protocol) คำต่อไปนี้ค้นแล้วไม่พบศัพท์บัญญัติในความหมายนี้ จึงใช้คำอธิบายภาษาไทยคู่กับคำอังกฤษ: code point (ตำแหน่งรหัสใน Unicode เขียนแบบ U+0E01), glyph (รูปอักษรที่ชุดแบบอักษรวาดออกมา), collation (การเรียงลำดับตามภาษา), name server (เครื่องบริการชื่อ) ส่วน normalization ของ Unicode บทนี้เรียกว่า การทำให้เป็นบรรทัดฐาน โดยยึดศัพท์บัญญัติของคำกริยา normalize (ทำให้เป็นบรรทัดฐาน) ในสาขาคอมพิวเตอร์ (คำนาม normalization มีศัพท์บัญญัติเฉพาะสาขาสถิติศาสตร์ว่า การทำให้เป็นปรกติ ซึ่งคนละความหมาย)

    UTF-8 ด้วยมือ: ทำไมอักษรไทยใช้ 3 ไบต์#

    RFC 3629 กำหนดว่า code point ในช่วง U+0800–U+FFFF เข้ารหัสเป็นสามไบต์ตามแบบ 1110xxxx 10xxxxxx 10xxxxxx บล็อกไทยทั้งบล็อกอยู่ในช่วงนี้ อักษรไทยทุกตัวจึงใช้ 3 ไบต์ใน UTF-8 ไม่มากไม่น้อยกว่านั้น

    ทำ ก (U+0E01) ทีละขั้น:

    1. 0x0E01 เป็นเลขฐานสองสิบหกบิตได้ 0000 1110 0000 0001
    2. แบ่งเป็นกลุ่ม 4 | 6 | 6 บิต: 0000 | 111000 | 000001
    3. เติมหัว: 1110 0000 | 10 111000 | 10 000001
    4. อ่านเป็นฐานสิบหก: E0 B8 81

    ขอบของบล็อก: U+0E00 ได้ E0 B8 80 และ U+0E7F ได้ E0 B9 BF ดังนั้นในข้อความไทยที่เข้ารหัส UTF-8 อักษรไทยทุกตัวขึ้นต้นด้วย E0 B8 หรือ E0 B9 และไบต์ที่สามบอกตำแหน่ง ถอดกลับได้ด้วยสูตร ตำแหน่งในบล็อก = (ไบต์ที่สาม − 0x80) + (0x40 ถ้าไบต์ที่สองเป็น B9) เช่น E0 B9 81 → 0x01 + 0x40 = 0x41 → U+0E41 คือ แ

    นับไบต์ด้วยสูตรเดียว: ข้อความที่มีอักษรไทย t code point และ ASCII a ตัวใช้ 3t + a ไบต์ใน UTF-8, 2(t + a) ไบต์ใน UTF-16 (ทุกตัวอยู่ใน BMP) และ t + a ไบต์ใน TIS-620 ผลที่ผู้เขียนรันด้วย Python ตรงกับสูตรทุกแถว:

    ข้อสังเกตจากตาราง: สำหรับข้อความไทยล้วน UTF-8 ใหญ่กว่า UTF-16 1.5 เท่า และใหญ่กว่า TIS-620 3 เท่า แต่สำหรับข้อความอังกฤษล้วน UTF-8 เล็กกว่า UTF-16 ครึ่งหนึ่ง เมื่อไทยกับอังกฤษปนกัน (เช่น ไทย123) สองแบบใหญ่เท่ากันพอดีที่ t = a เพราะ 3t + a = 2(t + a) เมื่อ t = a ข้อสรุปของผู้เขียน (อนุมาน): ขนาดไม่ใช่เหตุผลที่ UTF-8 ครองสาย เหตุผลคือมันเข้ากันได้กับ ASCII ไบต์ต่อไบต์ ซึ่งโปรโตคอลอย่าง DNS, HTTP และอีเมลสร้างอยู่บนนั้น

    คำจริงแตกเป็น code point#

    “สวัสดี” มี 6 code point: ส U+0E2A, ว U+0E27, ◌ั U+0E31, ส U+0E2A, ด U+0E14, ◌ี U+0E35 แต่ผู้อ่านเห็นเป็น 4 หน่วย เพราะสระบนเกาะกับพยัญชนะข้างหน้า Intl.Segmenter ของ Node (ICU 76.1) ตัดเป็น grapheme cluster (หน่วยที่ผู้ใช้รับรู้เป็นอักษรหนึ่งตัว ตามภาคผนวก UAX #29) ได้ ส | วั | ส | ดี ผลรันอื่น ๆ:

    เก 2 2 6
    ไทย 3 3 9

    กรณีขอบ: “น้ำ” ทั้งคำเป็นหน่วยเดียว เพราะวรรณยุกต์เป็น Extend และสระอำ U+0E33 มีคุณสมบัติ SpacingMark ในไฟล์ GraphemeBreakProperty ส่วน “เก” เป็นสองหน่วย เพราะสระเอ (U+0E40) ไม่มีคุณสมบัติพิเศษในไฟล์นั้น (จึงเป็นคลาส Other ไม่ใช่ Prepend) กฎของ UAX #29 จึงให้มีจุดตัดระหว่าง เ กับ ก ผลคือ “ความยาวของข้อความ” มีอย่างน้อยสามคำตอบ (code point, grapheme cluster, ไบต์) โปรแกรมที่ตัดข้อความตามจำนวนไบต์โดยไม่ดูขอบเขตอาจตัดกลางอักษร และโปรแกรมที่ตัดตาม code point อาจแยกวรรณยุกต์ออกจากพยัญชนะ

    สระหน้าเก็บตามลำดับที่ตาเห็น ไม่ใช่ลำดับเสียง#

    อักษรตระกูลอินเดีย (สืบจากอักษรพราหมี) อื่น ๆ ใน Unicode เก็บสระไว้หลังพยัญชนะเสมอ คือเก็บตาม ลำดับเสียง (logical order) แม้สระนั้นจะวาดไว้ทางซ้ายของพยัญชนะ อักษรไทยเป็นข้อยกเว้น (ร่วมกับลาวและไทเวียด) บทที่ 16 หัวข้อ 16.1 ของมาตรฐาน Unicode 18.0 เขียนว่าสระที่อยู่ทางซ้าย (เ แ โ ใ ไ) เก็บตาม ลำดับที่ตาเห็น คือพิมพ์และเก็บไว้ก่อนพยัญชนะ แม้จะออกเสียงทีหลัง ต่างจากขนบของอักษรอินเดียอื่นทั้งหมด และให้เหตุผลว่าจำเป็นเพราะแนวปฏิบัติการเข้ารหัสข้อมูลภาษาไทยตามมาตรฐานผลิตภัณฑ์อุตสาหกรรม (TIS-620) ไฟล์ข้อมูลยืนยันเรื่องเดียวกัน: PropList.txt ให้ U+0E40..U+0E44 (และสระลาว U+0EC0..U+0EC4) มีคุณสมบัติ Logical_Order_Exception และ IndicPositionalCategory.txt ให้ค่า Visual_Order_Left

    ตัวอย่างในตาราง 16-1 ของมาตรฐาน: “เก” เก็บเป็น U+0E40 U+0E01 (สระก่อน) ขณะที่ “กำ” เก็บเป็น U+0E01 U+0E33 ผลตามมาที่บทนี้จะเจออีกหลายครั้ง: ไบต์แรกของ “ไทย” คือสระไอ (E0 B9 84) ไม่ใช่ ท, การเรียงลำดับตามภาษาต้องสลับสระหน้ากับพยัญชนะก่อนเปรียบเทียบ และป้าย IDN ของ .ไทย เริ่มจาก U+0E44

    เครื่องหมายบนล่าง วรรณยุกต์ และการทำให้เป็นบรรทัดฐาน#

    ผู้พิมพ์สองคนอาจกดแป้นต่างลำดับแล้วได้ภาพเดียวกัน “ปู่” พิมพ์ได้ทั้ง ป + ◌ู + ◌่ และ ป + ◌่ + ◌ู การทำให้เป็นบรรทัดฐาน NFC จัดเรียงเครื่องหมายตาม ccc จากน้อยไปมาก สระอู (103) จึงมาก่อนไม้เอก (107) ผู้เขียนรัน unicodedata.normalize('NFC', …) แล้วได้ U+0E1B U+0E39 U+0E48 ทั้งสองแบบ การค้นหาหลังทำ NFC จึงเจอทั้งสองแบบ

    กรณีขอบที่ NFC ช่วยไม่ได้: “น้ำ” ที่ถูกต้องคือ น + ◌้ + ำ แต่ถ้าพิมพ์สลับเป็น น + ำ + ◌้ จะได้ code point ต่างกัน เพราะสระอำมี ccc 0 NFC จึงไม่สลับให้ ผลรันคือสองแบบไม่เท่ากันทั้งก่อนและหลัง NFC และตัวเปรียบเทียบ Intl.Collator ภาษาไทยก็ตอบว่าต่างกัน (compare = 1) ข้อความที่พิมพ์ผิดลำดับจึงค้นไม่เจอ ทั้งที่ชุดแบบอักษรบางชุดอาจวาดออกมาคล้ายกัน

    กรณีขอบอีกข้อ: สระอำมีการแยกส่วนแบบเข้ากันได้ (compatibility decomposition) <compat> 0E4D 0E32 คือ นิคหิต + สระอา NFKC จึงเปลี่ยน ำ เป็นสอง code point ผู้เขียนรันแล้วได้ U+0E4D U+0E32 ข้อนี้คือต้นเหตุของเรื่อง IDN ในหัวข้อหลัง

    เรียงลำดับตามพจนานุกรม ไม่ใช่ตามเลข code point#

    ถ้าเรียงตามเลข code point คำว่า เก แก โก ไก จะไปอยู่หลัง ขา เพราะ U+0E40 มากกว่า U+0E02 ผู้เขียนเรียงรายการเดียวกันด้วย Intl.Collator ภาษาไทยได้ ก, กา, กี, เก, แก, โก, ไก, ข, ขา ซึ่งเป็นลำดับแบบพจนานุกรม (เก อยู่ในหมวด ก) ภาคผนวก UTS #10 (Unicode Collation Algorithm) รุ่น 18 หัวข้อ 6.1.1 อธิบายว่าสระที่มีคุณสมบัติ Logical_Order_Exception ถูกสลับกับอักขระถัดไปในเชิงแนวคิด ตั้งแต่ UCA 4.1 ทำผ่าน contraction ในตาราง DUCET ก่อนหน้านั้นต้องประมวลผลสายอักขระล่วงหน้า กล่าวคือ การเก็บตามลำดับที่ตาเห็นทำให้การเก็บง่าย แต่ย้ายภาระไปที่การเรียงลำดับ

    ไม่มีช่องว่างระหว่างคำ: การตัดบรรทัดต้องใช้พจนานุกรม#

    บทที่ 16 ของมาตรฐานบอกว่าคำภาษาไทยไม่คั่นด้วยช่องว่าง และถ้าต้องการบอกจุดตัดบรรทัดให้ชัดควรใช้ U+200B ZERO WIDTH SPACE ภาคผนวก UAX #14 (รุ่นแก้ไขที่ 57) จัดอักษรไทยไว้ในคลาส SA (Complex Context Dependent, South East Asian) ซึ่งต้องค้นพจนานุกรมหาจุดตัด ถ้าไม่มีพจนานุกรมให้ถือเป็น AL คือไม่ตัดกลางคำเลย ในไฟล์ LineBreak.txt ตัวอักษรและเครื่องหมายไทยเป็น SA แต่มีข้อยกเว้น: ฿ เป็น PR (คำนำหน้าตัวเลข), ๏ เป็น AL, เลขไทยเป็น NU และ ๚ ๛ เป็น BA

    ผลรันตัวตัดคำของ ICU (Intl.Segmenter แบบ word):

    • “ภาษาไทยไม่มีการเว้นวรรคระหว่างคำ” → ภาษา | ไทย | ไม่มี | การ | เว้น | วรรค | ระหว่าง | คำ
    • “คนขับรถ” → คน | ขับ | รถ
    • “ตากลม” → ตากลม (หน่วยเดียว) ตัวอย่างนี้ผู้เขียนยกมาเองเพื่อแสดงความกำกวม: อ่านได้ทั้ง ตา | กลม และ ตาก | ลม ตัวตัดคำต้องเลือก ซึ่งพจนานุกรมอย่างเดียวตัดสินไม่ได้
    • สายอักขระว่าง → ไม่มีหน่วยเลย

    ผลตามมาเชิงวิศวกรรม (อนุมาน): เบราว์เซอร์ โปรแกรมพิมพ์ และระบบค้นหาที่ต้องตัดบรรทัดหรือทำดัชนีภาษาไทยต้องพกพจนานุกรมไปด้วย และผลอาจต่างกันเมื่อพจนานุกรมต่างรุ่น

    โครงสร้างของ TIS-620: ตำแหน่ง 00–7F คงความหมายตาม ISO 646 (7 บิต) และอักขระไทยใช้บิตที่ 8 เป็น 1 (หัวข้อ 6.1 ของมาตรฐาน) ส่วนตำแหน่ง 80–A0, DB–DE และ FC–FF สงวนไว้ (หัวข้อ 6.2) ก อยู่ที่ตำแหน่ง 10/1 = A1 หมายเลขอักขระ TC01

    ชื่อโดเมนภาษาไทย: IDN, Punycode และ .ไทย#

    DNS รับเฉพาะป้าย ASCII ชื่อโดเมนสากล (Internationalized Domain Name, IDN) จึงแปลงป้ายที่มีอักขระนอก ASCII ด้วยอัลกอริทึม Punycode (RFC 3492) แล้วเติมหน้า xn-- (RFC 5890 เรียกป้ายแบบนี้ว่า A-label) ผู้เขียนทดสอบกับ Google Public DNS ผ่าน DNS-over-HTTPS: ถามด้วย xn--o3cw4h ได้เครื่องบริการชื่อตรงกับที่ IANA บันทึก (พร้อมธง AD = true คือผ่านการตรวจ DNSSEC) แต่ส่งชื่อ “ไทย” เป็น UTF-8 ตรง ๆ ไปที่ API แบบ JSON ได้ HTTP 400

    Punycode ของ “ไทย” ด้วยมือ. พารามิเตอร์จาก RFC 3492: base = 36, tmin = 1, tmax = 26, skew = 38, damp = 700, initial_bias = 72, initial_n = 128 หลักทั้ง 36 ตัวคือ a–z (0–25) ตามด้วย 0–9 (26–35) อัลกอริทึมแทรกอักขระทีละตัวจาก code point น้อยไปมาก และเข้ารหัส “ระยะ” (delta) ที่ต้องนับไปถึงตำแหน่งแทรกเป็นเลขฐานผันแปร:

    ขั้น แทรก delta bias หลักที่ได้
    1 ท U+0E17 (3607) ลงในสายที่ยังว่าง (ตำแหน่ง 0) (3607 − 128) × 1 = 3479 72 o (14), 3 (29), c (2)
    2 ย U+0E22 (3618) ต่อหลัง ท (ตำแหน่ง 1 ใน “ทย”) 22 6 w (22)
    3 ไ U+0E44 (3652) ที่ตำแหน่ง 0 100 10 4 (30), h (7)

    ขั้น 1 ละเอียด: ที่ bias 72 เกณฑ์ t ของสองหลักแรกเป็น tmin = 1 หลักแรก = 1 + (3478 mod 35) = 14 → o และเหลือ 3478 div 35 = 99; หลักที่สอง = 1 + (98 mod 35) = 29 → 3 และเหลือ 98 div 35 = 2; หลักที่สาม t = tmax = 26 และ 2 < 26 จึงจบที่ 2 → c จากนั้นปรับ bias: 3479 div 700 = 4, บวก 4 div 1 ได้ 8, bias ใหม่ = (36 × 8) div (8 + 38) = 288 div 46 = 6 ผลรวมคือ o3cw4h และป้ายเต็มคือ xn--o3cw4h ตรงกับทั้ง codec idna ในตัว Python และรายงานของ IANA

    .ไทย ในโซนราก. รายงานของ IANA ลงวันที่ 16 กรกฎาคม 2010 เรื่องการมอบหมาย .ไทย ระบุว่า “ไทย” แทนด้วย xn--o3cw4h คือ code point U+0E44 U+0E17 U+0E22 (สังเกตว่าสระไอมาก่อน ตามลำดับที่ตาเห็น) รายงานเล่าว่า THNIC (Thai Network Information Center) ก่อตั้งปี 1988 เป็นความร่วมมือระหว่าง AIT กับจุฬาลงกรณ์มหาวิทยาลัย และเป็นมูลนิธิในปี 2007; มีเวทีสาธารณะเดือนมกราคม 2009, ยื่นขอผ่านกระบวนการ IDN Fast Track เดือนธันวาคม 2009 โดยมี สวทช. และภาควิชาภาษาศาสตร์ จุฬาฯ สนับสนุน, คณะกรรมการ DNS Stability Panel พิจารณาเมื่อ 22 มีนาคม 2010 และยื่นขอมอบหมายเมื่อ 19 เมษายน 2010 หน้าฐานข้อมูลโซนรากของ IANA บันทึกวันที่จดทะเบียน .ไทย เป็น 2010-08-19 ผู้ดูแลคือ Thai Network Information Center Foundation ส่วน .th จดทะเบียนตั้งแต่ 1988-09-07

    สองแถวสุดท้ายคือการปลอมหน้าตา (homograph): “แก” กับ “เเก” อาจดูเหมือนกันบนจอ แต่เป็นคนละชื่อ ตาราง confusables ของ UTS #39 (ฉบับ 2026-08-06) บันทึกว่า แ สับสนได้กับ เเ และ ด กับ ต สับสนได้กับ ค

    ข้อค้นพบ: IDNA2008 ห้ามสระอำ. ตาราง IDNA ของ IANA (รุ่น 12.0.0) ให้ U+0E33 สระอำ เป็น DISALLOWED เพราะเข้ากฎ “Unstable” ของ RFC 5892 หัวข้อ 2.2: toNFKC(toCaseFold(toNFKC(cp))) ≠ cp ซึ่งเป็นจริงสำหรับ ำ เพราะ NFKC แยกมันเป็น ํ + า (ดูหัวข้อการทำให้เป็นบรรทัดฐาน) ผลรัน:

    • แพ็กเกจ idna แบบ IDNA2008 ปฏิเสธ “น้ำ” ด้วยข้อความ Codepoint U+0E33 … not allowed
    • IDNA2003 และโหมด UTS #46 แปลงเป็น xn--q3c4c8cq แต่ถอดกลับได้ U+0E19 U+0E49 U+0E4D U+0E32 คือ น้ + นิคหิต + า ไม่ใช่ สระอำ เดิม
    • ตารางเดียวกันให้ ฿, ๏, ๚ และ ๛ เป็น DISALLOWED ด้วย ส่วน ๆ, ฯ และเลขไทยใช้ได้ (PVALID)
    • เปรียบเทียบ: ตารางอักขระของ .th ที่ THNIC ยื่นไว้กับ IANA (th_th-th_1.0 มีผล 21 มิถุนายน 2004 ในยุค IDNA2003 มีอักขระไทย 82 code point นอกเหนือจากอักขระ ASCII) รวม U+0E33 ไว้ แต่ไม่รวม ฿, ◌๎ (U+0E4E), ๏, ๚ และ ๛

    ความหมายของข้อนี้ (อนุมาน): ชื่อที่มีคำว่า “น้ำ” หรือ “ทำ” สะกดตามปกติใช้เป็นป้ายตามกฎ IDNA2008 ไม่ได้ ระบบที่ใช้ UTS #46 จะเปลี่ยนสระอำให้เงียบ ๆ ผลลัพธ์ที่ได้เป็นคนละลำดับ code point กับที่ผู้ใช้พิมพ์

    กรณีขอบอื่นที่รันแล้ว:

    • NFC: “ปู่” ที่พิมพ์ ป + ◌่ + ◌ู ถูก IDNA2008 ปฏิเสธ (Label must be in Normalization Form C) ส่วนโหมด UTS #46 ทำ NFC ให้ก่อน ได้ xn--s3c4d0b เท่ากับแบบที่พิมพ์ถูกลำดับ
    • ZWSP: ก + U+200B + ข ใน IDNA2003 ถูกลบ ZWSP ทิ้งเงียบ ๆ ได้ xn--12cc (เท่ากับ “กข”) ส่วน IDNA2008 ปฏิเสธ
    • ป้ายว่าง: ชื่อว่างและ .ไทย (ป้ายหน้าจุดว่าง) ถูกปฏิเสธ ส่วนจุดท้ายชื่อใช้ได้
    • ความยาว: ป้ายยาวได้ 63 ออกเต็ตหลังแปลงแล้ว ไม่ใช่ 63 อักขระไทย ก 57 ตัวติดกันแปลงได้ป้าย 63 ออกเต็ตพอดี ก 58 ตัวถูกปฏิเสธ (Label too long) ส่วนพยัญชนะต่างกัน 41 ตัวก็ยาวถึง 63 ออกเต็ตแล้ว เพราะ delta ของแต่ละตัวยาวกว่า ความยาวของป้ายไทยจึงขึ้นกับว่าใช้อักษรซ้ำหรือไม่ ไม่ใช่นับจำนวนตัวอย่างเดียว
    • ทั้งชื่อ: แพ็กเกจ idna จำกัดชื่อเต็มไว้ 253 อักขระ ป้าย 63 ออกเต็ตสี่ป้ายกับจุดจึงยาวเกิน ผู้เขียนเข้าใจว่า 253 มาจาก 255 ออกเต็ตของ RFC 1035 ลบออกเต็ตความยาวของป้ายแรกและออกเต็ตศูนย์ของราก (อนุมาน)

    แบบฝึกหัดดินสอ (เฉลยท้ายข้อ)#

    1. “ภาษาไทย 2567” ใช้กี่ไบต์ใน UTF-8? เฉลย: อักษรไทย 7 × 3 = 21 บวกช่องว่าง 1 และเลขอารบิก 4 = 26 ไบต์ (ผู้เขียนรันยืนยันแล้ว)
    2. เข้ารหัส ข (U+0E02) เป็น UTF-8 เฉลย: 0E02 = 0000 111000 000010 → E0 B8 82
    3. ไบต์ TIS-620 0xE4 คือ code point อะไร? เฉลย: 0xE4 + 0xD60 = 0xE44 → ไ
    4. ไบต์ UTF-8 E0 B9 81 คืออักษรอะไร? เฉลย: ไบต์ที่สองเป็น B9 จึงบวก 0x40: 0x01 + 0x40 = 0x41 → U+0E41 แ
    5. ทำไมการเรียงตามเลข code point จึงวาง “เก” ไว้หลัง “ขา”? เฉลย: เพราะ เ (U+0E40) ถูกเก็บก่อนพยัญชนะและมีเลขมากกว่า ข (U+0E02); การเรียงตามภาษาต้องสลับสระหน้ากับพยัญชนะก่อน

    ญาติของชนิดเดียวกัน#

    เพื่อนร่วมชนิดอีกไม่กี่รายได้หนึ่งประโยค — ชนิด ความหมายแชร์เดียวกัน ไม่ใช่ทัวร์องค์กรมาตรฐาน:

    • W3C และ WHATWG — Tim Berners-Lee ก่อตั้ง World Wide Web Consortium (1994) เพื่อดูแลมาตรฐานแพลตฟอร์มเว็บ; WHATWG ภายหลังรับสเปก HTML/DOM แบบ living เมื่อผู้ผลิตเบราว์เซอร์ต้องการเส้นทางวนรอบเร็วขึ้น ชนิด เดียวกัน: ใครกำหนดได้ว่าเอกสารและ API หมายความว่าอะไรในเบราว์เซอร์
    • IEEE — IEEE 802 คือเหตุผลที่ Ethernet (บทที่ 40) และ Wi-Fi ไม่ใช่ภาษาเกาะเฉพาะของผู้ผลิตที่ชั้นลิงก์
    • ISO และเพื่อน — มาตรฐานสากลแบบทางการนั่งข้างโลก RFC เมื่อการจัดซื้อ ความปลอดภัย หรือหน่วยงานชาติเรียกร้อง; อินเทอร์เน็ตส่วนใหญ่เผยแพร่ใช้งานบน RFC ก่อน แล้วค่อย harmonize ทีหลัง

    เหตุใดบทนี้จึงอยู่ในเส้นทาง#

    บทที่ 39–41 คือการเดิมพันทางวิศวกรรม: แพ็กเก็ต ชั้น สื่อที่ไม่เชื่อถือได้ บทนี้คือการเดิมพันด้านพลเมืองที่อยู่ใต้พวกนั้น: ความหมายแชร์คือโครงสร้างพื้นฐาน หากไม่มีใคร (และกระบวนการ) ตัดสินหมายเลข ชื่อ และการเข้ารหัส เครือข่ายใหม่ทุกอันคือภาษาส่วนตัว ประตูด้านบนคือแหล่งปฐมภูมิ — RFC, ทะเบียน, หน้า consortium

    เส้นทางข้างทางเลือกจากที่นี่: คน หา สิ่งต่าง ๆ และ คุย บนสายแชร์นั้นอย่างไร (บทที่ 43) หรือรหัสลับยามสงครามบังคับเครื่องที่เก็บความลับได้อย่างไร (บทที่ 66) แกนหลักยังเป็นแพ็กเก็ต → ระบบ → ซิลิคอน → attention; นี่คือจังหวะขยายเลนส์ที่คุณจะเข้าหรือข้ามก็ได้
