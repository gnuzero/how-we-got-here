    อินเตอร์คอนเนกต์ในระดับศูนย์ข้อมูล

    มกราคม 1, 2026

    บทที่ 56 ครอบคลุมการขยายหลาย GPU ภายในและข้ามเซิร์ฟเวอร์จำนวนน้อย — NVLink, NVSwitch, GPUDirect RDMA การฝึกขนาดใหญ่เป็นอีกอันดับ: GPU นับพันถึงหลายหมื่นข้ามเซิร์ฟเวอร์นับร้อยถึงนับพัน วิธีเดินสายสำคัญเท่าสเปกของ GPU ตัวใดตัวหนึ่ง

    ตอนตรวจสำรวจแหล่งภาษาไทยสำหรับบทนี้ เราไม่พบคำอธิบายภาษาไทยของ all-reduce เลยแม้แต่หน้าเดียว บทนี้จึงไล่ตั้งแต่ต้นว่า all-reduce คืออะไร ทำไมอัลกอริทึมแบบวงแหวนจึงส่งข้อมูลน้อยที่สุดเท่าที่จะเป็นไปได้ และทอพอโลยีของเครือข่ายเข้ามาเกี่ยวตรงไหน พร้อมตัวเลขที่คำนวณตามได้

    ศัพท์พื้นฐาน#

    • การฝึกแบบขนานข้อมูล (data-parallel training) — ทุก GPU มีสำเนาโมเดลครบชุด แต่ได้ข้อมูลฝึกคนละส่วนของแบตช์ แต่ละตัวคำนวณ เกรเดียนต์ (gradient, ศัพท์บัญญัติ; คือทิศทางและขนาดที่ควรปรับน้ำหนักแต่ละตัว ดูบทที่ 46) จากข้อมูลส่วนของตัวเอง
    • ก่อนปรับน้ำหนัก ทุก GPU ต้องได้ ค่าเฉลี่ย ของเกรเดียนต์จากทุกตัว ไม่อย่างนั้นสำเนาโมเดลจะค่อย ๆ ต่างกันไป
    • การดำเนินการร่วม (collective operation) คือการสื่อสารที่ทุกตัวในกลุ่มเข้าร่วมพร้อมกัน ตัวที่ต้องรู้จักมีสี่แบบ
      • reduce — รวมค่าจากทุกตัว (เช่น บวก) แล้วเก็บผลไว้ที่ตัวเดียว
      • broadcast — ส่งค่าจากตัวเดียวไปให้ทุกตัว
      • reduce-scatter — รวมค่าจากทุกตัว แต่ผลลัพธ์ถูกหั่นเป็นชิ้น แต่ละตัวได้เก็บชิ้นเดียว
      • all-gather — แต่ละตัวมีชิ้นของตัวเอง แล้วทุกตัวแลกกันจนทุกตัวมีครบทุกชิ้น
    • all-reduce = รวมค่าจากทุกตัว แล้ว ทุกตัว ได้ผลรวมครบทั้งก้อน เทียบเท่ากับ reduce ตามด้วย broadcast หรือ reduce-scatter ตามด้วย all-gather

    การเดินสายตรง ๆ ไม่สเกล#

    การต่อทุกเซิร์ฟเวอร์กับทุกเซิร์ฟเวอร์อื่นโตแบบกำลังสอง — เหลวไหลนานก่อนถึงโหนดนับพัน คลัสเตอร์จริงใช้สวิตช์แบบลำดับชั้น; โครงสร้างที่เลือกตัดสินทั้งแบนด์วิดท์ที่ทำได้ และว่าแบนด์วิดท์นั้นกระจาย สม่ำเสมอ เพียงใดใต้ทราฟฟิกฝึกหนัก

    ตัวเลขช่วยให้เห็นภาพ: การต่อตรงทุกคู่ระหว่าง N เครื่องต้องใช้สาย N(N − 1)/2 เส้น 1,000 เครื่องคือ 499,500 เส้น และแต่ละเครื่องต้องมีพอร์ต 999 พอร์ต ไม่มีเครื่องไหนทำได้

    วิธีแรกที่นึกออก: ส่งไปรวมที่เดียว#

    สมมติมี GPU 8 ตัว แต่ละตัวมีเกรเดียนต์ขนาด S = 2 GB (เช่น โมเดล 1 พันล้านพารามิเตอร์ เก็บเกรเดียนต์เป็น FP16 ตัวละ 2 ไบต์) และลิงก์ของแต่ละ GPU รับส่งได้ B = 100 GB/s ต่อทิศทาง (ตัวเลขสมมติเพื่อการคำนวณ)

    วิธีตรงไปตรงมาคือให้ GPU ตัวที่ 0 เป็นศูนย์กลาง อีก 7 ตัวส่งเกรเดียนต์มาให้ ตัวที่ 0 บวกรวมแล้วส่งผลกลับ ปัญหาคือลิงก์ของตัวที่ 0 ต้องรับ 7 × 2 GB = 14 GB ใช้เวลา 14 ÷ 100 = 140 ms แล้วต้องส่งกลับอีก 14 GB อีก 140 ms ระหว่างนั้นลิงก์ของอีก 7 ตัวแทบว่าง ยิ่งเพิ่ม GPU ตัวที่ 0 ก็ยิ่งเป็นคอขวด เวลาโตตาม N ตรง ๆ

    Ring all-reduce ทีละขั้น#

    ไอเดียของอัลกอริทึมแบบ วงแหวน (ring) คือกระจายงานให้ทุกลิงก์ทำงานพร้อมกันตลอดเวลา จัด GPU เป็นวง 0 → 1 → 2 → 3 → 0 แต่ละตัวส่งให้ตัวถัดไปอย่างเดียวและรับจากตัวก่อนหน้าอย่างเดียว แล้วหั่นเวกเตอร์ของแต่ละตัวเป็น N ชิ้นเท่า ๆ กัน

    ตัวอย่าง: 4 GPU เวกเตอร์ 4 ชิ้น#

    ให้แต่ละ GPU มีเวกเตอร์ 4 ค่า (ชิ้น A, B, C, D) ที่เลือกให้ตามรอยง่าย

    A B C D
    GPU 0 1 2 3 4
    GPU 1 10 20 30 40
    GPU 2 100 200 300 400
    GPU 3 1000 2000 3000 4000

    ผลที่ต้องการคือทุก GPU มี [1111, 2222, 3333, 4444]

    ช่วงที่ 1: reduce-scatter (3 ขั้น = N − 1) ทุกขั้น ทุก GPU ส่ง หนึ่งชิ้น ให้ตัวถัดไป ตัวที่รับเอาไปบวกเข้ากับชิ้นเดียวกันของตัวเอง

    • ขั้นที่ 1: GPU 0 ส่ง A=1 ให้ GPU 1 (A ของ GPU 1 กลายเป็น 11), GPU 1 ส่ง B=20 ให้ GPU 2 (B กลายเป็น 220), GPU 2 ส่ง C=300 ให้ GPU 3 (C กลายเป็น 3300), GPU 3 ส่ง D=4000 ให้ GPU 0 (D กลายเป็น 4004)
    • ขั้นที่ 2: แต่ละตัวส่งชิ้นที่เพิ่งได้รับและบวกแล้วต่อไป: GPU 0 ส่ง D=4004 ให้ GPU 1 (ได้ 4044), GPU 1 ส่ง A=11 ให้ GPU 2 (ได้ 111), GPU 2 ส่ง B=220 ให้ GPU 3 (ได้ 2220), GPU 3 ส่ง C=3300 ให้ GPU 0 (ได้ 3303)
    • ขั้นที่ 3: GPU 0 ส่ง C=3303 ให้ GPU 1 (ได้ 3333), GPU 1 ส่ง D=4044 ให้ GPU 2 (ได้ 4444), GPU 2 ส่ง A=111 ให้ GPU 3 (ได้ 1111), GPU 3 ส่ง B=2220 ให้ GPU 0 (ได้ 2222)

    จบช่วงแรก แต่ละ GPU ถือผลรวมที่ สมบูรณ์ อยู่หนึ่งชิ้น: GPU 0 มี B = 2222, GPU 1 มี C = 3333, GPU 2 มี D = 4444, GPU 3 มี A = 1111

    ช่วงที่ 2: all-gather (อีก 3 ขั้น) ส่งชิ้นที่สมบูรณ์ต่อไปรอบวงแบบเดิม แต่คราวนี้ผู้รับ เขียนทับ แทนการบวก หลังสามขั้น ทุกชิ้นที่สมบูรณ์เดินทางไปถึงทุก GPU ผลสุดท้ายคือทุกตัวมี [1111, 2222, 3333, 4444] ตรงตามต้องการ (ลำดับทั้งหมดนี้ตรวจแล้วด้วยการจำลองในโปรแกรม)

    ทำไมวงแหวนจึงดี: นับข้อมูลที่ส่ง#

    แต่ละขั้น แต่ละ GPU ส่งชิ้นเดียว ขนาด S/N มีทั้งหมด 2(N − 1) ขั้น แต่ละ GPU จึงส่งรวม

    2(N − 1) × S/N = 2 × (N − 1)/N × S

    • N = 4: ส่งคนละ 1.5 S
    • N = 8: ส่งคนละ 1.75 S
    • N ใหญ่มาก: เข้าใกล้ 2 S แต่ไม่เกิน

    ข้อสำคัญคือปริมาณที่แต่ละตัวส่ง แทบไม่โตตามจำนวน GPU ต่างจากวิธีรวมที่เดียวที่ศูนย์กลางต้องรับ (N − 1)S และทุกลิงก์ในวงทำงานพร้อมกันทุกขั้น Patarasuk และ Yuan (2009) พิสูจน์ว่ามีอย่างน้อยหนึ่ง process ที่ต้องสื่อสารข้อมูลอย่างน้อย 2 × (N − 1)/N × ขนาดข้อมูล วงแหวนจึงถึงขอบเขตล่างนั้นพอดี คือ เหมาะสมที่สุดด้านแบนด์วิดท์ (bandwidth optimal)

    กลับไปที่ตัวอย่าง 8 GPU ขนาด 2 GB ลิงก์ 100 GB/s: เวลาส่วนแบนด์วิดท์ = 1.75 × 2 GB ÷ 100 GB/s = 35 ms เทียบกับ 280 ms ของวิธีรวมที่เดียว เร็วขึ้น 8 เท่า

    ราคาที่วงแหวนต้องจ่าย: จำนวนขั้น#

    แต่ละขั้นมีค่าใช้จ่ายคงที่ α (เวลาเริ่มส่ง เดินทางผ่านสวิตช์ ซิงโครไนซ์ ไม่ขึ้นกับขนาดข้อมูล) แบบจำลองเวลาที่นิยมจึงเป็น

    T ≈ 2(N − 1) × α + 2 × (N − 1)/N × S/B

    สมมติ α = 5 µs

    • N = 8: ส่วน α = 14 × 5 µs = 0.07 ms เล็กมากเทียบกับ 35 ms
    • N = 1,024: ส่วนแบนด์วิดท์ ≈ 39.96 ms แต่ส่วน α = 2,046 × 5 µs ≈ 10.2 ms กลายเป็นหนึ่งในห้าของเวลาทั้งหมด

    เมื่อ GPU มากหรือข้อความเล็ก จำนวนขั้นที่เป็นเชิงเส้นของวงแหวนจะเริ่มเจ็บ อัลกอริทึมแบบ ต้นไม้ หรือแบบผีเสื้อ (butterfly) ใช้จำนวนรอบเป็นลอการิทึม เช่น 1,024 ตัวใช้ราว 2 × log₂ 1,024 = 20 รอบ ส่วน α เหลือแค่ 0.1 ms ไลบรารีจริงจึงเลือกอัลกอริทึมตามขนาดข้อความและทอพอโลยี และมักทำเป็น ลำดับชั้น (hierarchical): รวมกันภายในเซิร์ฟเวอร์ผ่าน NVLink ที่เร็วมากก่อน แล้วค่อยข้ามเครือข่ายระหว่างเซิร์ฟเวอร์ด้วยข้อมูลที่เหลือเพียงส่วนเดียว

    Fat-Tree จูนเพื่อการฝึก#

    Fat-tree จัดสวิตช์เป็นชั้น — leaf ที่เซิร์ฟเวอร์ spine ต่อ leaf — มุ่งแบนด์วิดท์แบ่งครึ่งสูง (ในอุดมคติไม่ oversubscribe); คลัสเตอร์ AI จริงอาจยัง oversubscribe หรือใช้ตัวแปรจูนราง นี่คือไอเดียเครือข่ายศูนย์ข้อมูลของบทที่ 42 ที่ระบอบ GPU นับพัน

    นิยามและตัวเลข#

    • แบนด์วิดท์แบ่งครึ่ง (bisection bandwidth) — ตัดเครือข่ายเป็นสองซีกที่มีเครื่องเท่ากัน แบนด์วิดท์รวมที่วิ่งข้ามรอยตัดได้ในกรณีแย่ที่สุดคือแบนด์วิดท์แบ่งครึ่ง ถ้ามันเท่ากับครึ่งหนึ่งของแบนด์วิดท์รวมของทุกเครื่อง แปลว่าครึ่งหนึ่งของเครื่องคุยกับอีกครึ่งได้เต็มความเร็วพร้อมกัน เรียกว่า full bisection
    • oversubscription — สวิตช์ leaf ที่มีพอร์ตลงไปหาเซิร์ฟเวอร์ 48 พอร์ต แต่มีพอร์ตขึ้นไปหา spine แค่ 16 พอร์ต (ความเร็วเท่ากัน) คือ oversubscribe 3:1 ถ้าทุกเครื่องใต้ leaf นี้ต้องคุยกับเครื่องนอก leaf พร้อมกัน แต่ละเครื่องได้แบนด์วิดท์แค่หนึ่งในสาม ประหยัดสวิตช์และสายได้มาก แต่ all-reduce ที่ต้องข้าม leaf จะช้าลงตามนั้น
    • Al-Fares และคณะ (SIGCOMM 2008) แสดงว่า fat-tree แบบ k-ary ที่สร้างจากสวิตช์ธรรมดาขนาด k พอร์ตเท่ากันทั้งหมด รองรับเครื่องได้ k³/4 เครื่องด้วย full bisection สวิตช์ 48 พอร์ตได้ 48³/4 = 27,648 เครื่อง (ตัวเลขที่เปเปอร์ยกมาเอง) สวิตช์ 64 พอร์ตได้ 64³/4 = 65,536 เครื่อง

    การออกแบบจูนรางจูนเพิ่มรอบแบบแผนการสื่อสารที่งานฝึกใหญ่สร้างจริง — ไม่ใช่ทราฟฟิกศูนย์ข้อมูลทั่วไป ทราฟฟิกฝึกต่าง; ทอโพโลยีที่สร้างเพื่อมันเอาชนะแบบทั่วไปได้

    รางคืออะไร#

    เซิร์ฟเวอร์ GPU ทั่วไปมี GPU 8 ตัว และมักมีการ์ดเครือข่ายแยกต่อ GPU ราง (rail) คือกลุ่มของ GPU ที่มี ลำดับในเครื่องเดียวกัน จากทุกเซิร์ฟเวอร์ เช่น GPU หมายเลข 3 ของทุกเครื่องคือราง 3 เครือข่ายแบบ จูนราง (rail-optimized) ต่อ GPU ในรางเดียวกันเข้ากับสวิตช์ชุดเดียวกัน แล้วใช้ชั้น spine เชื่อมระหว่างรางสำหรับทราฟฟิกที่เหลือ

    ทำไมถึงเข้ากับ all-reduce แบบลำดับชั้น: ขั้นแรกรวมภายในเครื่องผ่าน NVLink แล้วแบ่งให้ GPU แต่ละตัวในเครื่องรับผิดชอบชิ้นหนึ่งในแปด ขั้นที่สองคือ GPU หมายเลขเดียวกันของทุกเครื่องทำ all-reduce ของชิ้นนั้นร่วมกัน ซึ่งก็คือคุยกันภายในรางเดียว ทราฟฟิกจึงผ่านสวิตช์รางตัวเดียวโดยไม่ต้องขึ้นไปถึง spine Wang และคณะ (arXiv:2307.12169) วิเคราะห์ทราฟฟิกการฝึกโมเดลภาษาขนาดใหญ่แล้วพบว่า ทราฟฟิกที่ออกนอกเครื่องแทบทั้งหมดอยู่ภายในราง จนเสนอให้ตัดชั้น spine ทิ้งไปเลย (ข้อเสนอนี้เป็นงานวิจัย ไม่ใช่แนวปฏิบัติมาตรฐานของอุตสาหกรรม)

    All-Reduce คือแบบแผนที่ผูกมัด#

    การฝึก data-parallel (บทที่ 46) ต้องซิงค์ gradient ข้ามทุก GPU ที่ร่วมในทุกขั้น — gradient ท้องถิ่นจากชิ้นแบตช์ แล้วรวม (โดยปกติเฉลี่ย) ก่อนขั้นถัดไป All-reduce นั้นรันตลอดรอบฝึกเต็ม ประสิทธิภาพขึ้นกับแบนด์วิดท์ดิบ และ ทอโพโลยี: อัลกอริทึมแบบวงแหวนหรือต้นไม้รู้สึกการเดินสายกายภาพ ไม่ใช่เพียงยอดรวมทางทฤษฎี

    วงแหวนแสดงให้เห็นตรง ๆ ว่าทำไม: ทุกขั้นของวงแหวนต้องรอให้ทุกลิงก์ในวงส่งเสร็จก่อน ความเร็วของทั้งวงจึงเท่ากับ ลิงก์ที่ช้าที่สุด ในวง ถ้าวงแหวน 1,024 GPU มีหนึ่งช่วงที่ต้องวิ่งผ่าน spine ที่ oversubscribe 3:1 ทั้งวงจะวิ่งด้วยความเร็วหนึ่งในสามตลอดทุกขั้น ไลบรารีสื่อสารจึงพยายามจัดลำดับ GPU ในวงให้ตรงกับการเดินสายจริง

    ซ่อนการสื่อสารไว้หลังการคำนวณ#

    ขั้นย้อนกลับ (backward pass) คำนวณเกรเดียนต์จากชั้นท้ายของโครงข่ายไล่ขึ้นมาชั้นแรก เกรเดียนต์ของชั้นท้ายจึงพร้อมก่อน เฟรมเวิร์กจึงรวบเกรเดียนต์เป็นก้อน ๆ (bucket) แล้วเริ่ม all-reduce ของก้อนที่พร้อมทันที ระหว่างที่ GPU ยังคำนวณเกรเดียนต์ของชั้นที่เหลือ ถ้าการคำนวณที่เหลือนานพอ เวลา all-reduce ส่วนใหญ่ก็ถูกซ่อน ถ้าเครือข่ายช้าเกินไป GPU ก็ต้องนั่งรอหลังคำนวณเสร็จ ซึ่งคือจุดที่ “ทอพอโลยีเอาชนะสเปกชีต” ในหัวข้อถัดไป

    ทอโพโลยีเอาชนะสเปกชีตได้#

    GPU ยอดเยี่ยมบน fabric ออกแบบไม่ดีหรือ oversubscribe แพ้ GPU เรียบกว่าบนเครือข่ายจูนรางอย่างระมัดระวังได้ — เพราะ all-reduce กลายเป็นคอขวด ไม่ใช่ FLOPS สูงสุดของชิปใดตัวเดียว ธีมของชุดนี้อีกครั้ง: สเปกชิ้นส่วน (จำนวนทรานซิสเตอร์ ความเร็วคล็อก FLOPS สูงสุด) บอกเพียงส่วนของเรื่อง วิธีที่ชิ้นส่วนถูกเชื่อม — จากบัสในชิป (เฟส 5) ถึงทอโพโลยีของคลัสเตอร์ฝึก — มักตัดสินประสิทธิภาพที่ได้จริง

    ลองคิดด้วยตัวเลข (ตัวเลขสมมติ): ถ้าขั้นฝึกหนึ่งขั้นใช้เวลาคำนวณ 100 ms และ all-reduce ซ่อนหลังการคำนวณไม่ได้เลย 40 ms ขั้นหนึ่งจะกินเวลา 140 ms เปลี่ยนเป็น GPU ที่คำนวณเร็วขึ้นสองเท่าบนเครือข่ายเดิม ได้ 50 + 40 = 90 ms เร็วขึ้นแค่ 1.56 เท่า แต่ถ้าปรับเครือข่ายจน all-reduce เหลือ 10 ms โดยใช้ GPU รุ่นเดิม ได้ 110 ms เร็วขึ้น 1.27 เท่าด้วยเงินที่มักน้อยกว่ามาก และยิ่ง GPU เร็วขึ้น สัดส่วนของเวลาสื่อสารก็ยิ่งใหญ่ขึ้น
