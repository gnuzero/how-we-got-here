    ลำดับชั้นหน่วยความจำ GPU

    มกราคม 1, 2026

    บทที่ 35 ตั้งชื่อ memory wall: latency ของ DRAM ตาม compute ไม่ทัน อุตสาหกรรมจึงไล่ แบนด์วิดท์ ในที่ที่ latency ดื้อ ไม่มีที่ไหนที่การตอบนั้นมีผลมากกว่าหน่วยความจำ GPU — ปริมาณงานขนานของบทที่ 52–53 สร้างความอยากที่ DDR ทั่วไป (บทที่ 34) ป้อนไม่ได้

    บทนี้จะทำสามอย่าง: แกะว่า HBM ได้แบนด์วิดท์มาจากไหนด้วยเลขคณิตง่าย ๆ ไล่ลำดับชั้นภายใน GPU พร้อมขนาดจริงของแต่ละชั้น แล้วสร้าง แบบจำลอง roofline (roofline model) — เครื่องมือหนึ่งบรรทัดที่ตอบว่าโปรแกรมหนึ่ง ๆ ถูกจำกัดด้วยการคำนวณหรือด้วยหน่วยความจำ คำศัพท์พื้นฐาน: แบนด์วิดท์ (bandwidth, ศัพท์บัญญัติ) ในบทนี้หมายถึงจำนวนไบต์ที่ย้ายได้ต่อวินาที ส่วน เวลาแฝง (latency, ศัพท์บัญญัติ) คือเวลาที่ต้องรอไบต์แรก

    เหตุใด GPU จึงอดบนหน่วยความจำแบบ CPU#

    CPU รันสตรีมคำสั่งจำนวนพอประมาณ; แคช (บทที่ 15) มักดูดซับ working set GPU อาจมีเธรดนับพันข้ามหลาย SM ที่ต้องการหน่วยความจำพร้อมกัน การแคชบนชิปช่วย แต่ความต้องการแบนด์วิดท์รวมสูงกว่าระบบหน่วยความจำของ CPU ที่พลังงานใกล้เคียงมาก — ข้อจำกัดที่บังคับคำตอบทางกายภาพต่าง

    HBM: ซ้อนข้างได#

    High Bandwidth Memory ซ้อนได DRAM ในแนวตั้ง เชื่อมผ่าน through-silicon via (TSV) แทนรอย PCB ยาวไปยัง DIMM แยก รวมกับอินเทอร์เฟซกว้างมาก ให้แบนด์วิดท์สูงกว่า DDR เทียบเท่ามาก — จ่ายด้วยการบรรจุขั้นสูงของบทที่ 51 HBM กับไดคำนวณ GPU โดยปกติแชร์ silicon interposer: ตระกูลการบรรจุเดียวกับ chiplets นำไปใช้ที่นี่เพื่อวางหน่วยความจำ ข้าง compute แทนการแยกไดเชิงหน้าที่

    คำศัพท์ในย่อหน้านั้นยังไม่พบศัพท์บัญญัติทั้งคู่ จึงขอนิยามตามความ: TSV (through-silicon via) คือรูที่เจาะทะลุแผ่นซิลิคอนแล้วเติมโลหะ ทำหน้าที่เป็นสายไฟแนวตั้งที่ต่อไดชั้นบนกับชั้นล่างโดยตรง ส่วน interposer คือแผ่นซิลิคอนรองที่มีสายไฟละเอียดจำนวนมาก วางใต้ทั้งได GPU และกองหน่วยความจำ ให้ทั้งสองต่อกันด้วยสายสั้นและถี่กว่าที่แผงวงจรพิมพ์ทำได้มาก

    แบนด์วิดท์ = ความกว้าง × อัตราต่อขา#

    แบนด์วิดท์ของหน่วยความจำใด ๆ คำนวณได้จากสองตัวเลข: มีสายข้อมูลกี่เส้น (ความกว้างบัส) และแต่ละเส้นส่งได้กี่บิตต่อวินาที หารด้วย 8 ให้เป็นไบต์ ลองกับ A100 ตามเอกสารสถาปัตยกรรมของ NVIDIA:

    1. เอกสารระบุว่า A100 มี HBM2 ที่ทำงาน 5 กอง (stack) แต่ละกองซ้อน 8 ได และมีตัวควบคุมหน่วยความจำ 512 บิต 10 ตัว — หรือสองตัวต่อกอง แปลว่าแต่ละกองกว้าง 2 × 512 = 1,024 บิต รวมทั้งชิป 5 × 1,024 = 5,120 บิต
    2. อัตราข้อมูลระบุว่า 1,215 MHz แบบ DDR (ส่งทั้งขาขึ้นและขาลงของคล็อก จากบทที่ 34) → 2 × 1,215 × 10⁶ = 2.43 Gb/s ต่อขา
    3. แบนด์วิดท์ = 5,120 × 2.43 × 10⁹ / 8 = 1,555.2 GB/s — ตรงกับ 1,555 GB/s ที่เอกสารประกาศ (กองละราว 311 GB/s)

    สังเกตว่า 2.43 Gb/s ต่อขา ไม่ได้เร็ว เลย เคล็ดลับของ HBM คือ กว้าง ไม่ใช่ เร็ว เทียบกับช่องหน่วยความจำ DDR4-3200 ของพีซี (ตามชื่อรุ่น คือ 3,200 ล้านการโอนต่อวินาที บนช่องกว้าง 64 บิต): 64 × 3.2 × 10⁹ / 8 = 25.6 GB/s ต่อช่อง ต้องใช้ราว 61 ช่อง จึงจะเท่า A100 หนึ่งตัว การเดินสาย 5,120 เส้นบนแผงวงจรพิมพ์ไปยังโมดูลที่อยู่ห่างออกไปหลายเซนติเมตรนั้นเป็นไปไม่ได้ในทางปฏิบัติ แต่บน interposer ที่สายยาวเพียงระยะระหว่างไดที่วางชิดกัน มันทำได้ เอกสารของ NVIDIA สรุปว่าการวางกองหน่วยความจำไว้บนแพ็กเกจเดียวกับ GPU “ประหยัดพลังงานและพื้นที่อย่างมาก” เมื่อเทียบกับ GDDR5/6 แบบดั้งเดิม

    ตรวจความจุ: 40 GB ÷ 5 กอง = 8 GB ต่อกอง ÷ 8 ได = 1 GB (8 กิกะบิต) ต่อได สอดคล้องกัน รายละเอียดเล็ก ๆ อีกข้อ: ชิป GA100 เต็มตัวออกแบบมาให้มี HBM2 6 กอง แต่ผลิตภัณฑ์ A100 เปิดใช้ 5 — ตัวเลขในโฆษณาจึงมาจาก 5 กอง ไม่ใช่ 6

    ลำดับชั้นภายใน GPU#

    นอกจาก HBM-กับ-DDR GPU มีพีระมิดของตัวเอง สะท้อนรูปทรง register–cache–main-memory ของบทที่ 10 ด้วยชั้นเฉพาะ GPU Register file ของแต่ละ SM คือที่เก็บท้องถิ่นเร็วที่สุด Shared memory — scratchpad ที่โปรแกรมเมอร์จัดการบน SM — ให้เธรดในบล็อกแชร์ข้อมูลโดยไม่ต้องวนไกล L2 cache ครอบ GPU ทั้งก้อน HBM คือชั้น “หน่วยความจำหลัก”: แบนด์วิดท์สูงกว่า DRAM ของ CPU มาก ยังมี latency สูงกว่าอะไรบนชิป — tradeoff ระหว่าง latency กับความจุเดิม ที่สเกล GPU

    ใส่ตัวเลขของ A100 ตามเอกสารของ NVIDIA ลงในพีระมิด (จากบนลงล่าง ยิ่งล่างยิ่งใหญ่ ยิ่งไกล):

    ชั้น ขนาดใน A100 ใครจัดการ
    แฟ้มเรจิสเตอร์ (register file) 256 KB ต่อ SM รวม 27,648 KB ทั้งชิป คอมไพเลอร์ (แต่ละเธรดเห็นเฉพาะของตัวเอง)
    L1 + หน่วยความจำร่วม (shared memory) 192 KB ต่อ SM (แบ่งสัดส่วนได้) × 108 SM โปรแกรมเมอร์ (ส่วน shared)
    L2 40 MB ทั้งชิป ฮาร์ดแวร์
    HBM2 40 GB, 1,555 GB/s โปรแกรมเมอร์ย้ายข้อมูลเข้า-ออกเอง

    คำว่า หน่วยความจำหลัก (main memory) และ หน่วยความจำแคช (cache memory) เป็นศัพท์บัญญัติ ส่วน “shared memory” ของ GPU ยังไม่พบศัพท์บัญญัติ บทนี้เรียก “หน่วยความจำร่วม” มันต่างจากแคชตรงที่ ไม่มีใครเดาให้ ว่าจะเก็บอะไร โปรแกรมต้องสั่งโหลดข้อมูลเข้ามาเอง — ข้อเสียคือเขียนยากขึ้น ข้อดีคือโปรแกรมเมอร์รู้ว่าข้อมูลจะถูกใช้ซ้ำกี่ครั้ง ซึ่งเป็นกุญแจของหัวข้อถัดไป

    Roofline: การคำนวณหรือหน่วยความจำ อะไรเป็นเพดาน#

    ความเข้มเชิงคำนวณ#

    นิยาม ความเข้มเชิงคำนวณ (arithmetic intensity; ยังไม่พบศัพท์บัญญัติ ศัพท์บัญญัติของ intensity ในสาขาวิทยาศาสตร์คือ “ความเข้ม”) ของงานชิ้นหนึ่งว่า

    I = จำนวนการดำเนินการจุดลอยตัว (FLOP) ÷ จำนวนไบต์ที่ต้องย้ายจากหน่วยความจำ

    หน่วยคือ FLOP ต่อไบต์ มันเป็นคุณสมบัติของ อัลกอริทึมกับการจัดข้อมูล ไม่ใช่ของเครื่อง บทความต้นฉบับของ Williams, Waterman และ Patterson ใช้คำว่า operational intensity และระบุชัดว่านับเฉพาะไบต์ที่วิ่งระหว่างแคชกับ DRAM “หลังจากถูกกรองด้วยลำดับชั้นแคชแล้ว” โดยจงใจแยกจากคำว่า arithmetic intensity ในงานก่อนหน้าที่นับทราฟฟิกระหว่างโพรเซสเซอร์กับแคช ในบทนี้เราจะนับไบต์ที่วิ่งจาก HBM ตามความหมายแบบ Williams

    สองเพดาน หนึ่งสมการ#

    เครื่องมีขีดจำกัดสองอย่าง: คำนวณได้เร็วสุด P FLOP/s (เพดานการคำนวณ) และดึงข้อมูลได้เร็วสุด B ไบต์ต่อวินาที ถ้างานมีความเข้ม I ข้อมูลที่มาถึงทุกวินาทีจะเลี้ยงการคำนวณได้แค่ B × I FLOP/s ดังนั้น

    สมรรถนะที่ทำได้ ≤ min(P, B × I)

    นี่คือสมการเดียวกับในบทความของ Williams และคณะ บนกราฟที่แกนนอนเป็น I และแกนตั้งเป็น FLOP/s (สเกลลอการิทึมทั้งคู่) เพดาน B × I เป็นเส้นเฉียงขึ้น เพดาน P เป็นเส้นแนวนอน ได้รูปหลังคา — จึงชื่อ roofline จุดที่สองเส้นตัดกันเรียกว่า จุดสัน (ridge point) อยู่ที่ I* = P / B ซึ่งบทความนิยามว่าเป็น “ความเข้มขั้นต่ำที่ต้องมีเพื่อจะได้สมรรถนะสูงสุด” งานที่ I < I* ติดหลังคาเฉียง เรียกว่า ถูกจำกัดด้วยหน่วยความจำ (memory-bound) งานที่ I > I* ติดหลังคาแบน เรียกว่า ถูกจำกัดด้วยการคำนวณ (compute-bound) (ศัพท์บัญญัติของ bound ในคณิตศาสตร์คือ “ขอบเขต”)

    จุดสันของ A100 (จากตัวเลขในเอกสาร):

    • Tensor Core FP16: 312 × 10¹² ÷ 1,555 × 10⁹ ≈ 201 FLOP ต่อไบต์
    • FP32 แบบธรรมดา (ไม่ใช้ Tensor Core): 19.5 × 10¹² ÷ 1,555 × 10⁹ ≈ 12.5 FLOP ต่อไบต์

    อ่านว่า: ถ้าจะใช้ Tensor Core ให้เต็ม ทุกไบต์ที่ดึงจาก HBM ต้องถูกใช้ในการคำนวณราว 200 ครั้ง เทียบกับตัวอย่างในบทความของ Williams และคณะ ที่เครื่อง Opteron X2 มีค่ายอด 17.6 GFLOP/s กับแบนด์วิดท์ที่วัดได้ 15 GB/s จุดสันคำนวณได้ราว 17.6/15 ≈ 1.2 (ตัวบทความเองระบุไว้ว่า 1.0; เป็นค่าจุดลอยตัวความแม่นยำสองเท่า จึงเทียบกับ FP16 ตรง ๆ ไม่ได้ แต่แม้เทียบกับ FP32 ธรรมดาของ A100 ที่ 12.5 จุดสันก็ยังเลื่อนไปทางขวาราว 10 เท่าขึ้นไปในเวลาสิบกว่าปี) — นี่คือกำแพงหน่วยความจำของบทที่ 35 ในรูปตัวเลขเดียว

    ตัวอย่างที่ 1: บวกเวกเตอร์#

    c[i] = a[i] + b[i] ด้วย FP32: ต่อหนึ่งช่อง อ่าน 4 + 4 ไบต์ เขียน 4 ไบต์ รวม 12 ไบต์ ทำ 1 FLOP ดังนั้น I = 1/12 ≈ 0.083 FLOP/ไบต์ ห่างจากจุดสัน FP32 (12.5) ราว 150 เท่า สมรรถนะสูงสุด = 1,555 × 0.083 ≈ 130 GFLOP/s ไม่ถึง 1% ของ 19.5 TFLOP/s ถ้าเวกเตอร์ยาว 100 ล้านช่อง ต้องย้าย 1.2 GB ใช้เวลาอย่างน้อย 1.2 / 1,555 ≈ 0.77 ms ไม่ว่า GPU จะมีคอร์มากเท่าไร การเพิ่มพลังคำนวณให้งานนี้ไม่ช่วยเลย มีแต่แบนด์วิดท์ที่ช่วย

    ตัวอย่างที่ 2: เมทริกซ์คูณเวกเตอร์ และทำไมขนาดกลุ่มสำคัญ#

    น้ำหนัก W ขนาด n × n แบบ FP16 คูณกับอินพุต b คอลัมน์ (b = ขนาดกลุ่ม) FLOP = 2n²b ไบต์ ≈ 2n² (น้ำหนัก) + 4nb (อินพุตและเอาต์พุต) เมื่อ b เล็กกว่า n มาก ไบต์ถูกครองด้วยน้ำหนัก ได้ I ≈ b — ทุกน้ำหนักที่ดึงมาใช้ซ้ำหนึ่งครั้งต่อหนึ่งตัวอย่างในกลุ่ม ผู้เขียนคำนวณด้วย n = 8,192 บน A100:

    b I (FLOP/ไบต์) เพดาน min(P, B × I) % ของค่ายอด FP16
    1 1.0 1.6 TFLOP/s 0.5%
    8 8.0 12.4 TFLOP/s 4%
    64 63 98 TFLOP/s 31%
    256 241 312 TFLOP/s 100%

    ข้อสรุป: การประมวลผลทีละตัวอย่าง (b = 1) บนเครื่องที่มีจุดสัน 200 ใช้เครื่องได้ครึ่งเปอร์เซ็นต์ นี่คือเหตุผลเชิงตัวเลขที่ระบบฝึกและระบบให้บริการโมเดลพยายามรวมคำขอเป็นกลุ่ม และเป็นเหตุที่บทที่ 56 เตือนว่ากลุ่มย่อยที่เล็กเกินไปในไปป์ไลน์ทำให้การคูณเมทริกซ์ “ใช้ GPU ได้ไม่เต็ม”

    ตัวอย่างที่ 3: เมทริกซ์คูณเมทริกซ์ และบทบาทของหน่วยความจำร่วม#

    คูณเมทริกซ์จัตุรัส n × n สองตัวด้วย FP16: FLOP = 2n³ ถ้าอ่าน A กับ B และเขียน C อย่างละครั้งเดียว ไบต์ = 3 × 2n² = 6n² ได้ I = n/3 — ความเข้มโตตาม n ที่ n = 4,096 ได้ I ≈ 1,365 เกินจุดสันไปไกล ถูกจำกัดด้วยการคำนวณ (จุดตัดอยู่ที่ n ≈ 602) นี่คือเหตุผลเชิงโครงสร้างที่ทำให้การคูณเมทริกซ์ถูกยกเป็นศูนย์กลางของฮาร์ดแวร์ AI ในบทที่ 57: มันเป็นงานไม่กี่ชนิดที่ ยิ่งใหญ่ยิ่งใช้ข้อมูลซ้ำ

    แต่ I = n/3 สมมุติว่า “อ่านครั้งเดียว” ซึ่งต้องมีที่เก็บบนชิปใหญ่พอจะถือทั้งเมทริกซ์ — ไม่มี ในความเป็นจริงต้องแบ่งเป็น แผ่นย่อย (tile) ลองดูแบบจำลองง่าย ๆ ที่ผู้เขียนสร้างขึ้นเพื่ออธิบาย (ละเลยแคช L2):

    • ไม่ใช้ซ้ำเลย: ทุกการคูณ-บวก (2 FLOP) ดึง A หนึ่งตัวกับ B หนึ่งตัวจาก HBM (4 ไบต์) → I = 0.5 ติดหลังคาเฉียงที่ 1,555 × 0.5 ≈ 0.78 TFLOP/s
    • แบ่งแผ่นย่อย T × T ในหน่วยความจำร่วม: เพื่อคำนวณแผ่น T × T ของ C เราเดินไปตามมิติร่วม ทีละก้าว แต่ละก้าวโหลดแผ่นของ A และแผ่นของ B อย่างละ T² ตัว (2T² × 2 = 4T² ไบต์) แล้วทำ 2T³ FLOP ได้ I = T/2
    T I = T/2 เพดาน หน่วยความจำร่วมที่ใช้ (สองแผ่น FP16)
    32 16 25 TFLOP/s 4 KB
    64 32 50 TFLOP/s 16 KB
    128 64 100 TFLOP/s 64 KB
    256 128 199 TFLOP/s 256 KB — ไม่พอดี 192 KB

    จะถึงจุดสัน 201 ต้องใช้ T ≈ 400 ซึ่งใหญ่เกินหน่วยความจำร่วมของ SM หนึ่งตัว ในแบบจำลองนี้ หน่วยความจำร่วมอย่างเดียวจึงพาไปได้ราวหนึ่งในสามของค่ายอด ส่วนที่เหลือต้องมาจาก ชั้นอื่นของพีระมิด: แคช L2 ขนาด 40 MB ที่ให้หลาย SM ใช้แผ่นเดียวกันซ้ำโดยไม่ต้องไป HBM อีก และแฟ้มเรจิสเตอร์ที่ให้แต่ละเธรดใช้ค่าซ้ำภายใน นี่คือความหมายเชิงปริมาณของพีระมิด: แต่ละชั้นคูณการใช้ซ้ำเข้าไปอีกทอด จนความเข้มที่มองจาก HBM สูงพอข้ามจุดสัน (ตัวเลขในตารางนี้เป็นแบบจำลองเพื่อการสอน ไลบรารีจริงอย่าง cuBLAS จัดแผ่นซับซ้อนกว่านี้มาก)

    roofline บอกอะไร และไม่บอกอะไร#

    roofline เป็น ขอบบน ไม่ใช่การทำนาย งานที่อยู่ใต้หลังคามากแปลว่ามีคอขวดอื่น เช่น การกระจายงานไม่ทั่ว การแตกแขนงในวาร์ป (บทที่ 53) หรือการเข้าถึงหน่วยความจำแบบกระจัดกระจาย บทความต้นฉบับจึงเพิ่ม “เพดานย่อย” (ceilings) ใต้หลังคาหลักสำหรับการปรับแต่งแต่ละชนิด แต่คำถามแรกที่ roofline ตอบได้ทันทีด้วยการคูณหารสองครั้งนั้นมีค่ามาก: งานนี้ควรลงทุนเพิ่มการคำนวณ หรือเพิ่มการใช้ข้อมูลซ้ำ

    ป้อนสิ่งที่มาถัดไป#

    สถาปัตยกรรมนี้มีอยู่เพื่อเลี้ยงความอยาก compute มหาศาล Peak FLOPS ไร้ความหมายหาก operand มาไม่ทันและผลออกไม่ได้ Tensor core ในบทถัดไปคือโครงสร้าง compute ที่แบนด์วิดท์ของ HBM ถูกสร้างมาป้อน — พากรอบแบนด์วิดท์ไปด้วย: peak ของ tensor core มีความหมายเฉพาะเมื่อเทียบกับระบบหน่วยความจำที่ค้ำจุนมันได้

    ประโยคสุดท้ายนั้นคือ roofline ในรูปคำพูด: tensor core ยกหลังคาแบน (P) ขึ้นอีกหลายเท่า แต่ไม่ได้ขยับหลังคาเฉียง (B) จุดสันจึงเลื่อนไปทางขวา และงานที่เคยถูกจำกัดด้วยการคำนวณอาจกลายเป็นถูกจำกัดด้วยหน่วยความจำได้ทันทีเมื่อย้ายขึ้นเครื่องใหม่
