    การขยายหลาย GPU

    มกราคม 1, 2026

    GPU เดียวมี compute และ HBM จำกัด (บทที่ 54) โมเดลใหญ่ที่สุดวันนี้ต้องการหลาย GPU — ในเซิร์ฟเวอร์เดียว แล้วข้ามคลัสเตอร์ — และวิธีที่ GPU เหล่านั้นคุยกันมักตัดสินปริมาณงานจริงไม่น้อยกว่า peak ของ GPU ตัวใดตัวหนึ่ง

    บทนี้จะตอบสามคำถามตามลำดับ: (1) ทำไม GPU เดียวไม่พอ ทั้งในแง่หน่วยความจำและเวลา (2) มีวิธีแบ่งงานกี่แบบ แต่ละแบบต้องส่งข้อมูลอะไร มากเท่าไร และบ่อยแค่ไหน (3) ทำไมระบบจริงจึงผสมทั้งสามแบบ และวางแต่ละแบบไว้บนลิงก์คนละชนิด คำว่า การประมวลผลแบบขนาน (parallel processing, ศัพท์บัญญัติ) คือภาพรวม ส่วนคำว่า “ความขนาน” (parallelism) ในชื่อเทคนิคทั้งสามด้านล่าง ยังไม่พบศัพท์บัญญัติในสาขาคอมพิวเตอร์ บทนี้จึงเรียกว่า “การแบ่งขนานแบบ…” คู่กับชื่ออังกฤษ

    ทำไม GPU เดียวไม่พอ: นับไบต์ก่อน#

    การฝึกโมเดลต้องเก็บมากกว่าน้ำหนัก บทความ ZeRO (Rajbhandari และคณะ, 2019) แจกแจงไว้สำหรับการฝึกแบบ mixed precision ด้วยตัวปรับค่า Adam โมเดลที่มี Ψ พารามิเตอร์ต้องเก็บ:

    • น้ำหนักแบบ FP16: 2Ψ ไบต์
    • เกรเดียนต์ (gradient, ศัพท์บัญญัติ “เกรเดียนต์” หรือ “ความชัน”) แบบ FP16: 2Ψ ไบต์ — ทิศทางที่น้ำหนักแต่ละตัวควรขยับ คำนวณได้จากการแพร่ย้อนกลับ (บทที่ 46)
    • สถานะของตัวปรับค่า (optimizer state): สำเนาน้ำหนักแบบ FP32, โมเมนตัม, ความแปรปรวน อย่างละ 4Ψ รวม 12Ψ ไบต์

    รวม 16Ψ ไบต์ และยังไม่นับ แอกทิเวชัน (activation — ผลกลางของแต่ละชั้นที่ต้องเก็บไว้ใช้ตอนย้อนกลับ) ซึ่งโตตามขนาดกลุ่มข้อมูล ลองแทนตัวเลข: โมเดล 1.5 พันล้านพารามิเตอร์ (ขนาด GPT-2) ต้องใช้ 16 × 1.5 × 10⁹ = 24 GB ขณะที่น้ำหนัก FP16 ล้วน ๆ มีแค่ 3 GB (ตัวเลขทั้งสองตรงกับที่บทความ ZeRO ระบุ) โมเดล 7.5 พันล้านพารามิเตอร์ต้องใช้ 120 GB — เกินหน่วยความจำ 40 GB ของ A100 รุ่นที่เอกสารของ NVIDIA บรรยายไปสามเท่า ถ้าไม่แบ่ง ก็ฝึกไม่ได้เลย

    แม้จะใส่ได้ เวลาก็ยังเป็นปัญหา ภาคผนวกของบทความเรื่องการฝึก Megatron-LM บนคลัสเตอร์ GPU ปี 2021 (Narayanan และคณะ) นับ FLOP ของทรานส์ฟอร์เมอร์จากหลักการพื้นฐาน: การคูณเมทริกซ์ขนาด m×k กับ k×n ใช้ 2mkn FLOP (คูณหนึ่ง บวกหนึ่ง) ชั้นหนึ่งใช้ราว 24Bsh² FLOP ในรอบไปข้างหน้า (B = จำนวนลำดับในกลุ่ม, s = ความยาวลำดับ, h = ขนาดชั้นซ่อน) รอบย้อนกลับใช้เป็นสองเท่า เพราะต้องคำนวณเกรเดียนต์เทียบทั้งอินพุตและน้ำหนัก ถ้าคิดว่าโมเดลมีพารามิเตอร์ราว 12lh² (l = จำนวนชั้น) จะได้ว่า รอบไปข้างหน้ากิน 2 FLOP ต่อพารามิเตอร์ต่อโทเค็น รอบย้อนกลับกิน 4 รวม 6 (บทความนั้นใช้การคำนวณแอกทิเวชันซ้ำ เพิ่มรอบไปข้างหน้าอีกหนึ่ง จึงเป็น 8) นี่คือที่มาของกฎหัวแม่มือ “6 × พารามิเตอร์ × โทเค็น” — การอนุมานนี้เป็นของผู้เขียนจากสูตรในภาคผนวก

    การแบ่งงานไม่ฟรี#

    บทที่ 46 ครอบคลุมว่า เหตุใด การแบ่ง data-parallel และ model-parallel จึงมักจำเป็น ประสิทธิภาพขึ้นกับว่า GPU แลกข้อมูลกันเร็วเพียงใด หากการสื่อสารช้าเทียบกับ compute ของแต่ละ GPU เพื่อนจะค้างรอกัน — memory wall (บทที่ 35) อีกครั้ง นำไปใช้กับลิงก์ GPU-ถึง-GPU แทน CPU-ถึง-DRAM

    มีสามวิธีหลักในการแบ่ง ต่างกันที่ อะไร ถูกแบ่ง และ อะไร ต้องวิ่งข้ามลิงก์

    1. การแบ่งขนานแบบข้อมูล (data parallelism)#

    GPU ทุกตัวถือสำเนาโมเดลเต็ม แต่ละตัวรับ ส่วนต่างกัน ของกลุ่มข้อมูล (batch; ศัพท์บัญญัติสาขาคอมพิวเตอร์ใช้ “กลุ่ม”) คำนวณเกรเดียนต์ของตัวเอง แล้วทุกตัวต้องได้ ค่าเฉลี่ย ของเกรเดียนต์จากทุกตัวก่อนขยับน้ำหนัก ไม่งั้นสำเนาจะค่อย ๆ แยกทางกัน การรวมแล้วแจกผลกลับให้ทุกตัวแบบนี้เรียกว่า all-reduce (บทที่ 61) และมันคือ การประสานเวลา (synchronization, ศัพท์บัญญัติ) หนึ่งครั้งต่อหนึ่งขั้นการฝึก

    ต้องส่งเท่าไร? ด้วย ring all-reduce ที่ GPU N ตัวต่อกันเป็นวง แต่ละตัวต้องส่ง (และรับ) ประมาณ 2(N−1)/N × S ไบต์ เมื่อ S คือขนาดเกรเดียนต์ทั้งก้อน — เกือบ 2S ไม่ว่า N จะเท่าไร

    ตัวอย่างในเครื่องเดียว (ประมาณการของผู้เขียน): โมเดล 1.5 พันล้านพารามิเตอร์ เกรเดียนต์ FP16 S = 3 GB บน GPU 8 ตัว แต่ละตัวส่ง 2 × 7/8 × 3 = 5.25 GB ต่อขั้น

    • ผ่าน NVLink รุ่นที่ 3 ของ A100: เอกสารระบุ 12 ลิงก์ ลิงก์ละ 25 GB/s ต่อทิศทาง รวม 600 GB/s สองทิศ หรือ 300 GB/s ต่อทิศทาง → 5.25/300 ≈ 17.5 ms
    • ผ่าน PCIe Gen 4 x16 ที่เอกสารระบุ 31.5 GB/s → 5.25/31.5 ≈ 167 ms

    เทียบกับเวลาคำนวณ: สมมุติแต่ละ GPU ทำ 8 ลำดับ × 1,024 โทเค็นต่อขั้น (ตัวเลขประกอบการอธิบาย) ใช้ 8 FLOP ต่อพารามิเตอร์ต่อโทเค็น (รวมการคำนวณแอกทิเวชันซ้ำ ให้ตรงกับเงื่อนไขที่วัดอัตรา 137 TFLOP/s ด้านล่าง) × 8,192 โทเค็น × 1.5 × 10⁹ พารามิเตอร์ ≈ 9.8 × 10¹³ FLOP ถ้าทำได้ 137 TFLOP/s (อัตราที่ Narayanan และคณะวัดได้จริงต่อ GPU สำหรับโมเดลขนาดใกล้เคียงกัน คือ 1.7 พันล้านพารามิเตอร์) ใช้เวลา ≈ 0.72 วินาที การสื่อสารผ่าน NVLink จึงเพิ่มเวลาราว 2.4% ส่วนผ่าน PCIe เพิ่มราว 23% — และนั่นยังเป็นกรณีที่ไม่มีทราฟฟิกอื่นแย่งลิงก์ (ระบบจริงซ่อนเวลานี้ได้บางส่วนด้วยการเริ่มส่งเกรเดียนต์ของชั้นท้าย ๆ ขณะรอบย้อนกลับยังคำนวณชั้นต้น ๆ อยู่)

    ข้อจำกัดของแบบนี้: ทุก GPU ยังต้องถือ 16Ψ เต็ม ๆ การแบ่งแบบข้อมูลช่วย เวลา แต่ไม่ช่วย หน่วยความจำ ZeRO แก้ด้วยการกระจายสถานะของตัวปรับค่า เกรเดียนต์ และน้ำหนักไปเก็บคนละส่วนแทนการเก็บซ้ำ สำหรับโมเดล 7.5 พันล้านพารามิเตอร์บน 64 GPU บทความ ZeRO คำนวณว่า: แบบเดิม 120 GB ต่อ GPU; กระจายสถานะตัวปรับค่าอย่างเดียว 4Ψ + 12Ψ/64 ≈ 31.4 GB; กระจายเกรเดียนต์ด้วย 2Ψ + 14Ψ/64 ≈ 16.6 GB; กระจายทั้งสามอย่าง 16Ψ/64 ≈ 1.88 GB (ผู้เขียนคำนวณซ้ำได้ตรงกัน)

    2. การแบ่งขนานแบบเทนเซอร์ (tensor parallelism)#

    ถ้าแม้แต่ ชั้นเดียว ก็ใหญ่เกิน หรืออยากให้ชั้นเดียวเสร็จเร็วขึ้น ก็ต้องผ่าเมทริกซ์น้ำหนักของชั้นนั้นเอง Megatron-LM (Shoeybi และคณะ, 2019) แสดงวิธีผ่าเครือข่ายป้อนไปข้างหน้าสองชั้นของทรานส์ฟอร์เมอร์ Y = GeLU(XA) แล้วตามด้วย Z = YB ให้สื่อสารน้อยที่สุด ลองทำด้วยตัวเลขเล็ก ๆ ให้เห็นว่าทำไมต้องผ่า แบบนั้น (ใช้ ReLU = max(0, x) แทน GeLU เพื่อให้คิดในใจได้ เหตุผลเหมือนกันเพราะทั้งคู่ไม่เป็นเชิงเส้น)

    ให้ X = [1, 2] และ A มีสองแถว คือ [1, 0, 2, −1] กับ [0, 1, 1, 3]

    • XA = 1×[1, 0, 2, −1] + 2×[0, 1, 1, 3] = [1, 2, 4, 5] ดังนั้น Y = ReLU(XA) = [1, 2, 4, 5]
    • ให้ B เป็นเมทริกซ์ 4×2 ที่มีแถว [1, 0], [0, 1], [1, 1], [2, −1] จะได้ Z = YB = 1×[1,0] + 2×[0,1] + 4×[1,1] + 5×[2,−1] = [15, 1]

    ผ่าผิดทาง — ตามแถวของ A: GPU 1 ถือแถวแรก ได้ผลบางส่วน [1, 0, 2, −1]; GPU 2 ถือแถวที่สอง ได้ [0, 2, 2, 6] ถ้าแต่ละตัวทำ ReLU เองแล้วค่อยบวก จะได้ [1, 0, 2, 0] + [0, 2, 2, 6] = [1, 2, 4, 6] ซึ่ง ผิด (ช่องสุดท้ายควรเป็น 5) เพราะ ReLU(a + b) ≠ ReLU(a) + ReLU(b) แบบนี้ต้องประสานเวลา (บวกผลบางส่วน) ก่อน ฟังก์ชันไม่เชิงเส้นทุกครั้ง

    ผ่าถูกทาง — ตามคอลัมน์ของ A: GPU 1 ถือสองคอลัมน์แรก คำนวณ Y₁ = ReLU([1, 2]) = [1, 2]; GPU 2 ถือสองคอลัมน์หลัง คำนวณ Y₂ = ReLU([4, 5]) = [4, 5] ไม่ต้องคุยกันเลย เพราะแต่ละคอลัมน์ของผลขึ้นกับคอลัมน์ของ A คอลัมน์เดียว แล้วผ่า B ตามแถว ให้สอดคล้อง: GPU 1 คำนวณ Z₁ = Y₁ × (สองแถวแรกของ B) = [1, 2]; GPU 2 คำนวณ Z₂ = Y₂ × (สองแถวหลัง) = 4×[1,1] + 5×[2,−1] = [14, −1] จากนั้น all-reduce หนึ่งครั้ง: Z = [1, 2] + [14, −1] = [15, 1] ถูกต้อง

    นี่คือเหตุที่บทความ Megatron-LM ทำได้ด้วย all-reduce เพียง สองครั้งในรอบไปข้างหน้าและสองครั้งในรอบย้อนกลับ ต่อชั้นทรานส์ฟอร์เมอร์หนึ่งชั้น (บล็อก attention กับบล็อกป้อนไปข้างหน้า บล็อกละหนึ่งครั้งในแต่ละทิศ)

    แต่ “สองครั้งต่อชั้น” ถี่มาก ลองประมาณ (การคำนวณของผู้เขียน) สำหรับโมเดลขนาด GPT-3 (h = 12,288, 96 ชั้น) กลุ่มย่อยหนึ่งลำดับยาว 2,048 โทเค็น แต่ละ all-reduce มีขนาด 1 × 2,048 × 12,288 × 2 ไบต์ ≈ 50.3 MB ผ่า 8 ทาง แต่ละ GPU ส่ง 2 × 7/8 × 50.3 ≈ 88 MB ต่อครั้ง × 4 ครั้งต่อชั้น × 96 ชั้น ≈ 33.8 GB ต่อกลุ่มย่อยหนึ่งกลุ่ม ผ่าน NVLink 300 GB/s ใช้ ≈ 0.11 วินาที ผ่านการ์ด InfiniBand HDR 200 Gb/s (= 25 GB/s ซึ่งเป็นการ์ดที่คลัสเตอร์ในบทความใช้ โหนดละแปดใบ) ใช้ ≈ 1.35 วินาที — ช้ากว่า 12 เท่า และต้องรอทุกครั้ง เพราะชั้นถัดไปเริ่มไม่ได้จนกว่าผลรวมจะมา ข้อสรุปข้อแรกของ Narayanan และคณะจึงตรงไปตรงมา: ใช้การแบ่งแบบเทนเซอร์ได้ถึงจำนวน GPU ในเซิร์ฟเวอร์เดียว (g ตัวในเซิร์ฟเวอร์ g-GPU) แล้วค่อยใช้การแบ่งแบบไปป์ไลน์ข้ามเซิร์ฟเวอร์

    3. การแบ่งขนานแบบไปป์ไลน์ (pipeline parallelism)#

    ผ่าโมเดลตาม ชั้น: GPU 1 ถือชั้น 1–12, GPU 2 ถือชั้น 13–24 และต่อไป ข้อมูลที่ข้ามลิงก์มีแค่แอกทิเวชันที่ขอบระหว่างช่วง ส่งแบบจุดต่อจุดครั้งเดียวต่อช่วง จึงทนลิงก์ช้าข้ามเซิร์ฟเวอร์ได้ดีกว่ามาก นี่คือ การทำงานแบบสายท่อ (pipeline, ศัพท์บัญญัติ) แบบเดียวกับในบทที่ 13 แต่ขั้นของสายท่อคือ GPU ทั้งตัว

    ปัญหาคือ ถ้าส่งกลุ่มข้อมูลทั้งก้อนเข้าไป GPU 2 ต้องรอ GPU 1 ทำเสร็จ แล้ว GPU 1 ก็ว่างรอรอบย้อนกลับ ทางแก้ของ GPipe (Huang และคณะ, 2018) คือหั่นกลุ่มเป็น กลุ่มย่อย (microbatch) m ก้อนแล้วป้อนตามกันเหมือนสายพาน แต่ช่วงต้นและช่วงท้ายของแต่ละรอบยังมีช่วงที่บางขั้นว่าง เรียกว่า ฟองอากาศของไปป์ไลน์ (pipeline bubble) Narayanan และคณะให้สูตรง่าย ๆ: ถ้ามี p ขั้น เวลาฟองอากาศ = (p − 1) × (t_f + t_b) ขณะที่เวลางานจริง = m × (t_f + t_b) ดังนั้น

    สัดส่วนฟองอากาศ (เทียบกับเวลางานอุดมคติ) = (p − 1) / m

    แทนตัวเลขกับไปป์ไลน์ 8 ขั้น:

    กลุ่มย่อย m (p − 1)/m ประสิทธิภาพ = 1/(1 + (p−1)/m)
    8 7/8 = 0.875 ≈ 53%
    32 7/32 ≈ 0.219 ≈ 82%
    64 7/64 ≈ 0.109 ≈ 90%

    ตรวจความสอดคล้อง: ถ้าคิดเป็นสัดส่วน ของเวลาทั้งหมด จะได้ (p − 1)/(m + p − 1) ซึ่งตรงกับรูป O((K − 1)/(M + K − 1)) ที่บทความ GPipe เขียนไว้ (K = จำนวนขั้น, M = จำนวนกลุ่มย่อย) บทความ GPipe รายงานว่าในการทดลองของพวกเขา ฟองอากาศแทบไม่มีผลเมื่อ M ≥ 4K บทเรียน: ต้องมีกลุ่มย่อยมากกว่าจำนวนขั้นหลายเท่า — แต่กลุ่มย่อยที่เล็กลงก็ทำให้การคูณเมทริกซ์แต่ละครั้งเล็กลง และใช้ GPU ได้ไม่เต็ม (บทที่ 54 อธิบายด้วยแบบจำลอง roofline ว่าทำไมเมทริกซ์เล็กเสียเปรียบ)

    เส้นทางตรงภายในเซิร์ฟเวอร์เดียว#

    บทที่ 37 แนะนำ NVLink เป็นอินเตอร์คอนเนกต์ GPU-ถึง-GPU แบนด์วิดท์สูงที่ข้ามเส้นทาง PCIe ผ่าน CPU ภายในเซิร์ฟเวอร์ NVSwitch ทำให้เป็น all-to-all: ทุก GPU ถึงทุกตัวอื่นที่แบนด์วิดท์ของ NVLink แทนผ่าน PCIe และโฮสต์ สำหรับ workload ที่แลก gradient ใหญ่ตลอด เส้นทางตรงนั้นมักกำหนดปริมาณงานฝึกที่ได้มากกว่าตัวเลข peak-FLOPS แยกเดี่ยวใด ๆ

    ตัวเลขจากหัวข้อก่อนบอกว่าเส้นทางนี้สำคัญแค่ไหน: แบนด์วิดท์ (bandwidth, ศัพท์บัญญัติ) ของ NVLink ใน A100 (300 GB/s ต่อทิศทาง) สูงกว่า PCIe Gen 4 x16 (31.5 GB/s) ราว 9.5 เท่า และสูงกว่าการ์ด InfiniBand HDR หนึ่งใบ (25 GB/s) 12 เท่า การแบ่งแบบเทนเซอร์ที่ต้องประสานเวลาทุกชั้นจึงอยู่รอดได้เฉพาะในโดเมนนี้

    เกินหนึ่งกล่อง#

    การฝึกขนาดใหญ่ครอบหลายเซิร์ฟเวอร์ แนวคิด RDMA ของบทที่ 42 กลับมา: GPUDirect RDMA ให้ตัวปรับเครือข่ายอ่านหรือเขียนหน่วยความจำ GPU ข้ามเซิร์ฟเวอร์โดยไม่ต้องคัดลอกผ่าน DRAM โฮสต์เพิ่ม — เดิมพัน “ลดฮอป ทำให้แบนด์วิดท์ตรงสูงสุด” เดียวกัน ตอนนี้ที่สเกลคลัสเตอร์

    ประกอบสามแบบเข้าด้วยกัน. Narayanan และคณะเรียกการผสมว่า PTD-P (ไปป์ไลน์ + เทนเซอร์ + ข้อมูล) ตารางที่ 1 ของบทความรายงานการฝึกโมเดลหนึ่งล้านล้านพารามิเตอร์บน A100 จำนวน 3,072 ตัว: แบ่งแบบเทนเซอร์ 8 ทาง (เท่ากับจำนวน GPU ในหนึ่งเซิร์ฟเวอร์ DGX A100) แบ่งแบบไปป์ไลน์ 64 ขั้น ข้ามเซิร์ฟเวอร์ ที่เหลือเป็นการแบ่งแบบข้อมูล 3,072 / (8 × 64) = 6 สำเนา ได้ 163 TFLOP/s ต่อ GPU หรือ 52% ของค่ายอด 312 TFLOP/s และรวมทั้งคลัสเตอร์ 502 PFLOP/s (ตรวจ: 3,072 × 163 TFLOP/s ≈ 501 PFLOP/s ต่างจากตารางเพราะการปัดเศษ) แผนผังนี้คือบทเรียนทั้งบทในบรรทัดเดียว: วางการสื่อสารที่ถี่ที่สุดบนลิงก์ที่เร็วที่สุด

    อีกตัวอย่างจากตารางเดียวกัน โมเดล 1.7 พันล้านพารามิเตอร์ใช้การแบ่งแบบข้อมูลล้วน 32 GPU ได้ 137 TFLOP/s ต่อ GPU ผู้เขียนแทนค่าในสูตร FLOP ของภาคผนวก (24 ชั้น, h = 2,304, s = 2,048, คลังคำ 51,200 คำ, กลุ่ม 512 ลำดับ) ได้ราว 1.55 × 10¹⁶ FLOP ต่อขั้น หรือราว 3.5 วินาทีต่อขั้นที่อัตรานั้น ส่วน all-reduce ของเกรเดียนต์ FP16 ราว 3.3 GB ข้าม 32 GPU ผ่าน InfiniBand 25 GB/s ต่อ GPU ใช้ราว 0.26 วินาที (ประมาณการ ถ้าไม่ซ้อนกับการคำนวณ) — ราว 7% ซึ่งเป็นเหตุที่โมเดลขนาดนี้ยังฝึกแบบข้อมูลล้วนได้คุ้ม

    ปรัชญาที่ชุดนี้ตั้งชื่อซ้ำ#

    เส้นทาง GPU-ถึง-GPU ตรง ฮอปที่ไม่จำเป็นน้อยลง อินเตอร์คอนเนกต์เป็นข้อจำกัดชั้นหนึ่ง — ปรัชญาเดียวกันเบื้องหลัง fabric หน่วยความจำ GPU เฉพาะที่ชุดนี้กล่าวถึง: แนวทางเปิดบน PCIe สู่สิ่งที่ fabric กรรมสิทธิ์ทำภายในสแตกของผู้ขายหนึ่งราย เฟส 10 รับเส้นด้ายที่สเกลศูนย์ข้อมูลจริง — ไม่ใช่ GPU กำมือในกล่องเดียว แต่หลายพันข้ามคลัสเตอร์ฝึก เดินสายให้ compute รวมทางทฤษฎีไม่หายไปกับการประสาน
