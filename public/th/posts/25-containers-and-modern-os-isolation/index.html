    คอนเทนเนอร์และการแยกของ OS สมัยใหม่

    มกราคม 1, 2026

    หน่วยความจำเสมือน (บทที่ 24) แยกโพรเซสจากหน่วยความจำของกันและกัน มันไม่แยกพวกมันจากการแชร์ระบบไฟล์เดียวกัน พื้นที่ process-ID หรือการตั้งค่าเครือข่าย — โพรเซส Unix แบบดั้งเดิมยังเห็นและบางครั้งรบกวนผู้อื่นได้หลายทางนอกเหนือจาก RAM ดิบ คอนเทนเนอร์ขยายการแยกข้ามพื้นผิวส่วนนั้นมากขึ้น โดยไม่ไปถึงฮาร์ดแวร์ virtualization เต็มรูป

    คำศัพท์ก่อนเริ่ม (ศัพท์บัญญัติราชบัณฑิตยสภา สาขาคอมพิวเตอร์และเทคโนโลยีสารสนเทศ เว้นแต่ระบุ): เครื่องเสมือน (virtual machine, VM); ตัวเลียนแบบ หรือ โปรแกรมเลียนแบบ (emulator — ซอฟต์แวร์ที่จำลองการทำงานของเครื่องอีกแบบทีละคำสั่ง); กระบวนการ (process — ในบทนี้ใช้ทับศัพท์ “โพรเซส” ตามต้นฉบับ); kernel มีศัพท์บัญญัติว่า ใจกลาง แต่บทนี้ใช้ทับศัพท์ “เคอร์เนล” ตามต้นฉบับ; สารบบ (directory); ลำดับชั้น (hierarchy); เอกสิทธิ์ (privilege — สิทธิ์พิเศษระดับผู้ดูแลระบบ); การแยกเอกเทศ (isolation, สาขาวิทยาศาสตร์); คลังโปรแกรม (program library); ใส่ (mount — การนำระบบไฟล์มาต่อเข้ากับต้นไม้สารบบ); และ น้ำหนัก (weight, สาขาวิทยาศาสตร์) คำต่อไปนี้ยังไม่พบศัพท์บัญญัติ จึงใช้ทับศัพท์หรือคำอธิบาย: container (คอนเทนเนอร์), namespace (เนมสเปซ — “มุมมอง” ของทรัพยากรที่เคอร์เนลให้แต่ละกลุ่มโพรเซส), virtualization (การทำเสมือน), hypervisor, file system (ระบบไฟล์), root directory (สารบบราก), sandbox, dynamic linking (การเชื่อมโยงคลังโปรแกรมตอนรัน) และ hostname (ชื่อเครื่อง)

    Virtualization เต็มรูป: แข็ง หนัก#

    VM แบบดั้งเดิมรัน guest OS ครบ — เคอร์เนลของตัวเอง ไดรเวอร์ของตัวเอง — บน hypervisor ที่นำเสนอ CPU หน่วยความจำ ที่เก็บ และเครือข่ายแบบเสมือน (หรือ ด้วยความช่วยของฮาร์ดแวร์ ใกล้เนทีฟ) การแยกแข็งมาก: guest มองไม่เห็นโพรเซสของโฮสต์หรือ guest อื่น เว้นแต่บั๊ก hypervisor ร้ายแรง ต้นทุนจริง — แต่ละ VM บูตเคอร์เนลของตัวเอง แบก footprint ของเคอร์เนลนั้น และโดยทั่วไปจ่ายการเข้าถึงฮาร์ดแวร์บางอย่างช้ากว่ารันบนโฮสต์

    แล็บท้ายบทคือปลายสุดของสเปกตรัมนี้ ผู้เขียนอ่านซอร์สของแล็บ: มันใช้ v86 ซึ่งเป็นโปรแกรมเลียนแบบเครื่อง x86 ทั้งเครื่องใน WebAssembly (ไม่ใช้ความช่วยของฮาร์ดแวร์เลย ทุกคำสั่งของ guest ถูกจำลองด้วยซอฟต์แวร์) ตั้งหน่วยความจำไว้ 128 MB และบูตจากอิมเมจซีดีที่มากับหน้าเว็บ ผู้เขียนรันแล็บตัวเดียวกันแบบไม่มีหน้าจอใน Node.js แล้วพิมพ์คำสั่งเข้าไป: uname -a รายงาน Linux 4.16.13 สถาปัตยกรรม i686 เชลล์คือ BusyBox v1.28.4 nproc ได้ 1 CPU free เห็นหน่วยความจำรวม 116,984 KB (ส่วนต่างราว 14 MB จาก 128 MB คือส่วนที่เคอร์เนลกันไว้ใช้เองและไม่นับในยอดรวม) และเข้าสู่ระบบเป็น root (id ได้ uid=0) — ทั้งเคอร์เนล ไดรเวอร์ และเชลล์เป็นของ guest เอง ตรงตามนิยาม VM ข้างบน

    แชร์เคอร์เนล แยกมุมมอง#

    คอนเทนเนอร์เลือกการแลกอีกทาง: ทุกคอนเทนเนอร์บนโฮสต์แชร์เคอร์เนล เดียวกัน — ไม่มีการบูต guest OS ต่ออินสแตนซ์ — ขณะที่เคอร์เนลให้การแยกให้มุมมองของแต่ละคอนเทนเนอร์ดูแยก คุณสมบัติ Linux สองอย่างทำงานส่วนใหญ่ Namespaces แยกมุมมองของโพรเซสต่อทรัพยากรเฉพาะ — PID namespace ทำให้คอนเทนเนอร์เห็นเฉพาะต้นไม้โพรเซสของตัวเอง (โพรเซส 1 ข้างในไม่ใช่ PID 1 บนโฮสต์); network namespace ให้อินเทอร์เฟซและ routing เฉพาะ; mount namespace ให้มุมมองระบบไฟล์เฉพาะ Cgroups (control groups) จำกัดและบัญชี CPU หน่วยความจำ และ I/O เพื่อไม่ให้คอนเทนเนอร์หนึ่งทำให้ผู้อื่นบนโฮสต์เดียวกันอด

    เนมสเปซมีกี่ชนิด และดูได้จากไหน#

    คู่มือ namespaces(7) ของ Linux แสดงเนมสเปซแปดชนิด:

    ชนิด แฟล็ก สิ่งที่แยก
    Cgroup CLONE_NEWCGROUP สารบบรากของ cgroup
    IPC CLONE_NEWIPC System V IPC และคิวข้อความ POSIX
    Network CLONE_NEWNET อุปกรณ์เครือข่าย สแตก พอร์ต ฯลฯ
    Mount CLONE_NEWNS จุดที่ใส่ระบบไฟล์
    PID CLONE_NEWPID หมายเลขโพรเซส
    Time CLONE_NEWTIME นาฬิกา boot และ monotonic
    User CLONE_NEWUSER หมายเลขผู้ใช้และกลุ่ม
    UTS CLONE_NEWUTS ชื่อเครื่องและชื่อโดเมน NIS

    แต่ละโพรเซสมีสารบบ /proc/<pid>/ns/ ที่มีลิงก์หนึ่งตัวต่อหนึ่งชนิด คู่มือระบุกฎที่ใช้ตรวจได้ง่าย: ถ้าสองโพรเซสอยู่ในเนมสเปซเดียวกัน หมายเลข inode ของลิงก์จะเท่ากัน ในแล็บ ผู้เขียนรัน ls -l /proc/self/ns /proc/1/ns ได้เจ็ดรายการ: cgroup, ipc, mnt, net, pid, pid_for_children และ uts ทุกตัวมีหมายเลขเท่ากันระหว่างเชลล์กับ PID 1 (เช่น pid:[4026531836], uts:[4026531838]) — แปลว่าทุกอย่างในแล็บอยู่ในเนมสเปซเริ่มต้นชุดเดียว

    ตรวจเลขเอง: 4026531836 ในฐานสิบหกคือ 0xEFFFFFFC ตรงกับค่าคงที่ PROC_PID_INIT_INO ในซอร์สเคอร์เนล 4.16 (include/linux/proc_ns.h) เช่นเดียวกับ ipc = 0xEFFFFFFF (4026531839), uts = 0xEFFFFFFE (4026531838) และ cgroup = 0xEFFFFFFB (4026531835) ที่เห็นในแล็บ ส่วน mnt (4026531840 = 0xF0000000) และ net (4026531993) ไม่ใช่ค่าคงที่ในไฟล์นั้น ถูกจัดสรรตอนบูต เนมสเปซ เริ่มต้น จึงมีหมายเลขที่รู้ล่วงหน้า เนมสเปซที่สร้างใหม่จะได้เลขอื่น

    กรณีขอบ — สิ่งที่แล็บไม่มี: ไม่มีรายการ time (คู่มือระบุว่ามาใน Linux 5.6 ใหม่กว่าเคอร์เนล 4.16 ของแล็บ) และไม่มี user (ผู้เขียนอนุมานว่าเคอร์เนลนี้ไม่ได้เปิดตัวเลือกนั้นตอนคอมไพล์) BusyBox ของแล็บก็ไม่มีคำสั่ง unshare หรือ nsenter (ผู้เขียนลองแล้วได้ “unshare: not found”) จึง สร้าง เนมสเปซใหม่ในแล็บจากเชลล์ไม่ได้ — ดูได้แต่ของเดิม

    กรณีขอบของ PID namespace (จากคู่มือ pid_namespaces(7)): โพรเซสแรกในเนมสเปซใหม่ได้ PID 1 และทำหน้าที่ “init” รับเลี้ยงโพรเซสกำพร้า ถ้า init ตัวนี้จบ เคอร์เนลส่ง SIGKILL ฆ่าทุกโพรเซสในเนมสเปซนั้น และ fork ครั้งถัดไปเข้าเนมสเปซนั้นล้มเหลวด้วย ENOMEM — คอนเทนเนอร์ที่โพรเซสหลักตายจึงตายทั้งกล่อง เนมสเปซ PID ซ้อนกันเป็นต้นไม้ได้ลึกสูงสุด 32 ชั้น (ตั้งแต่ Linux 3.7) โพรเซสหนึ่งมองเห็นได้จากเนมสเปซของตัวเองและเนมสเปซบรรพบุรุษทุกชั้น จึงมีหมายเลข PID หนึ่งค่าในแต่ละชั้นที่มองเห็นมัน แต่โพรเซสในเนมสเปซลูกมองไม่เห็นโพรเซสของชั้นแม่

    สายเลือดเก่ากว่าคำฮิต: chroot (เปลี่ยนรากระบบไฟล์ที่โพรเซสเห็น ต้นทศวรรษ 1980) คือการแยกระบบไฟล์จำกัดหลายทศวรรษก่อน; cgroups และ namespaces สมัยใหม่ขยายแนวคิดนั้นข้ามโลกของโพรเซสมากขึ้น

    ทดลอง chroot ในแล็บ: ทำไมมันไม่พอ#

    แล็บมีคำสั่ง chroot จึงทดลองบรรพบุรุษของคอนเทนเนอร์ได้จริง ผู้เขียนรันทีละขั้น:

    1. คุกที่มีแค่โปรแกรมเดียว: สร้าง /tmp/jail/bin, คัดลอก /bin/busybox เข้าไป แล้วสั่ง chroot /tmp/jail /bin/busybox ls / ผลคือ “chroot: can’t execute ‘/bin/busybox’: No such file or directory” ทั้งที่ไฟล์อยู่ตรงนั้น กรณีขอบนี้หลอกตา: ls /lib บนเครื่องแสดงว่า BusyBox เชื่อมโยงกับคลังโปรแกรม uClibc ตอนรัน (ld-uClibc.so.0, libc.so.0) ภายในรากใหม่ไม่มีตัวโหลดนั้น “ไม่พบไฟล์” จึงหมายถึงตัวโหลด ไม่ใช่ตัวโปรแกรม (ผู้เขียนสรุปจากขั้นถัดไป: เติมคลังโปรแกรมแล้วรันได้ทันที)
    2. เติมคลังโปรแกรม: คัดลอก ld-uClibc.so.0 และ libc.so.0 เข้า /tmp/jail/lib แล้วรันใหม่ ls / ภายในคุกเห็นเพียง bin lib proc — การแยกระบบไฟล์ใช้ได้ นี่คือเหตุที่อิมเมจคอนเทนเนอร์ต้องพกคลังโปรแกรมทั้งหมดที่โปรแกรมต้องใช้ไปด้วย
    3. แต่โพรเซสไม่ได้แยก: ใส่ /proc ภายในคุกแล้วรัน ps | wc -l ทั้งในและนอกคุก ได้ 49 บรรทัดเท่ากัน — ในคุกเห็นทุกโพรเซสของเครื่อง เพราะ chroot ไม่แตะเนมสเปซ PID
    4. และหนีออกได้: ภายในคุก ls /proc/1/root/ แสดงรากจริงของเครื่อง (bin dev etc … usr var) ทั้งที่ ls / ในคุกเห็นแค่สามสารบบ — เพราะ /proc เปิดทางไปยังรากของ PID 1 ที่อยู่นอกคุก

    คู่มือ chroot(2) พูดตรง ๆ ว่า chroot “เปลี่ยนเพียงส่วนหนึ่งของการแปลชื่อพาธและไม่ทำอะไรอื่น” และ “ไม่ได้ตั้งใจให้ใช้เพื่อความปลอดภัยใด ๆ” พร้อมยกวิธีที่ superuser หนีออกได้ด้วย mkdir foo; chroot foo; cd .. ขั้นที่ 3 และ 4 คือเหตุผลที่คอนเทนเนอร์ต้องใช้ mount namespace และ PID namespace ร่วมกัน ไม่ใช่ chroot อย่างเดียว

    Cgroups ทำงานอย่างไร: ตัวเลขจากแล็บ#

    คู่มือ cgroups(7) ระบุว่า cgroups รุ่นแรกเข้ามาใน Linux 2.6.24 และรุ่นที่สอง (cgroups v2) เป็นทางการใน Linux 4.5 ในแล็บ cat /proc/cgroups แสดงตัวควบคุมสี่ตัว: cpuset, cpu, cpuacct และ freezer (คอลัมน์ hierarchy เป็น 0 คือยังไม่ถูกใส่ที่ใด) — ไม่มีตัวควบคุม memory หรือ pids ในเคอร์เนลรุ่นนี้ ผู้เขียนใส่ cpu,cpuacct ที่ /tmp/cg แล้วสร้างกลุ่มลูก

    กรณีขอบของค่า cpu.shares: ค่าเริ่มต้นคือ 1024 ผู้เขียนเขียนค่า 1 ลงไปแล้วอ่านกลับได้ 2 — ซอร์สเคอร์เนล 4.16 (kernel/sched/sched.h) กำหนด MIN_SHARES = 2 และ MAX_SHARES = 2¹⁸ = 262,144 ค่านอกช่วงถูกบีบเข้าขอบเงียบ ๆ ไม่มีข้อความผิดพลาด และไม่มีไฟล์ cpu.cfs_quota_us เลย (เขียนไม่ได้ “Permission denied”) คู่มือ cgroups(7) ระบุว่าการจำกัด “แบนด์วิดท์” CPU ต้องเปิด CONFIG_CFS_BANDWIDTH ผู้เขียนจึงอนุมานว่าเคอร์เนลของแล็บมีแต่การแบ่งตามน้ำหนัก ไม่มีเพดาน

    การทดลอง 1 — น้ำหนัก 2 : 1 บน CPU เดียว: สร้างกลุ่ม a (cpu.shares = 1024) และ b (512) ใส่ลูปว่างที่กิน CPU เต็มกลุ่มละหนึ่งโพรเซส ล้างตัวนับ cpuacct.usage แล้วรอ 10 วินาที (นาฬิกาของเครื่องเสมือน):

    กลุ่ม cpu.shares เวลา CPU ที่ได้ (ns) สัดส่วน ทฤษฎี 1024/1536 และ 512/1536
    a 1024 6,676,058,686 66.66% 66.67%
    b 512 3,338,980,397 33.34% 33.33%
    รวม 10,015,039,083 ≈ 1 CPU × 10 วินาที

    อัตราส่วน 6.676 / 3.339 = 1.9994 ใกล้ 2 : 1 มาก

    การทดลอง 2 — น้ำหนักไม่ใช่เพดาน: ฆ่าลูปของ b แล้ววัดใหม่ 10 วินาที กลุ่ม a ได้ 10,002,616,392 ns หรือ 100% ของ CPU ทั้งที่น้ำหนักเท่าเดิม คู่มือ cgroups(7) อธิบายว่าตัวควบคุม cpu รับประกัน “ส่วนแบ่งขั้นต่ำ” เมื่อระบบยุ่ง แต่ “ไม่จำกัดการใช้ CPU ถ้า CPU ไม่ยุ่ง” เอกสาร cgroup-v2 เรียกโมเดลนี้ว่า work-conserving: เฉพาะกลุ่มที่ต้องการทรัพยากรในขณะนั้นเท่านั้นที่ร่วมแบ่ง

    กรณีขอบ — ลบกลุ่มที่ยังมีสมาชิก: ระหว่างที่ลูปของ b ยังรัน rmdir /tmp/cg/b ล้มเหลวด้วย “Device or resource busy” และ tasks ยังแสดง PID 910 หลังฆ่าลูปแล้ว rmdir สำเร็จ

    การทดลอง 3 — แช่แข็ง: ใส่ตัวควบคุม freezer ย้ายลูปของ a เข้ากลุ่ม แล้วเขียน FROZEN ลง freezer.state: ใน 10 วินาทีถัดมา cpuacct.usage ของ a ได้ 0 ns พอเขียน THAWED ก็กลับมาได้ 10,002,629,957 ns ใน 10 วินาที (ตัวเลขทั้งหมดในหัวข้อนี้วัดจากการรันครั้งเดียวในเครื่องเสมือน รันซ้ำจะต่างเล็กน้อย)

    คำนวณต่อจากสูตรเดียวกัน (ส่วนแบ่งของกลุ่ม i = น้ำหนัก i ÷ ผลรวมน้ำหนักของกลุ่มที่ กำลังต้องการ CPU):

    สถานการณ์ ส่วนแบ่งที่ได้
    สามกลุ่ม 1024, 512, 512 ยุ่งทั้งหมด 50%, 25%, 25%
    กลุ่ม 512 กลุ่มหนึ่งว่าง 66.7%, 33.3% (กลุ่มที่ว่างไม่นับ)
    น้ำหนักขอบล่างสุด 2 แข่งกับขอบบนสุด 262,144 2 / 262,146 ≈ 0.00076% — แทบอด แต่ไม่ใช่ศูนย์
    มีกลุ่มเดียวที่ยุ่ง น้ำหนักเท่าใดก็ตาม 100%

    ใน cgroups v2 ตัวเลขเปลี่ยนชื่อและช่วง: เอกสารเคอร์เนลระบุว่า cpu.weight อยู่ในช่วง [1, 10000] ค่าเริ่มต้น 100 และถ้าต้องการ เพดาน จริงใช้ cpu.max รูปแบบ “$MAX $PERIOD” ค่าเริ่มต้น “max 100000” (ไม่จำกัด) เช่น “50000 100000” คือใช้ได้ 50 ms ในทุก 100 ms หรือครึ่ง CPU และ “200000 100000” คือเท่ากับสอง CPU ซึ่งบนเครื่อง CPU เดียวอย่างแล็บจะไม่มีทางใช้ได้เกิน 100% (สองตัวอย่างนี้ผู้เขียนคำนวณจากรูปแบบในเอกสาร ไม่ได้รันในแล็บเพราะเคอร์เนลของแล็บไม่มีการจำกัดแบนด์วิดท์) ส่วนหน่วยความจำ เอกสารระบุว่าเมื่อกลุ่มใช้ถึง memory.max และเคอร์เนลเรียกคืนหน่วยความจำไม่ได้ OOM killer จะถูกเรียก — นี่คือสาเหตุที่คอนเทนเนอร์ซึ่งตั้งเพดานหน่วยความจำต่ำเกินไปถูกฆ่ากลางคัน แทนที่จะแค่ช้าลงแบบ CPU

    เหตุใดการแลกนี้ชนะที่สเกล#

    เพราะคอนเทนเนอร์แชร์เคอร์เนลโฮสต์ พวกมันมักเริ่มในเสี้ยววินาที (ไม่บูตเคอร์เนล) และแบก footprint ต่ออินสแตนซ์เล็กกว่ามาก — ไม่มีภาพเคอร์เนลหรือแคชระดับเคอร์เนลดุ๊ป ประสิทธิภาพนั้นคือเหตุผลที่พวกมันกลายเป็นหน่วยแพ็กเกจและดีพลอยต์เริ่มต้นของโครงสร้างพื้นฐานคลาวด์สมัยใหม่: คอนเทนเนอร์มากกว่า VM มากบนฮาร์ดแวร์เดียวกัน ซึ่งสำคัญที่สเกลที่ระบบกระจาย (เฟส 7) รันจริง

    การแลก: เคอร์เนลแชร์หมายความว่าช่องโหว่เคอร์เนลที่ร้ายแรงพอสามารถ โดยหลัก ทำลายการแยกคอนเทนเนอร์ในทางที่โครงสร้างยากกว่าภายใต้ virtualization ที่แยกเคอร์เนล ระบบโปรดักชันส่วนใหญ่ยอมรับนั้นตั้งใจ บางครั้งซ้อนการแซนด์บ็อกซ์เพิ่ม บทสนทนา Kubernetes ของบทที่ 45 รับช่วงตรงนี้: เมื่อคุณมีหน่วยแยกเบาและเริ่มเร็ว ปัญหาถัดไปคือการจัดออร์เคสตราหลายพันตัวข้ามฝูง

    เปิดแล็บในแท็บใหม่ ↗

    ลองเองในแล็บ (คำสั่งทั้งหมดผู้เขียนรันผ่านในแล็บนี้แล้ว กด Boot VM แล้วคลิกหน้าจอดำก่อนพิมพ์):

    • ดูเนมสเปซ: ls -l /proc/self/ns /proc/1/ns — หมายเลขเท่ากันไหม?
    • คุก chroot: mkdir -p /tmp/jail/bin /tmp/jail/lib /tmp/jail/proc && cp /bin/busybox /tmp/jail/bin/ && chroot /tmp/jail /bin/busybox ls / (ดูข้อความผิดพลาด) แล้ว cp -L /lib/ld-uClibc.so.0 /lib/libc.so.0 /tmp/jail/lib/ และรันซ้ำ
    • ดูว่าคุกไม่แยกโพรเซส: mount -t proc proc /tmp/jail/proc && chroot /tmp/jail /bin/busybox ps | wc -l; ps | wc -l
    • น้ำหนัก CPU: mkdir -p /tmp/cg && mount -t cgroup -o cpu,cpuacct none /tmp/cg && mkdir /tmp/cg/a /tmp/cg/b && echo 512 > /tmp/cg/b/cpu.shares แล้วเริ่มลูปด้วย sh -c "echo \$\$ > /tmp/cg/a/tasks; while :; do :; done" & A=$! (และแบบเดียวกันสำหรับ b เก็บ PID ไว้ใน B) จากนั้น sleep 10; cat /tmp/cg/a/cpuacct.usage /tmp/cg/b/cpuacct.usage อย่าลืม kill $A $B เมื่อเสร็จ
