Every previous phase has been about building things — logic, a CPU, an operating system. This phase is about how they *talk to each other*. A bus is the shared communication path connecting CPU, memory, and I/O devices, and its design determines how fast a system can move data between the components Phase 3 and Phase 4 assumed were simply "connected."

## Three Kinds of Signals, One Physical Structure

A classic system bus carries three logically distinct kinds of signals over shared physical wires. The **address bus** carries the memory or device address a transaction targets — its width determines how much address space the system can reference (a 32-bit address bus tops out at 4GB of addressable space, which is why 32-bit systems hit a hard wall as memory sizes grew). The **data bus** carries the value being read or written — its width is a major factor in raw transfer bandwidth, since a wider bus moves more bits per transaction. The **control bus** carries the signals that coordinate the transaction: read/write direction, validity, timing/clock, and interrupt lines.

## Why Sharing a Bus Requires Arbitration

A bus is, by definition, a *shared* resource — multiple devices (CPU, DMA controllers, I/O devices) may need to initiate transactions, but only one can drive the bus at a time, or the electrical signals conflict. Arbitration decides, moment to moment, which device becomes "bus master" for the next transaction.

A simple approach is a bus request/bus grant handshake: a device asserts a request line, an arbiter (centralized, or distributed via daisy-chained priority) grants access to exactly one requester, and that device drives the bus for its transaction before releasing it. More sophisticated systems use priority schemes so latency-sensitive devices (a high-priority DMA transfer, for example) are not starved indefinitely by lower-priority ones — a resource-contention problem with real echoes of the scheduling fairness questions from Phase 4's operating-systems posts, just at the hardware signaling level instead of process scheduling.

## The Fundamental Limitation: One Transaction at a Time

Because a shared bus can carry only one transaction at a time, its total bandwidth is a hard ceiling shared across every connected device — the more devices contend, the more each waits its turn, and the less effective bandwidth any single device sees under contention. That is not a minor implementation detail; it is the central constraint the rest of this phase works around. Post 32 traces how bus design evolved to escape this shared-contention bottleneck — moving from a single shared parallel bus toward point-to-point serial links that do not force every device to compete for the same physical wires.
