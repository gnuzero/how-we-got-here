Started the campaign to support loading libraries.  Thanks to
crapweasel security constraints, we can only load libraries from
URLs on the same site we're running (which means users cannot
load their own libraries unless we host them, or they port the
emulator to their own site).  The loading is, of course,
asynchronous, which means we have to deal with call-backs for
each library reference.  This means turning the control structure
inside-out to no gain whatsoever (compared to, say, a wait for load
call with a maximum timeout, which returned success or an error code).
Consequently, we'll have to completely rewrite the expansion of
attendant includes to cope with this crap.  I shall defer this until
the morrow.

Well, after a evening's hair-pulling, I think I have library inclusions
working.  This is a completely straightforward process which is
turned into a plate full of tangled spaghetti by JavaScript's
callbacks and inversion of control structure, which transforms what
would be five or ten lines of code with proper co-operating processes
into snowdrifts of kludges, timers, global status variables, etc.

What was once a simple Program.submit() method is now split into
submit0(), which places the user's program on the card chain, and
submit1(), which does all of the transformations.  Submit1, in
turn, first calls Atttendant.expandLibraryRequests(), which scans
the card chain looking for library inclusions.  If it finds one, it
launches the asynchronous process to load it, and returns a "pending"
status.  When submit1 receives this status, it skips the subsequent
processing steps and kicks back the pending status to its caller.

The caller is submitProgram1() in webpage.js, which is called from
submitProgram() which, in turn, is called from the "Submit" button
in the Web page.  SubmitProgram1(), upon receiving a pending status,
starts a timeout process to call itself every 20 milliseconds, retrying
the Program.submit1() operation until it returns a 0 for success or
2 for failure.  (It's OK to call expandLibraryRequests() when a
request is still pending: it does nothing and returns the pending
status.)  When all of the includes have been processed, Program.submit1()
proceeds to do the rest of the processing (fixed point expansion,
loop and conditional translation), mounts the card chain, and returns
a 0 for normal completion or 2 for error.  Upon receiving this,
submitProgram1 allows its timeout loop to expire and returns.

This is still not airtight.  We should disable the Submit button when this
circus comes to town and only enable it once again when the timeout
process (if it has been started due to an include) has come to an
end.

All of this is made even more ugly by the fact that the call-backs
from the document retrieval process do not run in the context of
the object from which they were scheduled.  This calls into existence
nasty global variables to pass in the context as a hidden argument.

When a [program is loaded from the URL with the ?load= query, I added
code to automatically submit it.  It will be doubtless confusing for
people running examples if they have to submit the program before
running it.

Modified loadWebDoc() in definitions.js to take a context argument

objects calling it to recover their identity in the callback without
saving it in a static variable.  There's still, of course, a static
variable in loadWebDoc(), but it's hidden from those who call it.

Implemented the first cut of timing and statistics.  Methods in
timing.js will be called for mill, store, and card reader operations,
accumulate statistics by type of operation, and a run time estimate
is updated.  Run times are based upon the only statement I have been
able to find by Babbage on the speed of the engine: from the
chapter in his autobiography:
    http://www.fourmilab.ch/babbage/lpae.html
which states that the moving parts of the Engine move no faster
than forty feet per minute and that:
    Sixty additions or subtractions may be completed and printed in
    	one minute.
    One multiplication of two numbers, each of fifty figures, in one
    	minute.
    One division of a number having 100 places of figures by another
    	of 50 in one minute.
Further, from the discussion in Henry P. Babbage's 1888 paper:
    http://www.fourmilab.ch/babbage/hpb.html
it is claimed that addition and subtraction times are independent of
the arguments.  I have set one second as the time for these
operations.  In items 40-41, 51 it is explicitly stated that multiplication
detects the smaller of the two arguments.  I have made multiplication
have a set-up time of 10 seconds and be proportional to the size of
the smaller argument.  I base division times on my (poor) understanding
of how Friden electromechanical calculators do it.  I have a set-up
time of 10 seconds, plus a time proportional to the difference in the
number of digits in the dividend and divisor.  All of this will doubtless
be a matter of controversy and disputation, but the goal is just to provide
some order of magnitude estimate of how long the Engine would have taken
to perform a calculation.  I assume the Store is circular, and that
it takes no longer to slew from column 0 to column 999 than from column 0
to column 1.  You can change this to timings for a linear store by
setting StoreCircular = false in timing.js.

Statistics and timing are printed in the Attendant's Log with the new

attendant request card.  The statistics and timing counters are reset

panel.

Broke up the pseudorandom.ae program into two library routines:
prand_init.ae and prand_next.ae.  Prand_init.ae initialises the
generator based upon a seed specified in V000.  You can then call
prand_next.ae to produce successive pseudorandom numbers, which are
scaled to the number of decimal places specified to the attendant.
The pseudorandom values are returned in V000.  The generator uses
store columns V210 through V255 for its working storage.

Added a new montepi.ae example.  This estimates the value of pi
by plotting points within a random square of (-1, 1) in each
dimension with a circle with radius 0.5 inscribed.  The value of
pi is estimated by the measured number of hits within the circle
divided by the total number of points.  To avoid slowing down
due to growth of the display list, every 2500 points the display
is cleared and restarted.  You can suppress the plotting of points
by setting V150 to 0 at the top of the program.

A number card was accepted even if missing a number, for example:
    N121
It's a fairly common error to accidentally write a number card when
a load from the Store was intended, and this caused such goofs to go
undetected.  I modified the parsing code in engine.js so they will
now receive a "Bad number card" error.
