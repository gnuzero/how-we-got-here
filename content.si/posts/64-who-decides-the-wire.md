ARPANET (Post 39) සහ TCP/IP (Post 41) packets ගමන් කරන ආකාරය විසඳුවේය. ඒවා තනිවම නිහඬ ප්‍රශ්නයකට පිළිතුරු දුන්නේ නැත: *bits අදහස් කරන්නේ කුමක්දැයි කීමට අයිතිය ඇත්තේ කාටද?* Port 80, IPv4 prefix එකක්, `.com`, ก සඳහා code point එක — දුරස්ථ ක්‍රියාකරුවන් එකම හඳුනාගැනීම් එකම ආකාරයෙන් සලකන්නේ නම් මිස ඒවායින් කිසිවක් ක්‍රියා නොකරයි. අන්තර්ජාලයේ governance කතාව එම එකඟතාවේ කතාවයි: ජාලය මත පාර්ලිමේන්තුවක් නොව, **අංක**, **නම්**, සහ **encodings** සඳහා බෙදාගත් ledgers කට්ටලයක්.

## ආයතනවලට පෙර ලේඛන

පළමු සම්බන්ධීකරණ මෙවලම ලේඛන මාලාවක් විය. 1969 අප්‍රේල්හි, Steve Crocker [RFC 1](https://www.rfc-editor.org/rfc/rfc1) — *Host Software* — ARPANET පර්යේෂණ ප්‍රජාව සඳහා වැඩ සටහන් ලෙස ප්‍රකාශයට පත් කළේය. ස්වරය වැදගත් විය: "Request for Comments," "නියෝගයක්" නොවේ. Jon Postel දශක තුනකට ආසන්න කාලයක් මාලාව සංස්කරණය කර, අනියම් මතක සටහන් අන්තර්ජාලය ඇත්තටම ක්‍රියා කරන ආකාරයේ කල් පවතින ප්‍රසිද්ධ වාර්තාවක් බවට පත් කළේය. පිටවීමේ දොර: [RFC Editor history](https://www.rfc-editor.org/history/).

පර්යේෂණ ප්‍රජාව කොරිඩෝ රැස්වීම් ඉක්මවා වර්ධනය වූ විට, එය Internet Engineering Task Force (IETF) වර්ධනය කළේය. බර දරන වාක්‍යාංශය Dave Clark ගේ ය: *rough consensus and running code* — ප්‍රමිති ඡන්දයෙන් නොව නිකුත් කිරීමෙන් තමන්ගේ තැන උපයයි. IETF අන්තර්ජාලය හිමි නොකරයි; එය ක්‍රියාකරුවන් යෙදවීමට ඇති දෙයක් බවට protocols තර්ක කිරීමේ ක්‍රියාවලියක් හිමි කර ගනී. පිටවීමේ දොර: [ietf.org](https://www.ietf.org/).

## අංක: කවුරුහරි හඳුනාගැනීම් බෙදා දිය යුතුය

Packets protocol අංක, port අංක, address blocks, ASN අගයන්, media types රැගෙන යයි — කණ්ඩායම් දෙකක් විවිධ අර්ථ සඳහා එකම එකක් mint කරන්නේ නම් වටිනාකමක් නැති හඳුනාගැනීම්. වසර ගණනක් එම ledger එක එක් තැනක ජීවත් විය: Internet Assigned Numbers Authority (IANA), UCLA සහ පසුව USC/ISI හි පර්යේෂණ ගිවිසුම් යටතේ Jon Postel විසින් (Joyce Reynolds දිගුකාලීන සම්බන්ධතා ලක්ෂ්‍යයක් ලෙස) ප්‍රායෝගික සේවාවක් ලෙස ධාවනය කරන ලදී. IANA යනු *වර්ගයක* බීජයකි: implementations ට ද්විපාර්ශ්වික සාකච්ඡාවකින් තොරව අන්තර් ක්‍රියා කිරීමට protocol parameters සඳහා මධ්‍යස්ථ registry එකක්.

ජාලය එක් පුද්ගලයෙකුගේ සටහන් පොත ඉක්මවා පරිමාණය වූ විට, අංක සම්පත් *වර්ගය* අනුව බෙදුණේය. Protocol parameters IANA සමඟ රැඳුණේය. IP address space Regional Internet Registries දෙසට ගමන් කළේය — උතුරු ඇමරිකාවේ බොහෝ කොටස සඳහා ARIN (1997); RIPE NCC, APNIC, LACNIC, සහ AFRINIC අනෙක් කලාප සඳහා එම *වර්ගයම* වන අතර, කලාපය එම ආකෘතිය තෝරා ගත් තැන ඒවා යටතේ ජාතික හෝ දේශීය Internet registries (NIR) වාඩි වේ. රටාවම කරුණ ය: දුර්ලභ, අනන්‍ය හඳුනාගැනීම්වලට සෑම කෙනෙකුටම පෙන්විය හැකි භාරකරුවෙකු අවශ්‍ය ය. පිටවීමේ දොර: [iana.org](https://www.iana.org/), [arin.net](https://www.arin.net/).

## නම්: මිනිසුන්ට වචන අවශ්‍ය ය; යන්ත්‍රවලට අනන්‍යතාව අවශ්‍ය ය

Paul Mockapetris ගේ DNS පිරිවිතර ([RFC 1034](https://www.rfc-editor.org/rfc/rfc1034), [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035)) hierarchical නම් address fabric එක මත බෙදාහැරුණු lookup පද්ධතියක් බවට පත් කළේය. නම් අමු අංක නොවන ආකාරයකින් දේශපාලනික ය: මිනිසුන් වචන ගැන තර්ක කරයි. Jon Postel ගේ [RFC 1591](https://www.rfc-editor.org/rfc/rfc1591) මුල් domain ප්‍රතිපත්තිය භාරකාරත්වය ලෙස රාමු කළේය.

1990 ගණන්වල අගභාගය වන විට එක්සත් ජනපද රජයට එම සම්බන්ධීකරණ කාර්යයන් තනි පර්යේෂණ ගිවිසුමකින් පිටතට ගැනීමට අවශ්‍ය විය. ICANN (Internet Corporation for Assigned Names and Numbers) 1998 දී පිහිටුවන ලදී — අන්තරීම කථානායක Esther Dyson — IANA එම කුඩාකුඩු යටතේ මෙහෙයුම් registries ලෙස දිගටම යන අතරතුර නම් සහ අංක ප්‍රතිපත්තිය සඳහා ආයතනික ආසනය තබා ගැනීමට. ICANN තවත් *වර්ගයක* බීජයක් ලෙස කියවන්න: බෙදාගත් namespace එකේ ස්ථායිතාව සහ අනන්‍යතාව එහි රැකියාව වන multi-stakeholder ආයතනයක්, යෙදුම් අතර ජයග්‍රාහකයන් තෝරා ගැනීම නොවේ. පිටවීමේ දොර: [icann.org](https://www.icann.org/).

## Encodings: Payload එකට එකම Glyph අදහස් කළ යුතුය

අන්තර් ක්‍රියාකාරිත්වය නිහඬව අසාර්ථක වන්නේ අන්ත දෙක byte අනුක්‍රමයක් *කුමක්ද* යන්න ගැන එකඟ නොවන විට ය. Unicode Consortium (1991 දී පිහිටුවන ලදී; තනි character set එකක් අවශ්‍ය සමාගම් හරහා Joe Becker, Mark Davis, සහ අනෙකුන්ගේ මුල් වැඩ) අමූර්ත අක්ෂර සිට code points දක්වා බෙදාගත් mapping එක පවත්වා ගනී — තායි, Latin, සහ emoji එක් එක් යෙදුමට තමන්ගේ අක්ෂර වගුව සොයා ගැනීමකින් තොරව එකම වයර් එකක් බෙදා ගත හැකි හේතුව. UTF-8 පසුව එම repertoire සඳහා ප්‍රමුඛ *on-the-wire* encoding බවට පත් විය. පිටවීමේ දොර: [unicode.org](https://www.unicode.org/), [Unicode Standard](https://www.unicode.org/standard/standard.html).

## එම වර්ගයේම Kin

පේළි කිහිපයක් වාක්‍යයක් උපයයි — එම *වර්ගයේම* බෙදාගත් අර්ථය, ප්‍රමිති-ආයතන සංචාරයක් නොවේ:

- **W3C සහ WHATWG** — Tim Berners-Lee World Wide Web Consortium (1994) වෙබ් වේදිකා ප්‍රමිති භාරකාරත්වයට පිහිටුවා ගත්තේය; browser vendors ට වේගවත් iteration මාර්ගයක් අවශ්‍ය වූ විට WHATWG පසුව ජීවමාන HTML/DOM specs රැගෙන ගියේය. එම *වර්ගයම*: browser එකේ ලේඛනයක් සහ API එකක් අදහස් කරන්නේ කුමක්දැයි අර්ථ දැක්වීමට අයිතිය ඇත්තේ කාටද.
- **IEEE** — IEEE 802 නිසා Ethernet (Post 40) සහ Wi-Fi link layer එකේ proprietary දූපත් උපභාෂා නොවේ.
- **ISO සහ peers** — මිලදී ගැනීම්, ආරක්ෂාව, හෝ ජාතික ආයතන ඒවා ඉල්ලන තැන නිල ජාත්‍යන්තර ප්‍රමිති RFC ලෝකය අසල වාඩි වේ; අන්තර්ජාලය බොහෝ දුරට පළමුව RFCs මත නිකුත් වී පසුව සමගි විය.

## මෙය ගමනට අයත් වන්නේ ඇයි

Posts 39–41 ඉංජිනේරු ඔට්ටුවයි: packets, ස්ථර, විශ්වාස කළ නොහැකි පදනම. මෙම පෝස්ට් එක ඒවා යටතේ ඇති පුරවැසිභාව ඔට්ටුවයි: **බෙදාගත් අර්ථය යනු යටිතල පහසුකමකි**. අංක, නම්, සහ encodings තීරණය කරන කෙනෙකු (සහ ක්‍රියාවලියක්) නොමැතිව, සෑම නව ජාලයක්ම පුද්ගලික භාෂාවකි. ඉහත දොරවල් ප්‍රාථමික මූලාශ්‍ර ය — RFCs, registries, consortium පිටු.

මෙතැන් සිට විකල්ප පැත්ත මාර්ග: එම බෙදාගත් වයර් එකේ මිනිසුන් දේවල් *සොයා ගත්* සහ *කතා කළ* ආකාරය (Post 43), හෝ යුද්ධකාලීන crypto රහස් තබා ගත හැකි යන්ත්‍ර බල කළ ආකාරය (Post 66). ප්‍රධාන කශේරුකාව packets → පද්ධති → සිලිකන් → අවධානය මත රැඳේ; මෙය ඔබට ගත හැකි හෝ මඟහැරිය හැකි කාචය පුළුල් කරන බීට් එකකි.

## ගැඹුරින්: සිංහල අකුරු bytes බවට පත් වන හැටි (Unicode, UTF-8, ZWJ සහ පැරණි fonts)

### 1. මූලික පද

UCSC 2003 වාර්තාවේ Annex A (PDF p.15) මෙම වෙනස්කම් පැහැදිලිව දක්වයි:
- **අක්ෂරය (character):** අමූර්ත ඒකකයකි. උදා. "SINHALA LETTER AYANNA" (අ). එය හැඩයක් නොවේ.
- **Code point:** අක්ෂරයකට දෙන අංකයයි. උදා. අ = **U+0D85**.
- **Glyph:** තිරයේ ඇඳෙන හැඩයයි. **Font** එකක් යනු glyphs කට්ටලයකි.
- **කේතන ආකෘතිය (encoding form):** Code point එකක් bytes බවට හරවන නීතියයි. උදා. **UTF-8**, **UTF-16**.
- **පිලි (vowel signs / dependent vowels):** ා, ැ, ි, ු, ෙ වැනි ව්‍යඤ්ජනයකට (consonant) පසුව එන ලකුණු.
- **හල් කිරීම / අල්-ලකුණ (al-lakuna / virama), U+0DCA ්:** ව්‍යඤ්ජනයක ස්වරය ඉවත් කරයි.
- **ශුන්‍ය-පළල සම්බන්ධකය (zero width joiner, ZWJ), U+200D:** නොපෙනෙන අක්ෂරයකි. අකුරු බැඳීමට ඉල්ලයි.

N2737 ඏ සහ ඐ "වර්තමාන භාවිතයේ නැති" නමුත් සම්පූර්ණත්වය සඳහා ඇතුළත් කළ බව සඳහන් කරයි; වෙනසට හේතුව එය විය හැකි බව අපේ අනුමානයකි.) ඟ ඦ ඬ ඳ ඹ යන නාසික-පූර්ව (prenasalized) අකුරු පහ වෙනම code points වේ. Unicode §13.2 මෙසේ පෙන්වයි: අඬ <0D85, 0DAC> ("ශබ්දය") සහ අණ්ඩ <0D85, 0DAB, 0DCA, 0DA9> ("බිත්තරය") වෙනස් වචන වේ.
- UCSC 2003 (PDF p.11): 0D97–0D99 ඉදිරියේදී ස්වර සඳහා හිස්ව තබා ඇත. 0DB2, 0DBC, 0DBE, 0DBF සිංහල-දෙමළ අක්ෂර පරිවර්තනය (transliteration) සඳහා වෙන් කර ඇත. 0DC7–0DC9 අමතර ව්‍යඤ්ජන සඳහා ඇත.

### 3. UTF-8 අතින්: සිංහල අකුරකට bytes 3 යි

RFC 3629 (§3) අනුව U+0800 සිට U+FFFF දක්වා code point එකක් **1110xxxx 10xxxxxx 10xxxxxx** ලෙස bytes 3 කට කේතනය වේ.

**අ = U+0D85:**
- binary: 0000 1101 1000 0101
- පළමු bits 4 (0000) → 1110**0000** = **E0**
- ඊළඟ bits 6 (110110) → 10**110110** = **B6**
- අවසාන bits 6 (000101) → 10**000101** = **85**
- ප්‍රතිඵලය: **E0 B6 85** (bytes 3)

එබැවින් සිංහල block එකේ සෑම code point එකක්ම UTF-8 හි bytes 3 කි: U+0D80–0DBF → **E0 B6 xx**, U+0DC0–0DFF → **E0 B7 xx**. ZWJ (U+200D) → **E2 80 8D**.

**NIE p.107 හි "වැඩි මතකයක්" ප්‍රකාශය නිවැරදිව කියවීම:**
- UTF-8 හි ASCII අක්ෂර **byte 1 ක්** ලෙසම පවතී. ඉංග්‍රීසි පෙළට මතක දඬුවමක් නැත.
- Unicode Standard ch.2 (§2.5) මෙසේ කියයි: UTF-8 ASCII සඳහා UTF-16 ට වඩා බොහෝ කුඩාය, නමුත් හින්දි, තායි වැනි ආසියානු ලේඛන ක්‍රම සඳහා "significantly larger" (සැලකිය යුතු ලෙස විශාලය).
- සිංහල code point එකක් UTF-8 හි bytes **3** ක් වන අතර UTF-16 හි bytes **2** කි.
- UCSC 2003 (PDF p.4) Unicode "16-bit" ලෙස විස්තර කළේ Unicode 3.0 යුගයේ දෘෂ්ටියෙනි. UTF-8 variable-length කේතනයක් ලෙස ද එහි සඳහන් වේ.

| පෙළ | code points | UTF-8 bytes | UTF-16 bytes |
|---|---|---|---|
| computer | 8 | **8** | 16 |
| පරිගණකය | 7 | **21** | 14 |
| සිංහල | 5 | **15** | 10 |
| ශ්‍රී | 5 | **15** | 10 |

### 5. තාර්කික පිළිවෙල එදිරිව දෘශ්‍ය පිළිවෙල (logical vs visual order)

Unicode Standard ch.2 (§2.2) මෙසේ කියයි: Unicode පෙළ මතකයේ ගබඩා කරන පිළිවෙල **තාර්කික පිළිවෙල (logical order)** වේ. එය දළ වශයෙන් ශබ්ද පිළිවෙලට (phonetic order) අනුරූප වේ. සිංහලෙන් එය ඇසට පෙනෙන පිළිවෙලට වඩා වෙනස් විය හැකිය.

Unicode හි IndicPositionalCategory.txt (18.0) දත්ත ගොනුව සෑම පිල්ලක්ම ඇඳෙන්නේ කොතැනදැයි දක්වයි:

| පිල්ල | Code point | ඇඳෙන තැන (දත්ත ගොනුව) |
|---|---|---|
| ෙ කොම්බුව | U+0DD9 | Left (වම) |
| ෛ කොම්බු දෙක | U+0DDB | Left |
| ො, ෞ | U+0DDC, U+0DDE | Left_And_Right (දෙපැත්ත) |
| ේ | U+0DDA | Top_And_Left |
| ෝ | U+0DDD | Top_And_Left_And_Right |
| ා, ැ, ෑ | U+0DCF–0DD1 | Right (දකුණ) |
| ි, ී, ් | U+0DD2–0DD3, U+0DCA | Top (ඉහළ) |
| ු, ූ | U+0DD4, U+0DD6 | Bottom (පහළ) |

**ගෙදර** දෙස බලන්න:
- ඇසට පෙනෙන්නේ: **ෙ** පළමුව, පසුව **ග**.
- ගබඩා වන්නේ: **ග** (U+0D9C) පළමුව, පසුව **ෙ** (U+0DD9).
- Rendering engine එක (UCSC 2003 PDF p.13 "display driver" ලෙස හඳුන්වයි) ඇඳීමේදී කොම්බුව වමට ගෙන යයි.

**පිළිවෙල තුනක්:**
1. **ටයිප් කරන පිළිවෙල:** SLS 1134:2004 කෙටුම්පතේ (N2737 PDF p.18) කොම්බුව යතුර ව්‍යඤ්ජනයට **පෙර** ඔබයි ("in writing order"). UCSC 2003 (PDF p.12) ද කියයි: `@` (කොම්බුව) සහ `k` (ක) යතුරු ඔබන විට ජනනය විය යුත්තේ ප්‍රතිවිරුද්ධ පිළිවෙලයි, එනම් 0D9A පසුව 0DD9.
2. **ගබඩා පිළිවෙල:** ව්‍යඤ්ජනය, පසුව පිල්ල (N2737 §5).
3. **දෘශ්‍ය පිළිවෙල:** කොම්බුව වමේ.

UCSC 2003 Annex A (PDF p.15) මෙය සරලව කියයි: අප ටයිප් කරන අනුපිළිවෙල පරිගණකය තුළ ගබඩා කරන අනුපිළිවෙලට වඩා වෙනස් විය හැකිය.

### 6. අල්-ලකුණ, ZWJ සහ බැඳි අකුරු

Unicode Standard 18.0 §13.2 ("Virama (al-lakuna) and Consonant Forms"):
- ZWJ සමඟ නොවේ නම් අල්-ලකුණ **සෑම විටම පෙනේ**. එය ව්‍යඤ්ජන බැඳ නොදමයි.

### 7. සාමාන්‍යකරණය (normalization) සහ අකාරාදී පිළිවෙල (collation)

**සංයුක්ත පිලි:** Unicode 18.0 UnicodeData.txt හි canonical decompositions ඇත්තේ පිලි හතරකට පමණි:
- ේ U+0DDA ≡ 0DD9 + 0DCA
- ො U+0DDC ≡ 0DD9 + 0DCF
- ෝ U+0DDD ≡ 0DDC + 0DCA (NFD: 0DD9 0DCF 0DCA)
- ෞ U+0DDE ≡ 0DD9 + 0DDF

Python හිදී `unicodedata.normalize('NFC', 'ක\u0DD9\u0DCF')` මගින් ක + ො (0D9A 0DDC) ලැබේ. NFC ඒවා නැවත එක් කරයි. N2737 (PDF p.14) ද පිලි කිහිපයක් වෙනුවට තනි සංයුක්ත පිල්ල භාවිතා කිරීමට නිර්දේශ කරයි.

**සාමාන්‍යකරණයෙන් නොවිසඳෙන උගුල:** ආ **U+0D86** එක් code point එකකි. එයට decomposition එකක් නැත.
- Unicode Table 13-2 සහ N2737 (PDF p.13) දෙකම කියන්නේ ආ <0D85, 0DCF> (අ + ා) ලෙස කේතනය **නොකළ** යුතු බවයි.
- Python: `normalize('NFC', '\u0D85\u0DCF') == '\u0D86'` → **False**.
- එබැවින් "ආ" ලෙස පෙනෙන නමුත් bytes වෙනස් strings දෙකක් සෙවීමකදී (search) හෝ සැසඳීමකදී ගැළපෙන්නේ නැත.

**අකාරාදී පිළිවෙල:**
- UCSC 2003 (PDF p.11) අනුව, code chart එක සකස් කළේ code අනුව ස්වයංක්‍රීය වර්ග කිරීමට (sorting) හැකි තරම් පහසු වන ලෙසය. උදා. කෙ = 0D9A+0DD9 සහ කො = 0D9A+0DDC. එවිට කෙ ට පසුව එන්නේ කො මිස ගෙ (0D9C+0DD9) නොවේ.
- Python code-point වර්ග කිරීම: `sorted(['කො','ගෙ','කෙ','ක','කා'])` → **ක, කා, කෙ, කො, ගෙ**.
- එහෙත් N2737 පෙරවදන (PDF p.1) කියන්නේ අකාරාදී පිළිවෙල "බොහෝ දුරට" රඳවා ගත්තද, collation ඇල්ගොරිතම තවමත් අවශ්‍ය බවයි.
- Gunathilaka (PDF pp.58–59): ආචාර්ය රුවන් වීරසිංහ මෙහෙයවූ UCSC කණ්ඩායමක් ප්‍රධාන සිංහල ශබ්දකෝෂ අධ්‍යයනය කර අකාරාදී අනුක්‍රමයක් නිර්දේශ කළේය. එය ICTA හි දේශීය භාෂා ක්‍රියාකාරී කණ්ඩායමේ (LLWG) සාකච්ඡාවෙන් පසු **SLS 1134:2004 හි 1 වන කොටස** ලෙස ප්‍රමිතිගත විය.

### 8. යතුරුපුවරු: විජේසේකර සහ ශාබ්දික ආදානය

**යාන්ත්‍රණය:** UCSC 2003 (PDF p.3) මෙය පැහැදිලිව විස්තර කරයි. Unicode ට පෙර බොහෝ භාෂා මෘදුකාංගවල සහාය ලැබුවේ ASCII සමඟ පොදු codes (ඉලක්කම්, විරාම ලකුණු) තබාගෙන, **අනෙක් Latin අක්ෂරවල code points "overwrite" කිරීමෙන්**, එනම් ඒවාට එම භාෂාවේ glyphs ඇති "font" එකක් යෙදීමෙනි. ප්‍රතිඵලයක් ලෙස එකම අකුර විවිධ මෘදුකාංගවල විවිධ ලෙස කේතනය විය. ඒවා යෙදුම් හෝ පරිශීලකයින් අතර හුවමාරු කළ නොහැකි විය.
- Gunathilaka (PDF p.81) ද එසේම කියයි: එවකට භාවිතා කළ fonts සෑදුවේ ඉංග්‍රීසි හෝඩිය සඳහා භාවිතා කළ ASCII කේතවලට සිංහල අකුරු ඇඳීමෙනි.
- UCSC Annex A (PDF p.15): Unicode සිංහල fonts "real fonts – not encodings, as they now are" (දැන් මෙන් කේතන නොව, සැබෑ fonts) වනු ඇත.

**සැබෑ උදාහරණයක්: UCSC 2003 PDF එකම.** එම PDF එකේ සිංහල අකුරු ඇත්තේ "Kaputadotcomnormal" ලෙස embed කළ font එකකිනි (`pdffonts` මගින් පරීක්ෂා කළ; WinAnsi encoding, Unicode mapping නැත). Gunathilaka (PDF p.40) 'කපුටා' සිංහල **ASCII font** එකක් ලෙස හඳුන්වයි. එය 2000 දී දියත් කළ 'කපුටා' වෙබ් අඩවිය සමඟ ආ අතර දිවයින සහ රාවය අන්තර්ජාල සංස්කරණ සහ රාජ්‍ය පරිපාලන අමාත්‍යාංශ වෙබ් අඩවිය එය භාවිතා කළේය. පසුව එහි Unicode අනුවාදයක් නිකුත් විය (p.41). PDF එකේ PDF p.11 තිරයේ කෙ, කො, ගෙ ලෙස පෙනේ. නමුත් `pdftotext` මගින් ලැබෙන්නේ මෙයයි:

| තිරයේ | ගබඩා වූ අක්ෂර (Kaputa) | Bytes | Unicode අනුක්‍රමය | UTF-8 bytes |
|---|---|---|---|---|
| කෙ | `@k` | 40 6B | 0D9A 0DD9 | e0 b6 9a e0 b7 99 |
| කො | `` @k` `` | 40 6B 60 | 0D9A 0DDC | e0 b6 9a e0 b7 9c |
| ගෙ | `@g` | 40 67 | 0D9C 0DD9 | e0 b6 9c e0 b7 99 |

(`` @k` `` යනු @, k සහ backtick (0x60) යන අක්ෂර තුනයි.)

- `@` (0x40) = කොම්බුවේ glyph, `k` (0x6B) = ක, `g` (0x67) = ග, backtick (0x60) = ඇල-පිල්ල.
- ගබඩා පිළිවෙල **දෘශ්‍ය** පිළිවෙලයි: කොම්බුව පළමුව. Unicode එය **තාර්කික** පිළිවෙලට (ව්‍යඤ්ජනය පළමුව) ගබඩා කරයි.

**මෙයින් කැඩෙන දේ:**
1. **සෙවීම (search):** Unicode "කෙ" සොයන්නේ e0 b6 9a e0 b7 99 ය. ගොනුවේ ඇත්තේ 40 6B ය. ගැළපීමක් නැත. `k` සෙවුවොත් ඉංග්‍රීසි "keyboard" හි k ද සිංහල ක ද යන දෙකම හමු වේ.
2. **Copy-paste:** වෙනත් font එකක් ඇති යෙදුමකට ඇලවූ විට පෙනෙන්නේ `` @k` `` ය. අකුරු ගමන් කරන්නේ නැත. Font එක පමණක් "අර්ථය" රැගෙන ගියේය.
3. **Font ආදේශනය (font substitution):** ලබන්නාගේ පරිගණකයේ එම font එක නැත්නම් browser එක වෙනත් font එකක් ආදේශ කරයි. එවිට Latin අකුරු පෙනේ.
4. **වර්ග කිරීම (sorting):** Byte පිළිවෙලට `` sorted(['@g','@k','@k`','k']) `` → `@g`, `@k`, `` @k` ``, `k`. එනම් **ගෙ, කෙ, කො, ක**. ක අන්තිමට ද, ගෙ පළමුවට ද යයි. Unicode පිළිවෙල: ක, කෙ, කො, ගෙ (7 කොටස).

**පරිවර්තක (converters) ක්‍රියා කළ ආකාරය (සාමාන්‍ය යාන්ත්‍රණය, ආදර්ශ):** පැරණි-font පෙළ Unicode බවට හැරවීමට,
1. එක් එක් font එක සඳහා byte → Unicode වගුවක් අවශ්‍ය වේ (`k` → U+0D9A).
2. දිගම ගැළපීම (longest match) පළමුව: `@` + ව්‍යඤ්ජනය + backtick → ව්‍යඤ්ජනය + U+0DDC.
3. **නැවත පෙළගැස්වීම (reordering):** `@` + ව්‍යඤ්ජනය → ව්‍යඤ්ජනය + U+0DD9 (කොම්බුව පසුපසට).
4. බැඳි අකුරු glyphs → ව්‍යඤ්ජන + ් + ZWJ + ව්‍යඤ්ජන.

සෑම font එකකටම තමන්ගේම වගුවක් අවශ්‍ය විය. එබැවින් font එක දැන ගැනීම අනිවාර්ය විය. Gunathilaka (PDF p.43) සඳහන් කරන්නේ 2003 දී නැවත දියත් කළ 'හෙළවදන' පැකේජයට "ගතික ෆොන්ට පරිවර්තකයක්" ඇතුළත් වූ බවයි. එය ක්‍රියා කළ ආකාරය පොත විස්තර නොකරයි. ඉහත පියවර කිසිදු නිශ්චිත පරිවර්තකයක කේතයෙන් ගත්තක් නොවේ. ඒවා යාන්ත්‍රණයේ තාර්කික ප්‍රතිඵලයයි.

**FM fonts ගැන:** Gunathilaka (PDF p.104) අනුව "බහුල වශයෙන් භාවිතා කෙරෙන FM ෆොන්ට" විශාල ප්‍රමාණයක් පුෂ්පානන්ද ඒකනායක මහතා 1999 දී ලියාපදිංචි කළ 'ද ෆොන්ට් මාස්ටර්' සමාගම හරහා සකසන ලදී. එම සමාගම fonts 64 ක් එළිදක්වා ඇත. එම fonts හි කේතනය (ASCII-පාදකද යන්න) පොත නොකියයි. එබැවින් අපි ඉහත යාන්ත්‍රණය පෙන්වීමට කපුටා font එක පමණක් භාවිතා කළෙමු.

### 11. දැන් මෙය උත්සාහ කරන්න: bytes ඔබේම ඇසින්

[VM terminal lab](/labs/vm-terminal/?lang=si) එක විවෘත කරන්න. එය browser එක තුළ කුඩා Linux එකක් (BusyBox) ධාවනය කරයි. එහි console එකට සිංහල glyphs ඇඳිය නොහැකි අතර, සිංහල ටයිප් කිරීමද ක්‍රියා නොකළ හැකිය. එබැවින් bytes octal escapes ලෙස ලබා දෙන්න:

```
printf 'A' | od -An -tx1
printf '\340\266\205' | od -An -tx1
printf '\340\266\205' | wc -c
printf '\340\267\201\340\267\212\342\200\215\340\266\273\340\267\223' | od -An -tx1
```

අපේක්ෂිත ප්‍රතිදානය (lab image එකේ BusyBox v1.28.4 මත පරීක්ෂා කළ):
- `41` (ASCII 'A', byte 1)
- `e0 b6 85` (අ)
- `3`
- `e0 b7 81 e0 b7 8a e2 80 8d e0 b6 bb e0 b7 93` (ශ්‍රී, bytes 15; මැද ඇති `e2 80 8d` ZWJ වේ)

`xxd` ද එම image එකේ ඇත: `printf '\340\266\205' | xxd`.

### 12. පැන්සලෙන් අභ්‍යාසය

1. **ලංකා** code points සහ UTF-8 bytes වලට කඩන්න. Bytes කීයද?
2. ස = U+0DC3. 3 වන කොටසේ bit රටාව භාවිතා කර එහි UTF-8 bytes අතින් ගණනය කරන්න.
3. **කර්‍ම** UTF-8 හි bytes කීයද? UTF-16 හි කීයද?
4. කපුටා-font PDF එකෙහි `@g` bytes (40 67) ඇත. පරිවර්තකයක් ප්‍රතිදානය කළ යුතු Unicode අනුක්‍රමය සහ UTF-8 bytes මොනවාද?
5. String A = U+0D86. String B = U+0D85 U+0DCF. NFC සාමාන්‍යකරණයෙන් පසු ඒවා සමානද? නිවැරදි කේතනය කුමක්ද?
6. ද සහ ධ **ස්පර්ශ** ශෛලියෙන් (ද‍්ධ) ලිවීමට ද, **ලිගේචර** ශෛලියෙන් (ද්‍ධ) ලිවීමට ද අවශ්‍ය code point අනුක්‍රම මොනවාද?
7. **කොළ** හි ඇසට පෙනෙන කොටස් හතරකි (ෙ, ක, ා, ළ). ගබඩා වන code points කීයද? ඇයි?

(පිළිතුරු:
1. ල U+0DBD, ං U+0D82, ක U+0D9A, ා U+0DCF → e0 b6 bd | e0 b6 82 | e0 b6 9a | e0 b7 8f. Code points 4, bytes **12**.
2. 0x0DC3 = 0000 1101 1100 0011. 1110**0000** = E0; 10**110111** = B7; 10**000011** = 83 → **E0 B7 83**.
3. ක ර ් ZWJ ම = code points 5 → UTF-8 **15**, UTF-16 **10**.
4. ගෙ = **U+0D9C U+0DD9** → **e0 b6 9c e0 b7 99**. (කොම්බුව ව්‍යඤ්ජනයට පසුව යයි.)
5. **සමාන නොවේ**. U+0D86 ට decomposition එකක් නැති නිසා NFC B වෙනස් නොකරයි. නිවැරදි කේතනය **U+0D86** (Unicode Table 13-2; N2737 p.13).
6. ස්පර්ශ: **0DAF 200D 0DCA 0DB0** (ZWJ පළමුව). ලිගේචර: **0DAF 0DCA 200D 0DB0** (අල්-ලකුණ පළමුව).
7. **3**: ක U+0D9A, ො U+0DDC, ළ U+0DC5. "ො" යනු ව්‍යඤ්ජනයේ දෙපැත්තේ ඇඳෙන (Left_And_Right) එක් පිල්ලකි.)
